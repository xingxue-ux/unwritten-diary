# M2 · 修订与检索可见性

对应 issue [#54](https://github.com/xingxue-ux/unwritten-diary/issues/54) · 日期 2026-10-10 · 执行人 xingxue-ux

B3a（[M1 · 关键词索引](m1-关键词索引.md)）建的索引按**修订**存（`extracted_contents` /
`extracted_segments` 每个修订一份），B3d（[M2 · 记录正文进检索](m2-记录正文进检索.md)）
让用户自己写的文字也进检索。这一片补的是它们之间断掉的一环：**改过的正文**。

## 问题（实测，与决策相反）

用真实路径（建记录 → 导入并提取 → 提交 → `revise_text` 改正文 → 再提取 → 检索）跑出来的
是这样：

```
改之前：旧词「体检」命中 1 条
新修订提取失败：InvalidState
改之后：旧词「体检」命中 1 条；新词「爬山」命中 0 条
派生正文份数 1 · 片段 1 · 进了关键词索引的片段 1
```

两个毛病叠在一起：

1. **新修订提取不了**：`revise_text` 造出来的修订 `asset_id` 为空，而提取器要求「有关联
   原件」→ `InvalidState` → 新正文根本不进索引；
2. **旧修订的派生内容没有退出检索**：索引没按「当前修订」过滤，旧正文照旧被搜出来。

「改前能搜到、改后还能搜到旧的、搜不到新的」——两条都错。

## 决策

| 决定 | 理由 |
|---|---|
| **改过的正文当成新的一篇**，日期等元数据不变 | 修订是来源自己的历史，不是新记录；把日期改掉会让日记归属漂移 |
| **默认搜索只看当前修订** | 用户要的是「我改后的正文」，不是一堆历史版本。旧正文混进结果里比搜不到更糟 |
| **旧修订的派生内容与索引行都保留**（不删数据） | 它们是「可重建的派生数据」，也是将来「只搜变更前的内容」这类**用户显式触发**功能的原料。删掉容易，重建要整库重跑 |
| **上一版正文按需读取**，diff 由前端算 | 后端只给两版正文；算 diff、展示「修改部分」是呈现层的事（#55） |
| **不做版本历史搜索** | 决策就是「用户直接搜不到旧正文」。将来若要做，另开一片，这一片只保证默认行为 |

## 实现

### 1. 纯文本修订要能提取：`text_direct`

`crates/diary_core/src/extractors.rs`：`extract_source_revision` 现在有两条输入通路。

- **有原件**（导入的文件、录音）：按 mime 选提取器，和以前一样；
- **没有原件但有 `text`**（`revise_text` 造出来的修订）：**正文就是内容本身，没有解析这
  一步**。直接调用已有的 `paragraphs_to_outcome`（就是纯文本/Markdown 用的那个切段函数）
  产出 `coverage = complete` 的派生内容。

选择新造一个 `extractor_id` 而不是复用 `plain_text`：两者的输入根本不是一种东西——一个
是「文件字节 + 编码检测」，一个是「数据库里已经有的一串字符」。库里能看出走的是哪条路，
将来要排查「这段正文怎么来的」时不会误导。

```rust
pub const TEXT_DIRECT_EXTRACTOR_ID: &str = "text_direct";
pub const TEXT_DIRECT_EXTRACTOR_VERSION: &str = "1";
```

**它不实现 `Extractor` trait**：那个接口的输入是「一个只读的原件句柄」（`ExtractionInput`
里有 `Path`），而这条路径没有原件。硬塞一个假 `Path` 进去，会让「原件」这个概念在代码里
变得不可信。`version` 用常量而不是字面量，是因为「切段规则变了就要改版本」这条约定需要
一个能被引用、能被测试钉住的名字。

`text` 为空或全空白时**仍然报错**（`InvalidState`）：那是「既没有原件、也没有正文」，
不能悄悄产出一份空派生内容让它看起来像提过了。

### 2. 默认搜索只看当前修订：查询时过滤 **与** 重建时不索引，两条都做

权威只有一处：`source_items.current_revision_id`。`crates/diary_core/src/search.rs` 里用
一个函数生成这个条件（`extracted_contents` 的别名当参数，`source_items` 约定叫 `src`）：

```
(src.current_revision_id IS NULL OR <content>.source_revision_id = src.current_revision_id)
```

`current_revision_id` 为空时按「这一版就是当前版本」处理，而不是「整条来源都不算数」：
建 `source_items` 的三处（导入、录音、提交草稿）都会写上当前修订，空值属异常数据；让它继续
可搜比让它从检索里凭空消失更容易被发现，也和 `extractors::extracted_content` 已有的口径
一致。

加了过滤的位置：

| 位置 | 作用 |
|---|---|
| `ranked_matches`（产品检索路径 `search.start`） | 派生片段那一路的候选 |
| `load_page`（取正文） | 再加一次，保证「结果里没有旧修订」不只靠调用方记得先过滤 |
| `candidates` / `count_matches` | 测试与实测的口径，必须与上面一致，否则同一件事有三个数字 |
| `rebuild`（`SELECT id FROM extracted_contents …`） | 旧修订的派生内容不进索引 |
| `status` 的全部片段类计数 | 见下一节 |

**为什么查询过滤和重建不索引两条都要做**（这是本片最容易做漏的一处）：

- 只做「重建不索引」：**重建之前**就已经由增量索引写进 `search_docs` 的旧修订行会留在
  库里，照旧被搜到。用户改完正文不重建，就看到旧正文；
- 只做「查询过滤」：`rebuild` 会把旧修订的片段**重新捞回**索引表里（它按
  `extracted_contents` 全表重建），刚清干净的表又被污染，而且「重建后索引里有什么」变得
  说不清。

代价（要说清楚）：**增量索引路径不删旧修订的行**。提取是在「这一版就是当前修订」时写的，
之后有人 `revise_text`，旧片段仍留在 `search_docs` 里，只是不参与默认命中。这是刻意的
（旧内容是将来「显式搜历史版本」的原料），代价是索引表里有一批不参与默认检索的行——
`status` 的 `reasons` 会明说有多少（见下），`rebuild` 会清掉它们。

### 3. 重建：只索引当前修订，并清掉旧修订的索引行

`rebuild` 第一步先 `purge_retired_segment_docs`：把「不是当前修订」的片段索引行从
`search_docs` 删掉（`DELETE … WHERE segment_id IN (…非当前修订…)`）。然后再按
「当前修订」选 `extracted_contents` 重建。

清掉而不是只在查询里挡着，是因为重建的语义是「索引重新对一遍现状」：重建之后表里不该还
留着不参与检索的行。这也让 `status` 的物理计数与逻辑计数重新对齐。

迁移路径一致：v7 迁移只回填 `captures.draft_text`（B3d），**不碰 `search_docs`**，所以
「老库升级」这条路上没有第二处会把旧修订捞回索引。范围重建（`sourceScope`）同样是
「空数组 = 什么都不看」，与其它入口同一套语义。

> `crates/diary_core/src/chunks.rs` 的 `collect_pieces` 在这条分支上不存在（属于另一片），
> 所以这一条按任务书跳过。

### 4. `status` 的计数口径：旧修订**不算**

| 字段 | 算不算旧修订 | 说明 |
|---|---|---|
| `total_segments` / `indexed_segments` / `pending_segments` / `stale_segments` | **不算** | 只统计当前修订的片段：改前 2 条、改后 3 条，不是 2+3=5 |
| `failed_sources` | **不算** | 只数当前修订里 `status = 'failed'` 的派生内容 |
| `index_rows` / `index_terms` / `indexed_chars`（片段部分） | **不算** | 与上面同源，否则「索引里有多少行」会和覆盖状态打架 |
| `index_bytes` | **算（整库物理占用）** | `dbstat` 只能按表统计，页在来源之间共享；范围查询里它也永远是整库值（既有行为，`reasons` 里本来就写明） |
| `reasons` 里的一句 | — | 有旧修订索引行时追加「N 个片段属于非当前修订：不计入上面的数字，默认搜索也看不到它们（重建会把这些行清掉）」 |

这样「状态数字」与「默认搜索」自洽：不会出现「搜索看不到它、状态却说它已全部索引」。旧
修订的行数也没被藏起来——它出现在 `reasons` 里，并注明重建会清掉。

### 5. 按需读取上一版：`previous_source_revision`

```rust
pub fn previous_source_revision(&self, source_id: &str) -> Result<Option<SourceRevision>>
```

语义：取该来源**当前修订的父修订**。一条 SQL 两次 `JOIN`（`source_items → 当前修订 →
父修订`），所以三种「没有上一版」自然退化成「查不到行」，共用一个 `None`：

- 来源不存在，或 `current_revision_id` 为空；
- 当前修订就是第一版（`parent_revision_id` 为空）；
- 父修订 id 悬空（数据坏了）——给不出正文，如实当「没有」，不编一个空修订出来。

**注意父修订可能是原件型修订**：导入的文件、录音造出来的修订 `text` 为空、`asset_id` 有
值。这时「原正文」要从它的派生内容里取，不是从 `text` 取。测试
`previous_source_revision_can_be_an_original_asset_revision` 把这一点钉住了。

桥接（`crates/diary_bridge/src/api.rs`）：

- `BridgeSession::previous_source_revision(sourceId)` → 核心同名方法（`Option` 直接映射成
  Dart 的可空返回值）；
- `BridgeSession::revise_text(...)` → 核心 `revise_text`。**这一条本来就该在桥上**：契约
  4.1 节有 `sources.reviseText`，但桥接没接，前端根本改不了正文（端到端测试需要它）；
- `wired_capabilities()` 增加 `sources.reviseText` 与 `sources.previousRevision`。
  适配层的 `_wiredMethods` 是白名单，所以这两个名字不会自动出现在
  `packages/diary_bridge` 暴露的 `CoreInfo.capabilities` 里——能力声明仍然是诚实的。

## 契约侧待办（#55，前端那一片）

这一片**不动** `packages/diary_api/**` 与适配层（`packages/diary_bridge/lib/src/bridge_diary_api.dart`）。
留给 #55 的是：

1. 契约方法（建议签名，风格照 `sources.locate` / `sources.reviseText`）：

   ```
   sources.previousRevision | sourceId | 上一版 SourceRevision；没有上一版时为空
   ```

   返回修订而不是正文：前端要能分辨「上一版是原件型修订（`assetId` 非空、`text` 为空）」
   和「上一版是文字修订」，前一种只能提供「打开原件」，不能算 diff。

2. 适配层映射：`DiaryApi.previousRevision({required String sourceId})` →
   `BridgeSession.previousSourceRevision(sourceId: …)`；同时把 `sources.previousRevision`
   加进 `_wiredMethods`。
3. 前端入口：正文编辑用 `sources.reviseText`（改某一篇来源的原始文字），**改完必须调用
   `sources.extract`**，新正文才进索引（见下面「改完必须手动提取」）。
4. **diff 由前端算**：后端只给两版正文，不做逐字对比、不返回补丁。`extractedContent` 给
   当前版，`previousRevision` 给上一版。
5. 「看原正文」在上一版是原件型修订时的分支：界面应转向 `sources.locate` + 原件打开，
   而不是显示一段空文字。

## 明确不做

- 界面上「看原正文 / 展示修改部分」的呈现（#55）；
- **后端算 diff**：不给补丁、不给逐字对比结果；
- **版本历史进默认搜索**：语义、混合、时间线里都不会出现旧修订，`SearchFilters.includeOldDiaryVersions`
  仍然是个没有效果的开关（之前就已经在 `warnings` 里说明）；
- 递归追溯：`previous_source_revision` 只给**一层**父修订，不往回走多层。

## 没想清楚的地方（要看）

### 1. `captures.draft_text` 与来源修订的重叠 → **已按「保守同步」解决**

`captures.draft_text` 与某一篇的上一版可能是**同一段文字的两种存法**：提交时会把
`draft_text` 复制成一条 text 修订。如果改正文只改修订、不动 `draft_text`，记录文字那一路
（B3d 已索引）就仍然能搜到**旧正文**——决策是「用户直接搜不到旧正文」，所以这是必须堵的洞。

现在的做法（**相等才同步**）：

- `revise_text` 先看这一篇的**上一版修订的 `text`** 是否与 `captures.draft_text` 完全相同；
- 相同 → 在同一个事务里把 `draft_text` 改成新正文，并 `index_capture` 刷新记录文字的索引
  （它会推进索引代次，进行中的会话因此失效）；
- 不相同 → **一个字都不动**：那说明这条记录的文字另有出处（比如导入的材料，记录文字是空的），
  不能替用户下结论。

`draft_text` 的含义因此从「用户最后打的草稿」变成「正文的最新一份」（在这两种存法相同的
情况下两者本来就是同一件事）。测试：`revising_the_body_syncs_the_record_text_when_it_was_the_same`
（正向）与 `revising_a_source_does_not_touch_a_different_record_text`（反向守卫）。

### 1. `captures.draft_text` 与来源修订的重叠 → **已按「保守同步」解决**

`captures.draft_text` 与某一篇的上一版可能是**同一段文字的两种存法**：提交时会把
`draft_text` 复制成一条 text 修订。如果改正文只改修订、不动 `draft_text`，记录文字那一路
（B3d 已索引）就仍然能搜到**旧正文**——决策是「用户直接搜不到旧正文」，所以这是必须堵的洞。

现在的做法（**相等才同步**）：

- `revise_text` 先看这一篇的**上一版修订的 `text`** 是否与 `captures.draft_text` 完全相同；
- 相同 → 在同一个事务里把 `draft_text` 改成新正文，并 `index_capture` 刷新记录文字的索引
  （它会推进索引代次，进行中的会话因此失效）；
- 不相同 → **一个字都不动**：那说明这条记录的文字另有出处（比如导入的材料，记录文字是空的），
  不能替用户下结论。

`draft_text` 的含义因此从「用户最后打的草稿」变成「正文的最新一份」（在这两种存法相同的
情况下两者本来就是同一件事）。测试：`revising_the_body_syncs_the_record_text_when_it_was_the_same`
（正向）与 `revising_a_source_does_not_touch_a_different_record_text`（反向守卫）。

### 2.### 2. 默认搜索只看当前修订：查询时过滤 **与** 重建时不索引，两条都做

权威只有一处：`source_items.current_revision_id`。`crates/diary_core/src/search.rs` 里用
一个函数生成这个条件（`extracted_contents` 的别名当参数，`source_items` 约定叫 `src`）：

```

```

`current_revision_id` 为空时按「这一版就是当前版本」处理，而不是「整条来源都不算数」：
建 `source_items` 的三处（导入、录音、提交草稿）都会写上当前修订，空值属异常数据；让它继续
可搜比让它从检索里凭空消失更容易被发现，也和 `extractors::extracted_content` 已有的口径

加了过滤的位置：

| 位置 | 作用 |
|---|---|
| `ranked_matches`（产品检索路径 `search.start`） | 派生片段那一路的候选 |
| `load_page`（取正文） | 再加一次，保证「结果里没有旧修订」不只靠调用方记得先过滤 |
| `candidates` / `count_matches` | 测试与实测的口径，必须与上面一致，否则同一件事有三个数字 |
| `rebuild`（`SELECT id FROM extracted_contents …`） | 旧修订的派生内容不进索引 |
| `status` 的全部片段类计数 | 见下一节 |

- 只做「重建不索引」：**重建之前**就已经由增量索引写进 `search_docs` 的旧修订行会留在
  库里，照旧被搜到。用户改完正文不重建，就看到旧正文；
- 只做「查询过滤」：`rebuild` 会把旧修订的片段**重新捞回**索引表里（它按

  说不清。

代价（要说清楚）：**增量索引路径不删旧修订的行**。提取是在「这一版就是当前修订」时写的，
之后有人 `revise_text`，旧片段仍留在 `search_docs` 里，只是不参与默认命中。这是刻意的

  `packages/diary_bridge` 暴露的 `CoreInfo.capabilities` 里——能力声明仍然是诚实的。

## 契约侧待办（#55，前端那一片）

这一片**不动** `packages/diary_api/**` 与适配层（`packages/diary_bridge/lib/src/bridge_diary_api.dart`）。
留给 #55 的是：

1. 契约方法（建议签名，风格照 `sources.locate` / `sources.reviseText`）：

   ```
   sources.previousRevision | sourceId | 上一版 SourceRevision；没有上一版时为空
   ```

   返回修订而不是正文：前端要能分辨「上一版是原件型修订（`assetId` 非空、`text` 为空）」
   和「上一版是文字修订」，前一种只能提供「打开原件」，不能算 diff。

2. 适配层映射：`DiaryApi.previousRevision({required String sourceId})` →
   `BridgeSession.previousSourceRevision(sourceId: …)`；同时把 `sources.previousRevision`
   加进 `_wiredMethods`。
3. 前端入口：正文编辑用 `sources.reviseText`（改某一篇来源的原始文字），**改完必须调用
   `sources.extract`**，新正文才进索引（见下面「改完必须手动提取」）。
4. **diff 由前端算**：后端只给两版正文，不做逐字对比、不返回补丁。`extractedContent` 给
   当前版，`previousRevision` 给上一版。
5. 「看原正文」在上一版是原件型修订时的分支：界面应转向 `sources.locate` + 原件打开，
   而不是显示一段空文字。

## 明确不做

- 界面上「看原正文 / 展示修改部分」的呈现（#55）；
- **后端算 diff**：不给补丁、不给逐字对比结果；
- **版本历史进默认搜索**：语义、混合、时间线里都不会出现旧修订，`SearchFilters.includeOldDiaryVersions`
  仍然是个没有效果的开关（之前就已经在 `warnings` 里说明）；
- 递归追溯：`previous_source_revision` 只给**一层**父修订，不往回走多层。

## 没想清楚的地方（要看）

### 1. `captures.draft_text` 与来源修订的重叠（**影响验收语义**）

按本片决策，`revise_text` 只改来源修订，**不动** `captures.draft_text`。但 B3d 把
`draft_text` 也索引了。当一条记录的草稿正文和它提交出来的文字修订曾经是同一段文字时：

```
revise_text(来源修订, 旧→新) 之后，整库搜索：
  搜「不太好」（只在旧正文）：命中 1 条 —— 来自记录文字那一路，snippet 是旧正文
  搜「体检」：命中 2 条 —— 来源修订（新正文）+ 记录文字（旧正文）
```

实测输出见 `crates/diary_core/tests/revision_visibility_test.rs` 的
`revise_text_does_not_touch_the_capture_draft_text`。也就是说，在「用户写草稿 → 提交 →
`revise_text` 改正文」这条流程里，**用户仍然会搜到旧正文**（作为记录文字命中），这与
「用户在搜索里直接看不到旧正文」的验收意图冲突。

严格按 issue 的决策看，这不是漏实现：issue 明确写了「记录自己的文字（`draft_text`）不受
影响」，两种语义不要混。但**用户在界面上看到的就是旧正文还在结果里**。两条候选修法都要
跨层决定，本片没有权限单方面定：

- **保守同步**：`revise_text` 时若「上一版修订的 `text` == 该记录的 `draft_text`」，就顺手
  把 `draft_text` 也改成新正文并在同一事务里 `index_capture`。相等才同步，用户把两份改分叉
  时不碰。代价：`draft_text` 的含义从「用户最后打的草稿」变成「正文的最新一份」；
- **前端分流**：改「自己写的正文」走 `captures.saveDraft`（B3d 会先删后写，旧词项真的消失），
  `revise_text` 只用于改导入材料的原始文字。代价：已提交记录的 `saveDraft` 现在被
  `InvalidState` 拒掉，需要另开一条「改已提交记录正文」的契约。

**建议由 #55 的评审定这一条**，因为它决定了前端「编辑正文」按钮背后该调哪个方法。

### 2. 改完必须手动提取，中间有一段「什么都搜不到」

`revise_text` 不自动提取，调用方要再跑一次 `sources.extract`。这中间有个窗口：新修订还没
派生内容，旧修订又不是当前修订 → **这条来源的正文在默认搜索里完全消失**。导入之后也是
「先入库、再提取」，形态一致，但改正文是高频操作，值得考虑让 `revise_text` 自己触发提取
（或由任务队列保证）。本片没做，因为 `revise_text` 是带幂等回执的写路径，把可能失败的解析
塞进去会改变它的语义。

### 3. `previous_source_revision` 只有一层

只给直接父修订。若将来要「看更早的版本」，要么加递归，要么加 `revisionId` 版本的
`extractedContent`。原件型父修订拿不到正文这一点，只能靠前端转向「打开原件」或靠上面第 1
条里提到的「按修订取派生内容」入口。

### 4. `extractor_version` 没有消费方

这一片给纯文本修订定义了 `TEXT_DIRECT_EXTRACTOR_VERSION`，但**目前没有任何路径按
`extractor_version` 判断派生内容过期**：`status` 的 `stale_segments` 看的是
`tokenizer_version`（分词器），不是提取器。也就是说，将来改了切段规则、把版本从 `1` 改成
`2`，库里那些 `1` 的派生内容既不会被标过期，也不会被 `rebuild` 重跑（`rebuild` 只重刷
索引，不重新提取）。要么补一条「提取器版本不一致 → 重新提取」的校准路径，要么把
`extractor_version` 明确降级成「只进库、可审计」的字段（注释里已经这么写了）。

## 实测：这一片给查询加了什么代价

`current_revision_only` 让候选与计数查询各多了两个 join（`extracted_contents` 与
`source_items`，都是主键查找）。用仓库已有的 10 万片段实测跑一遍：

```bash
cargo test --release -p diary_core --test search_test -- --ignored --nocapture hundred_thousand
```

| 指标 | M1 记录（[M1 · 关键词索引](m1-关键词索引.md)，无过滤） | 这一片（有过滤） |
|---|---|---|
| 首屏 20 条（妈妈 / 离职 / 面试 / 加班） | 0.029–0.030 ms | 0.042–0.069 ms |
| 首屏 20 条（面试官） | 0.361 ms | 0.430 ms |
| 全量计数（`count_matches`） | 42–43 ms | 48–55 ms |

召回不变：四个词各自全召回（例：「妈妈」40828/40828）。涨幅与预期一致——全量计数要对每个
候选行多做两次主键查找；首屏那条是 `ORDER BY g.doc_id LIMIT 20`，扫到凑够 20 条就停，绝对
值仍在 0.1 ms 以下。`count_matches` 不在产品路径上（翻页靠快照游标），所以没有为它做优化；
真要拉回 42 ms，方向是 M1 记录过的「按各 bigram 取交集求候选」。

（上表是同机单次实测，只用来说明量级与方向，不当基准用。）

> 顺带发现：`crates/diary_core/tests/search_test.rs` 里那条复现命令写的是
> `-- --ignored --nocapture 十万`，而「十万」只出现在 `#[ignore]` 的理由与文档注释里，
> 不是测试名的一部分（测试名是 `hundred_thousand_segments_measurement`），所以照抄那行会
> 「跑 0 个测试、退出码 0」。这一片没有改它（属于别的切片），改用 `hundred_thousand` 过滤
> 才真正跑到。
