代码位置：`crates/diary_core/src/backup.rs`（快照、清单、自校验、恢复、拒绝）、
`crates/diary_core/src/model.rs`（`BackupCounts` / `BackupReport` / `BackupInspection` / `RestoreReport`）、

原件与快照都是流式读写，内存占用与库的大小无关。

## 定下的决定

| 决定 | 理由 |
|---|---|
| 数据库用 **`VACUUM INTO`** 导出，**不拷 `.sqlite` 文件** | 任务书 §3.4 的硬约束。资料库开着 WAL（`Core::prepare` 设的），最近的提交可能还在 `-wal` 里；拷主文件会得到一个「看起来是库、其实少一截」的东西。`VACUUM INTO` 按**读事务**的一致性视图导出成另一个完整文件（含 WAL 里已提交的内容），对源库只读 |
| **先取快照，再按快照复制原件**，全程**不加全局写锁** | 「有持续写入时备份」是 E34 的核心场景。加写锁等于把这条验收变成「停下来备份」，也把「用户正在记东西」变成备份失败的原因 |
| 备份包 = **一个 zip 文件**，包内固定三个位置：`manifest.json`、`db/library.sqlite`、`blobs/<sha 前两位>/<sha>` | zip 是已有能力（DOCX 提取在用），单文件、可流式、可增量读；DB 条目用 Deflate，原件用 Stored（媒体本来就压过，再压只是白烧 CPU，还要保证「按内容寻址的字节」在包里保持原样） |
| 清单里写 **`schemaVersion` / `apiVersion` / `coreVersion` / `createdAt` / 快照 sha256+大小 / 每条原件的相对路径+sha256+大小 / 关键行数** | 契约第 8 节要求「恢复先检验格式、版本、哈希、大小及安全路径」；清单是这些检验的唯一依据，也是「这个包是什么」的自描述 |
| **不回写资料的源库、不建备份历史表** | 备份是「只读现库 + 写一个新文件」；要不要记「上次备份是什么时候」是设置页/任务中心的账，不该靠 core 新增一张表来记（见「没有做到的」） |
| 写完**自校验**：重开包、逐条目重算哈希、比大小、比条目集合，不过就删包报错 | 「绝不产出看起来成功的备份」。写的时候已经核过一次（源文件 vs 库里记录的哈希），自校验是**第二次、面向已落盘字节**的核对，挡写入损坏 |
| 库里**已经有原件不可用**（文件被外部删掉）时备份**失败** | 「完整备份」是这一条的承诺，缺原件的包不该被当成可恢复的备份。要不要允许「如实标记为不完整」的部分备份见「没有做到的」 |
| 恢复只允许落到**新的空目录**（不存在，或存在且为空），且不能是当前资料库所在目录 | 任务书与契约都要求「恢复默认新建资料库，不直接覆盖现库」。空目录这条把「误覆盖」变成不可能，而不是靠调用方小心 |
| 解包先落在**目标同级的暂存目录**，全部校验通过才**一次 rename** 落地 | 恢复中途失败时目标目录保持原样（不存在或还是那个空目录），不会留下一个「看起来能用」的半成品库 |
| 恢复出来的库与快照**逐字节相同**：恢复阶段**不做迁移、不做恢复态修正** | 迁移与 `recover_on_open` 是**开库**的语义（`Core::open`），不是恢复的语义；把两件事揉在一起会让「恢复成功」这句话变得含糊。第一次 `Core::open` 时照既有语义处理，未完成的导入/录音因此如实显示为「没完成」 |
| **不碰 `recover_on_open`**（#82 尚未合入） | Android 后台唤醒会造第二个驱动那条还在改；本条只依赖它既有的「如实标记未完成」口径，不改语义 |
| 越界路径与损坏**共用一个契约错误码** `corrupted_backup`，靠 `issues` 的种类与文案区分 | 契约第 7 节只有 `corrupted_backup` / `incompatible_backup` 两个备份错误码；为「越界路径」新增一个码等于改契约，而它对用户的可执行动作与「包坏了」完全一样（换一份备份）。机器可读的种类在 `inspect` 的 `issues` 前缀里：`corrupted` / `unsafe_path` / `incompatible` |
| 这一轮是**同步**入口（`backups.create/inspect/restore` 的同步版），不做任务化 | issue #86 明确「是否任务化（#70）不阻塞本条」。契约那三行的返回是 `jobId`，所以 Dart 适配层**不**把这三个能力列进 `CoreInfo.capabilities`（能力清单是窄化过的），桥接层如实列——见第 6 节 |

## 1. 备份产物：格式与清单

### 1.1 包内布局

```
<备份包>.diarybak            # 就是一个 zip
├── manifest.json            # 清单：先读它，再决定要不要用这个包
├── db/library.sqlite        # VACUUM INTO 导出的数据库快照（单文件，不含 WAL）
└── blobs/<sha 前两位>/<sha> # 被快照引用的内容寻址原件，一条一份
    staging/<recording>/<file>  # 可选：未收尾录音的已封闭片段（随行片段）
```

包里**只有**清单声明的条目。恢复时**只按清单声明的路径写文件**；归档里多出来的任何
条目都会被当成「清单与内容不一致」拒绝，绝不按它解包。

### 1.2 清单示例（一份真备份包的输出，哈希截短；`transientClips` 那一条是「有未收尾录音」时的样子）

```json
{
  "format": "unwritten-diary-backup",
  "formatVersion": 1,
  "schemaVersion": 8,
  "apiVersion": "1.0",
  "coreVersion": "0.1.0",
  "createdAt": "2026-10-16T06:47:53.755Z",
  "sourceLibraryFileName": "library.sqlite",
  "snapshot": {
    "path": "db/library.sqlite",
    "sha256": "4b35c6af…de303",
    "byteSize": 278528
  },
  "blobs": [
    {
      "path": "blobs/4c/4cbaf696…57e4be",
      "sha256": "4cbaf696…57e4be",
      "byteSize": 22
    }
  ],
  "transientClips": [
    {
      "path": "staging/rec_01a1/seg-0.bin",
      "sha256": "…",
      "byteSize": 4096,
      "recordingId": "rec_01a1",
      "segmentIndex": 0
    }
  ],
  "counts": {
    "captures": 1,
    "sourceRevisions": 2,
    "assets": 1,
    "blobs": 1,
    "importsInFlight": 0,
    "openRecordings": 0
  },
  "notes": [
    "只包含数据库快照（db/library.sqlite）与内容寻址的原件（blobs/）。",
    "staging/ 下未完成导入的部分字节不在包里；未收尾录音的已封闭片段能拿到就随包（transientClips），拿不到就如实记进报告。",
    "索引与向量是派生数据：它们在快照里，恢复后也可以重建。"
  ]
}
```

| 字段 | 说明 |
|---|---|
| `format` / `formatVersion` | 包的格式标识与格式版本。`format` 不认识 ⇒ 拒绝；`formatVersion` **高于** 1 ⇒ `incompatible_backup` |
| `schemaVersion` | 快照的 `PRAGMA user_version`。**高于**本构建的 `SCHEMA_VERSION` ⇒ `incompatible_backup`；更老的照常恢复（迁移由开库接手） |
| `apiVersion` | 产出这份备份的核心 API 版本，与 `CoreInfo.apiVersion` 同一个常量（`diary_core::API_VERSION`）。`major.minor`，只有**高于**本构建才拒 |
| `coreVersion` | `CARGO_PKG_VERSION`，排查用 |
| `createdAt` | 快照的导出时刻（ISO-8601 UTC） |
| `sourceLibraryFileName` | 原库文件名，**仅供展示**；恢复出来的库固定叫 `library.sqlite`，清单里的字符串绝不参与路径拼接 |
| `snapshot` | 快照条目：包内路径（固定 `db/library.sqlite`）、sha256、字节数 |
| `blobs[]` | 内容寻址的原件。`path` 必须等于 `blobs/<sha 前两位>/<sha>`（对不上就是清单被改过）；同一条内容只有一条 |
| `transientClips[]` | **随行片段**：未收尾录音的已封闭片段（不是内容寻址的那一类，见第 2.3 节） |
| `counts` | 快照那一刻的关键行数：`captures` / `sourceRevisions` / `assets` / `blobs` / `importsInFlight` / `openRecordings`。恢复时拿恢复出来的库**逐项核对** |
| `notes` | 自描述说明：包里有什么、没有什么 |

`BackupCounts` 里 `assets` / `blobs` / `importsInFlight` / `openRecordings` 是可选字段：
`blobs` / `assets` / `import_sessions` 从 schema v2 起、`recording_sessions` 从 v3 起才存在，
一个 v1 时代的备份本来就不该有它们。核心自己产出的清单永远是全的。

## 2. 一致性快照与快照边界

### 2.1 为什么要 `VACUUM INTO`

`Core::prepare` 打开库时设了 `journal_mode=WAL`。WAL 下「已提交」不等于「已经在主文件里」：
最近的提交可能只活在 `-wal` 里，主文件还是几分钟前的样子。所以

- **不许** `fs::copy(library.sqlite, …)`：拷到的是旧状态，还可能拷到一个撕裂的中间态；
- **也不许**「先把 WAL 合并再拷」：合并（checkpoint）会打断正在写的写入者，等于给备份加了写锁。

`VACUUM INTO '<新文件>'` 是 SQLite 自己的导出：它在**一个读事务**的一致视图上写出一个
完整、无 WAL、已整理过的数据库文件，对源库**只读**。WAL 下读不挡写，所以：

- 备份期间用户可以继续记录、继续导入（E34）；
- 快照之后的新写入**不进**这份备份，但也不让备份失败。

### 2.2 快照边界为什么成立

顺序是死的：**先取数据库快照，再复制被快照引用的原件**。于是：

1. 快照里出现的每一条 `blobs` 行，都是**快照那一刻已经提交**的事实；
2. 原件的落盘顺序是「**先文件、后数据库**」：`assets::finish` 与 `recordings::finalize`
   都先把字节搬进内容存储（`blobs/<sha 前两位>/<sha>`）并校验哈希，再在一个事务里写
   blob / asset / revision 行。所以「快照里有这条引用」⇒「文件在快照之前就已经落定」；
3. 原件是**内容寻址**的：路径由内容的 sha256 决定，同名即同内容；
4. 核心**没有任何删除 blob 的路径**（回收站、清理、取消导入都不删原件；`purge` 还没实现），
   所以快照引用过的文件不会在复制途中消失；
5. 复制时**逐条重算 sha256**并与库里记录的值比对：内容被外部改过 ⇒ 整份备份失败，
   而不是把一份「和库里对不上」的字节塞进包里。

这五条合起来就是「快照边界」：**备份的内容 = 快照那一刻的数据库 + 那一刻被引用的全部
原件**，不多不少。快照之后的新记录、新导入不在包里，也**不会**让恢复失败。

### 2.3 哪一类原件不是内容寻址，怎么处理

去核对真实存储布局的结果（`assets.rs` / `recordings.rs`）：

| 东西 | 存储 | 是不是内容寻址 | 备份怎么处理 |
|---|---|---|---|
| 文件库原件（导入的文件、最终化后的录音音频） | `blobs/<sha 前两位>/<sha>` | **是**（`assets::blob_rel_path`） | 作为 `blobs[]`：**必须**随包，逐条核 sha256；缺一条就整份备份失败 |
| 未收尾录音的已封闭片段 | `staging/<recording_id>/<relative_file_name>`（文件名由平台层给） | **不是**：名字不是 hash，`finalize_recording` 成功后整个暂存目录还会被删 | 作为 `transientClips[]`：**能拿到就按片段行里登记的 sha256 校验后随包**；拿不到（并发最终化/取消把目录删了）就跳过，并把跳过数如实写进报告的 `warnings`。跳过**不让备份失败**——一场并发的最终化不该毁掉整份备份 |
| 未完成导入的部分字节（`.part`） | `staging/<import_id>.part` | 不是，而且**正在被平台层写** | **不随包**。它是进行中操作的临时工作区，不是任何已确认的原件；恢复出来的库里那条导入照旧是「没完成」，用户取消后重新导入 |

因此在验收口径里，「原件」= `blobs[]`（完整、必到、逐条核哈希）；
`transientClips[]` 是**随行**的临时工作区，不承诺完整、但**承诺不谎报**：
清单里只写真的进了包的片段，恢复时同样逐条核哈希。

## 3. 拒绝口径与错误码（E35）

`restore_backup` 的每一条拒绝都在**写任何东西之前**决定（包结构 → 路径 → 版本 → 目标目录），
错误信息里都带「已拒绝恢复；当前资料库没有改动，目标目录保持原样」。

| 场景 | 错误码 | 文案要点（取自真实输出，哈希与版本号做了示例化） |
|---|---|---|
| 不是 zip / 没有清单 / 清单解析不了 / `format` 不认识 | `corrupted_backup` | 「打不开这个备份包（不是有效的 zip 归档）：…。请换一份备份」 |
| 清单路径是绝对路径、含 `..`、含反斜杠/冒号、有空路径段 | `corrupted_backup` | 「原件条目 ../escaped.bin 不能当路径用（含越界路径段 `..`）。已拒绝恢复；当前资料库没有改动，目标目录保持原样」 |
| 归档里有清单没声明的条目 / 清单声明的条目不在包里 | `corrupted_backup` | 「包里有清单没声明的条目 X（拒绝解包，绝不写到清单之外的位置）」 |
| 条目哈希不符、大小不符、快照 `user_version` 与清单不符、关键行数不符、库里引用的原件在包里缺失 | `corrupted_backup` | 「条目 blobs/xx/yy 的 sha256 是 …，清单声明 …」／「恢复出来的库 blobs 有 3 行，清单声明 2 行」 |
| `schemaVersion` 高于本构建 | `incompatible_backup` | 「备份的 schemaVersion 是 9，本核心最高支持 8；请先升级应用再恢复。已拒绝恢复；当前资料库没有改动，目标目录保持原样」 |
| `apiVersion` 高于本构建 | `incompatible_backup` | 「备份的 apiVersion 是 2.0，本核心支持到 1.0；请先升级应用再恢复…」 |
| `formatVersion` 高于本构建 | `incompatible_backup` | 「备份包格式版本是 2，本核心只认识 1；请先升级应用再恢复」 |
| 目标已存在且非空 / 不是目录 / 就是当前资料库目录 | `invalid_state` | 「不是空目录；恢复只允许落到新的空目录，绝不覆盖已有资料库。已拒绝恢复；当前资料库没有改动…」 |
| 备份包文件不存在 | `not_found` | 「找不到备份包：…」 |
| 创建备份时目标已存在 | `invalid_argument` | 「备份目标已经存在，不能覆盖：…（换一个文件名，或先删掉旧的那一份）」 |
| 创建备份时源库已有原件不可用 / 原件内容与库记录不符 / 写完自校验不过 | `integrity_failed` | 「资料库里这条原件已经不可用：blobs/xx/yy（sha256 …）。备份不会假装它还在…」／「备份写完后的自校验没通过，已删除半成品、没有产出备份：…」 |

`inspect_backup` **不抛错**（除非连清单都读不出来）：它把上面的问题逐条放进
`BackupInspection.issues`，每条格式是 `种类: 细节`，种类只有三种：

- `corrupted:` —— 哈希 / 大小 / 结构 / 清单与内容不一致；
- `unsafe_path:` —— 绝对路径、`..`、反斜杠/盘符、清单之外的条目；
- `incompatible:` —— `schemaVersion` / `apiVersion` / `formatVersion` 高于本核心。

`compatible` 只反映**版本**能不能处理；`hashes_verified` 只在「结构没问题、逐条目哈希都过」
时为 true（有 `unsafe_path` / `corrupted` 时不做哈希校验，也不该做——那不值得为一个
不能用的包读一遍全部字节）。

## 4. 恢复流程

```
restore_backup(package, target_dir)
 0. 包在不在（not_found）→ 读清单（read_plan：结构 / 路径 / 条目集合 / 版本，不写任何东西）
    有 structural / incompatible 问题 ⇒ 按第 3 节拒绝，一个字节都没写
 1. 目标检查：不存在，或存在且是空目录；不能是当前资料库目录        （invalid_state）
 2. 建暂存目录 <目标父目录>/.<nonce>.restore/
 3. 逐条目解包进暂存目录：只按清单声明的路径写；边写边核 sha256 与大小
 4. 打开暂存里的 library.sqlite（**只读**）做校验：
      PRAGMA integrity_check = ok
      PRAGMA foreign_key_check 为空
      PRAGMA user_version == 清单 schemaVersion
      captures / source_revisions / assets / blobs 行数 == 清单 counts
      库里每条 blob ↔ 清单每条原件，双向一致（sha256 / 路径 / 大小）
      assets 指向的原件都在、source_revisions 指向的资产都在
 5. 落地：目标若是个空目录就先删掉它，然后 **一次 rename** 暂存目录 → 目标目录
 6. 报告：library_path / counts / 原件数 / 需知事项（warnings）
```

### 「绝不改当前资料库」是怎么保证的

- `restore_backup` 只读**备份包**与 `core.root`（后者只用来判「目标是不是现库目录」），
  **完全不碰** `core.conn`：现库的连接、WAL、原件目录都不在写入范围里；
- 全部写操作落在**目标同级的暂存目录**里；目标目录在最后一步之前不被创建/不被写入；
- 失败路径只有一句 `remove_dir_all(暂存目录)`：目标目录保持原样，现库一字不改；
- 每条拒绝文案里都写明这一点，测试用「整个资料库目录的逐文件哈希 + 关键行数前后对比」
  证明（见第 6 节）。

### 界面的用法（本条的边界）

恢复的产物是一个**新的资料库目录**。报告里的 `library_path` 直接交给
`BridgeSession.open`（或契约的 `core.open`）就能打开新库；要不要切过去、要不要提示
「已恢复到新资料库」，是前端的事。

## 5. 边界如实：没做完的东西不假装做完

- **未完成的导入**（`prepared` / `copying` / `verifying`）：快照里保留它们的真实状态，
  恢复出来的库**逐字节等于快照**——直接读那个库文件时状态还是 `prepared`。
  第一次 `Core::open` 会按**既有的** `recover_on_open` 语义把它标成 `recoverable`
  （「没完成，可以选择重试或取消」），不会假装 `ready`。本条没有改这套语义（#82 未合入）。
  这些导入的 `.part` 字节不在包里，所以重试 `finish` 会因为没有暂存文件而失败——
  正确的出路是取消后重新导入。
- **未收尾的录音**：恢复出来的库如实显示为未完成（`recoverable` / `interrupted`）。
  片段若随了包（`transientClips`），恢复后**还能继续最终化**（测试里真的拼出了音频）；
  没随包的，`finalize` 会因为片段不可读而拒绝，而不是伪造一段音频。
- **索引与向量**：它们是派生数据，跟着快照一起进包（不额外保证与原件一致），
  恢复后也可以重建（`indexes.rebuild`）。
- **迁移**：恢复阶段不做迁移。schema 比本构建老 ⇒ 恢复成功，第一次开库时迁移；
  比本构建新 ⇒ 恢复阶段就拒绝（`incompatible_backup`）。

## 6. 接口与能力项

| 层 | 东西 | 说明 |
|---|---|---|
| 核心 | `Core::create_backup(target_path) -> BackupReport` | 同步。目标**已存在**报 `invalid_argument`（不覆盖旧备份） |
| 核心 | `Core::inspect_backup(package_path) -> BackupInspection` | 同步，逐条目核哈希；坏在哪进 `issues`，不抛错 |
| 核心 | `Core::restore_backup(package_path, target_dir) -> RestoreReport` | 同步；目标必须是新的空目录 |
| 桥接 | `BridgeSession::create_backup` / `inspect_backup` / `restore_backup` | 字段级镜像上面三个报告；签名变化已重跑 codegen |
| 能力项 | Rust 侧 `wired_capabilities()` 列 `backups.create` / `backups.inspect` / `backups.restore` | 「桥接接了这三个方法」 |
| 能力项 | Dart 适配层 `BridgeDiaryApi._wiredMethods` **不列**它们 | 契约那三行返回 `jobId`（任务化 #70），同步入口还没接到契约接口上；能力清单在 Dart 侧是窄化过的，界面看不到没接的东西 |

契约第 1.2 节的 `apiVersion` 与清单里的 `apiVersion` 现在共用
`diary_core::API_VERSION`（`"1.0"`），不再各写一份字面量。

## 8. 没有做到的

- **增量 / 差异备份**：每次都是完整包（E34 要的就是完整备份）。增量要定义「基线」与
  「基线还在不在」，那是另一条。
- **加密**：包是普通 zip，**不宣称加密**（契约第 8 节：首版明确标注含私人资料、不宣称
  已加密）。加密备份要连密钥托管一起定，单列一条。
- **可读的 Markdown / 纯文本导出**：那是 B6 的插件示例或单列一条（契约里
  `exports.create` 与备份是**不同入口**）。这一条只做「能完整恢复的备份」。
- **任务化（#70）**：现在三个入口都是**同步**的，会占住调用线程。大库上这不是好形态，
  但任务化要等任务系统接更大的负载（见 [m4-任务调度与补做.md](m4-任务调度与补做.md)）。契约的 `jobId` 返回
  因此还没兑现，Dart 适配层也没接这三个能力。
- **真机大库的体积 / 耗时 / 内存实测**：只有单元测试与桥接端到端。口径是
  「全流程流式、64KB 缓冲，内存与库大小无关」，但**没有**在真机 10GB 级资料库上量过；
  可以预期的成本是：备份 ≈ 读一遍原件 + 写一遍包 + 自校验再读一遍包（≈ 3× 原件字节的
  I/O，其中两遍要算 sha256），恢复 ≈ 读一遍包 + 写一遍原件 + 算一遍哈希。要压成本得
  引入「自校验抽样」或任务化 + 进度，那是后话。
- **备份历史表 / 定时备份**：没有新增 schema。要不要在库里记「上次备份时间 / 包在哪 /
  成没成」，由设置页与任务中心定；核心只提供一次性的同步入口。
- **允许「不完整备份」**：库里已经有原件丢失时，现在**直接失败**（「完整备份」是承诺）。
  要不要给一个「如实标记为不完整、允许继续」的降级入口，需要产品拍板——它对用户的
  价值是「至少把剩下的保住」，代价是「不完整」这件事必须一路显示到 UI，不能被当成
  可恢复的备份。
- **包的来源认证（签名）**：包内哈希能发现**损坏**，但发现不了「整包被换过」（清单与
  条目一起被改，哈希自然自洽）。本地优先产品里这不是当前威胁模型，但要在威胁模型里
  写清楚：**没有签名，也没有加密**。
- **并发最终化的竞态**：未收尾录音的片段是「能拿到就拿」，并发最终化删掉暂存目录时
  那几个片段不进包（如实记进 warning）。没有做「重取快照重试」那一套。
- **恢复的断点续做**：恢复失败就是失败（清掉暂存目录），没有断点续传。
