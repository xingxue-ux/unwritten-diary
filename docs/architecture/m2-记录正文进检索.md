# M2 · 记录正文进检索

对应 issue [#44](https://github.com/xingxue-ux/unwritten-diary/issues/44) · 日期 2026-10-09 · 执行人 xingxue-ux

B3a（[M1 · 关键词索引](m1-关键词索引.md)）索引的只有**派生内容片段**，B3b（[M2 · 检索会话](m2-检索会话.md)）做的是会话状态机。这一片补上最大的那块缺口：**用户自己写的文字**（`captures.draft_text`）也要能被关键词搜到——搜「妈妈」要能找到自己写的那句话，不只是导入文件里的。

## 为什么另建两张表，而不是让 `search_docs` 支持「没有片段的文档」

我在 issue #44 里推荐的方案是「`search_docs.segment_id` 可空 + 增加 `capture_id`」。动手前读了一遍 schema，改掉这个决定，理由是**迁移风险**：

- `search_docs.segment_id` 是 `NOT NULL` + 外键，SQLite 没法用 `ALTER` 去掉非空约束；
- 要让它是可空，只有两条路：**整表重建**（`CREATE` 新表 → 拷 → `DROP` 旧的 → 改名）。但 `DROP TABLE search_docs` 会按 `ON DELETE CASCADE` 把 `search_grams` 里的词项全部级联删掉——现有索引当场清空，必须整库重建，而且是在迁移事务里；或者用 `PRAGMA legacy_alter_table=ON` 的改名技巧保住外键文本，那是依赖历史行为的偏方。

于是改成**纯增量的迁移**：新增 `search_capture_docs` / `search_capture_grams` 两张表，**现有 `search_docs` / `search_grams` 一行都不动**。代价是召回与取页各多一条查询分支（片段一路、记录文字一路），但升级路径是加法：老库的派生内容索引不受任何影响。

（版本号是 v7：v6 被 B3b 的**索引代次**占用了——那一版的指纹改成显式递增的代次，见 [M2 · 检索会话](m2-检索会话.md)。这一片的表建在 v7，回填已有记录文字也在 v7 完成。）

两张表的分工与 `search_docs` 完全对称（同样是「文档行 + 词项行」，同样 `WITHOUT ROWID` 的词项表、同样的 `tokenizer_version`），所以「重建」「词项生成」「摘录高亮」这些逻辑是共用的，不是两套。

## 定下的决定

| 决定 | 理由 |
|---|---|
| **迁移里回填已有记录的文字** | 不回填的话，老库升级后要先手动重建才能搜到自己的话——「升级完搜索变差了」是最糟的体验。回填只遍历 `draft_text` 非空的记录，代价与记录数成正比，与片段数无关 |
| **doc_id 用带来源的引用（`DocRef`），不用负数或偏移魔法** | 两张表的 `doc_id` 各自从 1 开始，会撞号。用「负数 doc_id」或「加大常数」这类技巧会让每个查询都要记住这个约定；显式区分来源一眼能看懂，也让排序键里能加一个稳定的家族序 |
| **排序键加家族序** | 同一日期、同一出现位置时，片段与记录文字的相对顺序必须确定，否则结果不可复现、测试会飘 |
| **记录文字属于 `text` 类型，只有 `kinds` 为空或含 `Text` 时才参与** | 它就是用户写的文字，归到文字类最诚实 |
| **`source_scope` 的映射：一条记录属于该范围，当且仅当它拥有该范围内的来源** | 记录文字本身没有来源，但它所属的材料在范围内，这条记录的文字就该被看到。空范围仍然是「什么都不看」，不退化成「看全部」 |
| **文字清空时删掉索引行，不留空文档** | 空文档会让「已索引」的计数虚高，也会让覆盖状态说假话 |
| **`commit` 不改 `draft_text`，所以提交后文字仍在索引里** | 提交是把草稿文字变成原始文字版本，草稿正文保持不变；所以一条记录「写完就搜得到」，提交与否都搜得到。这一点在测试里钉住 |
| **`IndexStatus` 增加 `indexed_captures` / `total_captures`，并让 `coverage` 同时看两边** | 只算片段的话，会出现「记录文字全都还没进索引，覆盖状态却报 complete」——那正是修这一片之前的真实状态。`index_rows` 也把记录文字的文档行算进去，注释跟着说清 |
| 命中映射：`hit_id = cap_<captureId>`、`group_id = captureId`、`capture_id = captureId`、`source_kind = text`、`locator = null`、`coverage = complete` | 记录文字就是用户原文，没有更细的定位（`locator` 为 null 是如实，不是缺失）；一段文字天然是一个组，不存在「相邻块占满结果」的问题。`capture_id` 与 `group_id` 在这一路恰好相同；**片段那一路不是**（`group_id` 是 `sourceId`），跳详情页一律用 `capture_id` |

## 对 B3b 的一处行为改变（要看）

B3b 的 `filters_to_params` 把 `sourceScope: []`（空数组）折成了 `None`，也就是「看全部」；而 `indexes.status` 对同样的空数组是「什么都不看」。同一个参数在两个方法里意思相反，早晚会出事故。这一片统一成**「什么都不看」**（`None` 才是「不限」），与 `indexes.status` 一致。

影响面：`search.start` 的**片段路径**以前传空数组会返回全部结果，现在返回 0 条。B3b 没有测到这一条，所以不是它红了才发现，是我实现这一片时对出来的。前端 F4 还没开始，没有消费者，现在改代价最小。

## 验证

`crates/diary_core/tests/search_capture_test.rs`（**13 项**，真库真提取）：

| 测的东西 | 断言要点 |
|---|---|
| 自己写的文字能被搜到 | `source_kind = text`、`locator = null`、`coverage = complete`、`hit_id = cap_<id>`、摘录/高亮正好落在查询词上 |
| `kinds` 门控 | `kinds = [image]` 时记录文字整路不参与；`kinds` 为空或含 `text` 时参与 |
| 改了文字 | 旧词不再命中、新词命中（先删后写，不是累积） |
| 清空文字 | 索引行被删掉，不再命中 |
| 只有空白（含全角空格 U+3000） | 不算「有文字」：既不入索引，也不计进 `total_captures` |
| 记录文字与派生片段同时命中 | 两条命中 `hit_id`/`group_id` 都不同，家族序片段在前 |
| 提交之后 | `draft_text` 不变、仍能搜到、计数不变（commit 不改草稿正文，所以不需要索引钩子） |
| 索引状态 | 手动删掉一条 `search_capture_docs` 后 `coverage` 立刻从 `complete` 变 `partial`，`reasons` 明说「1 条记录的文字还没进索引」 |
| 重建 | 删掉两张表里的记录文字行后 `rebuild` 能恢复搜索 |
| 范围语义 | `sourceScope = []` 对记录文字也是 0 条；单来源范围只算「拥有该来源的记录」 |
| 会话失效 | 会话期间改自己写的字，`nextPage`/`snapshot` 报 `search_expired` |
| **v6 老库升级** | 手工把库退回 v6（`DROP` 两张 v7 表 + `user_version = 6` + `schema_migrations`）后重开：`current < 7` 分支真的执行、回填真的发生、v6 已有的片段索引**一行没动**、行数/`tokenizer_version`/`text_length` 都对 |
| 词项数是**并集** | 同一句话既在自己写的文字里、又在导入材料的片段里（都有「妈妈」）时，`index_terms` 只算一次；测试同时断言「两路分别计数相加确实更大」，否则这条测试测不到东西 |
| 带范围的状态查询 | UNION 那条 SQL 里有**两处**范围过滤，绑定的参数份数必须跟着占位符个数走——写死成一份时范围查询直接报 `InvalidParameterCount(1, 2)`。这条是先被 B3a 自己的范围测试打红，才补上专门的回归断言（全库查询永远看不出来） |
| 内存库 | 不落盘也要能用（2-gram 并集、单字都能搜到） |

桥接 `bridge_search_test.dart` 从 3 项变 **4 项**：新增「`createDraft` + `saveDraft` 写中文 → `startSearch` 命中，`sourceKind = text`、`locator = null`、`hit_id = cap_<id>`」。`bridge_probe_test.dart` 的 `dataSchemaVersion` 期望跟着从 5 改成 6。

我自己独立跑过（不是只信实现的汇报）：`clippy --workspace --all-targets -D warnings` **0 问题**；`cargo test --workspace` **92 项通过**（B3b 基线 79 + 新增 13）；桥接静态分析干净、**11 项**端到端（7 + 4）。

## 没有做到的

- **不是用旧构建真造 v6 文件**：迁移测试里的 v6 状态是手工重建的（删 v7 表 + 改版本号），所以「老版本二进制写出的文件字节级长什么样」这层没覆盖；也没有测从 v1/v2 一次连升到 v7。
- **分词器版本升级时记录文字的重建没测**：要改 `TOKENIZER_VERSION` 字符串才能造出「旧版本索引行」，没做。状态侧对这种情况有计数（`stale_captures`）与提示，但没有测试钉住。
- **`include_trashed` 仍然无法端到端验证**：核心还没有「移到回收站」的对外接口，`state <> 'trashed'` 这条只有代码（与 B3b 的说明一致）。
- **同一句话可能出现两条命中**：记录文字与「它自己的派生片段」会各出一条。在今天的代码里，提交产生的 text 来源没有原件、`extract_source` 会报错，所以实际不会产出派生片段；但一旦将来允许对用户文字做提取（比如纠错、分段），重复就需要靠 `group_id` 折叠或去重策略处理。**界面怎么折叠留给 F4 决定**，我没有在这里发明策略。
- **`search_candidates` / `count_search_matches` 仍然只覆盖派生片段**：`candidates` 返回的是片段 ID，表达不了记录文字；`count_search_matches` 是测试与实测用来核对**片段召回**的。产品路径是 `search.start`，它把两路合在一起。两者都已在文档注释里写明范围，避免以后被当成「全部命中数」。
- **`index_bytes` 仍是整库值**：`dbstat` 只按表汇总页数，新加的两张表也进了这个数，但范围查询里它依然是整库值（B3a 审阅时定下的语义），`reasons` 里会说明。
- **没有性能数字**：记录文字让候选集从「片段数」变成「片段数 + 记录数」，`ranked_matches` 现在是两条 SQL 合并排序。没有重新测规模；B3a 的片段侧数字（首屏 0.029 ms）不受影响，但两路合并的整体代价未测。
- **Android / Windows 未验证**：只在 Linux（WSL2 x86_64）宿主跑过。
