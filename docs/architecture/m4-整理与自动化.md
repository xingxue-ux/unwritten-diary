## 定下的决定

| 决定 | 口径 | 为什么 |
|---|---|---|
| schema **v10 → v11**（合并 B4c 的 v12 后本构建是 **v13**） | `organize_settings`（**单行**，`enabled` 默认 0）+ `diary_model_calls`（每次**真的发出去**的调用一行） | 开关、模板、上限要跨重启活下来，而 v1–v10 没有一张键值配置表；配额与失败率必须认「真实花掉的调用」，凭估算或任务条数都不算账。迁移**不回填**，升级上来的库与新建库一样是**默认关** |
| 模板是**核心内置规则**（`source = "builtin"`），三类 | `merge_by_theme` / `proofread` / `compress`，参数只允许**整数与布尔**并带范围与默认值 | 规则属于**产品指令**：只在 system 消息里、由常量拼出。参数若能为自由文本，调用方（或将来的插件）就能把「忽略上面的指令」写进指令槽——那正是 #64 堵住的那条路 |
| #88 的对接点写在**数据形状**上，不写机制 | `OrganizeTemplate.source` / `plugin_id`；解析只有一个入口（`template_spec` → 将来查插件注册表） | 插件模板进来时，校验、冻结、提示词拼装三条路径一个字都不用改；这一片**不实现**插件机制，也不假装它能用。后续 #88 已提供独立的 `plugins.templates`，但**仍未并进**整理模板列表 |
| **默认关**，只有显式 `update_organize_settings(enabled = true)` 才开 | 关闭时排期函数立刻返回；驱动跑多少轮都不排任务、不发请求 | 「不偷偷消耗配额」是硬要求。测试用 `PanicTransport`（一调用就 panic）钉死这条 |
| 触发走**作业系统**，不另造调度 | 驱动（`run_due_jobs`）每轮开始调 `organize::plan_due`：判据 → 上限 → 冻结快照 → 排一条 `diary_generate`（`reason = scheduled`，`priority = AutoOrganize`） | 入队之后退避、补做、配置闸门、租约恢复、幂等全部是 #64/#67/#74 的既有机制。「到点把进程叫起来」仍是平台层（#19）的事 |
| 「现在整理这一天」= 设计好的 `diary.generate(reason = automatic)` | 用当前设置里的模板冻结快照并排任务，**不新增方法** | 契约 `diary.generate` 的 `reason` 本来就有 `scheduled / automatic`；共用场景 `edited-diary-then-new-material` 写的就是 `diary.generate(dayKey, reason=auto)` |
| 自动整理的结果**一律候选**，连「首次」也不例外 | `reason ∈ {scheduled, automatic}` 时不设当前版本；用户确认走 #87 `diary.setCurrent` / `diary.merge` | 自动整理是在用户不盯着的时候跑的，「绝不改用户当前正文」在自动路径上取**最保守**的解释。手动生成 / 重新生成沿用 #64 的规则不变 |
| 配额停下是**终态**，不落 `waiting_configuration` | 新增 `CoreError::OrganizeStopped`（错误码仍是契约的 `quota_exceeded`）→ 任务进 `failed` + `requires_user_action` | 队列对 `quota_exceeded` 的既有处置是 `waiting_configuration`，而配置闸门**每一轮**都会把「在等配置」的任务拉起来——对配额停下的整理任务，那等于每一轮偷偷再跑一次、每次都烧掉上限内的调用（跑通之前先被这个吃过一次，见「验证到了什么」） |
| 「一份输入只自动排一次」 | 判据是「`(dayKey, 快照哈希)` 有没有冻结过」，不是「有没有版本」 | 冻结过 = 产出过版本 / 排过任务（成功或失败）/ 还在队列里。重试靠任务自己的退避或人工 `jobs.retry`，不靠计划器一遍遍重排；材料或模板一变哈希就变，自动路径自然重新考虑 |
| 配额窗口用**滚动 24 小时**、按**真实时钟** | `diary_model_calls.called_at` 与 `support::now()` 比；排期/补做用驱动传进来的业务时钟 `now` | 配额说的是「现实里花掉了多少次」，与排期用的业务时钟是两回事；滚动窗口还避免了墙钟跳变（本机 WSL 每几秒跳一次）造成的日历日边界抖动 |
| 自动整理的**观察窗 = 最近 7 天** | 只看最近 7 天内有材料的日子；更早的日子不自动重排 | 第一次开启的那一晚不该把几个月前的日子全翻出来跑。更早的日子没丢：`diary.generate(reason = automatic)` 手动整理，状态里也写明这个窗口 |

## 三类整理模板（核心内置规则）

模板 id、参数、范围与默认值都是**代码常量**（`organize.rs`），设置与状态里原样回读；
`diary.generate` 的 `styleId` 与它们是两回事（风格是 `styles.*`；v17 已落地，自动整理用默认风格，见 [`m3-日记生成与版本.md`](m3-日记生成与版本.md)）。

| 模板 | 做什么 | 参数（范围 / 默认值） |
|---|---|---|
| `merge_by_theme`（按主题归并，**默认模板**） | 把一天零散材料按主题归并成有结构的日记；同一主题内可保留时间顺序 | `themeCount` 主题数（整数 **1–8**，默认 **3**）；`keepChronology` 主题内按时间（布尔，默认 **true**） |
| `proofread`（只改错别字与标点） | 最小修改：错别字 + 标点，保留口语、句子顺序与原来的说法；不合并、不概括 | `fixTypos` 改错别字（布尔，默认 **true**）；`fixPunctuation` 改标点（布尔，默认 **true**）；`keepColloquial` 保留口语（布尔，默认 **true**） |
| `compress`（压缩到指定长度） | 压到指定字数**以内**（上界，不是必须凑满），去重复与铺陈，不删掉发生过的事 | `targetChars` 目标字数（整数 **50–2000**，默认 **300**）；`keepNumbers` 保留具体信息（布尔，默认 **true**） |

参数的校验口径（`effective_params`）：**未知键、类型不对、越界一律 `invalid_argument`**，
消息里写清可用参数与合法范围，且**零改动**——`themeCount = 99` 被默默按 8 处理才是骗人。
生效参数 = 显式覆盖 + 模板默认值（键有序，进快照），设置里只存**显式覆盖**的那部分，
所以「用户改过什么」与「模板默认值后来变了」不会混在一起。

冻结与追溯：快照的 `body.organize` 记 `template_id` / `template_label` / **生效参数** /
**规则全文** / **规则哈希**（文本的指纹），`promptVersion` 用 `b4e-1`（手动的仍是 `b4b-1`）；
版本的 `generationInfo.generationOptions` 再记一份
`organizeTemplateId` / `organizeTemplateParams` / `organizeRuleHash` / `organizeReason`。

**规则全文为什么要进快照（#111）**：第一版只存哈希，执行时按 `template_id` 重新渲染当前的
模板常量。任务在应用升级期间排队时，这条路的输出用的是**新**规则、审计里却留着排队那一刻的
哈希——「这一版基于什么生成的」答不出来，重试也复现不了。现在快照存规则全文，执行时
**用冻结的那一份**：`rule_hash` 只是它的指纹（对不上 = 快照被改动，按 `invalid_state` 拒绝，
不拿被改过的指令去调模型）。代价如实说：快照 body 变大了几百字（规则文本），换来的是
「真正发出去的输入」与「审计记的哈希」永远一致。

冻结的是**模板规则文本**；产品基础指令（`SYSTEM_INSTRUCTIONS`）与两步走的中间指令仍是
构建常量，身份由 `promptVersion`（`b4e-1`）标识——这一片没有把它们也复制进快照。

**旧快照兼容**：`body.organize` 是 `#[serde(default)]` 的可选字段，B4b/B4c 时期冻结的快照
照样读得出来（读取路径不依赖这个字段）；B4e 早期冻结、**只有哈希没有规则全文**的快照走
兼容路径：按 `template_id` + 参数重渲染，但**必须与快照里的哈希一致**——跨升级（规则文本变了）
或模板已不存在时**明确失败**（`invalid_state`，任务 `failed` + `requires_user_action`，
不发请求、不落版本），绝不「用新规则、记旧哈希」。测试把两条路都钉住了
（`queued_organize_uses_the_frozen_rule_text_not_the_current_build`、
`legacy_snapshot_without_a_frozen_rule_needs_the_hash_to_match`）。

## 「什么算待处理」：可判定的判据

排期只做「盘点 → 判据 → 上限 → 入队」，判据全是**能在库里查出来的事实**，
没有一条是「AI 觉得该整理」，也**没有任何时间戳大小的比较**（材料一变哈希就变，
时间戳比较会引入墙钟依赖）：

1. **有可读正文**：这一天至少有一份材料有可读正文（提取中 / 提取失败的一份都没有 → 不算，
   也绝不拿空材料编日记）；
2. **这份输入从来没冻结过**：`diary_source_snapshots` 里没有 `(dayKey, 快照哈希)`。
   哈希覆盖**材料清单 + 模板 + 生效参数 + 提示词版本 + 协议参数**，所以它同时回答
   「已经产出过版本没有」「已经排过任务没有（成功或失败）」「还在队列里没有」；
3. **这一天需要一版**：还没有当前版本（`reason = first`），或者已经允许补做
   （`reason = supplement`，见 `supplement_on_new_materials`）；
4. **到了计划触发时刻**：`dayKey` 那天的本地 `autoOrganizeTime`（默认 22:30）按**当天材料自己的
   UTC 偏移**折成 UTC；没到就不进「现在该跑」，而是列进 `scheduledDays` 等时间到。

于是：

- 材料变了 / 模板或参数变了 → 哈希变 → 待处理自然重新成立（旧版本与旧快照都还在）；
- 材料没变 → 同一份输入**永远不会**被自动排第二次（版本、失败、在队列里三种情况都算「处理过」）；
- 迟到材料（当天已有当前版本，之后又来了新材料）→ 仍然待处理（`supplement`），
  设置里可以关掉它（`supplementOnNewMaterials = false` 时只整理还没有当前版本的日子）；
- 提取中 / 提取失败的日子不算待处理，也**不报成失败**；
- 一天的材料长到超过一次生成的分段上限（12 段）→ 如实列进 `skippedDays`
  （`invalid_argument` + 可执行文案），不排一条注定失败的任务。

## 开关与「什么时候会跑、跑哪些材料」

- **默认关**：`organize_settings.enabled` 默认 0，迁移种下的那一行也是 0；只有显式
  `update_organize_settings` 传 `true` 才打开。关闭时 `plan_due` 直接返回，
  驱动跑多少轮都不会排任务、发请求（测试用 `PanicTransport` 钉死）。
- **设置项**（`core.organize_settings()` / 桥接 `organizeSettings` / `updateOrganizeSettings`）：
  `enabled`、`templateId`、`templateParams`、`maxMaterials`、`maxChars`、
  `maxCallsPerRun`、`maxCallsPerDay`、`maxFailureRate`、`autoOrganizeTime`（`HH:mm`）、
  `supplementOnNewMaterials`、`revision` / `updatedAt`（只读）。
  范围与默认值：条数 1–200（50）、字数 200–200000（20000）、单次调用 1–16（8）、
  每日调用 1–1000（30）、失败率 0.0–1.0（0.5）、时间 `HH:mm`（22:30）。
  更新是「整份替换 + `expectedRevision`」：校验先行、过期 `revision_conflict`、
  **值没变就是无操作**（`revision` 不 +1）——与 `diary.setCurrent` 同一个口径。
- **可查询的状态**（`core.organize_status()` / 桥接 `organizeStatus`，**只读、不发请求**）：
  - `dueDays`：现在就该跑的日子，逐日给 `reason`（first / supplement）、材料条数与字数、
    预估调用次数、计划时刻、当前版本；
  - `scheduledDays` + `nextRunAt`：已经该整理但还没到计划时刻的日子，以及下一次触发时刻；
  - `quota`：最近 24 小时真实调用数、上限、还剩几次、失败率与样本数、最近一次调用时间；
  - `providerCode` / `providerReason` / `providerNextStep`：现在有没有可用服务、
    没有的话下一步做什么（来自 #66 的能力闸门，**不发起任何请求**）；
  - `blockedCode` / `blockedReason`：全局停下时（失败率过高 / 每日额度用完）是哪一条、为什么；
  - `skippedDays`：被单日上限或结构性问题跳过的日子与可执行文案；
  - `lastRun`：最近一次自动整理的真实结果（`state` / `errorCode` / `versionId` / **真实调用次数**）；
  - `notes`：观察窗、默认关、哪些不算待处理等如实说明。
- **什么时候会跑**：平台层按 `jobs.nextWakeup` 唤醒并调用 `jobs.runDue`；驱动每轮开始先排期。
  某一天到点且待处理 → 排任务 → 同一轮就能被领取执行。进程不在、系统省电延迟 → 下次运行时
  这一天的计划时刻已经过去，任务以**补做**身份入队（`nextAttemptAt = 计划时刻`，
  驱动晚跑时 `JobRunSummary.backfilled` 如实 +1）。**我们只说「补做」，不说「准时」。**

## 配额上限：超限要如实停下

上限有六条，超限的处理分三层，**每一层都不会静默分片、也不会拿半截结果当完整整理**：

| 上限 | 在哪里判 | 超限的结果 |
|---|---|---|
| 单次整理的材料**条数**（`maxMaterials`） | 排期（跳过那一天）+ 整理入口（`quota_exceeded`） | `skippedDays` / 直接报错，消息写清「N 条 > 上限 M 条」与下一步；**不发任何调用** |
| 单次整理的材料**字数**（`maxChars`） | 同上 | 同上（按可读正文的字符数） |
| 单次整理的**调用次数**（`maxCallsPerRun`） | 排期：预估次数 > 上限 → 跳过（不排注定跑不完的任务）；**执行期逐次**：每发一次之前再判一次 | 排期：`skippedDays`；执行期：`OrganizeStopped` → 任务 `failed` + `quota_exceeded` + `requires_user_action`，**不落版本** |
| 最近 24 小时的**调用次数**（`maxCallsPerDay`） | 排期（整轮停下，如实列出在等的日子）+ 整理入口（**只挡新请求**）+ 执行期逐次 | `blockedCode = quota_exceeded` + 「哪一条上限、已经做了什么、下一步怎么办」；没有版本 |
| **失败率**（`maxFailureRate`，样本 ≥ 3 才算） | 排期（整轮停下）+ 执行期逐次 | 同上，消息里给样本数、失败比例与上限 |
| 一次生成的分段上限（`MAX_INTERMEDIATE_CALLS = 12`，核心常量） | 排期盘材料时 | `skippedDays`（`invalid_argument`），不排任务 |

**入口的闸门只挡新请求（#111）**：`diary.generate` 的受理顺序是「算快照指纹 → 查
`operation_receipts` → 命中原票据就返回 → 没命中才做材料上限与配额预检」。契约 1.2 的
顺序本来就是「先查已完成操作」：配额用尽之后，拿着同一条 `operationId` 重试一条**已经受理过**
的请求必须取回原 ticket，而不是被配额错误挡在回执之外（那会让用户既拿不到票据、又看不出
原来那次已经受理了）。新的 `operationId` 照旧被挡住，一次调用都不发。测试：
`quota_exhaustion_does_not_hide_an_already_accepted_ticket`。

**调用账本**：每一次**真的发出去**的请求都记 `diary_model_calls`（成功与失败都记，带
`run_id` / `day_key` / `reason` / `provider_id` / `model` / `outcome` / `error_code` / `called_at`）。
配额与失败率只认这本账：估算、意图、任务条数都不算「花掉的调用」；被闸门挡下的调用**不记账**
（它没有发生）。账本里 `reason` 分开记，**用户主动要的那一版（manual / regenerate）不吃自动整理的额度**。

**超限时的可见状态**（都来自真实数据）：

- 排期层：`OrganizePlanSummary.blockedCode` / `blockedReason` / `blockedDays` / `skippedDays`，
  以及 `organizeStatus().blockedCode` / `blockedReason` / `skippedDays`；
- 执行层：任务 `state = failed`、`errorCode = quota_exceeded`、`requiresUserAction = true`
  （在任务面板里可见、可人工重试）；`organizeStatus().lastRun` 给出这一天的 `state` /
  `errorCode` / `versionId`（为空）/ **真实调用次数**；
- 文案一律含三段：**哪一条上限**（含具体数字）、**已经做了什么**（发出几次调用、产出过什么）、
  **下一步怎么办**（调高哪一项、等窗口滑过去、或人工重试）。

**为什么配额停下是终态而不是「等待配置」**：见上表的决定行。这是这一片真的踩到并修掉的坑——
第一版把 `quota_exceeded` 交给队列的 `waiting_configuration`，结果配置闸门每一轮都把它拉起来：
一轮驱动里同一个任务被领取 3 次、每次都发出 1 次调用直到把回放脚本用光（`job_attempts` 里
三条同一秒的记录），而 `attempt_count` 照旧不涨、永远不会停。现在它落 `failed` + 人工重试入口。

## 候选产出：绝不改用户当前正文

- 自动整理（`reason = scheduled / automatic`）产出的版本**一律是候选**：即使这一天
  「还没有当前版本、也没有用户版本」，也不会成为当前（比 #64 的首次边界更窄一刀）。
  用户确认哪一版走 #87 的 `diary.setCurrent`；要合并走 `diary.merge`。
- 当前版本永不因为一次整理改变：代码路径里「设当前」的调用被 `!reason.is_organize()`
  挡在自动路径之外，只更新这一天的时间语义（`touch_day`）。
- 整理结果**只新增版本**：`origin = generated`、`sourceSnapshotId` 指向冻结快照
  （模板 + 参数 + 规则哈希在里面），`parentVersionId = 那一刻的当前版本`，
  旧版本一行都不改、随时取回。
- 共用场景 `edited-diary-then-new-material`（验收 E26）有对应集成测试：人工编辑过的当前版本 +
  新材料到达 + 按当前设置整理 → 新版本进候选、`currentVersionId` 仍是用户那一版、
  用户正文与旧版本一字未动、材料计数如实更新。
- 自动整理**不写**用户来源：`captures.draft_text` / `source_revisions` 一个字节都不动
  （与 #64 同一口径）。

## 可恢复与幂等

- **入队幂等**：计划器的 `operationId` 由 `(dayKey, 快照哈希)` 决定（写进
  `diary_generations.operation_id` 供审计），但**真正的幂等保证是「这份输入冻结过没有」**：
  重放一轮排期，待处理的日子会先被这条判据过滤掉——比回执更强（同一份输入只可能有一条生成记录）。
- **入口幂等先于一切「新请求」的闸门**：`diary.generate` 先查 `operation_receipts`，再判材料上限
  与配额（#111）——重试已有请求不看配额；同一条 `operationId` 换了内容仍然 `idempotency_conflict`；
- **版本幂等**：同一份快照已有版本或还有活着的任务时复用那条任务（#64 的口径）；
  执行者重入（租约恢复）发现 `version_id` 非空就直接返回，不再花钱、不产第二版。
- **退出后补做且不重复**：任务留在 `running` 时进程被杀 → 下次驱动先回收
  （`recovered` 如实 +1）→ 接着跑完；跑完的那一版不会因为再跑一轮而重复
  （快照去重 + 计划器判据）。测试用「排期 → 领取 → 丢掉 Core → 重开 → 驱动」钉住：
  1 次真实调用、1 个版本，再跑一轮 0 调用、0 新版本。
- **「补做」不谎报「准时」**：排期把任务的 `nextAttemptAt` 设成这一天的计划时刻；
  驱动在计划时刻之后才跑 → `JobRunSummary.backfilled` +1。**已知边界**：被中断回收的任务
  在领取那一刻 `nextAttemptAt` 已被清空（#67 的既有口径），所以它**不计入** `backfilled`
  ——「有没有丢」由 `recovered` + `succeeded` 如实回答，不靠 `backfilled` 冒充。
- **错过不丢（E29）**：观察窗内的日子里，到点而当时没跑上的，下次驱动会以补做身份补上；
  失败率 / 每日额度挡下的整轮会在状态里列出「在等的日子」；执行期被配额停下的任务留在
  队列里（`failed` + 可人工重试），不会消失。

## schema v10 → v13（v11 是本片的；v12 是 B4c 的 `revision` 列）

**合并后的本构建是 `SCHEMA_VERSION = 13`**：11（本片的两张表）与 12（B4c 的
`diary_days.revision`，#101）是两条分支各自从 v10 抬的号，合并在 13 收口。迁移里
**两段都在，顺序固定 v11 → v12**，而且每段都带**结构性守卫**（不只看版本号）：

- `if current < 11 || !table_exists("organize_settings")` → 建两张表 + 种默认设置。
  这条兜底是为「只跑过 B4c 分支的库」准备的：它的 `user_version` 已经是 12、但没有这两张表，
  光看 `current < 11` 会整段跳过，升级后一碰整理设置就「no such table」。建表语句因此写成
  `CREATE TABLE IF NOT EXISTS`（种默认值本来就是 `INSERT OR IGNORE`），重复跑幂等——
  **已有设置一个字节都不会被改**；
- `if current < 12 || !column_exists("diary_days", "revision")` → 加列 + 回填成版本数。
  列已经在就整段跳过，**不重复回填**（否则会把已经推进过的 `revision` 改小）。

只加两张新表，**不回填旧数据**：

- `organize_settings`：单行（`CHECK (id = 1)`，与 `index_meta` / `search_index_epoch` 同写法）。
  迁移里由 `organize::seed_default_settings` 种一行默认值（**`enabled = 0`**），
  值的来源只有 `organize.rs` 的常量，不在 SQL 里抄第二份。从 v10 升上来的库与新建库完全一样：
  **自动整理是关的**，没有任何用量记录，也不会替用户猜一个模板或上限。
- `diary_model_calls`：调用账本（见上）。两张表都带必需的索引（按时间、按 run）。

旧库测试（三条升级路径都钉住）：

- `v10_library_migrates_to_latest_with_both_migrations`：把 v11 的两张表**与 v12 的 `revision`
  列**一起拆掉、`user_version` 退回 10、重开 → schema 到 13、两张 v11 表与 `revision` 列都在、
  设置默认关、账本为空、旧材料完好、升级后照样能整理出一版（产出的那一版把合并后的 revision
  推进到 1）；
- `a_b4c_only_library_gets_the_v11_tables_without_resetting_revision`：模拟**只跑过 B4c 分支**
  的库（`user_version = 12`、没有 v11 的两张表）→ 两张表被结构性兜底补上、设置默认关，
  而 `revision` **保持切换之后的 3**（不是被重新回填成版本数 2）；
- 另外四处**模拟更早版本**的既有迁移测试
  （`diary_generation_test` / `provider_test` / `search_capture_test` / `text_chunks_test`）
  同步拆掉了 v11 两张表与 v12 的列（它们整表 `DROP TABLE diary_days`，列随表一起没了）——
  它们模拟的是「老库」，新加的东西当然也要拆掉。

  不会自动重排——要用户调高上限后人工重试（`jobs.retry`），或者等材料/模板变化产生新输入。
  这是刻意的（见上表：重排会在配额没好之前每一轮偷偷烧一次调用），要不要做
  「本地配额停下且没有版本时允许计划器重排」留待拍板。
- **适配层（`BridgeDiaryApi`）没接整理入口**：核心与桥接层（`organizeTemplates` /
  `organizeSettings` / `updateOrganizeSettings` / `organizeStatus`）都通了，但 Dart 适配层
  的 `_wiredMethods` 这一片照旧没动——和 `jobs.status` / `indexes.rebuild` 一样，
  能力清单里看不到它们（清单只列契约方法名）。这是它诚实的地方，等界面真正要用时再接。
- **契约的 `settings.get / update` 只落了「整理」这一段**：完整设置对象还包括
  `diaryTimeZone` 等平台层字段，这一片没实现，所以**没有**把 `settings.get` 写进能力清单。
  将来完整设置对象落地时，整理这一段应当并进同一个 DTO（见「需要拍板」）。
- **「每天最多一次自动补充版本」没有单独开关**：迟到的材料只要有新输入就会排一次，
  由「一份输入只排一次」+ 单次/每日调用上限约束。任务书 7.3 建议的「每天最多一次 / 仅手动」
  这一档，现在只有「补做开/关」（`supplementOnNewMaterials`），没有按天的次数闸门。
- **观察窗是固定 7 天**：不是设置项，也没有「按日期范围批量整理」的入口
  （更早的日子要逐天手动 `reason = automatic`）。
- **规则全文进快照会让「同一份输入」的哈希变化（#111 的已知影响）**：升级到带 #111 的构建后，
  旧库里以前冻结过的同一天会按新哈希重算一次「待处理」——若那一天还没有当前版本，计划器会
  再整理一次（多一次模型调用、多一个候选版本）。B4e 尚未发布，所以只影响开发库；不在迁移里
  回填旧快照的规则文本，是因为回填要拿当前构建的规则去补，而**那正是这一片要避免的事**
  （旧快照宁可走「重渲染 + 校验哈希」的兼容路径，对不上就明确失败）。
- **DB 级唯一约束没做**：`organize_settings` 的单行由 `CHECK (id = 1)` 保证，
  但「同一份输入只排一次」仍靠单写者 + 事务内先查后插（与 #67 的业务键同一处境）。
- **配额窗口是滚动 24 小时**，不是自然日：跨零点时不会「重置」（第 25 小时才滑出去）。
  好处是不受墙钟跳变与设备时区影响；如果产品坚持「自然日」（例如「今天还剩几次」），
  要改口径并在状态里写明用哪个时区的自然日。
