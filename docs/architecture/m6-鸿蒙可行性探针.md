## 0 摘要：五个问题的结论

| # | 问题 | 结论 | 依据强度 |
|---|------|------|----------|
| Q1 | 真机是什么、APK 能不能装 | **HarmonyOS 6.1 PC（HUAWEI MateBook Pro / HAD-W32，2in1，API 23，aarch64）**；**APK 完全不能装**（无 Android 属性、无 `pm`/`cmd`、无 Android 运行库；包管理器 `bm` 只接受 hap/hsp/app）→ **鸿蒙化 = 原生重写，不是打包适配** | 实测（强） |
| Q2 | Rust 核心能不能编到鸿蒙 | **能，而且比预期简单**：stable Rust（1.94.1 / 1.98.1 均可）**自带 `aarch64-unknown-linux-ohos` 预编译 std，不需要 nightly、不需要 `-Z build-std`**；用 OHOS NDK 的 clang 作 linker 后，最小 crate **和 `diary_core` 全量依赖（含 `rusqlite` bundled 的 C SQLite、`tokenizers`、`pdf-extract`）都编过** | 实测（强） |
| Q3 | ONNX Runtime 能不能用 | **官方不支持 OHOS，但「自己编」这条路已被别人走通**：有 ORT 1.28.0 / 1.29.1 → `libonnxruntime.so`（aarch64-linux-ohos）的成品配方（8 个补丁 + 宿主 protoc）；**但该配方作者也没做设备侧运行验证**。设备自带 MindSpore Lite / NNRt / HiAI Foundation（syscap 为 true），可作换运行时路线，但 `ort` crate 驱动不了它 | 实测（设备 syscap）+ 引用（配方） |
| Q4 | 界面走 A（Flutter 鸿蒙分支）还是 B（ArkTS 重写） | **推荐 B**。A 的硬伤是**版本代差**：本仓库 CI 钉 `Flutter 3.44.6` + Dart `>=3.9.0` + FRB `2.13.0`，而鸿蒙 Flutter 分支最新只到 **3.27.4**（Dart 3.6）；FRB 的鸿蒙 fork 与 2.13.0 是否兼容未验证。好消息是本 App **插件依赖极轻**（只有 `path`、`path_provider`、`flutter_timezone`），UI 体量也小（7 个 dart 文件 / ~3.3k 行） | 实测（本仓库事实）+ 引用 |
| Q5 | 真机冒烟 | **编译、签名、推送全部成功；执行被系统策略挡住**：未签名 ELF 报 `Permission denied`，自签名（`.codesign` 段已生成）报 `Operation not permitted`，换目录、换文件都一样。**设备侧性能数字因此没拿到**。设备自带 `sqlite3` 3.44.4，但在 shell 上下文里连建库都被拒（`unable to open database file`） | 实测（强，含原始报错） |

**一句话**：**Rust 核心这半条路已经基本证明可行（最大风险已排除）；挡在前面的是「鸿蒙原生应用怎么跑起来」这一整块——HAP 打包 + ArkTS 界面 + 设备侧 AI 运行时验证。**

## 2 Q1 设备事实

### 结论

1. 设备是 **HarmonyOS 6.1 的 PC（2in1）**，不是手机：`HUAWEI MateBook Pro` / 型号 `HAD-W32` / `const.product.devicetype = 2in1`。
2. ABI 是 **arm64-v8a（= aarch64）**，与我们的交叉编译目标一致。
3. **APK 不能装，且是「体系上不能」，不是「没开权限」**：设备里没有任何 Android 兼容层。
4. 因为设备是 **2in1（PC）**，鸿蒙版的交互形态应当按**桌面窗口**设计（多窗口、键鼠、文件选择器），
   而不是手机 App 形态——这一条会影响 Q4 的界面工作量估算。

### 对本项目的直接含义

- 「鸿蒙版」不是给现有 Android 包换个壳，**核心之外的 UI 与平台能力（文件、录音、权限、窗口）都要用 ArkTS/鸿蒙 API 重写**。
- 但核心是 UI 无关的 Rust —— 因此**同一套 `diary_core` 可以被 Windows/Android/HarmonyOS 三端共用**，这是本次探针最有价值的结构性结论。

### 未验证 / 待确认

- **API 23 vs SDK API 26**：设备是 API 23，而本机 DevEco 自带 SDK 是 **API 26**。用 API 26 SDK 编译出的 HAP
  能不能装到 API 23 设备上（`compatibleSdkVersion` 需设为 ≤23），**本次没验证**（要真打一个 HAP 才能证实）。

- 设备是否处于开发者模式：`const.security.developermode.state` 等参数**在这台设备上不存在**（`errNum 1002`），
  所以无法用参数确认；但 `hdc` 能连、能 `bm get -u`，说明调试通道是开的。

## 3 Q2 Rust 核心能不能编到鸿蒙（最关键，结论：**能**）

### 结论

1. **不需要 nightly、不需要 `-Z build-std`**：`aarch64-unknown-linux-ohos` 现在有**官方预编译 std**，
   `rustup target add` 直接装（1.98.1 与仓库 `rust-version = "1.94"` 对应的 1.94.1 都实测装上）。
   （任务书里「tier-3、可能要 nightly + build-std」的预期**已被推翻**——它是 tier-2 了。）
2. **只需要一个东西：能链接 aarch64-linux-ohos 的 linker**（OHOS NDK 的 clang），外加给 C 代码用的 CC/AR。
   不配 linker 时 rustc 会用宿主 `cc`，报 `Relocations in generic ELF (EM: 183)`。
3. **`diary_core` 全量依赖交叉编译通过**，包括任务书点名的风险点 `rusqlite` bundled（真编了 SQLite 的 C 代码），
   以及 `tokenizers`、`ort`（load-dynamic，构建期不下载二进制）、`pdf-extract`、`jieba-rs`。
4. 最终可执行体只依赖 `libc.so`（SQLite 静态链进去了），解释器 `/lib/ld-musl-aarch64.so.1` —— 与设备一致。

## 4 Q3 ONNX Runtime 在鸿蒙上能不能用（决定语义检索的命门）

### 结论

**分三层，必须分开说：**

1. **官方：不支持。** ONNX Runtime 官方平台列表里没有 OpenHarmony/HarmonyOS，也没有官方 `libonnxruntime.so` for OHOS。
2. **自己编：可行，且已有成品配方**（ORT 1.28.0 / **1.29.1** → aarch64-linux-ohos 的 `libonnxruntime.so` + 头文件，
   8 个补丁）。这意味着 **Rust 侧 `ort` crate 一行都不用改**：它本来就是 `load-dynamic`，
   运行时 `dlopen` 一个 `libonnxruntime.so`，我们把这个 .so 打进 HAP 即可。
3. **但不能说「已验证可用」**：该配方作者**明确没做设备侧运行**（原文：「测试二进制为 aarch64，只能在 OHOS 设备上运行；
   本次未安排构建→传输→设备侧运行流程」）—— 这和我 Q5 撞到的墙是同一堵墙。
4. **换运行时**：设备**自带** MindSpore Lite（`SystemCapability.AI.MindSporeLite = true`）与 NNRt、HiAI Foundation，
   官方转换工具支持 `--fmk=ONNX` → `.ms`。但 `ort` crate **驱动不了 MindSpore Lite**（不同 C API），
   换运行时 = 重写推理接入层（Rust FFI 或把推理解到 ArkTS 侧），且 bge-small-zh-v1.5 的 BERT 转换未验证。

### 证据 C：换运行时路线（引用）

- 设备自带 MindSpore Lite（syscap 已实测 true）；鸿蒙侧调用面是 ArkTS `@ohos.ai.mindSporeLite`
  （[官方 API 文档](https://developer.huawei.com/consumer/cn/doc/harmonyos-references-v5/js-apis-mindsporelite-V5)）。
- MindSpore Lite 的离线转换工具**官方支持 ONNX 输入**：
  `converter_lite --fmk=ONNX --modelFile=model.onnx --outputFile=model` → `model.ms`
  （[端侧模型转换文档](https://www.mindspore.cn/lite/docs/zh-CN/master/converter/converter_tool.html)）。
- 社区已有的鸿蒙 ORT 相关项目：`ohos_onnxruntime`（NAPI 封装，[gitcode](https://gitcode.com/zhong-luping/ohos_onnxruntime)）、
  sherpa-onnx 的鸿蒙 HAR 包（[参考](https://blog.gitcode.com/ca2fac1a25fc88c6d7abad63335263b4.html)）——
  说明「ORT 类推理在鸿蒙上跑」在社区里有实践，但都不是官方支持，需要自行评估维护成本。

### 对本项目的建议（Q3 的落地选择）

| 方案 | 可行性 | 代价 | 建议 |
|------|--------|------|------|
| **① 自编 ORT + `ort` crate 原样复用** | 编译已被证明；**设备侧加载未验证** | 引第三方配方（8 补丁）、CI 首次构建机时较长、HAP 体积增加（ORT 全量 .so 通常十几 MB 级，**本次未实测体积**） | **首选**：Rust 侧零改动，语义检索能力完整保留 |
| ② 换 MindSpore Lite（`.ms`） | syscap 在；ONNX→ms 官方支持 | 重写推理接入（Rust FFI 或 ArkTS 侧推理）、bge 模型转换与算子覆盖未验证、向量维度/后处理要重接 | 备选，若 ① 设备侧加载失败再上 |
| ③ 降级：只做关键词检索 | 一定能做 | 丢语义召回 | 作为**保底开关**，不作为默认 |

**降级（只有关键词检索）的产品影响**：`diary_core` 的关键词路（FTS + jieba 分词 + 覆盖状态 + 检索会话）
完全不依赖 ORT，因此「记录、导入、原件库、时间线、任务调度、修订」这些功能一个都不少；
丢的是**「我记得说过类似的话，但想不起原词」这种口语化/同义查询的召回**——
对一个「检索自己记录」为主打的产品，这是**体验层的明显降级（中-高影响），但不影响功能可用性**。
因此鸿蒙首版完全可以「先关键词上线、语义作为阶段能力」，且必须**如实标注**（不要写成有语义检索）。

## 5 Q4 界面路线：A（Flutter 鸿蒙分支）还是 B（ArkTS 重写）

### 结论：**推荐 B（ArkTS 重写界面 + 核心走 C ABI / NAPI）**

理由按重要性排序：

1. **A 有硬性版本代差**：本仓库 CI 钉 `FLUTTER_VERSION: "3.44.6"`，`pubspec` 要求 Dart `>=3.9.0`，
   桥接钉死 `flutter_rust_bridge = 2.13.0`；而鸿蒙 Flutter 分支**最新只到 3.27.4**（Dart 3.6）。
   走 A 意味着把整个 App 降到一年半前的 Flutter，还要赌 FRB fork 与 2.13.0 兼容。
2. **B 的成本比想象小**：核心 UI 无关（已确认）；Flutter 侧体量小（**7 个 dart 文件、约 3,280 行**）；
   插件依赖极轻（`path`、`path_provider`、`flutter_timezone`，**没有**录音/相机/地图这类重插件）；
   `diary_bridge` 的公开 API 面只有 **29 个 `pub fn`**（+ 7,091 行 FRB 生成代码，这部分在 B 路线里直接不要了）。
3. **设备是 2in1 PC**：ArkUI 原生就是鸿蒙 PC 的一等公民（多窗口、键鼠、窗口尺寸），
   而 Flutter 鸿蒙分支在 PC 形态上的支持成熟度需要额外验证（未验证）。

## 6 Q5 真机冒烟：能做到哪一步

### 结论（**卡点明确，且是可复现的系统策略，不是我们的构建问题**）

| 步骤 | 结果 |
|------|------|
| ① 交叉编译出可执行体 | ✅ 成功（见 Q2） |
| ② 签名（`.codesign`） | ✅ 成功（`binary-sign-tool … -selfSign 1`，`.codesign` 段已生成） |
| ③ `hdc file send` 推到设备 | ✅ 成功（`/data/local/tmp/ohosprobe/…`，chmod 755） |
| ④ 执行 | ❌ **被挡住**：未签名 → `Permission denied`；自签名 → **`Operation not permitted`**（换目录、换文件名、换二进制都一样） |
| ⑤ 设备侧 SQLite 建库/读写（用我们自己的二进制） | ❌ 无法进行（被 ④ 挡） |
| ⑥ 设备自带 `sqlite3` 做旁证 | ⚠️ 能查到版本 3.44.4，但**在 shell 上下文里连建库都被拒**（`unable to open database file`） |
| ⑦ `libonnxruntime.so` 加载验证 | ❌ 没到这一步（①-④ 就断了；且 ORT 的 .so 这次没编） |
| ⑧ 设备侧性能数字（启动/建库耗时） | ❌ **没拿到**（不伪造） |

### 证据（原始输出）

## 7 建议的鸿蒙化路线 + 前三步

### 路线（推荐）

> **核心复用 + 界面原生**：`diary_core` 作为跨端共享核心（原样交叉编译到 `aarch64-unknown-linux-ohos`），
> 通过 **C ABI/NAPI** 暴露给 **ArkTS 原生界面**；语义检索**优先自编 ORT**，MindSpore Lite 作备选，
> 关键词检索作为保底且如实标注能力边界。目标设备按 **2in1 PC 桌面应用**设计。

技术栈定案（建议）：

| 层 | 选型 |
|----|------|
| 核心 | 现成 `diary_core`，`cargo build --target aarch64-unknown-linux-ohos`，stable Rust（1.94.1 或 1.98.1 均可） |
| 桥接 | 新增 `extern "C"` 稳定 ABI（≈29 个入口）+ NAPI 模块；**不用 FRB** |
| 界面 | ArkTS / ArkUI（2in1：多窗口 + 键鼠 + 文件选择器） |
| 存储 | 复用核心内 bundled SQLite（已实测能编过） |
| 语义检索 | 自编 `libonnxruntime.so`（ORT 1.29.1 配方）+ `ort` crate `load-dynamic`；失败则 MindSpore Lite / 降级关键词 |
| 构建 | WSL/Linux 侧 command-line-tools（本机已有）编 Rust + hvigor 编 HAP；签名用已有调试证书 |

### 前三步（按「先撞最可能推翻计划的墙」排序）

**第一步：打一个最小 HAP 并装到真机（1–2 天）——最高优先级**
先只用 DevEco 建一个空白 ArkTS 工程（`com.example.myapplication` 或产品 bundleName），
用已有调试证书签名，`hdc install` 到这台 HAD-W32。**这一步要一次回答两个问题**：
① API 26 SDK 编出的包能不能装到 API 23 的设备上（不能就要装 API 23 的 SDK 组件或调 `compatibleSdkVersion`）；
② 签名/安装链路是否真的通（用户的调试 Profile 里已有本机 UDID）。
**这是当前唯一可能推翻「鸿蒙版能做」的未知项**，必须最先做。

**第二步：把 `diary_core` 编成 `.so` 塞进 HAP，在应用沙箱里跑通 SQLite（3–5 天）**
`cdylib` 产物 → `libs/arm64-v8a/libdiary_core.so` → NAPI 暴露 2–3 个函数（open / write / query）→
ArkTS 调一次，拿到**设备侧建库耗时、写入耗时**（Q5 缺的数字）。同时验证沙箱内文件路径策略（`filesDir`）。

**第三步：语义检索的设备侧验证（3–7 天）**
按已有配方交叉编译 ORT 1.29.1 → `libonnxruntime.so` → 打进 HAP → 在沙箱内 `dlopen` 成功
→ 用 bge-small-zh-v1.5 跑一次真实嵌入，记录**单条嵌入耗时 / 内存峰值 / HAP 体积增量**。
失败就切 MindSpore Lite 或先上关键词检索（并如实标注）。

> 三步都过了，「鸿蒙版」就从「可行性」进入「工程量」；三步中任何一步卡住，都能在两周内知道。

### 13.2 坑 1：数字 `23` 不合法、`"26.0.0"` 装不上

| `compatibleSdkVersion` | 生成 `module.json` 的 `minAPIVersion` | 装到 API 23 设备 |
|---|---|---|
| `"6.1.0(23)"` | `60100023` | ✅ `install bundle successfully.` |
| `"26.0.0"` | `260000026` | ❌ `code:9568297 error: install failed due to older sdk version in the device.` |
| `"6.1.0(23)"` + target `"26.0.0"` | min `60100023` / target `260000026` | ✅ 也能装（min 才是闸门） |

### 13.3 坑 2：签名密码必须是 DevEco 加密串，明文直接报错

```console
$ # build-profile.json5 里 storePassword 填明文（<12 字符明文口令>）
> hvigor ERROR: 00303116 Configuration Error
Error Message: The length of the storePassword or keyPassword field in the signature
configuration is less than 32. At file: …/build-profile.json5
```

hvigor 6.26.4 对这两个字段**无条件**调用 `DecipherUtil.decryptPwd()`（`src/utils/decipher-util.js`）。
解密用的密钥材料取的是 **p12 所在目录下的 `material/`**（`path.resolve(storeFile, "..")`），
所以只要 p12 还在 `~/.ohos/config/`，在 **Linux 侧**用 `/mnt/c/Users/<user>/.ohos/config/xxx.p12`
绝对路径就能解密成功——**不需要 Windows、不需要 DevEco GUI**。

**加密串从哪来**：DevEco 自动签名后会写进项目的 `build-profile.json5`。本机从
`E:\huawei\a\build-profile.json5`（用户 9 月建过的工程）抄到了同一套 p12 的两个加密串。

**CI 可以完全自备**（本次已实测，见 §15）：`probes/ohos-hap-smoke/scripts/ohos-sign-pwd.js`
能反向解析/生成这套密文——所以团队自己生成的 p12（密码自己知道）也能变成 hvigor 要的格式。
密文格式（逆向 + 实测确认）：

```
[4B 大端头 h][IV][密文][GCM tag 16B]  → hex
hvigor 的切法：ivLen = 总长L - 4 - h；密文 = buf[4+ivLen : L-16]；tag = 末 16B
密钥派生：rootKey = PBKDF2(xor(fd0,fd1,fd2,内置component).toString(), material/ac, 10000, 16,'sha256')
          workKey = GCM_decrypt(rootKey, material/ce)
          （注意目录名与用途是反的：ac/ 当 salt，ce/ 是 workKey）
```

### 13.4 坑 3：hvigor 拒绝给「bundleName 与 Profile 不一致」的包签名（= 唯一真实卡点）

## 18 摘要：这一步的六个答案

| # | 问题 | 结论 | 强度 |
|---|------|------|------|
| **Q1** | 把 `diary_core` 编成 `.so` 塞进 HAP，在应用沙箱里能不能跑通 SQLite | **能，而且是全链路**：建库 → 跑迁移（schema v8）→ 写入 → 读回 → 切块 → 建关键词索引，`filesDir` 与 `databaseDir` 两处都成功，`errors: []`。SQLite 3.53.2（bundled C 代码静态链进 `.so`） | 实测（强） |
| **Q2** | 沙箱里能不能 `dlopen` 我们自己打包的原生库 | **能**。裸名字（`libdiary_core_smoke.so`）与绝对路径都能加载；`dladdr` 给出的真实加载路径是 `/data/storage/el1/bundle/libs/arm64/libdiary_core_smoke.so` | 实测（强） |
| **Q3** | 能不能 `dlopen` **应用可写沙箱（el2）里**的原生库 | **不能**。文件完整复制（字节数一致、ELF magic 正确、mode 755、`access(R_OK\|X_OK)` 都为真）后 `dlopen` 仍报 `Error loading shared library …: No such file or directory`。**与权限位、体积、内容无关，是加载器层面的路径策略** | 实测（强，含对照） |
| **Q4** | **ONNX Runtime 在沙箱里能不能用**（语义检索的命门） | **能，而且已经端到端跑通**：① 我们**自己编的 ORT 1.29.1**（OHOS/arm64，全算子集）在沙箱里 `dlopen` ✅、`GetApi(17)` ✅、建 `OrtSession` ✅、真跑推理输出与宿主一致 ✅；② **产品真实路径**（`ort` crate 的 load-dynamic：`ort::init_from` → `commit` → `Session::builder().commit_from_file` → `ort::inputs!` → `run` → `try_extract_tensor`）**全部成功，输出正确**（`crate_C_matches_expected: true`）。**语义检索不需要换 MindSpore Lite** | 实测（强） |
| **Q5** | 顺手验的「版本坑」有没有 | **有，而且已经量化并解决**：生态里能拿到的 OHOS 预编译 ORT **只有 1.16.3**，而 `ort` 2.0.0-rc 全系要求 **API ≥ 17**（= ORT ≥ 1.17）⇒ 必须自编 ORT（本次已编成并上机验证）。另外 `libc++_shared.so` **必须随 HAP 带** | 实测（强） |
| **Q6** | 我们的 `.so` 从哪加载、库文件落在哪、多大 | HAP 里放 `libs/arm64-v8a/`，设备上落到 **`/data/storage/el1/bundle/libs/arm64/`**（注意：目录名是 `arm64` 不是 `arm64-v8a`）；SQLite 库必须落在 el2（`filesDir` / `databaseDir`），库文件 272 KB | 实测（强） |

**一句话**：**「核心能不能在鸿蒙沙箱里跑」和「鸿蒙有没有语义检索」这两个问题，现在都有实测答案，而且都是「能」。**
同一份 `diary_core` + bundled SQLite 在真机上建库、迁移、读写、索引全部跑通（毫秒级）；
自编 ORT 1.29.1 在沙箱里被产品的 `ort` crate 正常加载并推理出正确结果。
剩下的**不是可行性风险，而是工程安排**：① 一份覆盖产品 bundleName 的调试/发布 Profile；② 把 ORT 的交叉编译做成 CI 里「首次构建 + 缓存产物」的一个 job。

> ① **HAP 里叫 `libs/arm64-v8a/`，设备上落到 `libs/arm64/`** —— `ApplicationInfo.nativeLibraryPath`
>    给的是 `/data/storage/el1/bundle/libs/arm64`，`dladdr` 打出来的实际加载路径也是它。写死
>    `libs/arm64-v8a` 去拼绝对路径会踩空，**要用系统给的 `nativeLibraryPath`（或干脆用裸库名让加载器自己找）**。
> ② **库文件大小要分「运行中」和「关闭后」两说**：WAL 模式下刚建完库主文件只有 4 KB，真正的数据在
>    `-wal` 里；不 checkpoint 就统计体积会得到严重偏小的数字。

## 22 `dlopen` 结论（本节最关键的一组证据）

### 22.1 我们自己打包的原生库：**能**（裸名 + 绝对路径都行）

设备侧原始输出（`filesDir` 那一轮的开头）：

```json
{"dlopen_ok":true,
 "dlopen_used":"libdiary_core_smoke.so",
 "dlopen_attempts":[{"name":"libdiary_core_smoke.so","ok":true,"err":""},
                    {"name":"/data/storage/el1/bundle/libs/arm64/libdiary_core_smoke.so","ok":true,"err":""}],
 "dlsym_ok":true,
 "abi":"diary_core_smoke/1 ohos-cdylib",
 "core_loaded_at":"/data/storage/el1/bundle/libs/arm64/libdiary_core_smoke.so"}
```

三条结论：
1. **裸名可用**：`dlopen("libdiary_core_smoke.so")` 直接成功 —— 应用进程的默认命名空间里**包含 HAP 的原生库目录**，
   不需要自己拼路径（这一点对将来的插件化最省事）。
2. **`dladdr` 给出真实加载路径**：`/data/storage/el1/bundle/libs/arm64/libdiary_core_smoke.so`。
3. **`dlsym` 拿到的符号可用**：`diary_smoke_abi()` 返回了版本戳，说明 C ABI 层是活的（不是「加载了但符号对不上」）。

### 22.2 可写沙箱（el2）里的原生库：**不能** —— 而且不是权限问题

这是本轮**新增的一条硬约束**，也是最容易被想当然的一条。对照实验（同一次设备运行）：

| 被复制并尝试 dlopen 的库 | 源字节 | 复制后字节 | stat 存在 | mode | `access(R_OK)` | `access(X_OK)` | 读回 ELF magic | **dlopen** |
|---|---|---|---|---|---|---|---|---|
| `libdiary_napi.so`（35 KB） | 35,448 | 35,448 | ✅ | 755 | ✅ | ✅ | ✅ | ❌ `No such file or directory` |
| `libonnxruntime.so`（19.6 MB） | 19,623,560 | 19,623,560 | ✅ | 755 | ✅ | ✅ | ✅ | ❌ `No such file or directory` |

（上一轮用 12.9 MB 的 ORT 1.16.3 做过同样实验，结论一致；两个体积差 365 倍的库表现完全一样。）

原始输出：

```json
{"dst_dir":"/data/storage/el2/base/haps/entry/files","results":[
 {"name":"libdiary_napi.so","src_bytes":35448,"copy_ok":true,"copy_bytes":35448,"dst_exists":true,
  "dst_bytes":35448,"dst_mode_oct":"755","readable":true,"executable":true,"readback_elf_magic":true,
  "dlopen_ok":false,
  "dlopen_err":"Error loading shared library /data/storage/el2/base/haps/entry/files/libcopy_napi.so: No such file or directory"},
 {"name":"libonnxruntime.so","src_bytes":19623560,"copy_ok":true,"copy_bytes":19623560,"dst_exists":true,
  "dst_bytes":19623560,"dst_mode_oct":"755","readable":true,"executable":true,"readback_elf_magic":true,
  "dlopen_ok":false,
  "dlopen_err":"Error loading shared library /data/storage/el2/base/haps/entry/files/libcopy_ort.so: No such file or directory"}]}
```

**怎么读这条**：文件确确实实存在、字节数一致、是可执行的 ELF、进程也有读/执行权限，加载器依然报 ENOENT。
两个体积差 365 倍的库表现完全一样 ⇒ 这**不是**「文件没写完」「少了 +x」「体积/内容问题」，而是
**OHOS 的加载器只从代码区（el1，即 HAP 内）加载 ELF**；`/data/storage/el2/...` 下的文件不在允许 dlopen 的路径集合里
（`errno` 被报成 ENOENT，与第 1 步 §6「shell 直接执行 ELF 被拒」是同一个策略家族）。

> **产品含义（重要）**：**不能靠「运行时下载一个 `.so` 再 dlopen」来分发原生代码**。
> ORT、任何原生插件、任何自带原生算子的模型运行时，**都必须打进 HAP**（或走系统认可的其它分发机制，本次未探索）。
> 模型文件（`.onnx`）本身是数据不是代码，放 el2 没问题（本次就是从 rawfile 落到 `filesDir` 再给 ORT 读的）。

**未验证**：系统是否有官方机制（HSP/HNP、`dlopen` 白名单、`nativeLibraryPath` 之外的可信目录）允许加载 el2 的原生库 ——
本次只证明了「直接放 el2 不行」。

### 23.3 为什么必须自编：`ort` crate 的版本门槛（**已查清的硬数据**）

`ort` 2.0.0-rc.13 的 `ort-sys` 里 `ORT_API_VERSION = 17`，即**要求 ORT ≥ 1.17**；
用 sherpa 那份 1.16.3 走产品路径，拿到的是**干净的 `Err`（不是崩溃）**：

```json
{"ort_so":"/data/storage/el1/bundle/libs/arm64/libonnxruntime.so",
 "crate_required_ort_api_version":17,"init_from_ok":false,
 "init_from_err":"ort 2.0.0-rc.13 is not compatible with the ONNX Runtime binary found at
   `/data/storage/el1/bundle/libs/arm64/libonnxruntime.so`; expected version >= '1.17.x', but got '1.16.3'"}
```

**这条错误的每一层都值得记住**：
1. 它**不是** `dlopen` 失败（`dlopen` 那一步已证明成功），也**不是**缺依赖 —— 报错文本是版本断言；
2. `GetApi(17)` 在 1.16.3 上返回 `NULL` —— **差一个 minor 就是全部差距**；
3. crate 在 `init_from` 里先读 `GetVersionString()` 做预检查，所以我们拿到的是一句人能读的话，而不是崩溃。

→ 换 1.17+ 的 ORT 之后，同一段代码 `init_from_ok / commit_ok / crate_session_ok` **全部为 true**（§23.1 ②）。

### 23.5 退路评估（供拍板）：自编 ORT ≥1.17 **vs** 把 `ort` crate 降到 1.16 档

> 这一节是**评估**，不是实测结论 —— 除了明确标注「实测」的数字，其余是查证 + 推断。

**先说一个决定性的查证结果：降级这条路比看上去窄。**

把 crates.io 上 `ort-sys` 整个 2.0.0-rc 系列的 `ORT_API_VERSION` 逐个拉下来看（`src/version.rs` 或等价位置）：

| `ort-sys` | 2.0.0-rc.1 | rc.2 | rc.3 | rc.4 | rc.5–7 | rc.8 | rc.9 | rc.10 | rc.11 | rc.12 / rc.13 |
|---|---|---|---|---|---|---|---|---|---|---|
| 要求的 ORT C API | 17 | 17 | 18 | 18 | 19 | 19 | 20 | 22 | 23 | **17**（注释 `minimum version`） |

**整个 2.0.0-rc 系列从来没有低到 API 16**（最低就是 17 = ORT 1.17）。
也就是说 **RNA「把 `ort` 固定到 2.0.0-rc 的更早版本」并不能吃到 ORT 1.16.3** ——
要降到 16，只能退到 **1.x 那条线**（`ort 1.16.3`，作者已停止维护的老 API），
那是**跨大版本的 API 迁移，不是版本号微调**。

**1.x 那条线的实际代价**（已核对 `ort 1.16.3` 的源码/Cargo.toml）：

| 项 | 2.0.0-rc.13（现用） | 1.16.3（退路） |
|---|---|---|
| 运行时库路径 | **`ort::init_from(path)`**（函数调用，路径是参数） | **`ORT_DYLIB_PATH` 环境变量**（`G_ORT_DYLIB_PATH`，在首次使用时读一次）；**没有 `init_from`** |
| Session 类型 | `ort::session::Session` | `ort::Session` |
| 张量类型 | `ort::value::Tensor::from_array((shape, data))` | 1.x 的 `Value`（`Tensor` 不是公开类型） |
| `ort::inputs![…]` | ✅ | ✅（同名宏仍在） |
| `try_extract_tensor::<f32>()` | ✅ | ✅ |
| FFI 来源 | 依赖 `ort-sys`（独立版本、按 API 号生成） | **自带 FFI，无 `ort-sys` 依赖**（所以「换个 ort-sys 版本」这种轻量做法不成立） |
| 维护状态 | 活跃（2.0 线） | 冻结（作者已转向 2.0），**不会再有安全/功能更新** |

**产品侧要改多少（实测清点）**：`diary_core` 用到 ORT 的代码**全部集中在一个文件**
`crates/diary_core/src/embedding.rs`，一共约 **8–10 处**：
2 个 `use`（40–41 行）、1 个结构体字段 `session: Mutex<Session>`（240）、`ort::init_from`（278）、
`Session::builder()…commit_from_file(…)`（295）、`ort::inputs![Tensor::from_array…]`（334–337、400–403）、
`try_extract_tensor::<f32>()`（343、407）、`ort::Error`（357）。
`semantic.rs` 与其它文件**不直接碰 ORT**。
所以迁移本身不大，但**「ORT 路径怎么进来」这件事变了**：现在是从配置里传路径给 `init_from()`，
1.x 得改成在首次使用前设 `ORT_DYLIB_PATH` 环境变量（意味着 nativeLibraryPath 要提前注入到核心，属 API 边界变化）。

**对比表（拍板用）**

| 维度 | ① 自编 ORT ≥1.17（首选） | ② 降级 `ort` 到 1.16 档 |
|---|---|---|
| **设备侧可行性** | ✅ 沙箱加载与推理**已实测**，且**产品 `ort` crate 路径也已跑通**（§23.1） | ✅ 沙箱里 1.16.3 也能 dlopen / 建 session / 推理（§23.1）；但它**吃不到产品的 `ort` crate**（版本门槛），选它就得付左栏「要做的事」里那份迁移代价 |
| 要做的事 | CI 加一个 **ORT 构建 job**（配方现成；**本次已全程跑通并上机验证**，见 §24.5）+ HAP 带 `.so`；**Rust 侧零改动** | 改 `crates/diary_core/Cargo.toml` 一行 + `embedding.rs` 约 8–10 处 + ORT 路径改走环境变量 + **B3c 全部检索用例回归** |
| 版本自由度 | 想升就升（1.17 → 1.29+），跟得上算子与性能改进 | **永久锁死在 ORT 1.16.3（2023-11 发布，已 EOL）**；未来要新 ORT 得再做一次跨大版本迁移 |
| 供应链 / 许可 | 我们自己的构建：可复现、可审计、可打补丁、可跟 CVE；ORT 本体 MIT | 依赖 **sherpa-onnx 的第三方预编译二进制**（非微软官方构建）：**无法验证构建配置**（是否 minimal、是否额外打补丁）、**不可复现**、**无 CVE 跟踪**、来源是 GitHub release（可用性风险）；许可上 MIT/Apache-2.0 允许再分发，但必须**保留并展示版权与许可声明**（要进 about 页/`models/manifest`） |
| 体积 | 实测 **19.62 MB**（1.29.1 全算子集，strip 后） | 实测 **12.93 MB**（1.16.3） |
| 长期维护成本 | 「首次构建 + 缓存产物」，不是每次都编；每年升一次版本 | 一次性迁移，但此后**技术债只增不减**（API 差异会越拉越大） |
| 主要风险 | 首次构建的机器时长（本次实测 ~24 min / 16 核；环境差异已全部趟平）；HAP **+19.6 MB（实测）** | 回归范围不可控（检索是核心功能）；上游停止发布则被动；锁死旧运行时 |

**结论（我的建议）**：**走 ①**。理由不是「② 不可行」——**② 的技术风险本次已经被实测排掉了大半**——
而是：① 只多一个**可缓存的构建 job**、产品代码零改动、版本自由、供应链可控；
而 ② 换来的是**一次跨大版本 API 迁移 + 永久锁死在 2023 年的 ORT + 依赖第三方二进制**，
省下的只是 CI 里的一个 job。**如果顾虑仅仅是「CI 里不想多一条构建流水线」，那不足以走 ②** ——
ORT 只需要**首次构建并缓存**，日常构建不会重复编它。

## 24 卡点与绕过方式（本轮撞出来的四堵墙）

### 24.1 `libc++_shared.so` 必须随包带（**最容易踩且最难猜**）

第一版 HAP 里只有我们的两个 `.so`，ArkTS 侧 `import` 得到 `undefined`，`hilog` 全量日志才看到真因：

```console
W MUSL-LDSO: load libc++_shared.so failed, namespace=ndk no inherits, errno=2
W MUSL-LDSO: load libc++_shared.so failed, namespace=moduleNs_default, errno=2
W MUSL-LDSO: Error loading shared library libc++_shared.so:
              (needed by /data/storage/el1/bundle/libs/arm64/libdiary_napi.so)
W MMG: [NMM:1207]key:default/diary_napi First: failed Error loading shared library libc++_shared.so: …
       Second: load module default/diary_napi failed..load  failed
E ArkCompiler: [ecmascript] export objects of native so is undefined, so name is @normalized:Y&&&libdiary_napi.so&
```

**设备上确实有 `/system/lib64/libc++_shared.so`（1,289,552 B，world-readable，本次实测 `hdc shell ls -l` 可见）**，
但**应用进程的 linker namespace 看不到它**（`namespace=ndk no inherits`）。
→ 解法：`cp $NDK/llvm/lib/aarch64-linux-ohos/libc++_shared.so entry/libs/arm64-v8a/`（DevEco 的 C++ 模板也是这么做的）。
同一个坑对 **ORT** 一样成立（它的 `NEEDED` 里就有 `libc++_shared.so`），所以 ORT 也必须跟它一起进包。

> **教训**：ArkTS 侧 import 原生模块失败只表现为 `undefined` + 一句 `export objects of native so is undefined`，
> **必须去看不带 tag 的全量 hilog**（`hdc shell "hilog -x"`），真因在那里。

### 24.2 跨 TU 的符号不能落在匿名 namespace 里（dlopen 会当场拒绝）

第二版加了 ORT 探针后，模块又加载失败：

```console
W MUSL-LDSO: relocating failed: symbol not found.
  dso=/data/storage/el1/bundle/libs/arm64/libdiary_napi.so
  s=_ZN12_GLOBAL__N_112OrtProbeImplERKNSt4__n112basic_stringIcNS0_11char_traitsIcEENS0_9allocatorIcEEEE
W MMG: [NMM:1207]… Error relocating …OrtProbeImpl…: symbol not found.
```

原因是 `OrtProbeImpl` 的**声明**被我写进了 `napi_shim.cpp` 的匿名 namespace（`_ZN12_GLOBAL__N_1…` 就是内部链接的标志），
而**定义**在 `ort_probe.cpp` 的全局作用域 —— 头文件里没有它，编译期不报错，**链接成 `.so` 时也没报错**（因为没有静态链接检查），
直到设备上 `dlopen` 才炸。
→ 解法：把声明挪到匿名 namespace 外面。

> **教训**：HAP 里的 `.so` 是**运行时才链接**的，`-Wl,--no-undefined` 之类的静态检查不会覆盖「本包内两个 `.so` 互相引用」的情况；
> 上设备前可以用 `llvm-readelf --dyn-syms <so> | grep UND` 自查有没有本应自足的 `UND` 符号。

### 24.3 `import 'libX.so'` 在纯命令行工程里需要三件套

ArkTS 侧 `import diaryNapi from 'libdiary_napi.so'` 想拿到类型（否则退化成 `any`，被 ArkTS 规则 `arkts-no-any-unknown` 挡下），需要：

1. `entry/src/main/cpp/types/libdiary_napi/{index.d.ts, oh-package.json5}` —— 后者 `"name": "libdiary_napi.so"` + `"types": "./index.d.ts"`；
2. `entry/oh-package.json5` 里登记本地依赖：`"libdiary_napi.so": "file:./src/main/cpp/types/libdiary_napi"`；
3. **跑一次 `ohpm install --all`**（离线、46 ms）把它做成 `entry/oh_modules/libdiary_napi.so` 软链。

缺第 3 步的症状是：编译报 `arkts-no-any-unknown`，同时有一条 warning
`Currently module for 'libdiary_napi.so' is not verified …`。
（DevEco 工程里这三件事是 IDE 自动做的，命令行工程要自己写齐。）

另外一个**不需要**的东西：**不需要 `externalNativeOptions` / `CMakeLists.txt`**。
把预编译好的 `.so` 放进 `entry/libs/arm64-v8a/`，hvigor 的 `ProcessLibs` 会自己收进 HAP 的 `libs/arm64-v8a/`
（还会顺手 strip 一遍）。本次两个库都是手写 `clang++`/`cargo` 编出来的，全程没写一行 CMake。

|---|---|

**途中解决的四个环境差异（对 CI 直接有用；全部是环境问题，不是技术风险）**：

```bash
# ① 宿主需要 clang/clang++（配方里 _find_tool 硬编码要找它们）——WSL 只有 gcc/g++
#    OHOS SDK 自带的 llvm/bin/clang 本身就是**宿主 x86_64 可执行文件**，可直接当宿主编译器：
file -L ~/command-line-tools/sdk/default/openharmony/native/llvm/bin/clang
#   → ELF 64-bit LSB pie executable, x86-64 …（不带 --target 时默认产出宿主 x86_64 二进制，已实测）
# ② 宿主 cmake 必须是 3.28 一档（protobuf 21.12 的 cmake_minimum_required 是 3.5，CMake 4.x 直接拒绝）；
#    SDK 自带 build-tools/cmake/bin/cmake 就是 3.28.2
# ③ 把 clang/clang++/cmake/ninja/llvm-ar/llvm-ranlib/llvm-strip… 软链到一个目录并前置到 PATH
#    （配方还要 _find_tool('llvm-ar') 与 _find_tool('llvm-ranlib')）
mkdir -p /tmp/ort-build/hostbin && cd /tmp/ort-build/hostbin
NDK=~/command-line-tools/sdk/default/openharmony/native
ln -sf $NDK/llvm/bin/clang clang; ln -sf $NDK/llvm/bin/clang++ clang++
ln -sf $NDK/build-tools/cmake/bin/cmake cmake; ln -sf $NDK/build-tools/cmake/bin/ninja ninja
for t in llvm-ar llvm-ranlib llvm-strip llvm-nm llvm-objcopy ld.lld; do ln -sf $NDK/llvm/bin/$t $t; done
# ④ 配方里的 _get_ohos_toolchain() 只认鸿蒙电脑的 /data/service/hnp/ohos-sdk.org；
#    WSL/CI 上要让它读环境变量（本次给配方加了这个兜底；**建议上游配方直接支持**）
export PATH=/tmp/ort-build/hostbin:$PATH
export OHOS_NDK_TOOLCHAIN_FILE=$NDK/build/cmake/ohos.toolchain.cmake
conan create . -pr:h=ohos-aarch64-wsl -pr:b=default -c tools.build:jobs=16
```

**还撞到一个 FetchContent 幂等性坑（值得写进 CI 手册）**：第二次进入同一个 conan build 目录时，
`onnx-populate` 的 patch step 会重跑并失败（GNU patch 报
`Reversed (or previously applied) patch detected! … 2 out of 2 hunks ignored`，退出码 1，configure 直接挂）：

```console
[ 11%] Performing patch step for 'onnx-populate'
patching file CMakeLists.txt
Reversed (or previously applied) patch detected!  Assume -R? [n]
Apply anyway? [n]
Skipping patch.
2 out of 2 hunks ignored -- saving rejects to file CMakeLists.txt.rej
gmake[3]: *** [CMakeFiles/onnx-populate.dir/build.make:116: …onnx-populate-patch] Error 1
```

本次的处置：确认 12 个依赖的 patch stamp 都已存在、源码已是「打过补丁」的状态之后，
把 `cmake/external/onnxruntime_external_deps.cmake` 与 `abseil-cpp.cmake` 里的
`${Patch_EXECUTABLE} -l -p1` 换成 `${CMAKE_COMMAND} -E echo`（no-op，rc=0），再手工 `cmake --build . -j16` 续跑。
**CI 里的正确做法**是让这些 patch 命令幂等（先 `patch -R --dry-run` 判断是否已应用），或每次从干净构建目录开始。

**上机验证**（这一条是全节最重要的）：编出来的 `.so` 放进 HAP → 装到真机 → 产品路径全通（§23.1 的 `ORT_CRATE` 那行）。
也就是说 **自编 ORT 这条路已全程跑通、可复现**；CI 需要的只是「**首次构建 + 缓存 `libonnxruntime.so` 产物**」，
不需要每次构建都编它。

## 29 打包体积账（ORT + 模型 + 核心 ⇒ 鸿蒙 HAP 预估）

### 29.2 合计

**已知项（核心 + 壳 + libc++ + ORT + bge int8 + tokenizer）**

```
0.13（壳）+ 3.93（核心）+ 0.035（shim）+ 1.26（libc++）+ 22.73 + 0.44（bge int8）
  = 28.53 MB（不含 ORT）
  + 19.62（自编 ORT 1.29.1 实测）   ⇒ 48.15 MB
```

**实测对照**：本次含自编 ORT 的 HAP（**不含 bge 模型**）是 **signed 25.25 MB**，与
`0.13 + 3.93 + 0.035 + 1.26 + 19.62 + tiny_add(0.0001) ≈ 24.98 MB`（unsigned 实测 24.98 MB）吻合。

### 29.3 两条打包约束对体积的影响

| 约束 | 体积影响 | 说明 |
|---|---|---|
| **原生库必须进 HAP**（el2 不能 dlopen，§22.2） | **不可规避**：ORT 19.62 MB + 核心 3.93 MB + shim 0.035 MB **全额计入** | 好处是没有「下载 + 校验 + 版本管理」那一套；坏处是**不能靠动态下发缩小首包** |
| **`libc++_shared.so` 必须随包**（§24.1） | **固定 +1.26 MB（一份）** | 所有 C++ 原生库共用这一份；ORT 自己 `NEEDED` 它，我们的 shim 也 `NEEDED` 它。**不要重复放** |
| （附带）**HAP 不压缩**（实测 debug 构建所有条目都是 `Stored`） | 模型与 `.so` **按原始体积**计入 | release 构建是否会压缩**未验证**；即便压，int8 权重通常也只压 5–10%，收益很小 |

### 29.4 体积吃紧时的杠杆（按性价比排序）

1. **转写模型的选型与量化档位** —— 这是唯一可能上百 MB 的项，也是唯一「换个模型就省几十 MB」的项；
2. **ORT 裁剪**：`MINIMAL_BUILD` + `include_ops_by_config`（只留 bge 需要的算子）或去掉用不到的 EP，
   **自编时这一项杠杆最大**（全算子集 19.6 MB ⇒ 裁剪版通常能砍掉一半以上；代价是要重验模型可加载）；
   另一个现成选项：`llvm-strip` 记得做（本次未 strip 时 31.96 MB → strip 后 19.62 MB）；
3. **不发用不到的 ABI**：只发 `arm64-v8a`（本次设备只有这一种）；
4. **模型文件与资源**：bge int8 已经是量化档；`background.png` 70 KB 这类是零头，别在这上面花时间；
5. **不要试图把 `.so` 移出 HAP** —— 已被 §22.2 判死。

> **一个需要产品去确认、本次没查证的外部约束**：AppGallery（鸿蒙应用市场）对单 HAP/整包的体积上限是多少、
> 是否有「首次安装包 + 资源包」的分发方式。本次没有查官方文档，**不作为结论**。

## 34 正确性对照：设备 vs 宿主（本任务的硬要求）

前置一致性**全部通过**（`compare.json` 的 `preconditions_all_same: true`）：语料指纹
`corpus_sha256=9846ccbf…`、模型 sha256 / 字节数、`dims=512`、`pooling=cls`、
`query_instruction=false`、`model_version` 在两边**逐字相同** —— 也就是说下面比的是**同代码、同模型、
同口径**下的两个架构，而不是两套实现。

| 文本 | token | 余弦相似度 | 最大逐元素偏差 | 平均偏差 |
|---|---|---|---|---|
| q1–q5（查询） | 8–11 | **1.000000000** | 2.98e-08 ~ 5.96e-08 | ~6e-09 |
| d1, d3, d4, d5 | 15–21 | **1.000000000** | 2.98e-08 ~ 5.96e-08 | ~7e-09 |
| near_a（16） / far（31） | 16 / 31 | **1.000000000** | 5.96e-08 / 4.47e-08 | ~6e-09 |
| near_b | 19 | 0.999774297 | 3.478e-03 | 7.381e-04 |
| d2 | 21 | 0.999822971 | 3.166e-03 | 6.402e-04 |
| long | 412 | 0.999097111 | 6.022e-03 | 1.523e-03 |
| main / short（同一段 30 token） | 30 | 0.998345835 | **1.101e-02** | 1.996e-03 |
| medium | 70 | **0.997986337**（最差） | 9.733e-03 | 2.254e-03 |

**结论（如实）**：

1. **不是逐位相同，也不该期望逐位相同**：17 段的 f32 字节 sha256 **没有一段相同**（0/17）。
2. 但 **11/17 段差异在 f32 ULP 量级（≤5.96e-08）** —— 这些文本在两边**实际上算出了同一个向量**
   （差别只在最后一位舍入）；另外 6 段（19–412 token）差异在 **1e-3 ~ 1.1e-2**，余弦 **0.99799–0.99982**。
3. **差异为什么集中在较长的文本**：**推断**（无直接证据）—— 设备 20 核 / 宿主 16 核，ORT intra-op
   线程分块不同 ⇒ 归约顺序不同 ⇒ int8 动态量化的 scale 有微小差别 ⇒ 反量化后误差被放大。
   短文本可能走了另一条（小尺寸/单线程）kernel 路径，所以完全对齐。
   `repeat_bit_identical=true`（同一台上重复跑逐位一致）说明这**不是随机性**，而是**架构间的确定性差异**。
4. **对照的一个已知不对称**：设备 ORT **1.29.1**、宿主 ORT **1.31.0**（python wheel）。
   上表里的差异**同时包含**「架构差异」与「ORT minor 版本差异」两部分，本轮**没有**把两者拆开
   （要拆需要一份 1.31 的 OHOS 构建，或一份 1.29 的宿主构建 —— 见 §39）。

## 37 真实产品风险：`embedding.rs` **没有截断/超长处理**（本次实测撞到）

> **这一节是本次探针最有产品价值的发现**；按要求**不改产品代码**（属另一条 PR）。

**现象**：把一段 **617 token** 的中文（`LONG_UNIT × 15`）交给
`diary_core::embedding::Embedder::embed_document`，设备与宿主**都返回同一条错误**（不是崩溃、不是静默出错）：

```
当前状态不允许该操作：语义嵌入 bge-small-zh-v1.5-ours 处于 ONNX 前向失败：
Non-zero status code returned while running Add node. Name:'node_add_18'
Status Message: …/onnxruntime/core/providers/cpu/math/element_wise_ops.h:583
void onnxruntime::BroadcastIterator::Append(ptrdiff_t, ptrdiff_t)
axis == 1 || axis == largest was false.
Attempting to broadcast an axis by a dimension other than 1. 512 by 617
```

**触发条件**：token 数 > 512（bge 的位置嵌入上限）。**512 以内正常**（本次 412 token 正常出向量）。
错的是一位**位置相关的 `Add`**：`position_embeddings`（512 行）与长度 617 的张量相加。

**影响面**：
- 直接调用面：`diary_core::embedding` 是 `pub`，`OrtEmbedder::embed_document/embed_query` 对任何
  >512 token 的输入**必然报错**（`CoreError::InvalidState`），且错误文本对用户/排障者不可读
  （`BroadcastIterator::Append` 是 ORT 内部符号）。
- 走产品切块路径时：`chunker.rs` 的 `MAX_CHUNK_CHARS = 400`（字符），纯中文 ≈ 410 token，
  **通常**在 512 以内 —— 本次 410 字（412 token）实测正常。
  但「400 字 ≤ 512 token」**只对中文成立**：英文/数字/符号/emoji 的字符→token 比 **> 1**
  （WordPiece 把长单词切成 subword，emoji/罕见字可能一字多 token），
  400 字符的英文段落完全可能 >512 token。`chunker.rs` 里**没有任何按 token 计的兜底**。
- 后果分级：单个 chunk 嵌入失败 ⇒ 该块没有向量 ⇒ 按 `semantic.rs` 的换代语义，
  整代次重建可能失败或留下大片空洞，而用户在界面上只会看到「语义未就绪 / 失败」。

**建议怎么修**（给产品侧，**不是本探针要做的**）：
1. **在嵌入入口做 token 级截断**：`tokenizer.encode(..., true)` 之后判断 `ids.len() > 512`，
   截到 512（保留特殊 token 语义：`[CLS] + 前 510 + [SEP]`），
   并把「被截断」这件事**如实带出来**（返回值/状态里要有位），不要静默）；
2. **更稳的是让切块按 token 而不是按字符切**：`MAX_CHUNK_CHARS` 之外加一条
   「切完用 tokenizer 复核，>480 token 就再切」——`diary_core` 已经有 tokenizer，成本可接受；
3. **错误文本要能指明「超长」**：现在这条错误读不出「超长」二字；
   建议超长走独立错误码/分支，不要混在「当前状态不允许」里；
4. **回归用例**：至少三条 —— 纯中文 410 字（本次已验正常）、英文 400 字符（**很可能越界**）、
   400 字混排 emoji/数字（边界）。CI 里不需要真模型即可断言「token 数 ≤ 512」这条不变式。

## 38 结论：**鸿蒙版语义检索 —— 可用（带一个必须补的截断保护）**

| 判定 | 依据 |
|---|---|
| ✅ **可用** | ① **真模型**（bge-small-zh-v1.5 int8，22.73 MiB）与 tokenizer 从 HAP 的 rawfile 落进可写沙箱，被**产品同一条路径**（`ort` crate load-dynamic + `diary_core::embedding`，CLS / 无前缀 / 512 维）正常加载，`errors: []`；② 设备上算出的向量与**宿主同代码同模型**的最差余弦 **0.997986**、最大逐元素偏差 **1.10e-02**（11/17 段在 ULP 量级）；③ 语义判据成立；④ **检索排序 5/5 与宿主完全一致**；⑤ 耗时可接受（加载 248 ms、短文本 2.5 ms、412 token 62 ms）；⑥ 内存可测可控（模型+会话 ≈ +45 MiB） |
| ⚠️ **不是「无条件可用」** | ① **>512 token 必然报错**，而 `embedding.rs` 没有截断（§37）——**上线前必须补**，否则英文/混排长文本会在索引期失败；② 正确性对照里**架构差异与 ORT minor 版本差异没有拆开**（设备 1.29.1 vs 宿主 1.31.0，§34）；③ 只测了**单条、串行**的嵌入（`embed_document` 一次一条，`Mutex<Session>` 后面），**批量与并发没测**（§39） |
| ❌ 不可用 | 无任何证据支持这一档。**不需要**换 MindSpore Lite（第 2 步已判），也不需要放弃语义检索 |

**一句话**：**鸿蒙版语义检索：可用 —— 前提是补上「>512 token 的截断/切块兜底」这一个保护（§37），
并在上线前跑一次批量与并发的压力用例（§39）。**

## 39 剩余未验证项（如实）

1. **批量与并发**：本轮只跑**单条** `embed_document`（`embedding.rs` 的 `Session` 在 `Mutex` 后面，
   同一进程内**串行**）。产品侧 `index_rebuild` / `semantic` 的批量路径、
   多线程调用下的表现（锁竞争、ORT 线程数 = 20 核时的抢占、长时间索引的内存曲线）**全部未测**。
2. **内存峰值与长跑**：只量了**一次探针**的 RSS/HWM。真实建索引是**几十分钟级**的连续嵌入：
   ORT arena 会不会持续增长、峰值会不会到 GB 级 —— **未测**。
3. **架构差异 vs ORT 版本差异**：设备 ORT 1.29.1 / 宿主 ORT 1.31.0，两者混在一起（§34）。
   要拆开需要一份 1.31 的 OHOS 构建或一份 1.29 的宿主构建。
4. **`embed_query` 与查询前缀**：本次只用 `embed_document`（正文口径）。`embed_query`（可带
   `QUERY_INSTRUCTION`）在设备上的行为**未单独测**（实现是同一个 `embed()`，风险低但没测）。
5. **冷启动 `load_ms` 的优化**：ArkTS 每次冷启都重写 24 MB 模型（`writeMs≈29–31 ms`）并重算 sha256
   （152 ms）。「跳过重复落盘」的收益**未验证**。
6. **多设备 / 其它 API 版本**：只有这一台 HAD-W32（API 23）。
7. **release 构建 / 上架签名 / 32 位 ABI / 模拟器**：仍未做（与第 2 步一致）。
8. **CI 落地**：`hdc` 的两个老坑（§15/4 的 rc 恒 0、§32.1 的 `aa start` 不重启）本次已封进脚本，
   但**没有在 CI 里跑过**。

## 40 探针执行者对「还有什么风险点」的判断

> 这是**判断**，不是实测结论；每条都给了「怎么验」。

| 风险 | 判断 | 怎么验（建议） |
|---|---|---|
| **长文本截断**（§37） | **最高优先级，且是必现 bug 而不是风险**：>512 token 一定报错 | 加 token 级断言 + 英文 400 字符用例；修在 `embedding.rs`（截断）与 `chunker.rs`（按 token 复核） |

| **`model_sha256` 冷启成本**（152 ms + 24 MB 落盘） | **低–中**：可接受，但每次冷启都付 | 落盘前先比 sha256；或在 `databaseDir` 存一份并校验；量「跳过落盘」后的冷启 |

| **多 ABI / 老设备** | **低**：目标机型只有 arm64-v8a | 若将来要 32 位，需重编 ORT（本机只有 arm64 配方） |
| **ORT 供应链**（自编 1.29.1 的长期维护） | **低**：已可复现、可缓存（§31 的恢复路径） | 把 ORT 配方固化成一键脚本 + 把 strip 后的 `.so` 进 CI 缓存 |
