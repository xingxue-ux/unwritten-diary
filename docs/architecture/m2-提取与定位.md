# M2 · 提取与来源定位（B2）

对应 issue [#26](https://github.com/xingxue-ux/unwritten-diary/issues/26) · 日期 2026-09-27 · 执行人 xingxue-ux

代码在 `crates/diary_core/`（`src/extractors.rs`、schema v4）。检索与索引是 B3，不在这一片。

## 定下的决定

| 决定 | 理由 |
|---|---|
| 「提取不出内容」与「解析失败」是两件事 | 空文本文件是 `complete`（它就是空的，带一句说明）；坏掉的 DOCX 是 `failed` + `unsupported_format`。混在一起用户永远不知道该修文件还是该配能力 |
| 能力缺失一律如实降级 | 没有 OCR 的图片、没有转写的音视频 → `metadata_only` + 用户可读原因（「按文件名、时间和备注仍能找到」），**不是**「没有相关内容」。契约 2.4 节的原话 |
| 扫描版 PDF 是 `metadata_only` 而不是失败 | 有文件、有页面，只是没有文本层。原因里写明需要 OCR |
| 页码不可靠就不写 | DOCX 定位到文档级（`pageNumber` 为空）；PDF 的页码来自真实页序，才写数字 |
| 提取失败也落一条记录 | 否则界面上「解析失败」会显示成「没有内容」。记录里带 `status=failed`、`coverage=unavailable`、错误码与原因 |
| 派生内容整体替换，不追加 | 同一个修订重新提取时先删旧记录再写新的。派生内容可重建是契约 2.4 节的前提 |
| 字符区间按 Unicode 标量值计数 | 契约 1.2 节的硬要求；用 `chars().count()` 而不是字节偏移 |
| 编码检测用 chardetng + BOM 优先 | 中文用户的旧文件常见 GBK。BOM 最可靠，其次交给检测器 |
| 导入完成就在同一个事务里排 `extract` 任务 | 与 B1c 的队列接上；任务目标是**源修订**，提取真正需要的东西 |
| `extract_source` 同时接受来源 id 与修订 id | 调用方手上有哪个都能用；给来源就取它当前的修订 |

## 验证到了什么

`cargo test -p diary_core` 共 **57 项**（12 提取 + 15 录音与任务 + 12 文件库 + 16 记录 + 2 单测）。

- **纯文本**：两段之间的空行正确切段；字符区间按标量值计数（`第一段第一行\n第一段第二行` → `[0,13)`）；不含结尾换行。
- **空文件不是失败**：`status=ready`、`coverage=complete`、原因写着「文件里没有可提取的文字内容」。
- **GBK 正确解码**：一句正常长度的 GBK 中文能被检测并读出，没有替换字符。
- **DOCX**（测试里现场拼的最小合法 DOCX）：按 `<w:p>` 切段、跳过空段落、`pageNumber` 留空。
- **文本 PDF**：两页各一段，页码是 1 与 2。
- **扫描版 PDF**：`metadata_only`，原因里写明需要 OCR，`error_code` 为空（是能力缺失，不是错误）。
- **图片无 OCR**（E16）：`metadata_only`，原因既说明搜不到正文、也说明还能按文件名找到。
- **不支持的二进制**（E17）：`failed` + `unsupported_format`，且**原件仍在**（`asset_stats` 计数为 1）。
- **坏掉的 DOCX**：报 `failed` 且原因里能看到「DOCX」，不是悄悄当成空文件。
- **可重建**：连续提取两次，派生内容只有一份；**原件的字节没有变化**。
- **导入后自动排队**：`extract` 任务的目标就是这次导入的源修订，用这个目标直接提取能跑通。
- **定位**：来源 id 能解析到资产与可用性；找不到的来源如实说「找不到」；纯文字来源说明「没有可打开的原件」。

另外：**Android arm64 编译检查通过**——`cargo ndk -t arm64-v8a check -p diary_core` 把 rusqlite（bundled）、pdf-extract、zip、quick-xml、encoding_rs 全部编到 aarch64 上成功。只到编译，没有在设备上运行。

## 没有做到的

- **转写与 OCR 一条都没做**：音视频与图片只走到 `metadata_only`。真实能力要接 provider（B4）与 OCR 包。
- **中文 PDF 未验证**：测试用的 PDF 是 ASCII 文本、标准 Helvetica 字体。中文 PDF 涉及字体与 CMap，`pdf-extract` 能不能正确处理**没有测过**，不能算数。
- **DOCX 只取正文**：表格文本、批注、页眉页脚、脚注都没处理；嵌套结构只按 `w:p` 切段。
- **短样本的编码检测不可靠**：6 个字节的 GBK 样本被 chardetng 猜成了泰文（Windows-874）。真实长度的文本没问题，但极短的旧文件可能猜错——检测到的编码会作为 warning 记下来，界面需要显示这个提示。
- **没有索引**：提取结果只是存下来了，还没有被检索到（B3）。
- **桥接仍未接线**：前端调不到这些方法。

# 平台层：原件定位（Flutter）

上面是核心这一侧（`extractors::locate` 只回答「原件在不在、能不能开、为什么不能开」）。
真正把原件打开的是平台层，代码在 `apps/diary_app/lib/src/source_original.dart`。

## 界面怎么用

搜索命中或来源详情页顶部有一张「原件」卡片：

| 来源类型 | 卡片给什么 |
|---|---|
| 录音 / 视频 | 就地播放器，**先跳到命中时刻**（`locator.startMs`），再按播放 |
| 图片 | 就地预览 |
| PDF | 显示「第 N 页」（页码来自 PDF 实际页序，核心只在可靠时才给），并提供「打开第 N 页」（走 `file:///…#page=N`，浏览器类程序认这个片段） |
| 其他文件 | 「用系统程序打开」，交给系统默认程序 |

**不能开就说清楚**：`available == false` 时把核心给的原因原样显示（原件不在文件库、
状态不是 ready、这个来源本来就没有可打开的原件），**不画播放器**——画了按下去没反应
比不画更坏。

## 边界

- 播放/预览走 `assets.open` 的**只读租约**，不自己拼 blob 路径；离开页面就释放；
- **播放前要复制一份带扩展名的副本**：文件库的 blob 用内容哈希当文件名（没有
  `.wav`），Windows 的 Media Foundation 打不开这种路径——`play()` 会一直等到
  30 秒超时。`playable_audio.dart` 按哈希把它复制到系统临时目录（同一份只复制
  一次）。这是播放层的事，不改文件库的命名；
- 唯一把路径交给外部程序的地方是用户点「用系统程序打开」那一下，只对这一个原件生效；
- 页码只在文档类原件上有意义；`#page=N` 是浏览器约定，Acrobat 之类不认，所以它是
  **另一个按钮**，不是默认行为，按下去没打开也不影响默认那条路。

## 验证

- `apps/diary_app/test/source_original_test.dart` 3 项：原件不在时只显示原因、不画播放器；
  原件在时显示定位时刻与播放按钮；没有命中位置时只提供打开（locator 类型回落到 `file`）；
- 核心与桥接这一侧由 `cargo test -p diary_core` 的定位用例与
  `packages/diary_bridge` 的端到端用例覆盖。

## 没有做到的

- **没有应用内 PDF 渲染**：不装 PDF 渲染器，所以「打开第 N 页」是把文件交给外部程序，
  不是画在应用里；
- **图片没有 OCR**，所以图片原件只能看，不能搜（与核心那侧的限制同源）；
- **没有把定位用在片段列表**：目前只有搜索命中与来源详情页有入口。
