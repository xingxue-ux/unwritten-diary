# M2 · 检索会话

对应 issue [#31](https://github.com/xingxue-ux/unwritten-diary/issues/31) · 日期 2026-10-09 · 执行人 xingxue-ux

关键词索引（[M1 · 关键词索引](m1-关键词索引.md)，B3a）解决了「查得全」；这一片解决「**查得下去**」：翻页、取消、快照失效与过滤。代码在 `crates/diary_core/src/search_session.rs`，契约方法 `search.start` / `search.nextPage` / `search.snapshot` / `search.cancel`，以及混合检索两阶段的升级入口 `Core::upgrade_search_to_hybrid`（桥接方法 `search.upgrade`，issue [#69](https://github.com/xingxue-ux/unwritten-diary/issues/69)）。

## 混合检索的两阶段（#69）

契约里一直有 `hybrid_ready` 这个阶段，但 #51 的混合是**一次算完**：`search.start(mode = hybrid)` 直接给融合结果、`phase` 恒为 `done`。#69 把它改成两步，让「先看到关键词结果、再补进语义召回」这件事在产品路径上真的可观察：

```
search.start(mode = hybrid)             → phase = keyword_ready（只算关键词那一路）
        │                                  结果不含只被语义召回到的篇，matchedBy 只有 [keyword]
        ▼
search.upgrade(sessionId)               → phase = hybrid_ready（这时才 RRF 融合 + 重排）
        │                                  matchedBy 如实更新；结果里补进语义独有的篇
        ▼
search.nextPage（若还有下一页）          → phase = hybrid_ready；翻完最后一页 → done
```

几条边界写死在实现里：

- **首屏不加载模型**。第一阶段只读库里的生效代次 / 块数与 `embedder_readiness`（env + stat），不建 ORT 会话——「语义到底行不行」的代价留到升级那一步；
- **升级前翻页只给关键词结果**，`phase` 一直是 `keyword_ready`：不假装已经融合；
- **升级是幂等的**：重复调用返回同一份快照，不重复算向量；
- **升级后从头给融合结果**：融合改变了顺序，原来「第几页」没有意义，所以游标重置为融合后第一章，并**递增结果代次**——升级前发出的**所有**显式游标（含第一页那个与融合后第一页偏移相同的）都会 `cursor_expired` 如实拒绝（#71）；
- **语义拿不出可融合的证据时不升级**，两种情形一个口径：**不可用**（没配模型 / 模型加载失败 / 没有生效代次 / 没有块）与**可用但没有可融合的证据**（候选全被 `HYBRID_SEMANTIC_MIN_SCORE` 滤掉；查询是空的、一条候选都没有）→ 都不融合：如实返回**关键词那份快照**（不是空、也不是被滤空的融合结果）、`phase` 仍是 `keyword_ready`，结果集没换所以代次不递增、升级前的游标继续可用；`warnings` 里写清原因（#60 复审）；
- **换模型未重建（跨向量空间）同样不升级**（#80）：生效代次的 `model_version` / `dims` / `storage` 与当前嵌入器不一致时（`Single(旧模型)`——用户换了模型配置但还没重建，最常见的真实情形；或历史遗留的 `Mixed`），查询向量与库向量来自两个向量空间，余弦全是垃圾但看起来正常。判据在**进入计算之前**（不生成查询向量、不读向量行）：混合第一阶段在嵌入器已加载时先拦、升级在模型刚加载出来时再拦一次，一律**不融合**——保留关键词那份快照、阶段停在 `keyword_ready`，警告点名「当前生效的向量代次是用另一个模型（或另一套口径）建的（… ≠ …），……重建语义索引即可恢复」；纯语义给**空结果 + 同一条警告**（不退化成关键词）；关键词照常；重建后警告消失、混合回到 `hybrid_ready`；
- **取消 / 过期 / 非混合会话不静默**：已取消返回 `cancelled` 快照；索引变了报 `search_expired`；`mode != hybrid` 报 `invalid_state`；
- **空查询**走同一条规则：第一阶段给空结果 + 「查询是空的」；升级时两路都空、没有任何可融合的证据，阶段仍如实停在 `keyword_ready`（空不等于假装融合过）。

## 三条规则决定了这里的形状

1. **旧查询的结果不能覆盖新查询**。核心按 `sessionId` + `queryRevision` 双校验：会话不存在、或索引在会话期间变了，一律报 `search_expired`，让前端重新发起，而不是把过期结果糊到新界面上。
2. **翻页绑定原会话与结果代次**。游标内部是 `<sessionId>:<generation>:<offset>`（对外仍是不透明字符串），拿别的会话的游标、或结果代次已经变了的旧游标来翻，报 `cursor_expired`——校验顺序见下一节。
3. **取消只停止后续处理，不删任何原件**。取消后 `phase` 是 `cancelled`、不再给游标，但已经返回的结果仍可读（`search.snapshot` 拿得到「已取消」这个状态）。

## 游标（内部格式）与校验顺序

游标对外是**不透明字符串**（契约第 2 章「不透明 cursor」）：调用方只应把上一次快照给的 `cursor` 原样回传，不该解析它。内部格式是：

```
<sessionId>:<generation>:<offset>
```

- `sessionId`：翻页绑定原会话；
- `generation`：**结果代次**，会话内从 0 起，**结果集被替换**（混合升级融合重排）时递增；
- `offset`：下一页从第几条（0 基）开始。

`search.nextPage` 收到显式游标时，游标**自身**的校验按这个顺序，任何一层不过都报 `cursor_expired`（会话不存在、索引在会话期间变了仍按现状报 `search_expired`，不改变这里的次序）：

1. **格式**：切不出三段，或代次 / 偏移不是数字；
2. **会话归属**：`sessionId` 与当前会话不一致（现状不变）；
3. **结果代次**：`generation` 与当前会话的代次不一致 → `cursor_expired`，**不看偏移**；
4. **偏移边界**：代次一致时，`offset` 必须正好等于「当前页之后的下一条」，否则也是 `cursor_expired`。

第 3 层是 #71 修的洞：`pageSize = 2` 时，升级前第一页与升级后第一页的偏移都是 2；只看第 4 层会把旧游标当成「正指向融合结果第二页」，于是界面若留着关键词阶段的第一页，就会把两个阶段的结果拼起来（乱序 / 重复 / 漏项）。

**幂等升级不递增代次**：第二次 `upgrade` 返回同一份融合快照、同一个代次，所以升级后已经发出的游标继续可用。今天只有「升级融合」这一个替换结果集的入口，代次也只在那一处递增；将来若有别的入口替换结果集（重跑查询、换过滤器等），它必须走同一个代次，否则同类错位会换个入口回来。

## 证据稳定性口径（#57）

**保证**：同一查询 + 同一库 + 同一生效代次 + 同一模型口径（`model_version` / `dims` /
`storage` 全同）下，语义与混合检索给出的**顺序、`snippet`、`locator` 的文字区间、
`title`、`matchedBy`** 以及 `semantic_ranking` 的 **f32 位模式**都逐字节一致——换一个
OS 进程再查一次也一样。把同一份内容重新导入成**另一个库**时，只要正文与切块规则相同，
语义路的顺序与摘录、以及混合路**正文不同的候选之间**的先后也相同；库内随机的 v7 UUID
不参与这些判定（只有正文也完全相同时才退到它兜底，见下面的「边界」）。

**靠什么做到**：

1. **候选给全序**：语义候选按
   `score DESC → day_key DESC → start_char ASC → end_char ASC → span_ordinal ASC →
   content_key ASC → chunk_id ASC` 排；折叠在排序之后做，「同一篇只留第一条」就是
   「得分最高、同分时篇内起点最靠前的那一块当证据」。完整契约见
   [M2 · 向量索引与换代](m2-向量索引与换代.md) 消费契约第 6 条。
2. **内容键不是库内 UUID**：`content_key` 是证据块正文（`text_chunks.text`）的 sha256，
   只由内容决定；`chunk_id` / `group_id` / `source_id` 的哈希或取值里带篇标识 v7 UUID，
   每建一次库都会变，所以只留作**最后**的库内兜底。这个哈希**只对前五道键完全相同的
   并列组**计算（那时才回表读正文）——不扫全表、不给每次查询加一遍全库正文 sha256。
3. **分数不糊**：`cosine` 按向量切片的固定顺序逐项 `f32` 累加，不重排、不四舍五入；
   `semantic_ranking` 报的就是这个原始 `f32`（测试比较 `to_bits()`，不是近似相等）。
4. **折叠容器只查表不迭代**：去重用的 `HashSet` 只回答「这个 `group_id` 见过没有」，
   输出顺序完全来自上面已经全序的 `Vec`；进程间随机的 `RandomState` 影响不到结果。
5. **正文口径固定**：来源篇按 `extracted_segments.ordinal` 用 `\n` 连接，span 的
   `start_char` / `end_char` 是篇内字符区间，摘录按同一区间截断——不依赖 SQL 的行顺序。

**为什么不能只把 `chunk_id` 留作同分兜底**：上一版修复（#57 前半）先比篇内区间，
挡住了「同一篇的两块同分」；但**不同篇**的两段完全可以拥有相同的（分数、日期、
篇内区间、段序号）——例如同一天导入两份等长文件、各被同一条规则切成两块。这时旧逻辑
落到 `chunk_id`，它的哈希输入含篇标识 v7 UUID，于是同一份内容在两次建库里谁排第一会
抛硬币，用户看到的第一条摘录跟着换人。`content_key` 把这一层也钉住。

**能红**：`semantic::tests::equal_position_different_content_is_ordered_by_content_not_chunk_id`
（纯排序层）与 `equal_score_across_pieces_is_ordered_by_content_across_libraries`
（16 份独立库、两份等长长文、四块同分）都验证过「删掉 `content_key` 这道键就红」；
`same_library_two_cores_agree_byte_for_byte` 与 `same_library_cross_process_is_byte_identical`
钉住「同一库、同查询、两个 Core / 两个进程逐字节相同」。

**边界（诚实）**：语义路只有两条候选的**块正文也完全相同**时才会落到 `chunk_id`；
混合路在 `content_key`（篇正文哈希）相同的极端情况下仍会落到 `group_id`（也是库内
UUID）。这两种情况下 `snippet` 逐字相同，但 `hit_id` / `title` /
`locator.sourceRevisionId` 里的库内 UUID 可能不同，**跨库的先后不承诺**（用户看到的
内容相同）；同一个库里这些 UUID 都是持久化的，所以同一库、同代次仍然逐字节确定。
关键词那一路的最后一道键仍是库内 `doc_id`，本口径覆盖的是语义与混合两路。

## 定下的决定

| 决定 | 理由 |
|---|---|
| 会话状态放内存，**不持久化** | 它记录的是「这一次查询翻到哪、快照还有效吗」，不是业务数据。重开资料库后旧 `sessionId` 一律 `search_expired`——比让前端拿着一个已经不存在的会话猜要好 |
| 快照失效靠**索引指纹**（`COUNT(*)` + `SUM(doc_id)` 于 `search_docs`） | 会话期间新导入/新提取会让指纹变，旧快照立刻作废。用 count+sum 而不是只看 count：删除与插入同时发生时也不容易撞上 |
| 会话里只存 **doc_id 列表**，正文按页现取 | 一次查询可能有几万条命中；把几万段正文常驻内存不值得。排序需要的「出现位置」在 SQL 里用 `instr()` 算，同样不用把正文读出来 |
| **排序并列必须给全序键**（#57） | 同分不能依赖 `HashMap` 迭代顺序、随机 UUID 或「看起来一样」：语义候选的最后一道内容是 `content_key`（块正文哈希），`chunk_id` 只在正文也相同时兜底。并列键写全，换进程 / 换建库顺序才不换结果 |
| 关键词模式排序：**日期从近到远 → 出现位置 → 写入顺序** | 可解释、便宜。**没有**做「整词命中优先」：那要为每一行查一次词表，代价随候选数线性增长。**混合模式**（#51）另有一套：相关度（RRF 分）优先，同档按时间降序，再按正文哈希——见 [M2 · 向量索引与换代](m2-向量索引与换代.md) 的「混合检索（RRF）」 |
| 一页上限 **100** 条（默认沿用契约的 20） | 挡住「一次要一万条」这种请求；界面本来也是一页一页取 |
| 过滤全部下到 SQL，**同一套条件作用于候选与总数** | 日期范围、来源范围、材料类型、是否含回收站四项共用一条 WHERE。含不含回收站默认**不含** |
| 语义模式未就绪时**空结果 + 诚实警告**，混合模式未就绪时**退化为关键词 + 明说** | 纯语义退化成关键词会让「语义」这个标签撒谎；反过来，混合里关键词那一路本来就能用，报空结果才是把能用的东西藏起来。两条都不静默（#51） |
| 生效代次与当前嵌入器**口径不一致**时语义这一路**整路不作数**（#80） | 换了模型还没重建索引时（`Single(旧模型)`，最常见的真实情形），查询向量与库向量来自两个向量空间，余弦全是垃圾但看起来像正常结果（有排序、有分数）。判据在进入计算前生效：混合退化为关键词、停在 `keyword_ready`，纯语义空结果 + 同一条警告，关键词照常；重建即可恢复（口径见 [M2 · 向量索引与换代](m2-向量索引与换代.md) 消费契约第 7、8 条） |
| 混合**分两阶段给**：`start` 只算关键词（`keyword_ready`），`upgrade` 才算融合（`hybrid_ready`）（#69） | 关键词那一路便宜、语义那一路贵（模型加载 + 全表余弦）。首屏先给能立刻显示的结果，界面不必等模型；「融合完成了」由显式升级表达，而不是让 `hybrid_ready` 当死值 |
| 游标带**结果代次**：`<sessionId>:<generation>:<offset>`，升级替换结果集时递增（#71） | 只带 `sessionId:offset` 时，升级前第一页与升级后第一页的偏移相同（`pageSize = 2` 时都是 2），旧游标会被当成「正指向融合后第二页」，把两个阶段的结果拼起来。代次不一致一律 `cursor_expired`、不看偏移；幂等升级不递增，升级后发出的游标继续可用 |
| `include_old_diary_versions` 给了提示 | 日记历史版本还没有进索引（**当前版本也没有**，B4c 把话说全了），这个开关现在没有效果，并指出旧版正文请用 `diary.listVersions` / `diary.getVersion` 按需读取——不说的话，前端会以为过滤生效了 |
| 摘录两边截断时加 `…`，高亮下标**相对摘录** | 契约里 `highlights` 的下标要有一个明确的参照；选摘录而不是整段正文，因为界面只渲染摘录 |
| 未知材料类型落到 `file` | 「有原件但不知道是什么」比丢掉一条命中更接近事实 |
| 命中的 `title` 取**来源修订的原件名**（经 `source_revisions.asset_id`） | 片段自己的 `asset_id` 只在图片/音视频定位里有值，文本片段是空的；用来源修订才能拿到导入文件名 |

## 验证到了什么

`crates/diary_core/tests/search_session_test.rs`（11 项，真库真提取）：

- **分页**：10 条命中按每页 3 条翻 4 页，不重不漏，最后一页 `phase = done`、游标为空；拿旧游标重翻报 `cursor_expired`；
- **游标归属**：拿另一个会话的游标来翻报 `cursor_expired`；
- **快照失效**：会话期间导入并提取新材料后，`nextPage` 与 `snapshot` 都报 `search_expired`；
- **取消**：`phase = cancelled`、不再给游标、已返回结果仍可读，再翻页报 `invalid_state`；
- **空查询**：空结果 + 说明，不报错；
- **降级与开关**：没有模型时 `hybrid` 请求退化为关键词并给提示（阶段如实停在 `keyword_ready`）、命中 `matchedBy` 只有 `keyword`，升级（`search.upgrade`）也**不**声称 `hybrid_ready`；`include_old_diary_versions` 给提示；混合融合本身的分页/同分/`matchedBy` 在 `semantic_index_test.rs` 里另有测试（#51）。
- **过滤**：日期上界/下界、来源范围、`kinds`（用 `image` 过滤得到 0 条，证明条件真的进了 SQL）各自生效，且日期近的排前面；
- **摘录与高亮**：高亮区间正好落在查询词上、两边截断有省略号、`title`/`locator`/`sourceKind` 齐全；
- **重开资料库**：旧会话报 `search_expired`，不会给旧结果。

`semantic_index_test.rs` 里 #69 新增的阶段测试（stub 嵌入器，CI 可跑）：

- `hybrid_fuses_two_paths_with_rrf_and_reports_matched_by`：`start` 是 `keyword_ready`、**不含**只被语义召回到的那篇（B）且 `matchedBy` 全是 `[keyword]`；`upgrade` 是 `hybrid_ready`、B 补进来且落在第 2（融合后的顺序）；
- `hybrid_upgrade_reorders_what_keyword_already_had`：升级前后**顺序真的不同**（关键词按日期 A 在前；融合把两路都中的 B 提到前面），并钉住幂等升级不重复算向量；
- `hybrid_upgrade_respects_cancel_expiry_and_non_hybrid_sessions`：升级前 / 后取消 → `cancelled`；索引变了 → `search_expired`；非混合会话 → `invalid_state`；会话不存在 → `search_expired`；
- `hybrid_upgrade_on_an_empty_query_still_checks_semantic_evidence`：空查询的升级也走同一条「没有可融合的证据就不假装」的规则——两路都空（关键词空 + 语义没有候选），阶段仍停在 `keyword_ready`、结果空、幂等；语义不可用时同样不假装；
- `hybrid_upgrade_keeps_the_keyword_snapshot_when_every_semantic_candidate_is_filtered`（#60 复审）：关键词有结果、但所有语义候选都低于 `HYBRID_SEMANTIC_MIN_SCORE` → **不融合**：`phase` 仍是 `keyword_ready`，结果与升级前**关键词那份快照**逐条相同、游标不变，警告保留，重复升级不重复算向量；
- `hybrid_treats_semantic_below_the_threshold_as_no_evidence`：关键词空 + 语义低于门槛 → 结果空**且**阶段 `keyword_ready`（不假装融合）；把门槛降下来就命中；
- `hybrid_sessions_page_and_snapshot_like_keyword_ones`：升级前翻页只给关键词（阶段一直 `keyword_ready`）、`snapshot` 幂等、`queryRevision` 沿用、升级后深页游标报 `cursor_expired`、升级后翻页保持 `hybrid_ready` 并在末页 `done`；
- `hybrid_upgrade_expires_every_pre_upgrade_cursor_even_at_the_same_offset`（#71）：`pageSize = 2` 时升级前**第一页**的游标（偏移与融合后第一页相同）也报 `cursor_expired`；升级前的深页游标同样过期；升级后返回的游标逐页翻完（`hybrid_ready` → `done`）且拼起来等于一次取全的融合结果；**重复 `upgrade` 不递增代次**，升级后发出的第一页 / 第二页游标在再次升级之后仍然可用；
- `without_a_model_keywords_keep_working_and_semantics_says_why` 与 `search_session_test::empty_query_and_degraded_modes_say_so`：没有语义证据时 `start` 退化为关键词，`upgrade` **仍然** `keyword_ready` + 「没有可融合的语义证据」；
- `switching_models_without_rebuild_keeps_semantic_out_of_both_paths`（#80）：建索引（模型 A）→ 换成模型 B（`model_version` / `dims` 都不同）→ **不重建**就搜。混合的结果逐条等于关键词那一路（不含只有语义能召回的 B）、`matchedBy` 只有关键词、`phase = keyword_ready`（升级也不融合），警告含「另一个模型／口径不一致」与「重建」；纯语义空结果 + 同一条警告；关键词照常；整代重算重建后警告消失、纯语义与混合恢复正常（`hybrid_ready`）；
- `a_mixed_generation_keeps_semantic_out_of_both_paths_until_rebuild`（#80）：历史遗留的 `Mixed` 代次（直接改一行的 `model_version`）走同一条路，警告点名「历史遗留的混合代次」；重建后恢复；
- `a_dims_mismatch_is_blocked_before_any_cosine`（#80）：整代 `dims` 不一致（行内自洽的 384 维 e0）在算余弦**之前**就被整代判据挡住（空结果 + 口径警告，不是 0 分、也不依赖逐行检查）；行内自洽但字节与记录不符的坏数据如实报错。三条都**验证过把判据去掉会红**（`Single(旧模型)` 那条从 `keyword_ready` 变回 `hybrid_ready`）；

## 没有做到的

- **用户自己写的文字还搜不到**：索引里只有派生内容片段（B3a 的范围），记录的草稿正文与日记正文都还没进索引。这是**这一片最大的缺口**——搜自己写过的话是日记应用最常见的用法。需要给 `captures.draft_text` / 日记正文建索引（要迁移 schema），已单独开 issue。
- ~~向量与混合检索~~ → **已实现**：`semantic`（B3c-2）与 `hybrid`（RRF，#51，B3c-3）都走真路径；#69 让混合变成「先 `keyword_ready`、再 `hybrid_ready`」两步。量测与阈值记在 [M2 · 向量索引与换代](m2-向量索引与换代.md)。
- **升级要调用方显式发起**：`search.upgrade` 不是一个后台自动跑的任务——核心不会在 `start` 之后自己接着融合。界面想拿到语义补充就得再调一次（F4 的呈现按阶段来）。不自动升级是刻意的：**升级要先把结果交付给用户**，谁来决定「什么时候值得再花一轮语义」是产品决定，不是核心偷偷决定。
- **融合本身不可中途取消**：`search.cancel` 能取消的是「后续翻页」，不能让一次已经在跑的 `upgrade` 停下来（`upgrade` 是同步调用，取消发生在它返回之后）。取消后再升级返回 `cancelled` 快照，但**不打断已经开始的这一次融合**。
- **没有做后台自动升级**：也没有做「首屏之后自动补一次」的调度、没有超时预算（比如「语义超过 X ms 就放弃并停在 `keyword_ready`」）。升级要么整个跑完，要么如实报错。
- **`search.upgrade` 的契约变更还差第二人审核**：这一片按 #69 新增了桥接方法（`search.upgrade`，Dart `upgradeSearch`）与能力项，而 `docs/development/01-共享接口契约.md` §4.4 原先只列了 `search.start / nextPage / snapshot / cancel`。工作树里已把契约（§2.6 的两阶段流程、§4.4 的 `search.upgrade` 条目与保证）和 `packages/diary_api` 的 `DiaryApi.upgradeSearch` 同步；Mock 如实沿用「退回 `keyword_ready`」的默认退化，不声称 `hybrid_ready`。按 CONTRIBUTING §5，契约变更还需要不在本 PR 的另一人以调用方身份审核（并补场景样例）才算走完流程。
- **降级路径（`keyword_ready` 的第一阶段）与升级后的候选形状不同**：拿不到语义证据时第一阶段走的是**纯关键词**的引用形状（按抽取片段出结果，一份多段材料会出现多条）；能升级时第一阶段给的是**按篇折叠**的关键词候选（与融合同一个单位，最多 `RRF_CANDIDATE_DEPTH = 50` 篇）。所以「同一份多段材料」在两种第一阶段里看到的条数可能不同；这是沿用 #51 退化路径与融合候选的既有口径，没有为了统一而改任何一边。
- **`include_trashed` / `kinds` 的部分取值无法端到端验证**：核心还没有「移到回收站」的对外接口，所以 `state <> 'trashed'` 这条只有代码；今天能被索引的内容类型实际只有 `file`，所以 `kinds` 只用「过滤后为空/不为空」证明它生效。
- **索引失效判断是「变了就作废」，不是增量续查**：会话期间索引一变，用户就得从头再来。对今天的库规模够用，但大规模写入时体验会差；将来可以改成「从已完成的部分续」。
- **没有做结果去重与分组折叠的策略**：`group_id`（同一来源）已经给出，但「一组显示几条」留给界面决定。
- **没有性能数字**：这一片没跑规模实测，B3a 的 10 万片段数据（首屏 0.029 ms、27.0 字节/字符）仍然成立，但会话路径（含 `instr()` 排序与指纹查询）尚未单独测。
- **Android / Windows 未验证**：只在 Linux（WSL2 x86_64）宿主跑过。
