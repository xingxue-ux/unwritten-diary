# M1 · 关键词索引

对应 issue [#30](https://github.com/xingxue-ux/unwritten-diary/issues/30) · 日期 2026-10-02 · 执行人 xingxue-ux

把已经入库的派生内容变成**能被检索的索引**，并让覆盖状态可查。代码在 `crates/diary_core/src/search.rs`，schema 是 v5。选型来自 [M0-技术验证](M0-技术验证.md) 第 2 节：**jieba 分词 + 2-gram，两者取并集**。检索会话（`search.*`）在 [#31](https://github.com/xingxue-ux/unwritten-diary/issues/31)，向量与混合在 [#32](https://github.com/xingxue-ux/unwritten-diary/issues/32)。

## 这一片解决了什么

- 派生文本进索引，**与提取写在同一个事务里**：不会出现「材料存了、索引没写、检索不到而没人知道为什么」。
- `indexes.status`：内容覆盖、已索引/待索引片段数、解析失败的材料数、分词器版本、索引占用。
- 桥接接线：`indexes.status` 接进 `BridgeSession`，并加进 `capabilities`。
- 索引体积、构建耗时、首屏延迟、召回都有了可复现的实测数字（见下）。

## 定下的决定

| 决定 | 理由 |
|---|---|
| **一张倒排表装三种词项**，靠长度区分：单字、2-gram、jieba 词 | 单字是一字查询的唯一依据（jieba 把「妈妈」切成一个词，只建词的索引查不到「妈」）；2-gram 是两字以上查询的候选来源，也是「短词藏在长词里」的唯一补救（M0 实测：查询「面试」在分词索引里漏 224 条）；jieba 词用于候选收窄与后续排序区分「词命中」。分三张表会多两份 b-tree 开销 |
| **`PRIMARY KEY (term, doc_id)` + `WITHOUT ROWID`** | 让主键本身当索引：不再需要「堆表 + 二级索引」两份存储，天然去重，也不需要额外的 `INSERT OR IGNORE` 冲突处理 |
| **`search_docs` 不重复存来源与内容 ID** | 那些是派生内容表里已有的事实，检索时 join 回去即可。每行省下约 130 字节：10 万片段上搜索索引占用从 107.1 MiB 降到 86.1 MiB |
| **候选之后一定回原文核对**（`instr`） | 2-gram 只是候选生成：`妈妈` 的两个 gram 都在的片段里也可能出现「妈……妈」而不连续。核对用 `instr`，所以召回是**精确**的——真正包含查询的文本一定包含查询的全部 gram |
| **候选过滤取「最长连续段的首个 gram」**，不取全部 gram 的交集 | 交集能缩小候选，但每多一路就多一次范围查询；精确性不受影响（核对始终是 `instr`）。代价见「全量计数」一栏 |
| **jieba 词典懒加载**（`OnceLock`） | 核心启动不做重活（任务书第 2 节）。第一次建索引才付词典代价：实测常驻内存 25 MiB → 68 MiB |
| **`ORDER BY g.doc_id`，不是 `d.doc_id`** | 倒排表主键是 `(term, doc_id)`，固定 term 后天然按 doc_id 有序，SQLite 能顺扫并在 `LIMIT` 处停下。写成 `d.doc_id` 会退化成「把几万条候选排进临时 B 树再取前 20 条」：实测 45.9 ms 对 0.018 ms |
| **索引与提取同一事务** | 增量索引是每个来源的小活（几万片段也只在一次导入里），同步做掉比排任务更可靠；整库重建才是重活，见「没有做到的」 |
| **大小写：只折叠 ASCII** | `lower()` 是 SQLite 的，只处理 ASCII；中文没有大小写。其他语系的大小写折叠没做，写在这里而不是假装支持 |

## 实测：10 万片段

语料与 M0 探针同一形态（同一子句内的词不加分隔，只有子句之间有标点），确定性生成、可复现。**索引表占用来自 `dbstat`**，不是库文件大小——库文件里还有原件文本与派生内容，和 M0 那个「只有索引」的探针库不可比。

| 项目 | 实测 |
|---|---|
| 语料 | 100,000 段 / 3,339,571 字（平均 33 字/段） |
| 导入 + 提取 + 建索引 | **17.3 s**（含文件写盘与提取，不只是索引） |
| 索引表占用 | **86.1 MiB** → **27.0 字节/源字符**（M0 的 jieba+2-gram 方案是 42 字节，降 36%） |
| 倒排行数 / 不同词项 | 5,405,371 / 100,533 |
| 首屏 20 条（妈妈/离职/面试/加班） | **0.029–0.030 ms** |
| 首屏 20 条（面试官） | 0.361 ms（命中少，要扫过更多候选才凑够 20 条） |
| 全量计数 | 42–43 ms（二字查询与「面试官」都是这个量级，原因见下） |
| 召回 | **5/5 全召回**（妈妈 40828、离职 43119、面试 41802、加班 40569、面试官 1971，与子串真值逐条相等） |
| 进程常驻内存 | 25 MiB → 68 MiB（jieba 词典懒加载，含建索引的过程开销） |

平台：Linux（WSL2 x86_64）宿主。**arm64 真机未验证**，模拟器上的数字不能外推到手机。

复现：

```bash
cargo test --release -p diary_core --test search_test -- --ignored --nocapture 十万
```

跑完库文件留在 `/tmp/diary-search-measurement/`，可以直接用 `sqlite3` 看查询计划与表占用（实测脚本会把计数查询计划也打出来）。

### 与 M0 数字的关系

- **体积可比**：27.0 对 42 字节/源字符，都是索引本身的占用。
- **首屏不可直接比**：M0 的 0.068 ms 走的是「分词索引 `LIMIT 40`、**不回原文核对**」的路径，它测的是候选生成，不是命中；这里的 0.029 ms **包含 `instr` 精确核对**，而且顺扫到凑够 20 条就停。两个数字说的是不同的事。
- **全量计数**：M0 测到 84 ms（取并集），这里 42–43 ms。

## 三个必须记住的观察

1. **`ORDER BY` 写哪一列决定生死**。`ORDER BY d.doc_id` 让规划器插了 `USE TEMP B-TREE FOR ORDER BY`：所有候选排完序才取前 20 条，10 万片段上 45.9 ms。改成 `ORDER BY g.doc_id`（倒排表主键的第二列，固定 term 后有序）后是 **0.018 ms**，差 2500 倍。这是本片最大的一处「看起来无关紧要的写法」。
2. **全量计数的代价由「过滤 gram 的候选行数」决定**，不由命中数决定。「面试官」只有 1971 条命中，却和四万条命中的「妈妈」一样要 43 ms——因为它的过滤 gram 是「面试」，命中 41802 行，这四万行都要回原文核对。改法也实测过：按各 bigram 取交集（`面试 ∩ 试官`）候选降到 1971 行，**8.1 ms**。产品路径翻页不需要全量计数（快照带游标），所以没有实现，但数字留在这里。
3. **`search_docs` 里存 36 字节的 UUID 是纯浪费**。初版每行存 `content_id`/`source_id`/`source_revision_id`/`indexed_at` 并配三个索引：那部分占 20 MiB 表 + 13 MiB 索引。来源与内容 ID 在派生内容表里已经有，join 回去即可。删掉之后索引占用 107.1 → 86.1 MiB。**顺带一提，`CROSS JOIN` 固定连接顺序不是性能修复**：SQLite 3.51 上 `JOIN` 与 `CROSS JOIN` 的计划本来就一样（实测 39.1 对 37.8 ms），它的作用是让候选与计数永远走同一种计划。

## 没有做到的

- **没有 `search.start` 会话**：这一片只提供候选取用（`search_candidates`）与精确核对，排序、分页游标、取消、`search_expired` 在 [#31](https://github.com/xingxue-ux/unwritten-diary/issues/31)。
- **`indexes.rebuild` 还没任务化**：核心有同步的 `rebuild_keyword_index`（可带来源范围），契约要求的「返回 jobId、可取消」需要 job runner，与 #31 一起做。
- **索引体积仍然不小**：27 字节/源字符，10 万片段 86 MiB。手机上这是真实代价。任务书提示的两条压缩路径（**高频 gram 剪枝**、**只对短查询启用 2-gram**）都还没试。
- **没有语义索引**：`indexes.status` 里 `semanticIndexReady` 恒为 false、`modelVersion` 恒为空，并明确写进 `reasons`——不让前端以为「已就绪」包含它。[#32](https://github.com/xingxue-ux/unwritten-diary/issues/32) 被 [#17](https://github.com/xingxue-ux/unwritten-diary/issues/17)（ort 退出段 SIGSEGV）与 [#18](https://github.com/xingxue-ux/unwritten-diary/issues/18)（转换产物授权未确认）卡住。
- **没有索引重建期间的并发语义**：核心是一个连接，单进程内天然串行；跨进程同时写库没有考虑。
- **没有容错检索**：简繁/异体字、拼音、错别字、同义词都没有。用户输入什么就找什么。
- **非 ASCII 语言的大小写折叠没有**：土耳其语、希腊语这类会漏。
- **没有索引日记正文与记录草稿**：现在只索引派生内容片段（提取出来的正文）。用户自己写的日记正文、记录草稿要进检索，得在 #31 里连元数据命中一起做。
- **arm64 真机未验证**。
