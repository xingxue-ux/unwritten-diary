B3c 是把关键词检索扩成「关键词 + 语义 + 混合」。这一片只做**第一半**：把「篇」变成可存储、可换代的**块**，把向量的表与代次元数据建好，并让状态如实反映「语义索引还没就绪」。

**这一片不接模型**：没有新依赖、不加载 ONNX、不跑 embedding（不引入 `ort` / `tokenizers`）。所以 `chunk_vectors` 一直是空表、`index_meta` 两列一直是 `NULL`、`embedded_chunks` 恒为 0。真实向量与语义检索是后半的事。

## 一句话结论

**分块只用于向量检索；用户实际看到的内容仍然以「篇」为单位。**

「篇」= 一个来源的正文，或者一条记录自己写的文字。块是为了算向量才把同一天的短篇拼起来的容器，所以它对用户**不可见**，检索结果必须按篇回报（见「消费契约」）。

## 四张表的分工

| 表 | 一行是什么 | 谁是权威 |
|---|---|---|
| `text_chunks` | 一块（B3c-1 打包出来的块） | **没有**权威归属：块可以跨记录，所以这里**没有 `capture_id`**。只有 `ordinal`（同一天内的第几块）、`text`、`day_key`、`chunker_version`、`created_at` |
| `chunk_spans` | 块里的一段 = 一篇 | **这里是权威值**：`capture_id`、`source_id`、`source_revision_id`、`kind`、`coverage`、`start_char`/`end_char` |
| `chunk_vectors` | 一块在某一代次下的向量 | `generation` / `model_version` / `dims` / `storage` / `vector` |
| `index_meta` | 单行（`id = 1`）元数据 | `active_generation`（正在服务检索的那一代）、`building_generation`（正在算的那一代） |

为什么 `chunk_spans` 单独一张表、不做 JSON：`sourceScope` 过滤要能走索引。所以 `source_id`、`capture_id`、`source_revision_id` 各有索引。

派生关系是**级联删除**：删块带走它的 span 与向量。所以重建时**只删「已经不存在」的块**，其余块用 UPSERT 原地更新（内容没变的块 `chunk_id` 不变，它的向量因此留了下来）。

`text_chunks.kind` / `text_chunks.coverage` **只是便于块级过滤的聚合值**，不是权威值：

- 块的 `kind` = 第一段的 `kind`（打包顺序确定，所以「第一段」是确定的）；
- 块的 `coverage` = 各段里**最弱**的那个（`unavailable` < `metadata_only` < `partial` < `complete`）；
- 要判断**某一篇**是什么类型、覆盖到什么程度，一律读 `chunk_spans` 上那一行。

## 块是怎么来的

`Core::rebuild_text_chunks(source_scope)`（实现在 `crates/diary_core/src/chunks.rs`）。正文只从库里已有的东西取，**绝不重新解析原件**：

| 篇 | 正文来自 | `piece_id` | `source_revision_id` | `kind` | `coverage` |
|---|---|---|---|---|---|
| 来源篇 | `source_items.current_revision_id` → `extracted_contents`，再取 `extracted_segments` 按 `ordinal` 用 `\n` 连接 | `source_id` | 当前修订 id | `source_items.kind` | `extracted_contents.coverage` |
| 记录自己的文字 | `captures.draft_text`（trim 后非空才算） | `capture_id` | **空串** | `text` | `complete` |

两处口径值得写下来：

- **用 `\n` 连接片段**，不是空格或直接拼接：B3c-1 的断点只认**段尾（换行）**，把段落粘成一整行会让「段尾断」失效。所以 `chunk_spans.start_char` / `end_char` 是**这个连接结果里**的字符区间；消费者要还原这一段，也按同一条规则拼（不要把区间当成 `extracted_contents.text` 的下标）。
- **记录自己的文字没有 `source_revision_id`**：它不对应任何 `source_revisions` 行，`captures.draft_text` 才是它的正文。`commit` 时确实会造出一个 `text` + `user` 的来源版本，但那是**要被跳过**的那一个（见下）；`revise_text` 之后记录里的来源文字与 `draft_text` 已经不是同一份，硬塞一个修订 id 只会误导消费者。空串就是「这里没有修订」的诚实说法。
- 记录自己的文字的 `chunk_spans.source_id` 写 `capture_id`：关键词那一路的 `groupId` 对记录文字就是 `capture_id`（片段命中才是 `source_id`），语义这一路必须与它一致——这样「按篇上报」对两路是同一条规则：`groupId = span.source_id`。

### 去重规则（一条，别处不要另立）

**`kind = 'text'` 且 `source_revisions.author_type = 'user'` 的来源跳过。**

理由：它的正文就是它所属记录的 `draft_text`（`commit` 复制出来的版本）。不跳过，同一句话就会有两个载体——一条来自 `draft_text`、一条来自这个来源的派生片段——检索结果里会出现两条几乎一样的命中（issue #44 记过这个坑）。规则写在 `chunks.rs` 的 `NOT (si.kind = 'text' AND sr.author_type = 'user')` 里，测试 `the_records_own_text_source_is_not_a_second_carrier` 钉住它。

注意这不是「用户写的正文不索引」：记录自己的文字**照样**进块（B3d 已经把它纳入关键词检索，语义这一路也必须能搜到自己写的话），被跳过的只是那个**重复的载体**。

### 打包与块的 id

打包直接用 B3c-1 冻结的 `chunker::pack_pieces`：先按 `day_key` → `occurred_at` → `capture_id` → 篇内位置 → 篇标识排序，再一次打包。`day_key` 必须排在最前：打包只在「相邻两篇同一天」时合块，按 `occurred_at` 排会让不同日子交错（本地日期与 UTC 顺序可以不一致），于是每篇各自成块、打包规则形同失效。

`chunk_id` 是**库内稳定**的内容哈希（`chunk_<sha256(chunker_version, day_key, text, 各 span 的篇标识与区间)>`），不是随机 UUID：

- **同一个库**里反复重建同一份内容得到同一批 id，排查时只比 id 就看得出「哪些块是新的」；将来把「先删后写」换成「按 id 差量更新」时，这也是让没变的块保住自己向量的前提（`support::new_id` 是带时间戳的 v7 UUID，两次重建必然不同，做不了这两件事）。
- 但哈希输入里有**篇标识**（`source_id` / `capture_id`，同样是 v7 UUID），所以同一份内容**导进另一个库**（或重新导入一遍）会得到**另一批** `chunk_id`。跨库要稳定的东西——排序、当证据的块、摘录、量测数字——**不能**拿 `chunk_id` 当键。issue [#57](https://github.com/xingxue-ux/unwritten-diary/issues/57) 就是同分时先比了 `chunk_id` 造成的；规则见「消费契约」第 6 条。

块内的 `ordinal` 是「这一天里的第几块」：给人看与排序用的，内容变了它就跟着变，**不作为身份**。

## 范围语义

`rebuild_text_chunks` 与 `indexes.status` 共用一套：

| `source_scope` | 含义 |
|---|---|
| `None` | 全库 |
| `Some([])` | **什么都不看**（不是「看全部」）：重建返回 0、不改动已有的块；状态里的 `total_chunks` 是 0 |
| `Some(scope)` | **拥有范围内来源的那些记录** |

**重打包的单位是日子，不是记录。** 分块规则按 `day_key` 合块，所以只重算范围内那几篇会让「同一天的块」随重建范围变化——同一份内容在两次不同范围的重建之后会有两种块边界，可重入就无从谈起。做法是：算出范围内记录所在的那几天，**整日删除、整日重算**。于是「按范围重建」的结果与「全库重建之后取这些日子」完全一致。

代价要说清：范围重建会**顺带重写同一天里范围外那几篇的块**。这是刻意的取舍——只删不建会让那些已经索引过的内容凭空消失，那比多写几行更糟。

状态里的 `total_chunks` 在范围查询下算的是「**至少有一段来自范围里记录**的块」：块可能混着范围外的篇，但它的内容确实属于这个范围。所以带范围的状态数字与「全库状态按天切片」不一定相等，两者口径不同、各自都说真话。

## 消费契约（后半必须照这个来）

这一片不实现语义检索，但规则先定下来，免得下一半各自解释。

1. **检索结果按篇上报。** 同一篇的多个块命中要**折叠**，只留得分最好的那一个（块是容器，不是结果）。
2. **`groupId` 与关键词那一路一致**：片段命中的 `groupId` = `source_id`，记录自己写的文字 = `capture_id`。在块这一路上就是 `chunk_spans.source_id`（记录文字那一段里它写的就是 `capture_id`）。
3. **合块的归属**：一块含多篇时，按 `chunk_spans` **分别归属到各自的篇**——同一块的相似度对这些篇**共享**，不是只归给「第一段」。
4. **snippet 用该篇自己那一段**（`start_char` / `end_char` 圈出的那一截），**不是整块拼接文本**：整块里混着别的篇，给用户看是不对的。
5. **`start_char` / `end_char` 是篇内区间**，不是块内偏移；对来源篇，下标基准是「`extracted_segments` 按 `ordinal` 用 `\n` 连接」得到的正文。测试 `a_chunk_packs_pieces_across_records_and_spans_are_authoritative` 钉住这一点。
6. **排序键与同分兜底是定死的**（issue [#57](https://github.com/xingxue-ux/unwritten-diary/issues/57)）：候选按

   `score DESC → day_key DESC → start_char ASC → end_char ASC → span_ordinal ASC → chunk_id ASC`

   排。折叠在排序**之后**做，所以「同一篇只留第一条」就是「**得分最高、同分时篇内区间起点最靠前**的那一块当证据」。

   同分时**先比篇内区间，不先比 `chunk_id`**：`chunk_id` 的哈希输入里有篇标识（`src_`/`cap_` 前缀的 v7 UUID，见「打包与块的 id」），同一份内容重新建库就会换一批 id——拿它当同分键会让「谁当证据」在两次建库之间抛硬币，同一份数据报出来的摘录会变。`start_char` / `end_char` / `span_ordinal` 只由内容与冻结的切块规则决定，跨库稳定。

   `chunk_id` 只作**最后的全序兜底**：只有两条候选的（日期、篇内区间、段序号）都完全相同才会走到它。那时两条命中的内容已经一模一样，顺序不影响用户看到什么；代价是这种极端同分下结果顺序只在**同一个库内**稳定（用户看到的内容仍是一样的）。回归测试 `equal_score_evidence_is_the_same_across_libraries` 钉住这条规则，并且**验证过退回旧逻辑会变红**。

7. **口径不一致时语义那一路不作数**（issue [#80](https://github.com/xingxue-ux/unwritten-diary/issues/80)）。生效代次的 `model_version` / `dims` / `storage` **三者与当前嵌入器全同**才算同一个向量空间；任一不同就是「跨向量空间算分」——查询向量来自新模型、库向量来自旧模型，余弦**全是垃圾但看起来正常**（有排序、有分数）。所以判据在**进入计算之前**生效（不生成查询向量、不读向量行、不算余弦），整路不作数，由调用方按各自模式如实处理：

   | 模式 | 口径不一致时 |
   |---|---|
   | `semantic` | **空结果 + 明确警告**（不退化成关键词——那会让「语义」这个标签撒谎） |
   | `hybrid` | **退化为关键词**（结果就是关键词那一路），阶段如实停在 `keyword_ready`，**不返回** `hybrid_ready` |
   | `keyword` | **照常可用**（本地优先功能不被它挡住） |

   触发这条的两种真实情形：`Single(旧模型)`（用户换了模型配置、还没重建——**最常见的真实情形**）与历史遗留的 `Mixed` 代次（#58 修复前激活的）。警告必须点名原因与恢复办法：生效的是什么口径、与当前的什么不一样、**重建语义索引（`build_semantic_index`）即可按当前模型整代重算并恢复**。判据与文案的唯一来源是 `semantic::caliber_mismatch` / `CaliberMismatch::reason`。
8. **`dims` 不一致的向量行不静默算分**。余弦的两个向量必须**同维**；不同维时**如实报错**（`CorruptedData`，写清是哪一块、各是多少维），绝不 `zip` 到短的那一段给 0 分或半截分。承担这条口径的是第 7 条的**整代判据**（它在读向量行之前就挡住「整代是另一个模型/另一套维度建的」）；逐行检查只作坏数据兜底，不承担主线。

## 换代流程（building → active）

`index_meta` 的两个代次就是为这件事存在的。**这一片只建结构，不执行**；下面是后半要按着做的顺序：

1. **建块**：`rebuild_text_chunks(scope)`。块 id 是**内容的函数**，所以只有内容真变了的块会换 id——旧 id 的块被删掉（连同它的所有代次向量），内容没变的块原地 UPSERT、**向量保住**。这样换代期间不会有「重建把正在服务的那一代删掉」的空洞。
2. **开新代次**：`building_generation = COALESCE(building_generation, COALESCE(active_generation, 0) + 1)`。**不在原地更新 `active_generation`**：正在服务的检索继续读旧那一代，界面不会突然空掉。
3. **写向量**：往 `chunk_vectors` 写 `(chunk_id, building_generation, model_version, dims, storage, vector)`。模型换了（`model_version` 变）、维度换了（`dims` 变）、存储格式换了（`storage` 变）或切块规则换了（`chunker_version` 变）都必须**开新代次**，不能原地改：新旧向量混在一张表里就没法回滚，也说不清哪条结果来自哪个模型。
   **续跑前先核对口径**：`building_generation` 是上一次中断/取消留下的，若那一代里**已有**的向量有任何一条与当前嵌入器的 `model_version` / `dims` / `storage` 不一致（中途换过模型或换过存储格式），就整代清理（`DELETE FROM chunk_vectors WHERE generation = building_generation`，幂等、不留孤儿行）、按当前模型**从零重算**，不在混合基础上续算。`missing_chunks` 的「已完成」判据也跟着改成「存在**且**口径一致」——只按 `(chunk_id, generation)` 是否存在判断，会把旧模型的半成品当成算好了，剩下的块由新模型补算，最后切出一个混合代次（回归 `switching_models_mid_build_discards_the_half_built_generation`）。
4. **切代次**：全部写完之后，在**一个事务**里 `active_generation = building_generation; building_generation = NULL`。「生效」是一次原子切换，不存在「一半新一半旧」的服务状态。
5. **清理**：`DELETE FROM chunk_vectors WHERE generation < active_generation`。
6. **中断/取消**：`building_generation` 留着，下一轮从它继续；没有半成品会被激活。同口径（同一个模型、同维度、同存储格式）的续跑**复用**已算好的块，不会白重算；换了口径则如第 3 条所述整代废弃重算。

`model_version` 也从这里来，但**不能只看任意一行**：一个代次里若出现不止一种模型版本（历史遗留的混合代次），挑一行报出去就是撒谎。`index_status.model_version` 因此按**整代**给值——整代一致才报那个版本；混了不止一种就报 `None`，同时在 `reasons` 里点名「口径不一致」，并且 `semantic_index_ready = false`（这一代不是同一个向量空间，说就绪等于骗人；检索路径从 #80 起也**不拿它的分数**——整路不作数，见消费契约第 7 条）。正常操作产不出混合代次：第 3 条的核对保证续跑不会混，一次重建也会把历史遗留的混合生效代次按当前模型整代重算、自愈。回归 `a_mixed_active_generation_is_reported_honestly`。

## 退化路径

没有模型、没有向量时，**一切照旧**：

- 关键词检索（`start_search` / `search_candidates` / `count_search_matches`）完全不受块影响：块不进 `search_docs` / `search_grams`，也不动 `search_index_epoch`；
- `IndexStatus.coverage` 仍然只描述**关键词索引**的覆盖程度，不因为块的多少变化；`keyword_index_ready` 同理；
- `semantic_index_ready` 不是写死的 `false`，而是「有一代向量在服务、且这一代把范围内的块都覆盖了」——这一片必然为 `false`，将来某一代被激活会自己跟上；
- `reasons` 里那句「语义索引未就绪」的判断依据是**库里的状态**（生效代次 + 块的向量覆盖），不是写死的常量文案。三段原因与 `semantic_index_ready` **严格互补**——就绪时没有原因，有原因时一定不就绪：

  | 库里的状态 | 原因 |
  |---|---|
  | `active_generation IS NULL` | 还没有生效的向量代次（这一片还没有接模型） |
  | 有生效代次，但没有块 | 范围内还没有文本块 |
  | 有生效代次，但向量没覆盖完 | 生效代次只覆盖了 N 块里的 M 块 |

  这一片只会走到第一句；后两句是换代中间态要用的，测试 `status_follows_the_active_generation` 用直接改 `index_meta` 的方式把三种状态都跑了一遍（产品路径现在还到不了后两种）；
- 没有块的时候（还没重建、或库里真的没内容）状态报 `total_chunks = 0`、`embedded_chunks = 0`，不报错。

测试 `keyword_search_is_untouched_by_chunks_without_a_model` 与 `status_reports_chunks_and_stays_honest_about_semantics` 钉住这一整条。

## 迁移（v7 → v8）

v8 是**纯增量**：四张新表 + 一条 `index_meta` 初始行，`SCHEMA_VERSION` 7 → 8。**不回填块**——块是派生数据，`extracted_contents` / `captures.draft_text` 才是事实来源；把整库重算塞进开库路径是重活，而这一片还没有任何消费者需要历史块。

v7 的关键词回填不能照搬这个理由：那边不回填会让「以前搜得到的话现在搜不到」，是用户直接看得见的退化；块对用户不可见。

测试 `v7_library_migrates_to_v8_without_backfilling_chunks` 钉住「旧表一行未动 + 新表为空 + 之后能重建」。

## 模型接入（bge-small-zh-v1.5，我们自导出的 ONNX）

- **配置**：`DIARY_MODEL_DIR`（模型目录）与 `DIARY_ORT_DYLIB`（ORT 动态库；兼容探针一直用的
  `ORT_DYLIB_PATH`）。两个都设了才启用语义一路；**没配就是退化路径**（关键词照旧、`semantic_index_ready = false`），
  报错信息会区分「缺目录」「缺动态库」「加载失败」「维度不符」，不一律说「语义未就绪」。
- **模型版本**：`bge-small-zh-v1.5-ours@<模型文件 sha256 前 12 位>`（本机实测 `…@d44978e451a0`）。
  换模型文件必然换代，不会新旧向量混在一张表里。
- **依赖形态**：核心直接依赖 `ort`（`load-dynamic`）与 `tokenizers`——构建期**不下载二进制、不链接 .so**，
  所以没有模型没有 ORT 的 CI 机器照样能编过。真实实现参与 clippy/test 编译；CI 只跑注入 stub 的换代逻辑。
- **生命周期照 #17**：进程级单例、退出不释放（`libonnxruntime.so` 的 C++ 静态析构会在退出阶段崩）。
- **内容永久不写进被向量化的正文**：正文只放正文，文件名/日期/来源类型不进向量（过滤与排序用元数据）。

### f32 vs int8 与 10 万块的投影

| 存储 | 每向量 | 向量间余弦（对 f32） | 召回 | 10 万块裸向量 |
|---|---|---|---|---|

## 混合检索（RRF）（#51，B3c-3；两阶段 #69）

`SearchMode::Hybrid` 在这一片**真实现**了（此前只给「未实现」警告并降级到关键词）。
代码在 `crates/diary_core/src/search_session.rs`：第一阶段 `hybrid_start`、融合
`fuse_hybrid`、升级入口 `upgrade`（`Core::upgrade_search_to_hybrid`）。口径是可审计常量：

```
HYBRID_FUSION_VERSION = "hybrid-rrf-k60-depth50-over200-min0.40"
RRF_K = 60 · RRF_CANDIDATE_DEPTH = 50 · RRF_KEYWORD_OVERSCAN = 200 · HYBRID_SEMANTIC_MIN_SCORE = 0.40
```

`k` / 候选深度 / 关键词扫描窗口 / 语义门槛任何一项变了都要改这一行（照 `CHUNKER_VERSION` 的先例），
有一条测试 `hybrid_fusion_constants_are_frozen` 钉住它。**没有**在 36 条合成语料上
调参：那个规模撑不起「调出来的最优」，留下的只有过拟合痕迹。

### 两阶段：先 `keyword_ready`、再 `hybrid_ready`（#69）

#51 的混合是**一次算完**的：`search.start(mode = hybrid)` 直接返回融合结果、`phase`
恒为 `done`，契约里的 `hybrid_ready` 是个**死值**——产品路径永远观察不到。#69 把
「什么时候给哪一阶段」改成分步，**融合怎么算一个字没动**：

```
search.start(mode = hybrid)   → phase = keyword_ready
                                只算关键词那一路；不含只被语义召回到的篇；
                                matchedBy 只有 [keyword]
search.upgrade(sessionId)     → phase = hybrid_ready
                                这时才 RRF 融合 + 重排；matchedBy 如实更新
翻页（若还有下一页）           → phase 保持 hybrid_ready；翻完最后一页 → done
```

- **首屏不等模型**：第一阶段只读生效代次 / 块数与 `embedder_readiness`（env + stat），
  不建 ORT 会话。模型加载与查询向量 + 全表余弦都留在升级那一步；
- **升级前翻页 / 快照只给关键词结果**，阶段一直是 `keyword_ready`——诚实，不假装融合过；
- **升级幂等**：重复调用返回同一份快照，不重复算向量（stub 测试用嵌入器调用计数钉住）；
- **升级后从头给融合结果**（游标按融合后的第一章重置，并**递增结果代次**）：融合改变了顺序，
  「第几页」已经没有意义。升级前发出的**所有**游标都会被 `cursor_expired` 拒绝——包括第一页
  那个与融合后第一页偏移相同的（`pageSize = 2` 时都是 2；只看偏移会把两个阶段的结果拼起来，
  #71）。幂等升级不递增代次，升级后发出的游标继续可用；
- **语义拿不出可融合的证据就不升级**，两种情形一个口径：**不可用**（没配模型 / 加载失败 /
  没有生效代次 / 没有块）与**可用但没有可融合的证据**（候选全被 `HYBRID_SEMANTIC_MIN_SCORE`
  滤掉；查询是空的、一条候选都没有）→ 返回**关键词那份快照**、阶段仍是 `keyword_ready`，
  `warnings` 写清原因（`Unavailable` 那句「没有可融合的语义证据」，或 `NoEvidence` 那句
  「这一路没有贡献结果」）。**绝不**假装 `hybrid_ready`；结果集没换，所以代次不递增、
  升级前的游标继续可用（#60 复审）；
- **取消 / 过期 / 非混合会话不静默**：已取消返回 `cancelled` 快照；索引变了报
  `search_expired`；`mode != hybrid` 报 `invalid_state`；
- **空查询**走同一条规则：`start` 给空结果 + 「查询是空的」；升级时两路都空、没有任何
  可融合的证据，阶段仍如实停在 `keyword_ready`（空不等于假装融合过）。

**融合口径不变、数字也不变**：36 条质量集的混合 R@1 97% / R@10 100% / MRR 0.984、
`no_answer` 4/4 空、`matchedBy` 43（keyword 独占 0 / 语义独占 12 / 两者 31）与 #51
基线逐项一致（探针改成 start + upgrade 之后量的是融合后那份快照，见下）。

**渐进式的延迟**（同一次真模型量测，36 条各一次；嵌入器已注入、模型已加载）：

| 步骤 | 中位 | 均值 | p95 | 最大 |
|---|---|---|---|---|
| 关键词首屏 `search.start`（只算关键词那一路） | 1.86 ms | 2.17 ms | 4.61 ms | 6.10 ms |
| 升级 `search.upgrade`（查询向量 + 全表余弦 + RRF 合并） | 2.04 ms | 2.37 ms | 6.21 ms | 7.13 ms |
| 合计（首屏 + 升级） | 4.11 ms | 4.54 ms | 9.80 ms | 13.23 ms |

首屏只花「两步合计」的约 45%（1.86 / 4.11 ms），用户不必等语义那一路。这份合成语料很小，
升级那一步主要就是一次查询嵌入 + 全表余弦；**真正的省钱点在别处**：首屏不建 ORT 会话，
探针里嵌入器是预先注入的，量不到模型加载那一笔（产品里若模型还没加载，升级会额外付它）。

**延迟是这些数字里唯一会抖的**：同机复跑一次（与一个 release 构建并行）中位变成
首屏 1.85 ms / 升级 2.53 ms；两次复跑里 R@1 / R@10 / MRR / `no_answer` / `matchedBy` /
阈值扫描表**逐字节一致**，只有毫秒数不同（上表取独占机器的那一次）。

### 融合与排序

- **公式**：`score(篇) = Σ_paths 1 / (RRF_K + rank_path(篇))`，`rank` 从 1 起，`RRF_K = 60`
  （Cormack 等 2009 的常用值）；
- **候选深度**：两路各取前 **50 篇**再融合。关键词那一路的候选要折叠、还要算正文哈希，
  所以只为排序最靠前的 **200 条文档**读正文（`RRF_KEYWORD_OVERSCAN = 4 × 深度`）：
  正常数据足够折出 50 篇，病态数据会少一些（见「没有做到的」）；
- **融合单位是篇**：语义那一路本来就是按篇折叠的（消费契约第 1 条）；**关键词那一路不是**
  ——一个来源可以被抽成多段，每段一个索引文档，所以混合里要自己按 `groupId` 折叠
  （issue #51 的正文说「两路各自已按篇折叠」，对语义成立、对关键词不成立，见「没有做到的」）；
- **关键词的并列名次**：关键词这一路没有分数，名次就是它的排序位置。`sort_key` 的前三项
  （日期、出现位置、家族）都相同时视为**并列**、取同一名次（competition ranking）。第 4 项是
  库内的 `doc_id`，拿它给两篇同分内容发不同的 RRF 分，等于让融合结果跟着建库顺序走；
- **排序**：`score DESC → day_key DESC → 正文哈希 ASC → groupId ASC`。对外口径是
  **相关度优先，同档按时间降序**；
- **同分键跨库确定**：正文哈希（`support::content_hash`，sha256）**只由内容决定**。
  不用 `chunk_id` / `source_id` / `hit_id`——它们的哈希输入或本身带每库不同的 v7 UUID
  （issue [#57](https://github.com/xingxue-ux/unwritten-diary/issues/57) 的教训）。`groupId`
  只作最后的全序兜底：走到它时两边的正文哈希已经相同（内容一样），先后不影响用户看到什么；
- **`matchedBy` 如实**：两路都中就是 `[keyword, semantic]`。一条融合命中只出一条结果，
  正文取**关键词那份**（它带高亮）；语义那一路没有「哪几个字对上」这回事，不给假高亮；
- **覆盖状态**：取两路里较弱的那一个（一路没覆盖完，融合结果就可能不完整）。

### 语义证据门槛（阈值怎么定的）

纯语义是 kNN，对任何查询都会返回「最像的几条」：4 条 `no_answer` 实测 **4/4 都返回结果**
（最高分 0.32 / 0.24 / 0.27 / 0.38），这是 B3c-2 就记下的最大风险。规则：

- 语义候选的余弦**低于门槛**就算「这一路没有证据」，不参与融合；一条都不剩时语义这一路
  不贡献结果；
- 关键词那一路空 + 语义无证据 → **返回空**，并在 `warnings` 里写明（「低于证据门槛」
  与「两路都没有达到证据门槛」）——不为「有结果」放宽。

通过 `Core::set_hybrid_min_score_for_test` 换阈值，融合代码不另写一套）。

- `keyword_only` / `time_filter` / `long_transcript` 都是 **100%，没有变差**；
  `contradiction` 从语义的 40% 回到 **100%**（推导见下）；
- **融合开销看得见**：混合中位延迟 2.4–3.2 ms，比关键词（1.3–2.0 ms）与纯语义（1.3–2.0 ms）
  都高一点——两路候选 + 合并，而语义那一路仍是全表扫描（B5 待办）。**注意**：这一列是
  #51「一次算完」时量的；#69 改成两步后，探针把 `start` + `upgrade` 都算进「一次查询」，
  重新量的数字与拆分见上一节的延迟表（混合中位变成 3.6–5.2 ms，多出来的正是关键词首屏）；
- 命中广度 **1.2** 个来源/条（关键词 0.9、纯语义 2.4）：比纯语义收敛，没有让语义的噪声
  淹没关键词的精确命中；
- **`no_answer`：混合 4/4 返回空**（纯语义 0/4）。

**为什么 `contradiction` 回到 100%**：每条 case 只有两篇（A 早、B 晚），两路都把两篇收进候选。

- 关键词名次是 B=1、A=2（日期降序）。语义名次若与它一致（B=1、A=2），RRF 分 B 更高 → B 在前；
- 语义名次若**相反**（A=1、B=2），两篇的 RRF 分都是 `1/61 + 1/62`，**完全相同**，落到时间降序
  → 仍然是 B 在前。

两种情形都是「更晚的那一份」在前——这正是新口径「相关度优先，同档按时间降序」在质量集上的
表现，也是那 5 条 `expectedSourceIndex` 可以照旧不改的原因（标注约定见
[M2 · 质量集与分块](m2-质量集与分块.md)）。

### 退化与诚实

- 语义未就绪（没模型 / 没生效代次 / 没有可用的块）→ 混合第一阶段就**退化为关键词**，
  并在 `warnings` 里明说（「混合检索退化为关键词：…；这次只跑了关键词那一路（不是静默降级）」）。
  退化不报空结果：关键词那一路本来就能用，把它藏起来才是骗人；
- 退化之后**升级也不撒谎**（#69）：`search.upgrade` 返回的仍是关键词结果、阶段仍是
  `keyword_ready`，只多一句「升级到混合检索没有可融合的语义证据：…」——绝不假装
  `hybrid_ready`；
- **语义可用、但候选全被证据门槛滤掉**（#60 复审）走的是同一条「不融合」的路，只是状态记成
  `NoEvidence` 而不是 `Unavailable`：保留关键词那份快照与 `keyword_ready`，警告是
  「语义一路最像的内容相似度 …，低于证据门槛 …，这一路没有贡献结果」；结果集没换，代次
  不递增、升级前的游标继续可用；
- 纯语义（`mode = semantic`）**不退化**：未就绪时空结果 + 诚实原因——B3c-2 的口径没变；
- **换模型未重建（跨向量空间）同样不作数**（#80）：生效代次与当前嵌入器口径不一致时，
  混合在候选计算**之前**核对口径（第一阶段在嵌入器已加载时核对、升级在模型刚加载出来时
  再核对一次；两条都不加载模型也不读向量行），不一致就**不融合**——保留关键词那份快照、
  阶段停在 `keyword_ready`，警告点名原因与恢复办法：「当前生效的向量代次是用另一个模型
  （或另一套口径）建的：…（… 维、… 存储），其中 N 行与当前嵌入器 …（… 维、… 存储）
  口径不一致，两边不是同一个向量空间；跨空间的余弦相似度不作数，所以语义这一路不参与。
  重建语义索引（`build_semantic_index`）即可按当前模型整代重算并恢复」；纯语义给
  **空结果 + 同一条警告**（不退化成关键词）；关键词照常。重建之后警告消失、混合回到
  `hybrid_ready`。回归 `switching_models_without_rebuild_keeps_semantic_out_of_both_paths`
  （`Single(旧模型)`：模型 B 与 A 的 `model_version` / `dims` 都不同）、
  `a_mixed_generation_keeps_semantic_out_of_both_paths_until_rebuild`（历史遗留的 `Mixed`）、
  `a_dims_mismatch_is_blocked_before_any_cosine`（`dims` 不一致的行内自洽向量：整代判据
  在算余弦前挡住；行内自洽但字节与记录不符的坏数据如实报错）——**三条都验证过把判据去掉会红**；
- 语义建索引中途（有 `building_generation`）→ 检索继续用 `active_generation`（与 B3c-2 一样）；
- 混合会话的指纹**带上语义生效代次**（与纯语义一样）：向量换代之后旧快照作废，不会把过期的
  融合顺序糊在新界面上。

### 同分确定性与测试

测试 `hybrid_tie_break_is_the_same_across_libraries`（照 #57 的方法）：同一进程里建 **12 份**
独立库，每份都是「同一天两篇、正文都以查询词开头」——关键词的出现位置与家族都相同、名次并列，
RRF 分相同；语义这一路对这两篇都过不了门槛（向量与查询正交），分野只剩同分键。为了让融合
真的发生（#60 复审：语义全被门槛滤掉时不融合），另放**另一天**的第三篇只被语义命中、RRF 分
同样是 `1/(k+1)`——它排在 A/B 之后，不动 A/B 的并列关系。断言每份库里 A/B 都是**正文哈希
升序**，且 12 份完全一致。两篇的哈希顺序与「先建库的那一篇在前」**相反**，所以
**临时退回旧键（同分先比 `groupId`）第 0 轮就红**（验证过）：

```
left:  ["25aab618…123e"(A), "0702a773…0663"(B)]   ← 旧键：groupId（建库顺序）在前
right: ["0702a773…0663"(B), "25aab618…123e"(A)]   ← 正文哈希升序
```

CI（无模型、无 ORT）覆盖：

  关键词有结果、语义全被门槛滤掉 → **不融合**：阶段 `keyword_ready`、结果与升级前关键词

## 没有做到的

- **arm64 真机仍未验**：模型加载与推理只在 Linux 宿主 / Windows x64 / Android **x86_64 模拟器**上量过（M0 第 3 节）。模拟器数字不能外推到手机——这比换模型更该先补；
- **查询时全量载入向量（这一片最大的短板）**：当前实现把生效代次的全部向量读进内存再算余弦，10 万块 f32 = **195 MiB/次查询**。mmap / 低精度存储 / ANN 索引布局都没做，排序与质量变化也没量过。小库（几千块）可用，10 万块这一档现在不能上 → B5；
- **CI 跑不到真实模型**：CI 里没有权重也没有 ORT 动态库，只能跑**注入 stub** 的换代逻辑与退化路径。真实模型的量测是手动命令（见上），不进 CI；
- **int8 只在小语料上验过**：与 f32 召回一致（36 条合成语料），但不足以支撑改默认存储；等真实数据。**换存储格式按换口径处理**：`storage` 是口径三字段之一，中断留下的旧格式半成品在续跑时整代废弃重算（回归 `a_half_built_generation_with_a_foreign_storage_format_is_discarded`）；
- ~~混合检索还没做~~ → **已做**（#51，B3c-3）：RRF 融合 + 语义证据门槛（0.40，扫描表见上），
  `no_answer` 回到 4/4 空、`semantic_only` 从 0% 到 83%、三类对照 R@1 97%；
- **渐进式的升级要调用方显式发起**（#69）：`search.upgrade` 不是后台任务，核心不会在
  `start` 之后自己接着融合；融合本身也**不可中途取消**（`search.cancel` 管的是后续翻页，
  不是打断一次已经在跑的同步 `upgrade`）；没有自动升级、没有「语义超过 X ms 就放弃」的
  超时预算。产品什么时候补这一轮由界面决定；
- **延迟表量的是「嵌入器已注入」**：探针里模型在量测前就 `set_embedder` 好了，所以
  「首屏不建 ORT 会话」这一点在数字上看不出来；真实产品里模型没加载时，首屏与升级的
  差距会比这张表更大（升级那一步多一次模型加载），这一条没有实测；
- **关键词扫描窗口 200 条文档是个拍出来的上界**：它只保证「正常数据能折出 50 篇」，
  没有量过真实库里的段落分布；病态数据（前 200 条都是一个来源的段）会让关键词一路
  贡献少于 50 篇，这一条只在注释与这里说明，没有测试（构造 200 段同一来源的语料成本
  比它证明的事大）；
- **融合口径（k=60、深度 50）没有调参、也没有真实数据校验**：这两个值取的是文献常用值与
  一个整数深度，只在 36 条合成语料上验过「不比单路差」，换真实语料要重量（尤其深度：候选
  深度影响的是「两路各取前 50 篇」这个上限什么时候起作用，小语料根本碰不到）；
- **阈值 0.40 只有 4 条 `no_answer` 撑着**：可行窗口 (0.376, 0.411) 很窄，而且窗口上界是
  `sem-04` 的期望来源（0.411）——换语料/换模型都要重扫这张表，不能把这个数当常数搬走；
- **「关键词独占」（`matchedBy = [keyword]`）在质量集上没有样本**：这批语料里关键词命中的篇
  几乎都被语义同时命中；那一路只有 stub 测试覆盖；
- **关键词那一路在混合里被按篇折叠了**，而它自己（`mode = keyword`）仍按抽取片段出结果：
  同一个来源被抽成多段时，两种模式看到的「一条结果」粒度不同。issue #51 的正文以为两路都已
  按篇折叠——实际只有语义那一路是。要不要把纯关键词那一路也改成按篇上报是另一个决定（会动
  既有的关键词排序与量测口径），这一片没做；
- **本页语义那一路的数字从 88% 变成 84%**（`keyword_only` 从 100% 掉到 91%）：本页那组数字
  是 #57 的同分兜底改动**之前**量的，`keyword_only` 里有一条第 1 名翻转。混合不依赖这个差异
  （那一条在混合里仍是 R@1），但读数的人要知道两组数字不是同一次量出来的；
- **后台任务化还没做**（B5）：现在 `build_semantic_index` 是同步入口。按实测外推，10 万块在桌面约 280 秒、Android 模拟器约 10 分钟——真机未知，不能同步跑在用户路径上；

- **桥接还没有产块入口**：`rebuild_text_chunks` 只在核心侧可调，`packages/diary_bridge` 只带出了新增的状态字段。产品路径上「什么时候重建块、要不要做任务化」是后半的事（与向量构建一起）；

- ~~中断后换模型续跑会混用不同模型的向量~~ → **已解决**（评审 #58 第二轮的发现）：`build_generation` 遇到已有的 `building_generation` 不再无条件沿用——续跑前核对那一代里**每条**已有向量的 `model_version` / `dims` / `storage`，只要有与当前嵌入器不一致的就整代清理、按当前模型从零重算；`missing_chunks` 也只把「存在**且**口径一致」的行算已完成；`index_status.model_version` 按**整代**给值（历史遗留的混合代次报 `None` + `reasons` 点名口径不一致，且不说就绪）。回归 `switching_models_mid_build_discards_the_half_built_generation` 与 `a_mixed_active_generation_is_reported_honestly`，**验证过退回旧逻辑会变红**；
- ~~换模型未重建就搜索会跨向量空间算分~~ → **已解决**（#80）：#58 已经备好的口径判据接到**检索路径**上——`semantic::candidates` 在生成查询向量/读向量行**之前**比对整代口径，不一致就返回 `ForeignSpace`（语义这一路不作数）。混合退化为关键词、阶段 `keyword_ready`；纯语义空结果 + 同一条可执行警告；关键词照常；重建后自动恢复。`cosine` 不再 `zip` 到短的那一段：不同维如实报错。判据与文案的**唯一来源**是 `semantic::caliber_mismatch`（消费契约第 7、8 条）。回归 `switching_models_without_rebuild_keeps_semantic_out_of_both_paths`、`a_mixed_generation_keeps_semantic_out_of_both_paths_until_rebuild`、`a_dims_mismatch_is_blocked_before_any_cosine`，**验证过把判据去掉会红**（`Single(旧模型)` 那条从 `keyword_ready` 变回 `hybrid_ready`）；
- **改过的正文：语义这一路现在会缺** → 决策已定，实现见 **#54**：**改过的正文当成新的一篇**（日期等元数据不变），**旧正文不再被直接搜到**，查看新正文时再提供「看原正文 / 看修改部分」。实测过现状：`revise_text` 造出的新修订没有原件、提取报 `InvalidState`，所以**新正文进不了索引、旧正文照样能搜到**——正好相反。要做的三件事（新修订能进索引、检索只看当前修订、能按需取上一版正文）都记在 #54；本片的 `collect_pieces` 已经是「取当前修订」，与那个方向一致；
- **分块是整库/整日粒度，没有增量**：改一条记录会重打包它所在的那一天（不是那一条记录）。对「一天几十条短记录」的真实数据，代价与影响面都没有量过；
- **块级聚合 `kind` / `coverage` 的取值规则是这一片定的**（第一段 / 最弱），没有真实消费者验证过它够不够用；
- ~~`index_bytes` 没算块与向量表~~ → **已补**：dbstat 的查询现在包含 `text_chunks` / `chunk_spans` / `chunk_vectors` / `index_meta` 及其索引；
- **回收站里的记录照样进块**：与 `rebuild_keyword_index` 保持一致（那边也不按 `state` 过滤，过滤发生在检索时）。代价是块会比「检索能看到的篇」多，没有量过；
- **范围重建会重写同一天里范围外的块**（见「范围语义」）：这是一个刻意的取舍，但它意味着按范围重建**不是**「只碰范围内的内容」，调用方不能拿它当隔离的写操作；
- **`text_chunks` 没有 `capture_id`**（块跨记录，本来就不成立），所以「按记录删块」这类需求只能走 `chunk_spans`；`text_chunks.day_key` 上的索引是给「整日重打包」用的；
- **只在 Linux（WSL2 x86_64）宿主验过**，Android/Windows 未验（这一片不涉及模型，风险主要在 SQL 与打包顺序，与平台无关）。
