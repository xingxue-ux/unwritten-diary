### 0.2 三句话版本

- **能用的链路**：录音 → 2 秒分片 → `finalize` → 转写任务；今日/历史列表与条目详情
  （`captures.list/get`）；关键词/语义/混合检索（`search.start` + `nextPage` +
  `upgrade` + `cancel`，`mode=semantic` 需要 `WITH_SEMANTIC=1` 构建）；任务中心逐条
  （`jobs.list/get` + `retry/cancel/acknowledgeAttention`）；索引就绪与重建进度
  （`indexes.status` + `jobs.get.progress`）；本机转写配置；语义重建任务
  （只排队，真正跑要 `jobs.runDue`）。
- **当前 main 还缺的**：只剩 `#136` 要求的**前端入口**（设置页「一键重建语义索引」、
  `semantic_index_ready=false` 时显眼提示；见 `#140`）。C ABI 侧的 `captures.get/list` /
  `indexes.status` / `jobs.*` / `search.nextPage/upgrade/cancel` 已在 #143 接齐
  （30 条，§8.1/§10.1）。`search.snapshot`、`jobs.nextWakeup`、`core.events` 仍没接，
  所以搜索快照恢复和事件推送只能靠轮询或重新发起查询。
- **所有 30 个契约方法都是同步阻塞的**。不要在主线程调 `search` / `runDueJobs` /
  `extract` / 大库上的 `coreInfo`；用 TaskPool worker，见 §1.2。

### 0.3 包与模型的一句话账

| 构建 | 包内有什么 | signed HAP | 关键词 | 语义 | 转写 |
|---|---|---:|---|---|---|

## 1 分层、线程与生命周期

### 1.1 从 ArkTS 到核心的三层

```text
ArkTS 页面 / VoiceRecorder
  │  import { DiaryCore } from '../core/DiaryCore'
  ▼
DiaryCore.ets        拼 {"method","params"}、拆信封、ok:false → DiaryError
  │  diaryNapi.call(handle, json) / open(path) / close(handle)
  ▼
libdiary_napi.so     C++ NAPI shim（7 个同步函数，句柄 id 表）
  │  dlopen + dlsym
  ▼
libdiary_capi.so     Rust：diary_open / diary_call / diary_close / diary_capi_version /
                     diary_string_free / diary_last_error（JSON 进 / JSON 出）
```

- C ABI 一共 6 个导出符号，签名见
  [`m6-核心-C-ABI.md` §4.1](m6-核心-C-ABI.md#L61-L75)；
- `diary_call` **永远返回信封 JSON**：成功是
  `{"apiVersion":"1.0","data":…,"ok":true}`，失败是
  `{"apiVersion":"1.0","error":{"code":…,"message":…,"retryable":…},"ok":false}`；
- `DiaryCore` 把 `ok:false` 变成 `DiaryError` 异常。业务代码用 `try/catch`，
  不要自己解析信封；需要原始信封排障时用 `rawEnvelope()`。

**能力清单**：`core.info.capabilities` 是「已经接到 C ABI 的方法名」，
不是「这个安装包能不能做这件事」。例如默认 HAP 没装 ORT 1.29.1，
`capabilities` 里仍然会有 `indexes.rebuildSemantic`，但语义索引跑不起来。
不要用 `capabilities` 判断包的能力（见 §5.8）。

### 1.2 同步阻塞：不要在 UI 线程调核心

`DiaryCore` 的 30 个契约方法都是**同步**的，直接在调用线程上跑 SQLite / 推理 / 音频处理。
仓库实测（真机 HAD-W32 / API 23）：

| 调用 | 实测耗时 | 说明 |
|---|---:|---|
| Smoke（`open` + `core.info` + `runDue`） | 中位 **268 ms**，事件循环额外延迟 **99–129 ms**，约 **16–17 帧** | 产品在主线程直接调会明显卡顿 |
| `jobs.runDue` 一轮 | **687 ms** | 有活任务时更久 |
| `sources.extract` 大文本 | **305 ms** | 未含转写 |
| 语义重建（bge 加载 + 两条日记切块/向量） | **323–401 ms** | 不含后续转写 |
| 转写冷启动（239.5 MB 模型 + 推理） | **3,440–3,573 ms** | 必须后台 |

来源：[`README` 第 7 项](../../apps/ohos-diary-core/README.md#L731-L747)、
[`README` 问题清单](../../apps/ohos-diary-core/README.md#L895-L901)、
[`DiaryCore.ets` 头注释](../../apps/ohos-diary-core/entry/src/main/ets/core/DiaryCore.ets#L14-L16)。

**推荐做法**：把「打开 + 重活」放到 TaskPool worker；worker 里用同一个资料库路径
`DiaryCore.openInDirectory(filesDir)`，不要试图把 `DiaryCore` 对象传过去（句柄字段私有、
TaskPool 只传可序列化值）。仓库已有 worker 示例：

- [`ConcurrentWorker.ets`](../../apps/ohos-diary-core/entry/src/main/ets/verify/ConcurrentWorker.ets)：
  `callSameHandle` 传 handle id；`openAndCall` 在 worker 里自己 open/close；
- 真机结论：「同一句柄 2 个 worker + 主线程，800+800+500 次，0 error；
  各自 open 同一路径 1200+1200 次，0 error；无 panic/死锁」
  （[`README` 第 8 项](../../apps/ohos-diary-core/README.md#L750-L774)）。

**不要**在 `readData` 回调里做核心重活：录音链路已经只在片段封闭时
`registerSegment`（2 秒一次）、每秒一次 `updateState`，常规回调只写文件 + 增量哈希
（[`VoiceRecorder.ets`](../../apps/ohos-diary-core/entry/src/main/ets/recording/VoiceRecorder.ets#L18-L19)）。

### 1.3 生命周期

```ts
const core = DiaryCore.openInDirectory(context.filesDir); // <filesDir>/library.sqlite
try {
  const info = core.coreInfo();
  // ...
} finally {
  core.close();
}
```

- `open(libraryPath)` 的 `libraryPath` 是**文件路径**，不是目录；
- 同一路径多次 `open` 会共享同一个核心，**最后一个句柄关闭**才真正释放 SQLite；
- `close()` 重复调用是 no-op；关闭后任何调用都抛 `invalid_state`；
- `open` 失败会抛 `DiaryError`：`permission_denied` / `storage_full` /
  `invalid_argument` / `native_unavailable`（原生库没打进包时）；
- 产品建议：**应用级打开一次**，Ability 销毁时在停止录音、停掉 worker 之后才 `close()`。
  不要在录音/任务运行时关闭。

诊断用（不要放进主界面）：

| 方法 | 用途 |
|---|---|
| `DiaryCore.version()` | 版本戳，例如 `diary_capi/0.1.0 apiVersion=1.0` |
| `DiaryCore.nativeLibraryDir()` | 原生库加载目录，排查打包问题 |
| `DiaryCore.openHandleCount()` | 所有 `DiaryCore` 都 close 后应为 0 |
| `rawEnvelope(method, params)` | 原始信封，只在用户同意的诊断包里用（可能含正文） |

### 2.2 每个动作的最小流程

#### 说话记录

```text
权限（ensureMicrophonePermission）
  → createDraft（拿 capture_id / revision=1）
  → recordings.prepare（拿 recording_id / asset_id / staging_ticket）
  → 长时任务 + setWindowKeepScreenOn(true)
  → AudioCapturer（16 kHz / 单声道 / 16 bit）
  → 每 2 秒封一段：registerSegment（核心重算哈希/字节数）
  → 每秒：updateState(recording, elapsed_ms=received, persisted_through_ms=persisted)
  → 停止：停采集器 → 封最后一段并 registerSegment
  → updateState(stopping, received, persisted)
  → recordings.finalize(last_segment_index, end_reason)
  → 释放常亮 + 长时任务
  → jobs.runDue（在 worker 里）→ 转写
```

- 不要自己实现录音链路：直接用
  [`VoiceRecorder.ets`](../../apps/ohos-diary-core/entry/src/main/ets/recording/VoiceRecorder.ets)；
- `VoiceRecorder.start()` 内部已经做了 `createDraft` / `prepare` / 长时任务 / 常亮 /
  `AudioCapturer`；
- 页面只负责权限、按钮状态、计时、错误提示、恢复提示；
- **`VoiceRecorder` 只调 `finalize`，不调 `commit`**：录音结束后 capture 仍是 `draft`
  （来源和转写已经建好，搜索得到）。如果产品要求「正式记录 / 今日列表里是 committed」，
  需要另外 `commit`；`finalize` 已经把 capture revision +1，**用 `captures.get` 读回
  `revision` 再 commit，不要猜**（见 §7.3）。

#### 搜索

```ts
const first = core.search({
  request: {
    query,
    mode: 'hybrid',        // 或 'keyword' / 'semantic'
    page_size: 20,          // 最大 100
    filters: { from_day_key: '2026-10-19', to_day_key: '2026-10-19' }
  },
  query_revision: 1
});
// 还有下一页：首屏 phase 会是 keyword_ready（keyword/hybrid）或 done（semantic 一次算完）
const next = first.cursor === null ? null : core.nextPage({ session_id: first.session_id });
// 只有 mode=hybrid 能升级：显式调用才有融合结果；语义拿不出证据时仍停在 keyword_ready + warnings
const upgraded = core.upgradeSearch({ session_id: first.session_id });
```

- `results` 是**当前页的完整快照**，不是增量；不要拿两份快照拼；
- `matched_by` 是数组：`["keyword"]` / `["semantic"]` / `["metadata"]`；
- `highlights` 的下标相对 `snippet`，不是相对全文；
- `locator` 对音频有 `start_ms` / `end_ms`，可直接做「跳到这段」；
- `cursor` 是不透明字符串：翻页时原样回传，省略则用会话记着的下一页；**不要解析或自己拼**
  （§7.1/§7.4）。

#### 看今天 / 历史列表 / 条目详情

```ts
// 今日列表：day_key 是当天的 YYYY-MM-DD；历史列表省略 day_key
const today = core.listCaptures({ day_key: '2026-10-19', limit: 20 });
// 翻页：next_cursor 原样回传；null = 没有下一页
const next = today.next_cursor === null
  ? null
  : core.listCaptures({ day_key: '2026-10-19', cursor: today.next_cursor, limit: 20 });
// 详情：revision / state / ordered_source_ids / processing_summary
const detail = core.getCapture({ capture_id: today.captures[0].id });
```

- 列表按 `occurred_at DESC, id DESC`；`limit` 默认 20、核心夹 1–100；
- `captures.get` 对草稿和已提交都可用；录音 `finalize` 之后用 capture id 读回新 `revision`；
- `draft_text` 是草稿正文；`processing_summary` 给转写/索引状态摘要，不要自己从计数推。

#### 看转写

```ts
const content = core.extract({ source_ref: revisionId }); // 来源 id 或修订 id
```

- `source_ref` 来自 `SearchHit.revision_id` 或 `SearchHit.source_id`；
- `status`：`pending` / `processing` / `ready` / `partial` / `failed` / `stale`；
- `coverage`：`complete` / `partial` / `metadata_only` / `unavailable`；
- `coverage_reason` 是用户可读原因（例如「还没有配置转写能力…」）；
- `segments[].locator` 带 `start_ms` / `end_ms` / `text_start` / `text_end`。

> 录完音的 `finalize` 只返回 `asset_id` / `recording_id`，**不返回 `source_id` /
> `revision_id`**；而 `sources.extract` 不接受 asset id。用
> `captures.get(capture_id).ordered_source_ids` 拿刚建的来源 id，再
> `extract({ source_ref: source_id })` 即可（§7.2）。

#### 配置模型

- 转写：`providers.save`（`adapter_id=sherpa_onnx`，`model` 是模型**目录**）→
  `providers.test`（会真的加载模型并转写 0.05 秒静音）→ `jobs.runDue`；
- 语义：写 `<filesDir>/core-config.json` 的 `modelDir` / `ortDylib` → **重新 open 核心** →
  `coreInfo().runtime_config.semantic` → `rebuildSemanticIndex` → `runDueJobs`；
- 配置只在 `Core::open` 时读一次；改文件不重开不生效。

#### 重建索引

```ts
const job = core.rebuildSemanticIndex({
  reason: 'user_rebuild',
  operation_id: `op-sem-${Date.now()}`
});
// job.state = queued；只排队，不同步建
await core.runDueJobs({ budget_ms: 30000, trigger: 'manual' }); // worker
const status = core.jobsStatus(); // 看 waiting_configuration / queued / due_backlog
const index = core.indexStatus(); // 看 semantic_index_ready / embedded_chunks / total_chunks / reasons
const current = core.getJob({ job_id: job.id }); // 单任务 progress；可能为 null
```

- `indexes.rebuildSemantic` **没有 scope**，总是整库；
- 真正干活的是 `jobs.runDue`；只调 `rebuildSemanticIndex` 会永远停在 `queued`；
- 语义任务可分段让出：预算到点会回 `queued`，`JobRunSummary.due_backlog > 0`
  表示还要再跑一轮；
- `indexStatus()` 的 `semantic_index_ready=false` 不一定是「没结果」：覆盖不全时检索仍会
  用已嵌入的块（§4.3）；
- 关键词重建是另一条路：`indexes.rebuild({scope:'all', reason, operation_id})`，
  不要拿它当语义重建。

### 2.3 当前 main 还缺什么

`captures.list/get`、`indexes.status`、`jobs.*`、`search.nextPage/upgrade/cancel` 已在
#143 接上（§8.1）。界面侧还剩这些缺口：

| 想做的界面 | 缺什么 | 现在能做的替代 | 影响 |
|---|---|---|---|
| 设置页「一键重建语义索引」、未就绪时显眼提示 | **前端入口**（C ABI 已有 `indexes.status` / `indexes.rebuildSemantic`） | 先在设置页常驻重建按钮；用 `indexStatus().semantic_index_ready` 控制提示强度 | `#136` 的前端入口缺口，见 `#140`；不是 C ABI 缺口 |

| 语义模型配置写入 | 没有写 `core-config.json` 的 API（仓库也没实现） | 产品自己原子写文件，再重新 `open` 核心 | 配置不会热生效，见 §5.4 |

## 3 状态语义（最重要）

### 3.1 先分清两套状态

| 状态族 | 出现在 | 取值 | 用途 |
|---|---|---|---|
| **录音会话** `RecordingSession.state` | `recordings.updateState` / `recordings.recover` | `idle` / `preparing` / `recording` / `paused` / `stopping` / `saved` / `interrupted` / `recoverable` / `error` | 录音按钮、计时、收尾 |
| **持久任务** `Job.state` | `indexes.rebuild` / `indexes.rebuildSemantic` 返回的 `Job`、`jobs.status` 计数 | `queued` / `running` / `succeeded` / `retry_wait` / `waiting_configuration` / `waiting_dependency` / `waiting_network` / `failed` / `cancelled` | 任务中心、转写/索引状态 |

不要把 `RecordingSession.state` 当 `Job.state` 用，也不要把
`finalize.state=saved` 当成「转写已完成」。`finalize` 只表示音频资产已最终化，
转写任务只是**同一事务里排上**（`transcription_queued=true`）。

> `paused` 只有平台层**显式**调用 `recordings.updateState(state='paused')` 才会出现：
> 核心不会自己写这个状态，`VoiceRecorder` 也从不报它（没有实现 pause/resume）。
> 见到它只能说明宿主自己上报过；不要据此做「继续录音」按钮。

### 3.2 `JobState` 9 个状态 → 界面

来源：[`JobState` 定义](../../crates/diary_core/src/model.rs#L506-L519)、
[`m4-任务调度与补做.md` 状态表](m4-任务调度与补做.md#L100-L137)、
[`jobs.rs` 等配置语义](../../crates/diary_core/src/jobs.rs#L620-L700)。

| `state` | 界面显示 | 可以给的按钮 | **不能给** | 备注 |
|---|---|---|---|---|
| `queued` | 排队中 | 想取消用 `jobs.cancel`（已接） | 「重试」「去配置」 | 可能 `next_attempt_at` 在未来；被闸门从等待态晋升也会在这里 |
| `running` | 处理中 | 取消用 `jobs.cancel`（已接） | 「重试」「开始」 | 语义索引可能在 `progress` 里有完成/总数；用 `jobs.get` 读 |
| `succeeded` | 已完成 | 无 | 「重试」 | 终态 |
| `retry_wait` | 等待自动重试 | 无 | 「重试」（会破坏退避） | `next_attempt_at` 是下次自动尝试时刻；不是失败终态 |
| `waiting_configuration` | **需要配置** | **`attention_key` 以 `job-config:` 开头 ⇒ 只给「去配置」** | 「重试」 | 不是失败：不退避、不消耗重试额度；见 §3.3 |
| `waiting_dependency` | 等待前一步 | 无 | 「重试」「去配置」 | 等 `extract` 等前置；`requires_user_action=false`；`error_code` 例如 `waiting_extract` |
| `waiting_network` | 等待网络 | 无 | 「重试」 | **当前没有写入者**，计数恒 0；不要为它做界面分支 |
| `failed` | 未完成 / 已放弃 | 「可重试 + `jobs.retry`（已接）」才给「重试」；否则只给「查看原因」 | 对 `storage_full` / `invalid_state` 给「重试」 | 终态；`requires_user_action` 通常为 1 |
| `cancelled` | 已取消 | 无 | 「重试」 | 由 `jobs.cancel` 产生（已接）；界面很少见到 |

**任务中心的四个聚合**（任务书口径，见
[`02-前端开发任务书.md`](../development/02-前端开发任务书.md#L115)）：

| 聚合 | 包含 | 说明 |
|---|---|---|
| 处理中 | `queued` + `running` | 不要把它们算成失败 |
| 等待 | `retry_wait` + `waiting_dependency` + `waiting_network` | 自动重试/前置/网络，不是用户要动手 |
| 需要处理 | `waiting_configuration` + `failed` | 这两个才需要用户看见 |
| 完成 | `succeeded` | `cancelled` 单独收在「已取消」二级里 |

### 3.3 `requires_user_action` 与 `attention_key`

**字段名是 snake_case**：ArkTS 的 `Job` 里是 `requires_user_action: boolean` 与
`attention_key: string | null`（[`Models.ets`](../../apps/ohos-diary-core/entry/src/main/ets/core/Models.ets#L242-L243)），
不是 `requiresUserAction` / `attentionKey`。写成 camelCase 会拿到 `undefined`，
`!undefined === true`，判定树会直接走错分支。

**规范口径**（[`m4` §等配置](m4-任务调度与补做.md#L100-L137)、
[共享契约 2.7](../development/01-共享接口契约.md#L143-L150)）：

- `waiting_configuration` **恒为** `requires_user_action = true`；
- `attention_key` **恒为** `job-config:<kind>:<error_code>`；
- `failed` 终态通常 `requires_user_action = true`；
- `waiting_dependency` / `queued` / `running` / `retry_wait` / `succeeded` 不需要用户动手；
- `attempt_count` 只区分「有没有真的跑过一次」：闸门在领取前挡下 = 0，执行期才发现 = 如实记账。

**界面判定树**（只认前缀，不自己拼文案）：

```text
if (!job.requires_user_action) {
  // 只显示状态，不给「去处理」
} else if (job.attention_key?.startsWith('job-config:')) {
  // 给「去配置」；用 <kind> 决定跳转页面：
  //   semantic_index → 语义模型设置
  //   transcribe     → 转写引擎/模型设置
  //   respond        → AI 服务设置
  //   index / extract→ 解析/索引设置（通常只是等，不应出现）
  // 不要根据 <error_code> 写用户文案；文案来自页面自身的状态说明 + core 的 reason
} else if (job.attention_key?.startsWith('job-terminal:')) {
  // 终态、需要人工；给「查看原因」，不要给「去配置」
} else {
  // 没有 key：显示「需要处理」，但不要猜原因
}
```

**为什么不能按 error code 拼文案**：`attention_key` 的形状只有一处
（`jobs::configuration_attention_key`），同一个待处理问题也只提示一次；
按 code 各写一套文案，会在 core 加/改码时漂移。规范见
[`m4` §等配置](m4-任务调度与补做.md#L130-L131) 与
[`#96`](https://github.com/xingxue-ux/unwritten-diary/pull/96)。

**当前 main 怎么落地**：`jobs.list` / `jobs.get` 已接，每条 `Job` 都带
`attention_key` / `progress`，所以「任务中心逐条」可以直接按上面的树做；
重试/取消/已读回执分别是 `jobs.retry` / `jobs.cancel` /
`jobs.acknowledgeAttention({ attention_key })`。**只有 `jobs.status.recent_errors`
仍没有 `attention_key` / `message`**（字段只有 `job_id` / `kind` / `error_code` /
`occurred_at` / `requires_user_action`）：

- 「需要处理」列表优先用 `jobs.list({ states: ['waiting_configuration', 'failed'] })`，
  从每条 `Job` 读 `attention_key`；`recent_errors` 只做历史错误摘要；
- 如果只有 `recent_errors`，按 `kind` 路由到设置页只是**临时替代**；不要把 `kind`
  路由写死成用户文案；
- `attention_key` 展示过之后调 `jobs.acknowledgeAttention`，跨重启去重；同一个 key
  重复调用是幂等的。

> `#97` 也记录了「闸门的完整理由没有桥接出去」这一问题。`recent_errors` 没有
> message，用户看到的只能是页面自己的解释；页面标题用「语义索引需要配置」这类
> **领域文案**，具体原因显示 `runtime_config.*.reason` 或未来的 job message。

### 3.4 错误码与重试：哪些重试无用

`DiaryError.retryable` 来自核心的 `ErrorCode::retryable()`；只有 5 个码是 true：
`search_expired` / `cursor_expired` / `network_unavailable` / `provider_timeout` /
`rate_limited`（[`error.rs`](../../crates/diary_core/src/error.rs#L305-L314)）。
不要自己判断「这个看起来可以再试」。

**核心码（21 个，`DiaryError.code` 可能出现的业务码）**：

| 错误码 | 用户可见含义 | `retryable` | 界面动作 |
|---|---|---:|---|
| `invalid_argument` | 参数不合法/缺失/拼错；C ABI 的「未接入方法」也用它 | false | 修调用参数；不要把「未接入」当业务错误重试 |
| `not_found` | 目标不存在 | false | 回列表/说明已被清理，不静默成功 |
| `invalid_state` | 当前状态不允许这个操作 | **false** | **不要重试同一个调用**；刷新真实状态/回到正确页面 |
| `revision_conflict` | 读到的 revision 过期 | false | 展示当前版和待保存内容；不覆盖 |
| `idempotency_conflict` | 同一个 operationId 换了输入 | false | 保留输入；换新的 operationId 再提交（仅当输入真的变了） |
| `storage_full` | 空间不足，没保存/录音停止 | **false** | **不要立刻重试**；显示空间信息，清理后让用户重新发起 |
| `asset_missing` | 原件不在 | false | 显示不可播放/不可打开 |
| `permission_denied` | 权限被拒 | false | 说明权限，提供去设置；**不要循环弹权限框** |
| `integrity_failed` | 文件/哈希不对，没保存 | false | 说明材料不完整；保留暂存，让用户重新选择/取消；不要自动重试 |
| `unsupported_format` | 格式不支持提取 | false | 保留附件，注明仅文件信息可搜 |
| `search_expired` | 检索会话过期（索引变了/重启丢失） | **true** | 安静重新发起当前查询；丢弃旧会话结果 |
| `cursor_expired` | 游标过期/不属于当前会话/升级后失效 | **true** | 用当前快照的游标重新翻；不要自己拼游标 |
| `provider_not_configured` | 服务/模型没配好 | false（等配置） | 去配置，不重试 |
| `authentication_failed` | 认证失败 | false（等配置） | 去配置/检查密钥，不重试 |
| `network_unavailable` | 网络不可用 | **true** | 材料已保存；任务自动退避；界面显示等待 |
| `rate_limited` | 被限流 | **true** | 尊重 `Retry-After`；不要手动连点 |
| `quota_exceeded` | 额度问题 | false（等配置/暂停） | 显示额度，提供手动处理 |
| `provider_timeout` | 超时 | **true** | 有限重试；不承诺远端未计费 |
| `model_unavailable` | 模型/包不对 | false | 检查包/模型；关键词仍可用，语义状态可见 |
| `corrupted_backup` | 备份包结构/哈希/清单与内容不一致 | false | 不要恢复；让用户重新选择备份或重新导出 |
| `incompatible_backup` | 备份包来自更新的核心 | false | 不要降级恢复；升级核心或换备份 |

**宿主码（1 个，不是核心契约码）**：

| 错误码 | 用户可见含义 | `retryable` | 界面动作 |
|---|---|---:|---|
| `native_unavailable` | 原生库没加载/调用没发生（`ERR_DIARY_*`、信封不是合法 JSON） | false | **这是打包/部署问题**，不是用户错误；显示诊断入口，不要叫用户重试 |

来源：[共享契约第 7 节](../development/01-共享接口契约.md#L490-L515)、
[`DiaryError.ets`](../../apps/ohos-diary-core/entry/src/main/ets/core/DiaryError.ets#L16-L41)、
[`error.rs` `ErrorCode::wire()`](../../crates/diary_core/src/error.rs#L55-L90)。

**别把两套码混着用**：`native_unavailable` 不在 `CORE_ERROR_CODES` 里，
`DiaryError.isCoreError()` 会返回 false；不要把它写进「核心 21 码」的错误表，
也不要用它判断业务状态。

**`Job.error_code` 与 `DiaryError.code` 是两套东西**：前者是任务失败原因，
后者是一次调用失败原因。不要拿 `DiaryError.retryable` 去决定一个 `failed` 任务
要不要重试——任务的 `retry_wait` / `failed` 由队列自己决定。

### 3.5 什么时候不能给按钮（速查）

| 场景 | 不能给 | 为什么 |
|---|---|---|
| `state=running` | 重试、开始 | 已经在跑；重复入队/重试会打乱 |
| `state=queued` | 重试 | 还没跑，重试无意义 |
| `state=succeeded` | 重试 | 终态 |
| `state=cancelled` | 重试 | 用户/系统已取消；要重新发起新动作 |
| `state=retry_wait` | 手动重试 | 已有退避排期；手动会破坏退避 |
| `state=waiting_dependency` | 重试、去配置 | 等前置，不需要用户 |
| `state=waiting_network` | 重试 | 没有写入者；即使出现也应等网络 |
| `state=waiting_configuration` | 重试 | 不是失败；只给「去配置」 |
| `state=failed` + `storage_full` | 重试 | 空间不清理，重试必失败 |
| `state=failed` + `invalid_state` | 重试 | 状态不变，重试必失败 |
| `state=failed` + `permission_denied` / `authentication_failed` / `quota_exceeded` | 重试 | 先改权限/配置/额度 |
| `requires_user_action=false` | 「需要处理」「去配置」 | 系统会自己处理 |
| `attention_key=null` | 任何深链 | 没有可靠目标；乱跳会误导 |
| `semantic_index_ready=false` + 没有生效代次/范围无文本块/模型不可用/口径不一致 | 假装语义可用、不给解释 | 这几类 `mode=semantic` 会返回**空结果**（不退化）；提示配置/重建，并原样显示 `warnings` |
| `semantic_index_ready=false` 且只是覆盖不全（有生效代次、口径一致、模型能加载） | 把已返回的语义结果丢掉/当成空 | 检索**仍返回已嵌入块的结果**，只是 `warnings` 说可能不完整；保留结果 + 覆盖提示 |
| `semantic_index_ready=false` 且 `embedded_chunks>0`，但口径不一致/模型加载失败 | 把「库里有向量」当成「一定搜得到」 | 这两种仍会返回**空结果 + warning**；`embedded_chunks>0` 不是「有结果」的充分条件 |
| 录音 `preparing` / `stopping` | 开始/停止 | 正在过渡，按钮应禁用 |
| 录音 `error` 且 `segmentCount()==0` | 「保存已录部分」 | 没有可最终化片段，`finalize` 会 `invalid_state` |
| 权限 `granted=false` | 「开始录音」 | 没有权限不能录；不要假装在录 |

### 3.6 任务中心可观测性（当前）

`jobs.status` 给的是**计数**，不是任务列表：

```json
{"queued":0,"running":0,"retry_wait":0,"waiting_configuration":1,
 "waiting_dependency":0,"waiting_network":0,"failed":0,"cancelled":0,
 "succeeded":17,"due_backlog":0,"next_wakeup":null,
 "recent_errors":[{"job_id":"job_…","kind":"transcribe",
   "error_code":"provider_not_configured","occurred_at":"…",
   "requires_user_action":true}]}
```

（字段来自 [`JobStatus`](../../crates/diary_core/src/model.rs#L747-L769)；
示例中的数字来自真机日志节选
[`m6-平板与PC平台能力.md`](m6-平板与PC平台能力.md#L374-L380)。）

- `recent_errors` 最多 5 条（`RECENT_ERROR_LIMIT`）；
- `recent_errors` 没有 `message`、没有 `attention_key`；需要逐条任务与 `attention_key`
  时用 `jobs.list` / `jobs.get`（已接）；
- `core.info.recovery.pending_jobs` **只数 `queued` + `retry_wait`**，
  不含 `waiting_configuration` / `waiting_dependency`，不要拿它当「所有待办」；
- `jobs.runDue` 的 `processed` 包含「语义任务让出一段」的次数，
  所以 `processed` 不等于 `succeeded`；`due_backlog > 0` 表示还要再跑一轮。

## 4 索引状态与语义检索

### 4.1 `indexes.status` 给什么

核心有完整的 `IndexStatus`（[`model.rs`](../../crates/diary_core/src/model.rs#L984-L1040)），
界面最关心这些字段：

| 字段 | 含义 | UI 用途 |
|---|---|---|
| `keyword_index_ready` | 关键词索引是否就绪 | 关键词搜索入口/覆盖提示 |
| `coverage` | 关键词覆盖：`complete` / `partial` / `metadata_only` / `unavailable` | 「结果可能不全」提示 |
| `semantic_index_ready` | 生效向量代次是否覆盖全部块且口径一致 | 语义入口是否可用 |
| `model_version` | 生效代次的模型版本；混合代次/无代次为 null | 显示「用哪个模型建的」 |
| `total_chunks` / `embedded_chunks` | 块总数 / 其中有当前代次向量的块数 | 重建进度、覆盖 |
| `reasons[]` | 用户可读原因（中文整句） | **原样展示**，不要自己改写 |
| `index_bytes` | 整库索引占用（含语义表） | 存储设置 |

### 4.2 现在怎么读它（#143 已接）

`indexes.status` 已经接进 C ABI 和 `DiaryCore`：

- [`WIRED_METHODS`](../../crates/diary_capi/src/methods.rs#L90-L121) 包含 `indexes.status`；
- [`DiaryCore.ets`](../../apps/ohos-diary-core/entry/src/main/ets/core/DiaryCore.ets#L316-L320)
  有 `indexStatus(params?: IndexStatusParams | null)`；
- `tools/check_arkts_capi_contract.py` 核对的是 30 条已接方法（#143 之后）。

```ts
// 整库（省略 source_scope）
const all = core.indexStatus();
// 只看某些来源：省略 = 整库；空数组 = 「什么都不看」（两者刻意不同）
const scoped = core.indexStatus({ source_scope: ['src_…'] });
```

- `reasons[]` 原样展示；`index_bytes` 是整库占用，不随 `source_scope` 变；
- **不要用 `core.info.runtime_config.semantic.state=ready` 冒充索引就绪**——它只表示
  「模型加载过」，不表示向量代次覆盖了所有块（§4.3）；
- `semantic_index_ready=false` 不一定是「检索必然空」；见下节。

### 4.3 `semantic_index_ready=false` 时到底发生什么

**先纠正一个常见误读**：`semantic_index_ready=false` **不等于**「语义检索一定为空」。
它是以下几条的合取：有生效代次、`total_chunks > 0`、`embedded_chunks == total_chunks`、
整代口径一致（存储格式/维度/模型版本，且不是混合代次）。任何一条不满足都是 `false`，
但只有下面几类「真空」会返回空；**其他条件都成立、只是覆盖不全时，返回的是部分结果**：

| `false` 的原因 | `mode=semantic` 的结果 | `warnings` / `coverage` | UI 应该 |
|---|---|---|---|
| 没有生效代次 | **空结果**，不退化 | 警告「语义索引还没有生效的代次…这次没有结果（没有退化成关键词…）」 | 提示先建索引/配置；不要把「空」显示成「没搜到」 |
| 范围里没有文本块（`total_chunks=0`） | **空结果**，不退化 | 警告「语义检索没有找到相近的内容」；`coverage=unavailable` | 提示先导入/提取内容；不要显示成「索引坏了」 |
| 模型/运行库加载失败 | **空结果**，不退化 | 警告「语义检索不可用：…；这次没有结果」 | 显示原因 + 去配置；不要静默改用关键词 |
| 口径不一致（存储格式/维度/模型版本，或混合代次） | **空结果**，不退化 | 警告「语义检索没有结果：…没有拿跨空间的分数当结果」；可能自动排重建 | 给「重建语义索引」；不要拿旧分数冒充 |
| **有生效代次、口径一致、模型能加载，只是 `embedded_chunks < total_chunks`** | **返回已嵌入块的结果**（可能有值） | 警告「语义索引还没有覆盖全部内容，结果可能不完整」；`index_coverage=partial` | **保留结果**，同时显示覆盖不全 + 重建入口；不要丢掉有效结果 |
| 空查询 / 真的没有命中 | 空结果，但**不是**「索引不可用」 | 警告「查询是空的」/「语义检索没有找到相近的内容」 | 按「没搜到」展示；不要引导重建 |
| `semantic_index_ready=true` | 索引口径层面正常返回 | `coverage=complete`，没有覆盖警告 | 正常展示；但模型仍可能在真正加载时失败（那时是空结果 + warning），别把 warning 吞掉 |

来源：[`semantic_search`](../../crates/diary_core/src/search_session.rs#L314-L388)（空结果只在
无代次 / 无块 / 模型失败 / 口径不一致时发生；覆盖不全只加 warning）、
[`index_status` 的 `semantic_index_ready` 计算](../../crates/diary_core/src/search.rs#L631-L634)、
[`semantic_coverage`](../../crates/diary_core/src/search_session.rs#L939-L958)。

**哪些模式会退化**：只有 **`mode=hybrid`** 在语义拿不出证据时退化为关键词
（`phase=keyword_ready` + warning）。`mode=semantic` 无论哪种失败都**不退化**；
但「覆盖不全」不是失败，它是**部分结果**——照常展示，别丢。

**为什么语义模式不退化**：代码注释写得很清楚——「没有退化成关键词，那会让『语义』
这个标签撒谎」（[`search_session.rs`](../../crates/diary_core/src/search_session.rs#L326-L330)）。
界面如果统一宣传「语义不可用会自动用关键词」，会与实际行为不符。

### 4.4 `reasons` 里会出现什么

以下是核心真实文案（[`search.rs`](../../crates/diary_core/src/search.rs#L669-L798)），
界面应**原样展示**，最多做换行/折叠：

- 没配模型：「语义索引未就绪：还没有配置本地模型（DIARY_MODEL_DIR / DIARY_ORT_DYLIB），
  当前只有关键词索引」；
- 模型不可用：「语义索引未就绪：本地模型不可用（…）」；
- 没建过代次：「语义索引未就绪：还没有生效的向量代次（模型已就绪，等一次
  build_semantic_index）」；
- 存量库口径不一致（最常见）：「语义索引未就绪：存储格式从 f32 变为 int8，需要重建
  （build_semantic_index 会按当前格式整代重算）」；
- 维度不一致：「语义索引未就绪：生效代次里的向量是 512 维，当前模型是 768 维；…
  需要重建语义索引」；
- 模型版本不一致：「语义索引未就绪：生效代次的向量是模型 X 建的，当前模型是 Y；…
  需要重建语义索引」；
- 混合代次：「语义索引未就绪：生效代次里的向量有 N 种模型口径…」；
- 覆盖不全：「语义索引未就绪：生效代次只覆盖了 X 块里的 Y 块」；
- 正在建：「语义索引有一代在建（第 N 代）：已经写了 X / Y 块的向量；生效代次仍是第 N 代，
  检索照旧读它…」。

最后一条是**补充事实**，不要把它当成「未就绪」的又一条原因；它可能与
`semantic_index_ready=true` 同时出现（旧代次还在服务，新代次在建）。

### 4.5 自动重建：只覆盖很窄的情况

核心自动排语义重建的规则（[`semantic_index_job.rs`](../../crates/diary_core/src/semantic_index_job.rs#L20-L100)）：

| 条件 | 说明 |
|---|---|
| 模型 `Configured` / `Ready` | 没配模型**不排**（避免长期挂 `waiting_configuration` 噪声） |
| 有生效代次且那一代有向量 | 第一次构建**不会自动排**，必须显式 `rebuildSemanticIndex` |
| 整代口径不一致 | `storage` / `dims` 总是比；`model_version` 只在内存里已知时比 |
| 没有活着的 `semantic_index` 任务 | 失败/取消留下的 `building_generation` 不挡重排 |
| 同口径自动尝试 < 2 次 | 持久标记；**同一口径最多自动排两次**（首次 + 失败/取消后一次） |
| 发现点 | `Core::open`（不加载模型，只读列）或检索加载模型之后 |

**第三次起不会自动排**，必须由界面提供手动入口。`#136` 明确要求设置页有
「一键重建语义索引」，并在 `semantic_index_ready=false` 时显眼。
`indexes.status` 已接（§4.2）：用 `indexStatus().semantic_index_ready` 控制提示强度；
设置页仍建议**常驻**「重建语义索引」，不要依赖自动。这里剩下的只是 `#136` 的
**前端入口**（`#140`），不是 C ABI 缺口。

> `#136` 还说明：只换 `model_version`（同 dims、同 storage）时，`open` 不会自动排，
> 因为 `open` 不算模型哈希；检索加载模型后才会发现。换模型流程结束后应主动提示
> 「建议重建索引」。

### 4.6 手动重建流程（界面可直接照做）

```ts
// 1. 先看模型状态，不要在没配模型时假装能建
const config = core.coreInfo().runtime_config?.semantic;
if (config?.state === 'absent' || config?.state === 'invalid') {
  // 去配置页；不要排重建（会进 waiting_configuration）
  return;
}

// 2. 只排任务（不同步建）
const job = core.rebuildSemanticIndex({
  reason: 'user_rebuild',
  operation_id: `op-sem-${Date.now()}`
});

// 3. 在 worker 里真跑；可能需要多轮（语义任务会分段让出）
await core.runDueJobs({ budget_ms: 30000, trigger: 'manual' });
const status = core.jobsStatus();
const index = core.indexStatus();
const current = core.getJob({ job_id: job.id });
if (status.due_backlog > 0 || status.queued > 0) {
  // 前台时再排一轮；不要 tight loop
}
```

- `operation_id` 幂等：同一个点击/重试复用；新的用户请求换新的；
- `rebuildSemanticIndex` 的返回 `Job` 是**排队那一刻**的快照；之后不会自动更新；
- 单条进度用 `jobs.get` 的 `progress`（`completed` / `total`，可能为 null）；不要假定
  `progress` 一定在，也不要在 null 时编百分比；
- 语义任务在块与块之间让出；`budget_ms` 小会多轮，属正常。

### 4.7 界面怎么呈现（`indexes.status` 已接）

| 情况 | 能确定的信息 | 建议 UI | 不要做 |
|---|---|---|---|
| `semantic.state=absent` | 没配模型 | 「语义检索未配置」+「去配置」为主；「重建」可保留为次按钮 | 不要把「重建」当唯一主按钮（会进 `waiting_configuration`） |
| `semantic.state=invalid` | 配了但不可用 | 显示 `reason` +「重新配置」 | 不要重试 |
| `semantic.state=configured` | 文件在，但没证明能加载 | 「已配置，待验证」；首次搜索/重建会真正加载 | 不要说「已就绪」 |
| `semantic.state=ready` | 模型加载过 | 可显示模型版本；**索引是否就绪仍看 `indexStatus`** | 不要用它替代 `semantic_index_ready` |
| `indexStatus().semantic_index_ready=false` 且 `embedded_chunks=0` | 语义这一路当前没有可服务向量 | 显示 `reasons` +「重建语义索引」；语义入口可禁用但要说原因 | 不要静默把语义入口当成可用 |
| `indexStatus().semantic_index_ready=false` 且只是覆盖不全（有生效代次、口径一致、模型可用，`embedded_chunks>0`） | 有部分结果，覆盖不全 | 保留检索结果 + 「覆盖不全」提示 + 重建入口 | 不要把部分结果丢掉/显示成空 |
| `indexStatus().semantic_index_ready=false` 且 `embedded_chunks>0`，但口径不一致/模型加载失败 | 库里虽有向量，这一路仍不可检索 | 显示 `reasons` + 「重建语义索引」/去配置；以 `warnings` 为准 | 不要因为 `embedded_chunks>0` 就承诺有结果 |
| `search(mode=hybrid)` 返回 `keyword_ready` + 退化 warning | 语义这一路当前不可用 | 显示关键词结果 + warning +「重建语义索引」 | 不要把标签写成「混合结果」 |
| `jobs.status.waiting_configuration > 0` | 有任务在等配置 | 显示「有任务在等配置」；用 `jobs.list` 的 `attention_key` 路由 | 不要只按 `recent_errors[].kind` 猜 |
| `search(mode=semantic)` 空结果 + warning | 看 warning 区分「不可用」与「没命中」 | 原样显示 warning；只有 warning 说未就绪/不可用/跨空间时才给重建或去配置 | 不要对所有空结果都引导重建（没命中不是索引坏了） |

### 5.1 `core.info.runtime_config` 的形状

`core.info` 在契约字段之外多一格 `runtime_config`（camelCase；只 stat，不加载模型）：

```json
"runtime_config": {
  "file": {"path": "…/core-config.json", "present": true, "error": null, "ignoredFields": []},
  "semantic": {
    "state": "ready",
    "configSource": "file",
    "modelDir": "…",
    "modelDirSource": "file",
    "ortDylib": "…",
    "ortDylibSource": "file",
    "modelVersion": "bge-small-zh-v1.5-ours@d44978e451a0",
    "reason": null
  },
  "transcription": {
    "state": "ready",
    "configSource": "file",
    "modelDir": "…",
    "modelDirSource": "file",
    "engineLib": null,
    "engineLibSource": "platform",
    "providerId": "local_asr_ohos",
    "reason": null
  }

```

来源：[`m6-设备配置与双ORT.md` §1.4](m6-设备配置与双ORT.md#L79-L111)。
键是 camelCase；`core.info` 外层仍是 snake_case。`Models.ets` 里
`LibraryInfo.runtime_config?: RuntimeConfig` 是**可选**的，读取时要判空。

### 5.2 `state` 怎么展示

#### 语义（`semantic.state`）

| `state` | 含义 | 界面 | 按钮 |
|---|---|---|---|
| `absent` | 没有模型配置 | 「语义检索未配置」 | 去配置（写 `core-config.json`） |
| `configured` | 配了、文件在、还没加载 | 「已配置，待验证」 | 「重建语义索引」；首次加载失败会转 `invalid` |
| `ready` | 模型已加载 | 显示模型版本 | 语义入口可用（但索引另说） |
| `invalid` | 配了但不可用 | 显示 `reason`（缺哪个文件/ORT 不在） | 「重新配置」；不要重试 |

#### 转写（`transcription.state`）

注意：转写**没有 `invalid`**。缺文件/缺库时它报 `configured` + `reason`，
只有完全没解析到模型目录才是 `absent`（[`config_file.rs`](../../crates/diary_core/src/config_file.rs#L298-L378)）。

| `state` | 含义 | 界面 | 按钮 |
|---|---|---|---|
| `absent` | 没有模型目录 | 「转写未配置」 | 「配置转写」 |
| `configured` | 解析到了路径，但不完整/未证明 | 显示 `reason`；不要显示绿色就绪 | 「测试连接」；测试会真的加载模型 |
| `ready` | 文件齐全 | 「转写已配置」 | 「测试连接」仍建议保留（真加载才算数） |

`transcription.engineLibSource=platform` 且 `reason` 说「还没有探测过」时，
**不是错误**：移动端按库名解析，第一次任务/测试才会真 dlopen。不要标红。

### 5.3 来源字段怎么用

四个 `*Source` 字段**不是一个取值集合**，逐字段看：

| 字段 | 可能取值 | 来自 |
|---|---|---|
| `semantic.configSource` | `env` / `file` / `absent` | [`embedding.rs`](../../crates/diary_core/src/embedding.rs#L282-L308) |
| `semantic.modelDirSource` | `env` / `file` / `absent` | 同上 |
| `semantic.ortDylibSource` | `env` / `file` / `absent` | 同上 |
| `transcription.configSource` | `env` / `file` / `provider` / `bundled` / `absent` | 模型目录的来源（[`local_engine.rs`](../../crates/diary_core/src/provider/local_engine.rs#L58-L65)） |
| `transcription.modelDirSource` | `env` / `file` / `provider` / `bundled` / `absent` | 同上 |
| `transcription.engineLibSource` | `env` / `file` / `bundled` / **`platform`** / `absent` | 只有这一档有 `platform`：没有显式路径、按库名交给系统解析；`bundled` = 可执行文件旁找到（[`local_engine.rs`](../../crates/diary_core/src/provider/local_engine.rs#L407-L423)、[`config_file.rs`](../../crates/diary_core/src/config_file.rs#L243-L255)） |

所以：**不要把 `provider` / `bundled` / `platform` 当成 `semantic.*Source` 的合法值**；
也不要把 `platform` 当成转写模型目录的来源；`engineLibSource` 的 `bundled` 是合法的
（引擎库就在可执行文件旁边）。

- 主界面只显示「从哪来」的一句话即可；详细来源放「高级/诊断」；
- `modelVersion` 只在 `ready` 时有值；
- `reason` 是用户可读的，**原样显示**，不要自己翻译成「模型未就绪」；
- `file.present=false` 且 `file.error=null`：没有配置文件，正常；
- `file.error` 非空：读不了/JSON 坏/字段类型不对；配置不致命，会回落，但要在诊断页显示；
- `file.ignoredFields` 非空：字段名拼错/不认识，例如把 `modelDir` 写成 `modelPath`、
  `ModelDir`（大小写不符）；**`model_dir` 是 `modelDir` 的合法别名，不会进
  `ignoredFields`**（[`config_file.rs`](../../crates/diary_core/src/config_file.rs#L90-L104)）。
  这是最容易被忽略的配置错误，应该显示。

### 5.4 `core-config.json`：位置、字段、生效时机

```json
{
  "modelDir": "/data/storage/el2/base/haps/entry/files/models/bge-small-zh-v1.5-ours",
  "ortDylib": "/data/storage/el1/bundle/libs/arm64/libonnxruntime-diary-1.29.1.so",
  "asrEngineLib": "/data/storage/el1/bundle/libs/arm64/libsherpa-onnx-c-api.so",
  "asrModelDir": "/data/storage/el2/base/haps/entry/files/asr/sense-voice"
}
```

- 位置：**资料库文件旁边**，即 `<filesDir>/core-config.json`，不是 HAP 内；
- 精确路径从 `coreInfo().runtime_config.file.path` 读，不要硬编码；
- 四个字段全可选；逐字段优先级：
  - 语义：环境变量 → 文件 → `absent`；
  - 转写模型目录：`DIARY_ASR_MODEL_DIR` → `asrModelDir` → `providers.model` → 随包默认；
  - 转写引擎库：`DIARY_ASR_ENGINE_LIB` → `asrEngineLib` → 可执行文件旁 → 按库名（移动端）；
- **只在 `Core::open` 时读一次**；改了文件必须关闭再打开核心才生效；
- `ortDylib` / `asrEngineLib` **不能指向应用数据目录**（`/data/storage/el2/...`、
  `/data/storage/el1/base/...`）；linker 只允许从 HAP 的 `libs/arm64` dlopen。
  配置解析时就报 `invalid` / `invalid_argument`，不是等第一次加载才失败。
- 文件不存在：行为与没有它逐位一致；坏 JSON 不致命，回落并写 `file.error`；
- 建议 UI 写文件时用「临时文件 + 原子 rename」，避免半截 JSON；**仓库没有实现这条写路径**，
  这是建议，不是既有事实。

**语义配置后要重新 open 才生效**。如果此时正在录音/跑任务，先等它结束；不要在
`Core` 打开期间改文件然后期待 `coreInfo` 变化。

### 5.5 转写 provider：本地引擎

本地引擎的 `adapter_id` 是 **`sherpa_onnx`**；`model` 是**模型目录**，不是远端模型名。
真机样例（[`README`](../../apps/ohos-diary-core/README.md#L317-L329)）：

```json
{"id":"local_asr_ohos","label":"本机转写（OHOS 沙箱模型）","adapter_id":"sherpa_onnx",
 "endpoint":null,"model":"/data/storage/el2/base/haps/entry/files/asr/sense-voice",
 "capabilities":["transcribe_audio"],"credential_ref":null,"enabled":true,"test_status":"untested"}
```

保存：

```ts
const saved = core.saveProvider({
  config: {
    id: 'local_asr_ohos',
    label: '本机转写（OHOS 沙箱模型）',
    adapter_id: 'sherpa_onnx',
    endpoint: null,
    model: `${context.filesDir}/asr/sense-voice`,
    capabilities: ['transcribe_audio'],
    credential_ref: null,
    enabled: true,
    test_status: 'untested'
  },
  secret: null
});
// 本机引擎：saved.test_status 一定是 'untested'；调用方写 'ok' 会被忽略
// （provider/mod.rs 的 save_local 恒写 untested）
// 远端 provider：功能参数（adapter_id / endpoint / model / 密钥）没变时保留旧
// test_status；变了才清回 'untested'。只改 label / enabled 不作废验证结论。
```

- `endpoint` 必须是 null/空；本地引擎填 endpoint 会 `invalid_argument`；
- `model` 留空合法：用随包/环境变量解析的默认目录；核心保存时**不校验目录存在**，
  不存在会在任务闸门/测试时暴露；
- `test_status` 由核心维护：**本机引擎**保存后恒回 `untested`；**远端 provider** 只在
  功能参数变化时清回 `untested`（未变则保留旧值）。两种都不允许调用方写成「已验证」；
- `providers.list` **不包含**内建引擎行；没有配置行不等于不能转写（可能走 bundled）；
- 测试：

```ts
const report = core.testProvider({
  provider_id: 'local_asr_ohos',
  scope: ['transcribe_audio']
});
// report.results.transcribe_audio: 'ok' / 'failed'
// report.actual_call_made: 本机引擎真的跑了推理 => true；不是 HTTP
// report.message: 可达性/模型/下一步；Rust 是 Option，可能是 null
```

- `scope` 不能为空，否则 `invalid_argument`；
- 本机引擎的 `actual_call_made` 表示「真的发生了一次推理」，不是「发了 HTTP」；
- 报告失败分两种：能力不支持走报告（`actual_call_made=false`），认证/超时/网络走错误码；
- 内建引擎可用 `builtin_local_asr` 测试；`providers.remove` 删内建行会 `invalid_state`。

### 5.6 模型下载 / 导入：必须 sha256 + `.part` 原子替换

**模型不进 HAP**（[`m6-设备配置与双ORT.md`](m6-设备配置与双ORT.md#L162-L163)）：
SenseVoice 239.5 MB（228.4 MiB）、bge 24.3 MB（23.1 MiB）。应用沙箱**不能**用
`hdc file send` 写，只能由应用自己下载/导入。

仓库里**唯一**的下载实现是
[`ModelDownload.ets`](../../apps/ohos-diary-core/entry/src/main/ets/recording/ModelDownload.ets)，
调用方必须给 `{bytes, sha256}`，没有「大小未知就放行」的路径。顺序：

```text
写 <dest>.part
  → HTTP 2xx
  → Content-Length == 期望 bytes
  → 实收字节 == 期望 bytes
  → sha256(part) == 期望 sha256
  → 同目录原子 rename(part, dest)
```

- 任何一步失败：**只删 `.part`，旧 `dest` 一个字节都不动**；
- 最多 3 次尝试；每次从 `.part` 重新收（**没有断点续传**）；
- 失败原因写日志，不把半截文件当模型；
- 期望值（真机实测，[`README`](../../apps/ohos-diary-core/README.md#L308-L316)）：

| 文件 | 字节 | sha256 |
|---|---:|---|
| `asr/sense-voice/model.int8.onnx` | 239,233,841 | `c71f0ce00bec95b07744e116345e33d8cbbe08cef896382cf907bf4b51a2cd51` |
| `asr/sense-voice/tokens.txt` | 315,894 | `f449eb28dc567533d7fa59be34e2abca8784f771850c78a47fb731a31429a1dc` |
| `models/bge-small-zh-v1.5-ours/model_quantized.onnx` | 23,830,209 | `d44978e451a0b4e0c561b8c6bb2cfaf5aac734f2729359aae46e1db893499f43` |
| `models/bge-small-zh-v1.5-ours/tokenizer.json` | 439,125 | `48cea5d44424912a6fd1ea647bf4fe50b55ab8b1e5879c3275f80e339e8fae26` |

来源：[`models/manifest/sense-voice-small-int8-2024-07-17.json`](../../models/manifest/sense-voice-small-int8-2024-07-17.json)、
[`models/manifest/bge-small-zh-v1.5.json`](../../models/manifest/bge-small-zh-v1.5.json)。

**界面必须知道的限制**：

- `downloadToFile` **没有进度回调**，只在结束时返回；当前只能做 indeterminate 进度条，
  或先扩展实现（加 `dataReceive` 回调/进度回调）；
- **没有导入实现**：仓库只有网络下载。若产品要「从文件选择器导入」，
  必须由应用把文件复制到沙箱，再走同一套 `bytes + sha256 + .part + rename`；
  不能 `fs.copyFile` 直落最终路径。这条是**待确认**（产品是否要做）；
- 下载源/URL **不在仓库里**：`downloadToFile(url, dest, expected)` 由调用方给 URL。
  产品要定 CDN/对象存储/签名 URL，不要硬编码宿主机 `127.0.0.1`（那只是验证通道）；
- 239.5 MB 不能在 UI 线程下：会卡死/ANR；放 worker，页面只订阅状态；
- 首次下载峰值 ≈ 模型大小；**替换已有模型时**旧 `dest` + `.part` 会同时存在，
  峰值约 2 倍（按实现推导；不是实测数字），设计「剩余空间」提示时要算进去；
- 下载前可先 `sha256OfFile(dest)` 跳过；但 228.4 MiB 的哈希本身也要时间，放 worker。
  现有 `TranscriptionVerify.downloadModels` 没有做 skip，直接重新下载。

### 5.8 默认包与语义能力识别（硬缺口）

`core.info.capabilities` 只反映「C ABI 有没有这个方法」，**不反映安装包有没有
ORT 1.29.1**；默认包的 `capabilities` 仍然包含 `indexes.rebuildSemantic`。
`runtime_config.semantic.state` 在用户没配置时是 `absent`，也不会告诉你「这个包
根本不支持语义」。

因此当前无法只靠 C ABI 在界面上可靠区分：

- 「用户还没配语义模型」； vs
- 「这个安装包没有语义运行时，配了也没用」。

**建议**（需要后端/构建配合，当前未实现）：构建期注入一个只读的应用能力标记
（例如 `BuildProfile` / 常量 `semanticRuntimeSupported`），或提供一个
`core.info` 字段说明「包内是否有 1.29.1」。在此之前：

- 默认包可以隐藏语义入口，或显示「当前安装包不含语义检索，需安装语义版」；
- 但**不要**用 `capabilities` 判断；
- 也不要在用户配置 `ortDylib` 失败后才说「包不支持」——太晚。

## 6 录音交互

### 6.1 权限

[`MicPermission.ets`](../../apps/ohos-diary-core/entry/src/main/ets/recording/MicPermission.ets)：

```ts
const outcome = await ensureMicrophonePermission(context);
if (!outcome.granted) {
  // 显示「需要麦克风权限」+ 去设置；不要创建草稿/票据/开始录音
  return;
}
```

- 先 `checkAccessTokenSync`，已授权不重复弹框；
- 未授权才 `requestPermissionsFromUser(context, ['ohos.permission.MICROPHONE'])`；
- `authResults`：`0=授权`，`-1=拒绝`，`2=声明/条件不对`；
- `checked=false` 表示查询权限状态失败（不是「没权限」），但仍会尝试请求；
- 拒绝时**没有** `CAPTURE` / `PREPARE` / `START`，不会假装在录（真机实测，
  [`m6-平板与PC平台能力.md` §7.5](m6-平板与PC平台能力.md#L468-L477)）；
- **不要循环弹权限框**（共享契约错误表）；拒绝后引导用户去系统设置，
  从设置回来后再查一次，不要自动反复请求。

### 6.2 录音时保持屏幕常亮（硬性要求）

平台限制：**熄屏/锁屏时系统强制 STOP 音频采集，亮屏也不恢复**；
应用层绕不过（[`m6-平板与PC平台能力.md` §7.3](m6-平板与PC平台能力.md#L402-L445)、
[`#131`](https://github.com/xingxue-ux/unwritten-diary/issues/131)）。
所以录音开始必须：

```ts
// VoiceRecorder.start() 内部已经做；产品页面不要绕过
this.keepScreen = await this.screen.enable(this.context);
// keepScreen.ok / error_code / error_message 要暴露给页面
```

- `setWindowKeepScreenOn(true)`；停止/异常/`abort`/Ability 销毁时**必须**释放
  （`false`），不能让用户设备一直亮着；Ability 的 `onDestroy` 至少调一次 `abort()`
  兜底（若已 stop 则是空操作）；
- 设置失败**不阻断录音**，但页面要显示「无法保持屏幕常亮，熄屏可能中断录音」；
- 不做电源状态操作（不按 Power、不 suspend、不改息屏超时）；
- 实测：8 秒用例 `KEEP_SCREEN_ON ok=true`、4 段/8000 ms、停止后 `released`
  （[`m6` §7.6](m6-平板与PC平台能力.md#L479-L506)）；
- **未验**：系统息屏超时 30,000 ms，8 秒用例没有跨过阈值；「超过 30 秒仍不熄屏」
  没有真机验证。产品文案不要承诺「任何时长都不会熄屏」，只说「录音期间保持屏幕常亮」。

**UI 必须明说**：录音页显示「录音期间屏幕会保持常亮（系统限制：熄屏会停止采集）」；
用户主动按 Power 仍然会中断，且不会自动恢复。

### 6.3 录音状态机（页面按钮）

`VoiceRecorder` 的阶段与核心 `RecordingSession.state` 不是一一对应，页面按下面做：

| 阶段/状态 | 来源 | 页面 | 按钮 |
|---|---|---|---|
| `idle` | `currentPhase()` | 未开始 | 「开始录音」 |
| `preparing` | `currentPhase()` | 准备中（权限/草稿/票据/采集器） | 全禁用 |
| `recording` | `currentPhase()` 或 `RecordingSession.state` | 计时、波形、常亮提示 | 「停止并保存」 |
| `stopping` | `currentPhase()` | 保存中 | 全禁用 |
| `saved` | `finalize` 返回值 | 已保存；显示 `logical_duration_ms`、`transcription_queued` | 「完成」/「再录一条」 |
| `recoverable` | `finalize` 返回值 / `recover` | 已保存但**不完整**；显示丢失提示 | 「保存已录部分」/「稍后」 |
| `interrupted` | `recover` | 被系统中断；可能没有可用片段 | 「重新开始」；不要给「保存」除非有片段 |
| `error` | `currentPhase()` / 异常 | 录音出错；显示 `error()` | 有片段：「保存已录部分」；无片段：「重新开始」 |
| `paused` | 平台经 `recordings.updateState` **显式上报** | 已暂停 | **不要做「继续」按钮**：核心不自己写这个状态，`VoiceRecorder` 也从不报 pause/resume |

**中途出错**：`VoiceRecorder.fail()` 会把 `phase=error`，但核心会话**故意保持
`recording`**，以便进程被杀后下次 `recover` 能找到；此时页面给「保存已录部分」，
`stop('capture_error')` 仍可最终化已登记片段
（[`VoiceRecorder.ets`](../../apps/ohos-diary-core/entry/src/main/ets/recording/VoiceRecorder.ets#L517-L539)）。

**用户取消**：`VoiceRecorder.abort()` 会停止采集、删当前半截片段、释放常亮/长时任务，
但**不 finalize**；核心会话仍然存在，下次启动 `recover` 会提示。
如果产品要「彻底丢弃」，当前**没有核心方法**（§6.8）。

### 6.4 分片文件约定（自己实现采集时必看）

- PCM：16,000 Hz / 单声道 / 16 bit 小端；
- 默认 2 秒一段（`RecorderOptions.segmentMs=2000`），产品可改 10–30 秒；
- **第 0 段 = 44 字节 WAV 头 + PCM；第 N 段（N≥1）= 裸 PCM**；
  `finalize` 按字节拼接，如果每段都带 WAV 头，第二个头会被当 PCM 读；
- WAV 头里的 `RIFF size` / `data size` 是流式占位 `0xFFFFFFFF`；核心按
  `min(声明长度, 剩余长度)` 读取，所以能拼到 blob 末尾；外部播放器可能显示 4 GiB
  或拒绝播放，**播放/导出未验**；
- 片段文件名稳定、补零（`segment-000000.wav`、`segment-000001.pcm`…）；
  `registerSegment.segment.relative_file_name` 是**相对暂存目录的文件名**，不是绝对路径；
- `duration_ms` 按 PCM 字节算（`bytes × 1000 / 32000`），不按墙上时间；
- 核心会重算 sha256 / 字节数；声明不对报 `integrity_failed`；
- 只有 `registerSegment` 成功（`durable=true`）才把这段算进 `persistedMs`。

来源：[`m6` §3.1/§3.2](m6-平板与PC平台能力.md#L100-L131)、
[`VoiceRecorder.ets`](../../apps/ohos-diary-core/entry/src/main/ets/recording/VoiceRecorder.ets#L386-L455)。

### 6.5 中断、熄屏、来电

- `stateChange` 在 `recording` 期间变成非 `RUNNING` ⇒ `interrupted=true`；
  `audioInterrupt` 只记日志，不置位（[`VoiceRecorder.ets`](../../apps/ohos-diary-core/entry/src/main/ets/recording/VoiceRecorder.ets#L230-L245)）；
- 停止时 `end_reason` 写成 `<reason>_interrupted`；日志 `CAPTURE INTERRUPTED` /
  `STOP interrupted=true`；
- **熄屏 STOP 后没有自动恢复**；亮屏也不会续采；
- **`finalize.state=saved` 不代表完整**：如果用户按了 Power，系统在墙上时间上少了音，
  但核心只看已登记片段有没有缺口，仍可能报 `saved`。页面必须结合
  `wasInterrupted()` 显示「可能少录」；
- 这个「墙上时间缺口」核心表达不了，产品/核心要一起定（`m6` §10 拍板项 4）；
  当前 UI 不要报精确少录秒数，只能说「可能少录」。

### 6.6 崩溃恢复：`persisted` vs `received`

每次启动先 `recoverRecording({})`（核心 `open` 时已把未收尾会话标成
`recoverable` / `interrupted`）：

```ts
const recovery = core.recoverRecording({});
if (recovery.recording_id !== null) {
  const saved = recovery.persisted_ms;
  const tail = Math.max(0, recovery.received_ms - recovery.persisted_ms);
  // 显示「已保存 X 秒；崩溃前可能还有约 Y 秒未保存（不完整）」
}
```

| 字段 | 含义 | 怎么用 |
|---|---|---|
| `recording_id` | 最近的未收尾录音；没有则 null | 有才显示恢复卡片 |
| `state` | `recoverable` / `interrupted` / … | `interrupted` 可能没有片段 |
| `closed_segment_indexes` | 真实已登记序号 | `finalize` 的 `last_segment_index = max(...)`；空则不能保存 |
| `persisted_ms` | **已登记**片段时长之和 = 真正能拼出的音频 | **只能用它当「录音有多长」** |
| `received_ms` | 采集器最后一次上报的收到量 | 下界；可能落后约 1 秒，不能当长度 |
| `gap_ms` | 已知缺口估算（按平均段长） | 有缺口时显示；0 不代表没丢 |
| `notes` | 中文整句说明 | **原样显示**，不要自己编 |

来源：[`RecordingRecovery`](../../apps/ohos-diary-core/entry/src/main/ets/core/Models.ets#L559-L570)、
[`recordings.rs` recover](../../crates/diary_core/src/recordings.rs#L404-L481)、
[`m6` §6.1/§7.7](m6-平板与PC平台能力.md#L265-L335)。

**保存已录部分**：

```ts
const last = Math.max(...recovery.closed_segment_indexes);
const result = core.finalizeRecording({
  recording_id: recovery.recording_id!,
  last_segment_index: last,
  end_reason: 'recovered_on_startup'
});
// result.logical_duration_ms === recovery.persisted_ms（断言口径）
// result.transcription_queued === true
```

**界面铁律**：

1. 不要用 `received_ms` 当录音长度；可播放/可转写只有 `persisted_ms`；
2. 有尾巴时**显式提示**，建议文案：「已保存 3.0 秒音频；崩溃前还有约 0.5 秒未保存
   （不完整）」；
3. 提示里不要报精确丢失时长：`received_ms` 可能落后最多约 1 秒，只能说「约/至少」；
4. `gap_ms=0` 不代表完整：notes 可能说「最后一段之后仍可能有没封闭的尾巴」；
5. 恢复后先展示「已保存 / 可能丢失」，再让用户决定是否保存；不要自动把缺尾巴的
   音频当完整一段；
6. `closed_segment_indexes` 为空时不要调 `finalize`（会 `invalid_state`）；
7. **不要重复 finalize**：成功 finalize 后再点一次会 `invalid_state`
   （有缺口的情况还可能 `integrity_failed`，见 §6.8）。

### 6.7 长时任务与后台

- `ContinuousTask.start(context)` 在采集器启动前申请 `AUDIO_RECORDING` 长时任务；
  系统会挂「正在录音」通知；
- 必须在 UIAbility 还在前台时申请；失败**不阻断**前台录音，但结果在
  `ContinuousTaskResult`（`ok` / `error_code` / `error_message`）；
- 真机：Home 后台仍能录（8 秒/4 段/finalize 成功）；
  锁屏/熄屏 STOP（§6.5）；
- 页面不显示 `bgTask.ok` 的技术细节，但失败时应提示「后台录音不可用，请保持应用在前台」；
- 当前**没有**后台唤醒/定时任务（没有 WorkScheduler / 闹钟 / 开机自启，
  [`m6` §9](m6-平板与PC平台能力.md#L618-L619)）。
  转写/索引任务只能在应用启动/回前台/用户操作后由 `jobs.runDue` 推进；
  被系统杀掉后任务留在库里，下次启动继续。

### 6.8 已知缺陷（录音，来自 #133 评审汇总）

这些是**当前 main 的真实问题**，不是界面能修的；做界面前要知道，避免把 bug 当产品行为：

| # | 问题 | 对界面的影响 | 来源 |
|---|---|---|---|
| 1 | `stop()` 里 `writer.finish()` / `reportState()` 在 try 之外；这两处抛错时 `releaseHold()` 不执行 | 屏幕常亮/长时任务可能不释放；UI 在 `stop()` catch 里调 `abort()` 兜底释放 | [`#133` 第 2 条](https://github.com/xingxue-ux/unwritten-diary/issues/133) |
| 2 | `recover({})` 只返回最近一条未收尾会话 | 更早的崩溃会话被压住；启动恢复要按上限循环处理（注意下一条） | [`#133` 第 4 条](https://github.com/xingxue-ux/unwritten-diary/issues/133) |
| 3 | 有缺口的 finalize 仍标 `recoverable`，但 staging 已删 | 下次 `recover` 还会返回它；再 finalize 会 `integrity_failed`。UI 要记住已处理的 `recording_id`，或捕获 `integrity_failed` 显示「已保存过，不再重复保存」 | [`#133` 第 5 条](https://github.com/xingxue-ux/unwritten-diary/issues/133) |
| 4 | 幂等重登记也会累加 `persistedPcmMs` | 若未来加重试，`persisted` 会虚高；页面不要用旧值做精确进度 | [`#133` 第 3 条](https://github.com/xingxue-ux/unwritten-diary/issues/133) |
| 5 | `persisted` 按段各自 round、`received` 对总量 round | 正常停止也可能差 1..n/2 ms 的「假尾巴」；不要显示毫秒级丢失 | [`#133` 第 6 条](https://github.com/xingxue-ux/unwritten-diary/issues/133) |

> 这些缺陷已由评审记录，但**没有在本文档的提交里修**（本任务只写文档、不改代码）。
> 产品接入前应与后端确认修复计划。

## 7 搜索 / 看转写 / 看今天

### 7.1 搜索：三种模式

| `mode` | 行为 | `phase` | 语义不可用时 | UI 标签 |
|---|---|---|---|---|
| `keyword`（默认） | 关键词索引 | 还有下一页 = `keyword_ready`；最后一页/结果装得下 = `done` | 不受影响 | 关键词 |
| `semantic` | 语义检索；需要模型 + 可用语义索引 | `done`（一次算完）；取消后 `cancelled` | 无代次/模型失败/口径不一致：**空结果 + warning，不退化**；覆盖不全：**部分结果 + warning** | 语义 |
| `hybrid` | 先关键词（`start`），再显式 `search.upgrade` 融合 | `start` 恒 `keyword_ready`；升级成功 = `hybrid_ready`（融合后首屏，不保证还有下一页）；之后 `nextPage` 翻到最后一页 = `done`；升不了级 = `keyword_ready` | **退化关键词 + warning**（`phase=keyword_ready`） | 关键词（语义未融合）/ 混合（已升级） |

- **`phase` 不是「结束标志」**：`keyword_ready` / `hybrid_ready` 是结果所处的阶段
  （关键词首屏 / 已融合首屏），`hybrid_ready` 也可能没有下一页；只有 `done` 才是
  「这一路算完了」，`cancelled` 是取消快照。**有没有下一页看 `cursor`**（null = 没有）。
- `matched_by` 是每个 hit 的命中原因；只有包含 `semantic` 才显示「语义命中」徽标；
- `index_coverage` 是覆盖程度；`partial` / `metadata_only` 时显示「结果可能不全」；
- `warnings` 是核心给的整句，**原样显示**；不要自己判断「为什么没结果」；
- `page_size` 默认 20、最大 100；`cursor` 不透明，翻页原样回传 `nextPage`（§7.4）；
- **不要按每个按键发一次搜索**：每次 `search.start` 会建会话；混合检索的语义回退路径
  仍有成本（#135 修复前最坏 1.2–1.4 s，修复后约 **650–700 ms**，见
  [`m5-大库可用性.md` §5.2 末尾](m5-大库可用性.md#L392-L396)）。
  用防抖 + 可取消的本地请求序号（旧响应丢弃）。

### 7.2 看转写

- 有 `source_ref`（来源 id 或修订 id）时：`extract` 返回 `ExtractedContent`；
- 转写没配置时，音频提取器可能返回 `metadata_only` + `coverage_reason`
  「还没有配置转写能力，原音频可以保存和播放，但正文暂时搜不到」；
- 转写已完成时：`sources.extract` 会优先返回已有的转写正文（不会覆盖成
  metadata_only）——代码在
  [`extractors.rs`](../../crates/diary_core/src/extractors.rs#L708-L720) 有「已有正文就原样返回」；
- `status=partial` 时显示「部分完成」+ `coverage_reason`；`failed` 显示 `error_code`；
- `segments[].locator` 的 `start_ms`/`end_ms` 可用于音频跳转；
- **录完直接看**：`finalize` 只返回 `asset_id` / `recording_id`，不返回 `source_id`；
  但 `captures.get(capture_id).ordered_source_ids` 里已经有刚建的来源 id，
  把它当 `source_ref` 传给 `extract` 即可（`source_ref` 接受来源 id 或修订 id）。
  不要拿 `asset_id` 去调 `extract`。

### 7.3 看今天 / 历史列表 / 条目详情（已可用）

`captures.list` / `captures.get` 已在 #143 接上，是「看今天」的数据源：

```ts
// 今天：day_key 是当天的 YYYY-MM-DD
const today = core.listCaptures({ day_key: '2026-10-19', limit: 20 });
// 历史：省略 day_key；翻页把 next_cursor 原样放回 cursor
const history = core.listCaptures({ cursor: today.next_cursor, limit: 20 });
// 详情
const detail = core.getCapture({ capture_id: today.captures[0].id });
```

- `CapturePage`：`captures[]` + `next_cursor`（null = 没有下一页）；排序
  `occurred_at DESC, id DESC`；`limit` 默认 20、核心夹 1–100；
- `Capture`：`id` / `revision` / `state` / `day_key` / `draft_text` /
  `ordered_source_ids` / `processing_summary`；
- `captures.get` 对草稿和已提交都可用；录音 `finalize` 之后用 capture id 读回新
  `revision`，**不要猜 revision 去 `commit`**；
- `processing_summary` 当前实现恒为默认值（`capture_from_raw` 里
  [`ProcessingSummary::default()`](../../crates/diary_core/src/lib.rs#L2171)），
  **不要拿它当真实处理状态**；要看转写/索引用 `sources.extract` / `indexes.status` /
  `jobs.list`。

`core.info.capture_count` 只是一个数字，不要拿它当列表；`search.start` 需要有关键词，
空查询返回「查询是空的」而不是列表。

### 7.4 分页、升级、取消（已可用）与快照（仍缺）

| 想做的 | 方法 | 现状 |
|---|---|---|
| 搜索结果下一页 | `search.nextPage` | ✅ 已接；`cursor` 原样回传，省略则用会话记着的下一页；取消后报 `invalid_state`，过期/跨代报 `cursor_expired` |
| 混合检索第二阶段 | `search.upgrade` | ✅ 已接；`start(mode=hybrid)` 先给 `keyword_ready`，升级成功给 `hybrid_ready`（融合后首屏；之后 `nextPage` 翻到底才是 `done`）；语义拿不出证据时仍停在 `keyword_ready` + `warnings` |
| 取消搜索 | `search.cancel` | ✅ 已接；返回 `phase=cancelled` 快照；重复取消幂等；之后 `nextPage` 报 `invalid_state` |
| 搜索快照恢复 | `search.snapshot` | ❌ 仍未接；会话在内存里，重启/过期只能重新 `search.start` |

- **`upgrade` 是显式的**：不要把 hybrid 做成「先出关键词、后台自动融合」——不调
  `upgradeSearch` 就不会发生融合；
- 升级成功后旧游标一律失效（`cursor_expired`）；用升级返回快照里的新 `cursor`；
- `phase=keyword_ready` / `hybrid_ready` 都不是结束标志；`hybrid_ready` 的**首屏**（刚升级）
  也可能没有下一页——有没有下一页只看 `cursor`（null = 没有），不要拿 phase 推（§7.1）。

## 10 待确认与能力缺口

### 10.1 #143 之后：C ABI 缺口已清，只剩前端入口

原来这 5 件事已在 #143 全部接上（`WIRED_METHODS` 19 → 30）：

| # | 原缺口 | 现状 | 证据 |
|---:|---|---|---|
| 1 | `captures.list` / `captures.get` | ✅ 已接；「看今天」/历史列表/条目详情有数据源，`finalize` 后用 `captures.get` 读回 revision | `captures_get_and_list_use_real_cursor_pagination` |
| 2 | `indexes.status` | ✅ 已接；`semantic_index_ready` / `reasons` / `model_version` / 块计数都可读，可选 `source_scope` | `indexes_status_exposes_semantic_readiness_and_scope` |
| 3 | `jobs.list` / `jobs.get` | ✅ 已接；逐条带 `attention_key` / `progress`，游标是键集真游标 | `jobs_list_and_get_use_real_cursor_pagination` |
| 4 | `jobs.retry` / `jobs.cancel` / `jobs.acknowledgeAttention` | ✅ 已接；`failed` 可人工重试，取消可用，`attention_key` 可跨重启去重 | `jobs_retry_cancel_and_acknowledge_attention` |
| 5 | `search.nextPage` / `search.upgrade` / `search.cancel` | ✅ 已接；真翻页、显式融合、取消快照 | `search_pagination_upgrade_and_cancel` |

（测试都在 [`crates/diary_capi/src/tests.rs`](../../crates/diary_capi/src/tests.rs)。）

**现在唯一阻塞产品界面的缺口是前端入口，不是 C ABI**：

- `#136` 要求设置页有「一键重建语义索引」，并在 `semantic_index_ready=false` 时显眼；
  `indexes.status` / `indexes.rebuildSemantic` 都已就绪，缺的是页面接线。跟踪见 `#140`。

**还没接、但不阻塞本文界面的**（需要时另开切片）：

| 没接的方法 | 影响 | 现在的替代 |
|---|---|---|
| `search.snapshot` | 重启/索引变化后不能恢复旧搜索快照 | 重新 `search.start`；捕获 `search_expired` 后安静重查 |
| `core.events` / `jobs.nextWakeup` | 没有事件推送/精确唤醒；只能轮询 | 回前台补 `runDueJobs`；页面可见时低频轮询 `jobs.list` |
| `captures.moveDay` / `trash` / `restore` / `previewPurge` / `purge` | 记录生命周期管理（移动日期/删除/恢复/清理）做不了 | 不在本文「录音/看今天/搜索/配置」范围内 |
| `sources.extractedContent` / `previousRevision` / `reviseText` / `locate` | 来源级读取/改正文/定位做不了 | 用 `sources.extract` + `captures.get` |
| `imports.*` / `assets.*` / `backups.*` | 导入、原件打开、备份恢复做不了 | 不在本文范围 |

> 这些不是「设计没想好」，而是 **C ABI 方法子集**还没覆盖；核心实现大多已经存在。
> 接线时注意 `WIRED_METHODS`、`DiaryCore.ets`、`Models.ets`、契约核对工具四处一起改。

### 10.2 产品/实现待确认

| # | 待确认 | 现状 | 影响 |
|---:|---|---|---|
| 1 | 默认包是否允许「只有关键词」 | 默认 HAP 30 MB 不含 1.29.1；`#108` 要求首版含语义 | 发布包选择；界面不能补 |
