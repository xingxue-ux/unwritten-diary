# m5 · 大库可用性：10 万块的语义查询（#90）

> 状态：已完成（2026-10-18）。量测环境是本机 WSL（Linux x86_64、16 核、7.8 GiB）、
> `bge-small-zh-v1.5-ours`（512 维）、SQLite（rusqlite 0.40 bundled）。语料是
> 探针生成的确定性虚构中文，**每块一篇**（100k 块 = 100k 篇）。没有真实用户语料，
> 也没有 Android/鸿蒙真机（见「没有做到的」）。
>
> 结论先给：**1.5 秒里余弦只占 38 ms（2.3%）**。钱花在「逐行 join 取行」（749 ms，
> 45%）与「与查询无关的覆盖状态计数」（540 ms，32%）。两段式精确扫描 + 覆盖计数
> 快路径 + AVX2 之后：100k f32 **P50 1552 → 380 ms**、int8 **1291 → 156 ms**；
> 查询峰值 RSS 增量 **+56.6 → +1.8 MiB**（f32）。**不需要 ANN**。

## 1. 怎么量的

- 基准工具：`tools/probe/src/large_bench.rs`（`large-bench build/query/recall-quality`），
  与产品路径共用 `build_semantic_index` + `start_search(mode = semantic)`，没有另写一套
  余弦或融合；
- 每个规模 **40 次查询**，前 4 次不计（预热），热态 **36** 次取 P50/P95；
- 「冷查询」= 新进程、模型已加载、SQLite 页缓存冷时的**第一次**查询；
- 「查询峰值 RSS」= 查询前 RSS 与查询期间采样峰值的差（不含模型加载与构建）；
- 每块 396 字、单独一天；5 万/10 万的 f32 与 int8 都用**确定性哈希向量**灌库
  （构建时间这一栏不作数）；1 万 f32 用真模型、1 万 int8 用哈希向量；查询向量一律
  来自真模型；
- 对照的「优化前」是 `142a1f1` 的代码在同一台机器、同一批库上的实测（不是文档里的旧数字）。

复现（`$BIN` = `target/release/diary_probe`）：

```bash
export DIARY_MODEL_DIR="/path/to/bge-small-zh-v1.5-ours"
export DIARY_ORT_DYLIB="/path/to/libonnxruntime.so"
# 查询（--profile 打分段计时；--scan-depth 改快速路径候选上限）
$BIN large-bench query 100000 --storage f32  --dir "$HOME/big90-scratch/bench-100k-f32-hash"  --queries 40
$BIN large-bench query 100000 --storage int8 --dir "$HOME/big90-scratch/bench-100k-int8-hash" --queries 40
# 质量集（f32 vs int8，36 条 case）
$BIN large-bench recall-quality
# 2000 块自查询
$BIN large-bench recall-large 2000 --dir "$HOME/big90-scratch/bench-2k-recall"
```

## 2. 「1.5 秒花在哪」：优化前的分段表

100k 块、f32、热态 26 次查询的中位数，墙钟 P50 **1670.03 ms**（带 `--profile`；
探针每条查询额外打点的开销已包含在内）。「占墙钟」是相对 1670 ms。

| 段 | ms | 占墙钟 | 说明 |
|---|---:|---:|---|
| 取行 · SQLite 步进 | 749.30 | 44.9% | 4 张表逐行 join：`chunk_spans` 全扫 + `captures` / `chunk_vectors` / `text_chunks` 每行一次 B-tree 探查 |
| 取行 · 取 13 列（含 BLOB） | 69.27 | 4.1% | 10 万个 `Vec<u8>` + 7 个 `String` 的分配 |
| 反序列化 → `Vec<f32>` | 33.33 | 2.0% | 每行再分配 2 KiB |
| 余弦 / 点积 | **37.92** | **2.3%** | **不是瓶颈** |
| 拼候选 | 6.28 | 0.4% | 又一组字符串移动 |
| 排序 | 37.31 | 2.2% | 10 万条候选 |
| 折叠 | 34.17 | 2.0% | 10 万个 `group_id` 的 `HashSet` + clone |
| 查询嵌入 | 6.07 | 0.4% | 模型推理 |
| SQL 准备 | 0.15 | 0.0% | 语句编译 |
| **候选路径合计** | **1130.05** | **67.7%** | |
| **语义覆盖状态计数** | **539.98** | **32.3%** | `chunks::counts`：两条「逐块相关子查询」的 COUNT，与查询文本无关 |
| 首屏结果装配 | 0.43 | 0.0% | 只取 20 条正文 |
| 会话/装配余量 | -0.5 | -0.1% | 打点误差 |

三个反直觉、但决定后续所有改动的发现：

1. **余弦不是瓶颈**（38 ms，2.3%）。100k×512 的点积本来就该是几十毫秒；
2. **一半以上的钱花在「取行」的 join 上**，而且 `chunk_vectors` 上每行还要回查
   `captures` 与 `text_chunks`——后者**一列都没选**，是纯浪费；
3. **三成的钱花在一条与查询无关的计数上**：覆盖状态每次查询重算，而它只在索引/
   回收站/修订变化时才变。10 万块上是 540 ms，几乎抵得上整个候选路径的一半。

## 3. 改了什么，每项多少收益

| # | 改动 | 收益（100k f32，热态） | 位置 |
|---|---|---|---|
| 1 | **覆盖状态计数快路径**：全库没有「无 span 的块」「过期 span」时，两个计数退化成三条简单查询；有异常才回退精确 SQL | 540 → 25 ms | `chunks::counts_fast_checked` |
| 2 | **去掉没选任何列的 `text_chunks` join** | 步进 749 → 533 ms | `semantic::candidates_impl` |
| 3 | **两段式精确扫描**：单表扫向量选 top-K 块（`FAST_SCAN_DEPTH = 4096`），只对 K 块 join `chunk_spans`/`captures`；有块被后置过滤掉就整条回退精确 SQL | 整条候选路径 1130 → 367 ms（第 2–7 项合计） | `semantic::candidates_fast` |
| 4 | **打分不分配 `Vec<f32>`**：直接从 BLOB 字节读；查询向量模长只算一次；三条路径共用 `score_of` | 反序列化 33 → 0；余弦 38 → ~8 | `semantic::score_of` |
| 5 | **AVX2 点积**（运行时探测；非 x86_64 走标量四累加器） | f32 余弦 52 → 7.6 ms；int8 58 → 9.1 ms | `dot_norm_*` |
| 6 | **堆里只留 top-K**（原来留全部候选的元数据） | 查询峰值 RSS +56.6 → +1.8 MiB | `candidates_fast` |
| 7 | top-K rowid 升序取元数据（页局部性） | 元数据段约 -10% | `candidates_fast` |

### 3.1 两段式扫描的边界（为什么这不是 ANN，也不是「偷工减料」）

- **保留范围内的名次逐条精算**：top-K 的选法是全量扫描 + 精确余弦，K 条之间按完整
  同分键排序；没有聚类、没有近似距离、没有随机化；
- **只保留前 K 块**：K = 4 096 块（默认每页 20 条时约 200 页），第 K 块之后的结果不再
  返回。**这不是召回损失**（前 K 名的名次不变），是**结果深度上限**。上限是「块」不是
  「篇」：一篇超长材料（例如 4 096 块的长转写）理论上能把 K 个名额占满、折叠后只剩
  一条结果。正常语料不会这样，但这一片**没有做自适应扩深**，写在这里；
- **过滤查询不走快速路径**：日期 / 类型 / 来源范围会把候选限制在子集里，单表扫描
  没有这些列，先选 top-K 再过滤会漏掉「分数不高但符合过滤条件」的块。这类查询
  仍走逐行 join 的精确 SQL（候选集通常小得多）；
- **默认过滤器下的后置核对**：`include_trashed` 与「来源修订是否仍是当前」需要
  span/capture 列。快速路径对 top-K 做这两个核对；**只要有一条被过滤掉，就整条回退
  到精确 SQL**——「前 K 条恰好都有效」不能证明「第 K+1 条没有更该出现」；
- **逐位一致**：三条路径（快速、流式精确、全量参考）共用同一个 `score_of`，分数
  逐位相同。既有测试 `streaming_scan_matches_the_load_all_reference` 与新测试
  `fast_scan_falls_back_when_a_top_candidate_is_filtered_out` 钉住这两条。

### 3.2 试过但没采用：mmap

`PRAGMA mmap_size = 512 MiB` 把 f32 100k 的 P50 从 615 → 544 ms（-70 ms），但查询
峰值 RSS 从 **+5 MiB 涨到 +511 MiB**（映射页计入 RSS）。用 +511 MiB 常驻内存换 12%
的延迟，在移动端不可接受，**没有进产品默认**；探针保留 `--mmap-mib` 供以后复查。
比 mmap 更好的方向是把向量放进独立文件做**顺序读**（见「没有做到的」），那是另一个
存储布局，不在这一片。

## 4. 优化后的分段（100k，`--scan-depth 4096`）

墙钟 P50：f32 **389.76 ms**、int8 **185.90 ms**（带 `--profile`；不带打点分别约
380 / 156 ms。打点本身在 int8 上约 +30 ms，因为每行两次 `Instant::now`）。

| 段 | f32 ms | 占墙钟 | int8 ms | 占墙钟 |
|---|---:|---:|---:|---:|
| 快速路径 · 单表向量扫描 | 195.54 | 50.2% | 89.90 | 48.4% |
| ├ 取行 · SQLite 步进 | 159.66 | 41.0% | 45.68 | 24.6% |
| ├ 取行 · 取列（含 BLOB） | 11.86 | 3.0% | 15.55 | 8.4% |
| ├ 余弦 / 点积 | 7.77 | 2.0% | 9.10 | 4.9% |
| └ top-K 维护 | 5.51 | 1.4% | 4.55 | 2.4% |
| 快速路径 · top-K 元数据 | 34.67 | 8.9% | 33.39 | 18.0% |
| 查询嵌入 | 7.32 | 1.9% | 7.15 | 3.8% |
| 排序 | 0.99 | 0.3% | 1.03 | 0.6% |
| 折叠 | 0.73 | 0.2% | 0.73 | 0.4% |
| 语义覆盖状态计数 | 25.24 | 6.5% | 25.14 | 13.5% |
| 首屏结果装配 | 0.30 | 0.1% | 0.30 | 0.2% |
| **候选路径合计** | **366.67** | **94.1%** | **161.27** | **86.7%** |

剩下的账：

- **SQLite 顺序读整代向量**是最大的一笔（f32 160 ms / int8 46 ms）。195 MiB 的 BLOB
  在 SQLite 里以 ~1.2 GB/s 读出来，已经不是「每行 join」的问题，而是**向量体积**的
  问题——所以 int8 的扫描只有 f32 的约 1/2.2；
- **top-K 元数据**（K=4096 个块的 span+capture）33–35 ms，其中 29–30 ms 是 SQLite
  的 3 张表随机探查。这一笔随 K 线性增长（见下表的深度曲线）；
- **覆盖状态计数** 25 ms 是「不做缓存」的代价：它仍然可以再省，但要知道什么时候
  失效就必须在每一次写路径上挂钩子，风险大于收益，这一片不做。

### 4.1 候选上限（深度）vs 延迟，100k

| `--scan-depth` | f32 P50 | int8 P50 | 说明 |
|---:|---:|---:|---|
| 2048 | 347 ms | 136 ms | 约 100 页（每页 20 条） |
| **4096（默认）** | **366 ms** | **156 ms** | 约 200 页（每页 20 条） |
| 8192 | 411 ms | 200 ms | 约 400 页（每页 20 条） |

取 4 096：int8 的 P95 才能稳定压在 200 ms 以内，同时保留 200 页的翻页深度。这是
**结果深度**的取舍，不是召回取舍；写死在 `semantic::FAST_SCAN_DEPTH`，探针可覆盖
来扫曲线。

「冷」= 新进程、页缓存冷时的第一次查询。

| 10k | f32 | 19.5 MiB | 113.2 ms | **79.5 ms** | 124.8 ms | **91.3 ms** | 131–685 ms | 50–454 ms* | +5.2 MiB | **+0.3 MiB** |
| 10k | int8 | 4.9 MiB | 97.4 ms | **47.6 ms** | 111.6 ms | **60.3 ms** | 113–376 ms | 52–246 ms* | +5.2 MiB | **+1.2 MiB** |
| 50k | f32 | 97.7 MiB | 715.7 ms | **213.2 ms** | 836.9 ms | **242.2 ms** | 833 ms | 702 ms* | +26.0 MiB | **+4.3 MiB** |
| 50k | int8 | 24.6 MiB | 628.6 ms | **114.9 ms** | 685.0 ms | **140.8 ms** | 636 ms | 654 ms* | +26.4 MiB | **+2.7 MiB** |

| 100k | int8 | 49.2 MiB | 1291.2 ms | **155.9 ms** | 1422.8 ms | **178.5 ms** | 3758 ms | **263 ms*** | +58.8 MiB | **+1.0 MiB** |

\* 这一列的冷查询受「上一轮跑过什么」影响很大（页缓存里还留着库文件）：同一套
代码在 10k 上两次跑出 82 ms 与 454 ms 都出现过。上表的「冷」是同一轮矩阵里的第一次
查询，**只能作量级参考**，小库的冷热差异不作为回归依据。为了给一个可复现的冷数字，另用
`posix_fadvise(DONTNEED)` 主动驱逐库文件后各跑两次：

| 100k | 优化前 | 优化后 |
|---|---|---|
| f32 冷查询 | 4 280 / 4 612 ms | **2 688 / 2 903 ms** |
| int8 冷查询 | 4 065 / 5 108 ms | **2 391 / 2 591 ms** |

冷查询仍然是**秒级**：它要把整代向量从磁盘读进来（f32 195 MiB / int8 49 MiB），
这台 WSL 机器的冷盘速度只有几十 MB/s。**热态**才是用户翻来覆去查的那个数字；
冷启动要再快，得靠「后台预读 / 首屏不阻塞」这类产品策略，这一片没做。

### 5.1 小库没有变慢（但首次查询多了一次元数据查询）

1k 块（各跑 3 次）：热态 P50 优化前 15.8–19.1 ms、优化后 14.4–15.3 ms（略快）；
主动驱逐页缓存后的首次查询：优化前 34/54/34 ms、优化后 46/50/46 ms——**冷启动慢
约 10 ms**，来自快速路径的第二段（只取 top-K 元数据）多读一遍库。产品里首次语义
查询还包含模型加载（秒级），这 10 ms 不在关键路径上；热态完全不慢。

10k 块（各跑 2 次取中位）：f32 113 → 80 ms、int8 97 → 48 ms（覆盖计数与 join 的
收益已经显现）。**没有出现「为了大库把小库拖慢」**；唯一可见的代价是 1k 冷启动
那约 10 ms。

**0/32 条查询的名次发生变化。** 这是「量化没有改变排序」的直接证据。

### 6.2 2000 块自查询（`large-bench recall-large 2000`）

| | R@1 | R@10 | MRR | 名次变化 |
|---|---:|---:|---:|---:|
| f32 | 77% | 94% | 0.835 | — |
| int8 | 77% | 94% | **0.833** | 10/100 |

自查询（拿被查块自己的前 40 字当查询）只回答「量化有没有改变排序」，不代表真实
改写过的查询；它给的是**边界**：R@1/R@10 不变，MRR 掉 0.002，100 条里 10 条名次
变化（多为相邻名次互换）。

### 6.3 结论：保留 f32 默认，int8 记为「体积优先 / 大库推荐」

按任务书的口径逐条对：

- **R@1 / R@10 不降**：36 条质量集逐项相同、2000 块自查询也相同；
- **MRR 有轻微下降**：2000 块自查询 0.835 → 0.833（-0.002，100 条里 10 条名次变化，
  多为相邻互换）。36 条质量集上是 0.917 → 0.917（0/32 变化）；
- **没有真实语料**：两组都是合成语料/自查询。项目一贯的口径是「没有量到就不假装
  量到了」，所以**不把「小语料上一致」当成「可以改所有人的默认」**。

因此这一片**保留 f32 默认**，把 int8 明确记为：

- **体积优先**：100k 裸向量 195.3 → 49.2 MiB（4.0×）；
- **大库推荐**：100k 热查询 380 → 156 ms（10k/50k 同样约 2×）；
- **代价**：构建时多一遍量化编码（2000 块上 f32 148.9 s vs int8 172.0 s，+15%，
  同一批块各整代重算一次、含模型推理，偏差较大）；已有库换格式 = **整代重算**
  （`storage` 是口径三字段之一，#58 的路径），大库上是一次重活；量化误差仍在
  （每分量 ≤ 半个 scale），只是这两组语料上没有改变 R@1/R@10。

**需要拍板**：①要不要把 `DEFAULT_VECTOR_STORAGE` 改成 int8（一行，但会让所有已有库
在下一次 `build_semantic_index` 时整代重算）；②要不要给用户一个「体积优先」开关
（现在 `set_vector_storage_for_test` 是 `#[doc(hidden)]`，产品没有暴露这个选择）。
在真实语料上复验之前，这一片不动默认。

## 7. 要不要 ANN？

**不要。** 依据：

1. 精确扫描已经进了可接受区间：100k int8 **P50 156 ms / P95 179 ms**；f32 380/405 ms。
   再用 ANN 换来的加速（通常 2–5×）不足以抵消它带来的三件事：有损召回（要调
   `ef`/`M`/`nprobe`）、索引构建与内存、以及「同一批查询两次结果可能不同」的
   不确定性；
2. 这一片的所有优化都**没有牺牲名次**：快速路径是精确 top-K，不是近似最近邻。
   引入 ANN 之后，「为什么这条没搜到」会变成一类无法如实回答的问题；
3. 真正的下一个瓶颈是**向量字节的磁盘/内存带宽**（f32 195 MiB 顺序读 160 ms），
   ANN 不解决它；换 int8、独立向量文件的顺序读、或内存索引才解决。

**什么时候再考虑 ANN**：库到 100 万块量级（int8 ~490 MiB，外推 1.5–2.5 s/查询），
且产品要求亚秒级；或者移动端要求 200 ms 以内而 CPU 更弱。那时的第一步不是 HNSW，
而是先量「顺序读 + int8 + 多线程点积」能到多少。

## 8. 什么规模用什么配置

| 规模 | 推荐 | 热查询（P50/P95） | 说明 |
|---|---|---|---|
| ≤1k | f32 或 int8 都行 | 约 15 ms | 模型加载/首屏才是主要成本；查询不是瓶颈 |
| 1k–10k | f32 可用；体积敏感用 int8 | f32 75 ms · int8 48 ms | 10k f32 裸向量 19.5 MiB，int8 4.9 MiB |
| 10k–50k | **int8** | 50k：115 / 141 ms | f32 在 50k 已到 213/242 ms |
| 50k–100k | **int8** | 100k：156 / 179 ms | f32 380/405 ms，仍可用但差距明显 |
| >100k | 未实测 | 外推 | 按 O(n) 线性外推；届时先量独立向量文件/内存索引 |

「大库」的判据不是块数本身，而是**向量总量**：f32 100k ≈ 195 MiB，int8 ≈ 49 MiB。
默认存储仍是 f32（见 6.3），所以 10 万块的默认体验是 380/405 ms；int8 的 156/179 ms
目前要改默认常量或加产品开关才能拿到——两者都是待拍板的口径变更，不是这一片擅自
改的。

## 9. 没有做到的

- **Android / 鸿蒙真机**：没有量。AVX2 只在 x86_64 上用；aarch64 走标量四累加器
  （正确性有测试，速度没量）。移动端的 CPU、磁盘、内存压力都与本机不同，这一片的
  数字**不能直接外推到手机**；
- **并发**：`Core` 是单连接、同步的；多个查询并发会串行。没有量「查询与后台建索引
  同时跑」时的延迟与锁等待，「10 万块 + 构建中查询」也没量；
- **100k 以上的外推**：只有 1k/10k/50k/100k 四个点。按扫描字节线性外推，100 万块
  f32 约 1.9 GB/次查询、int8 约 0.5 GB/次；这只是算术，不是实测；
- **冷启动优化**：冷查询仍要 2.4–2.9 s（磁盘读整代向量）。后台预读、首屏先给关键词、
  向量独立文件 + 顺序读都没做；
- **覆盖计数的缓存**：25 ms/查询仍在。要做对必须在所有写路径上挂失效钩子（回收站、
  修订、重建、导入），这一片选择了「宁可算，也不缓存错」；
- **结果深度上限**：快速路径只保留前 4096 块（约 200 页）。更深的翻页拿不到结果；
  超长文档占满 top-K 时，折叠后的结果会明显少于 4096 篇（最坏 1 篇）。正常使用翻不到，
  但这是一条**行为变化**，写在 `FAST_SCAN_DEPTH` 的注释里；
- **真实语料**：质量集是合成的 36 条 + 2000 块自查询；没有真实用户的查询改写、
  多语言、长文档分布。int8 的「召回不降」只在这两组语料上成立。
