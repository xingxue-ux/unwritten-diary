## 2. 中文短词检索

### 2.1 方法

语料是虚构日记片段：同一子句内的词不加分隔地连在一起，只有子句之间有标点。这一点很关键——如果每个词都用逗号隔开，`unicode61` 会因为标点切分而**假性通过**，测不出中文分词的真正问题（第一版语料就是这样，结论完全反了）。

每条路径测两个指标：

- **全量计数**：`count(*)` 真实命中条数，用来核对召回是否完整，也是最坏情况延迟。
- **首屏 20 条**：`LIMIT 20`，更接近用户真实体验。

### 2.2 结果：10 万片段（约 330 万字）

| 路径 | 索引体积 | 构建 | 二字查询首屏 | 召回 |
|---|---|---|---|---|
| FTS5 unicode61 | 15.0 MiB | 543 ms | 0.026 ms | **0/5** |
| FTS5 trigram | 20.2 MiB | 451 ms | 0.016 ms | **1/5**（只有三字词） |
| 自建 n-gram（2-gram + 1-gram） | 158.1 MiB | 5550 ms | 34.9 ms | 5/5 |
| jieba 分词 + 2-gram 补充（并集） | 138.6 MiB | 4922 ms | **0.068 ms** | **5/5** |

查询集：`妈妈`、`离职`、`面试`、`加班`（二字）与 `面试官`（三字）。真值由子串匹配得出（例如 `妈妈` 命中 40828 条）。

### 2.3 三个必须记住的观察

1. **`unicode61` 对中文完全不可用**：0/5 召回。中文连续文本会被当成一个长 token，`妈妈` 根本不是一个 token。任务书 5.3 节的警告成立，不是理论担忧。
2. **`trigram` 只解决三字以上**：`面试官` 全召回，而 `妈妈`/`离职`/`面试`/`加班` 全部 0 命中——因为 trigram 无法匹配短于三个字符的查询。而「妈妈」「离职」恰恰是用户最常输入的形态。
3. **纯 n-gram 与分词方案的代价结构不同**。纯 2-gram 索引体积是分词方案的 1.14 倍，首屏延迟是 500 倍（34.9 ms 对 0.068 ms）——因为分词索引先把候选缩小，2-gram 只用来补漏。反过来，分词方案的全量计数更慢（84 ms 对 34 ms），因为它要多取并集；但真实查询要的是首屏，不是全量。

### 2.4 选型与已知代价

选 **jieba 分词 + 2-gram 补充（并集）**，不是二选一。具体约定：

- 分词索引与 2-gram 索引**永远取并集**，不能做成「分词查不到才回退」。实测中 `面试官` 被 jieba 切成一个词，查询 `面试` 在分词索引里漏掉 224 条（20k 语料），只做回退就永远补不回这些。
- 索引体积是真实代价：约 **42 字节/源文本字符**（138.6 MiB / 3.3M 字）。这远大于 FTS5 的约 4.7 字节/字符。M2 需要用「高频 gram 剪枝」或「只对短查询启用 2-gram」来压。
- **未测量**：jieba 词典的包体与常驻内存代价（需要单独做打包测量）；10 万片段以上的扩展性；多字查询（4 字以上）的召回；`matchedBy` 两路分数的合并（RRF）表现。

### 2.5 两端复跑

同一份断言在 Windows x64 与 Android x86_64 模拟器上复跑（各 3000 片段），四条路径的**召回结论完全一致**：

| 平台 | unicode61 | trigram | 纯 n-gram 首屏 | jieba+2-gram 首屏 |
|---|---|---|---|---|
| Linux 宿主（10 万片段） | 0/5 | 1/5 | 34.9 ms | **0.068 ms** |
| Windows x64（3000 片段） | 0/5 | 1/5 | 0.377 ms | **0.097 ms** |
| Android x86_64 模拟器（3000 片段） | 0/5 | 1/5 | 0.489 ms | **0.051 ms** |

片段数不同，绝对延迟不能横向比较；可比的是召回结论，以及「jieba+2-gram 的首屏远快于纯 n-gram」这个相对关系——三处都成立。

复现：

```bash
cargo run --release -p diary_probe -- short-word-search 100000
# Android：cargo ndk -t x86_64 build --release -p diary_probe --no-default-features --features search
#          再把可执行文件 adb push 到 /data/local/tmp 执行
```

### 3.2 质量

3 条虚构查询各配 3 个候选句，检查相关句能否排第一：**3/3 正确**（余弦 0.502–0.659）。这**不构成质量评估**——任务书要求的检索质量集还没有建，bge 系列建议的查询指令前缀也没有验证。

### 3.3 退出阶段崩溃（issue #17，**两个平台分别解决**）

**症状**：`ort` 用 `load-dynamic` 加载 ONNX Runtime 后，进程**退出阶段**崩，而且
**两个平台的成因不同**：

| 平台 | 症状 | 退出码 |
|---|---|---|
| Linux 宿主（WSL2 x86_64），ORT 1.22.0 | 全部输出之后裸 SIGSEGV | 139 |
| Android x86_64 模拟器，同一份 ORT 1.22.0 | `FORTIFY: pthread_mutex_lock called on a destroyed mutex` 之后 abort | 134 |
| Windows x64 | 从未观察到 | — |

**两个猜测都被实测否掉了。** 最初写的是「动态库卸载与 ORT 自身析构的顺序冲突」，
后来又想成「Rust 在退出前释放了 session」。实验逐个排除：

| 实验 | 退出码（Linux 宿主） |
|---|---|
| 只初始化环境（`ort::init_from` + `commit`）、不建 session | **0** |
| 建 session 之后正常析构 | **139** |
| 自己再 `dlopen` 一次同一个库并把句柄泄漏（把引用计数钉住，防卸载） | **仍然 139** |
| session 放进 `static`（Rust 不跑 static 的析构） | **0** |

第三行否掉了「库被卸载」：把引用计数钉住之后库一直在映射里，崩溃照旧；何况 Rust 的
`static` 本来就不跑析构。第一行说明光有环境和库也没事。**Linux 上**真正的组合是
「会话被释放 + ORT 退出阶段的全局收尾」。

**但 Android 上这条修复不管用。** 在 Android x86_64 模拟器上复验（同一份源码、
同一个 ORT 1.22.0）：桌面拿到的 `0` 在 Android 上是 **3/3 都是 134**。tombstone 把
调用链指清楚了：

```
#04..#08  libonnxruntime.so       ← ORT 内部
#09       __cxa_finalize+205  libc.so
#10       exit+31 / #11 __libc_init+124
```

崩溃发生在 **libonnxruntime.so 自己注册的 C++ 静态析构**里（`exit → __cxa_finalize`），
**与 Rust 释放不释放无关**——session 已经在 `static` 里、Rust 确实没析构它，照样 abort。
所以「资源放进 static」在 Android 上从原理上就挡不住这条路径。

**采用的写法（两段，针对两条不同的路径）：**

1. **进程级单例**（两个平台都要）：模型资源放 `static`，退出不释放。

   ```rust
   /// Rust 不跑 `static` 的析构，所以这些资源既不会被释放，也不会在退出阶段被第二次收尾。
   static EMBEDDER: OnceLock<Mutex<Model>> = OnceLock::new();

   struct Model {
       session: Session,
       tokenizer: Tokenizer,
   }
   ```

   顺带也是性能上的正解：模型只加载一次（省掉每次约 300 ms 的加载）。

2. **Android 上跳过 C 运行时的退出收尾**：`libc::_exit(0)`（先 flush 标准输出）。

   ```rust
   #[cfg(target_os = "android")]
   {
       use std::io::Write;
       let _ = std::io::stdout().flush();
       let _ = std::io::stderr().flush();
       unsafe { libc::_exit(0) }   // 不跑 atexit / __cxa_finalize
   }
   ```

   `_exit` 直接走系统调用退出。这是**绕过**而不是修好 ORT 的 Android 退出收尾；
   之所以可以接受，是因为这条路只在「会被当成 CLI 跑、要求退出码」的入口上有意义
   ——**产品不需要它**：Android 回收应用进程用 SIGKILL，本来就不跑这些析构。

**验证**（修复后、这两段都生效）：

| 平台 | 命令 | 结果 |
|---|---|---|
| Linux 宿主 | `ORT_DYLIB_PATH=… ./target/release/diary_probe vector-model; echo $?` | 退出码 **0**，多次 |
| Android x86_64 模拟器 | `adb shell "cd /data/local/tmp/ortprobe && DIARY_MODEL_DIR=… ORT_DYLIB_PATH=… ./diary_probe vector-model; echo $?"` | 退出码 **0**，**5/5 次**，logcat 无 FORTIFY/abort |

`std::mem::forget(session)` hack 已从探针删除。复现与验证：

```bash
# 桌面
cargo build --release -p diary_probe --features model
ORT_DYLIB_PATH=/path/to/libonnxruntime.so ./target/release/diary_probe vector-model; echo $?

# Android（x86_64 模拟器）
cargo ndk -t x86_64 build --release -p diary_probe --no-default-features --features model
adb push target/x86_64-linux-android/release/diary_probe /data/local/tmp/ortprobe/
# 还要把 libonnxruntime.so 与模型推过去，运行前设 DIARY_MODEL_DIR 与 ORT_DYLIB_PATH
```

**给真实集成（B3c 向量检索）的规则**：

- 模型/session 放**进程级单例**，退出阶段不显式释放；不要 `drop`、也不要
  `mem::forget`；
- **不要指望 ORT 的退出收尾**：Android 上它在库内部就会 abort（本次实测）；核心代码
  不要负责进程退出，也不要让任何入口在退出路径上调用 ORT 的收尾；
- 需要显式释放的场景（热重载、切换模型）**没有验证过**：释放之后不能再让 ORT 的
  退出收尾跑，也不能在同一进程内反复初始化/释放。做之前先补实验。

**CI 覆盖不到**：`model` feature 不进 CI（要权重与 ONNX Runtime 二进制，都不入库），
所以这两条护栏都是代码结构本身——把资源从 static 挪回局部变量会变回 139，
把 Android 的 `_exit` 去掉会变回 134。

**顺带说明**：修复不碰推理路径。质量余弦与 M0 记录完全一致（0.640 / 0.502 / 0.659）。
耗时**有波动**：Linux 宿主短文本 1.8–5.8 ms、482 token 24.5–63.7 ms；Android 模拟器
短文本 4.5–6.8 ms、482 token 128.7–143.2 ms、32 条 7.1–8.5 ms/条。Android 的长文本与
吞吐**三次都高于 3.1 节的旧值**（+12.5%～+42%），没有排除的干扰是「模拟器未重启、
连续跑、负载未控制」——**不作为新基线**，要新基线得在重启后的模拟器上重测。

### 3.4 授权（issue #18，已定论）

**结论：不再分发第三方转换产物，改用我们自己从上游 MIT 权重导出的 ONNX。**

核对到的事实（2026-10-10，HuggingFace API 与仓库文件列表）：

| 对象 | 事实 |
|---|---|
| 上游 `BAAI/bge-small-zh-v1.5` | `cardData.license = mit`（tags 含 `license:mit`）；但仓库里**没有 ONNX**，只有 safetensors / pytorch / 分词器 |
| 第三方转换 `Xenova/bge-small-zh-v1.5` | `cardData` 只有 `base_model` 与 `library_name`，**没有 license 字段**，tags 里也没有 `license:*`，仓库文件列表里**没有 LICENSE 文件** |

上游是 MIT，但那份 ONNX 是第三方转的、且对方没有给出授权声明，所以不能把上游的 MIT
直接当成转换产物的授权。我们不去赌这一条，也不等作者回复：**自己导出**——权重的授权
是清楚的（MIT，随包保留版权与许可声明），导出脚本是我们自己的文件，产物哈希也是对
我们自己的文件算的。

- 导出脚本：`tools/model-export/export_bge_small_zh.py`（固定上游 revision
  `7999e1d3…`、opset 17、INT8 动态量化 QInt8；**不修改**任何 manifest，只打印与写结果文件）
- 产物与哈希：`models/bge-small-zh-v1.5-ours/`（`model_quantized.onnx` 23830209 字节、
  `tokenizer.json` 439125 字节），机器可读记录在同目录 `export-info.json`
- 授权全文（随发布包分发）：`models/manifest/bge-small-zh-v1.5-LICENSE-MIT.txt`
- manifest 的结论与全部证据链接：`models/manifest/bge-small-zh-v1.5.json` 的
  `license` / `licenseEvidence` / `files` / `m0Artifact`

**自己导出的产物要重测一遍**（量化方式与第三方那份不同，数字不会逐位相同）。宿主
（WSL2 x86_64，ORT 1.22.0）复测：短文本中位 3.6 ms、482 token 52.6 ms、32 条 2.2 ms/条、
峰值增量 73 MiB、质量 **3/3 排序正确**（余弦 0.630 / 0.552 / 0.702，对比第三方那份
0.640 / 0.502 / 0.659——排序结论相同，分数不同是量化差异）。这些与 3.1 节基线同量级，
但耗时有波动，**不作为新基线**。

`sources` 那份第三方产物的哈希保留在 manifest 的 `m0Artifact` 里，只作历史记录；
**发布包里不带它**。

范围说明：以上是工程判断与可核对的事实记录，不构成法律意见；发布前按 M5 清单再核一次。

## 4. 插件运行时候选

用 `wasmi` 2.0 解释执行一个 194 字节的最小 Wasm 模块，验证任务书 8.2 节要求的预算能不能真的强制：

| 检查项 | 结果 |
|---|---|
| 指令预算（fuel） | 死循环在 **1,000,000 条指令**处被中止，报 `all fuel consumed by WebAssembly` |
| 线性内存上限 | 上限 128 KiB（2 页）；申请 1 页返回 1，申请 5 页返回 **-1（被拒）** |
| 宿主权限边界 | 未授权读取原件 → **-1（拒绝）**；宿主授权后 → 返回数据 |
| 调用开销 | 20,000 次纯计算调用 3.5 ms，平均 **0.17 µs/次**（含每次重置 fuel） |

结论：**声明式优先的定位不变；代码插件用 wasmi 在预算与权限上是可以强制住的。** 插件不能直接拿到原件——唯一入口是宿主函数，权限判定在宿主侧，插件无法绕过。

调用开销这一项说明「每次插件调用都走解释器」本身不是瓶颈；真正的成本在数据编组与宿主请求，还没有测。

三处平台复跑，结论与数字都一致：

| 平台 | 调用开销 | fuel 中止点 | 内存超限申请 | 未授权读取 |
|---|---|---|---|---|
| Linux 宿主 | 0.17 µs | 1,000,000 条 | -1 | -1 |
| Windows x64 | 0.12 µs | 1,000,000 条 | -1 | -1 |
| Android x86_64 模拟器 | 0.12 µs | 1,000,000 条 | -1 | -1 |

**未测量**：宿主函数自身的超时（需要真实 IO 才能测）、插件包体与加载耗时（需要真实插件包）、arm64 真机上的表现。

复现：

```bash
cargo run --release -p diary_probe -- plugin-runtime
cargo check --release -p diary_probe --no-default-features --features plugin --target aarch64-linux-android
```

## 5. 本轮的方法学教训

这三条比数字更值得留给后来的人：

1. **语料会骗人。** 第一版语料把每个词都用逗号隔开，`unicode61` 得到 5/5 全召回，看起来「FTS5 直接能用」。改成连续中文后，同一个实现是 0/5。测量中文检索必须用连续文本语料。
2. **`count(*)` 不是查询延迟。** 第一版只测全量计数，`jieba` 方案看起来比纯 n-gram 慢 2 倍；加上「首屏 20 条」后，结论完全反过来（0.068 ms 对 34.9 ms）。选型要按真实查询形态测。
3. **回退式设计会漏召回。** 「分词查不到再查 n-gram」听起来合理，实际会漏掉分词切分造成的缺口。必须是并集。
4. **把 MSRV 钉在 CI 上是值的。** 本地用 Rust 1.98 编译通过的一处泛型推导（`&'a [T] -> &'a T` 靠自动解引用），在 CI 的 1.94.1 上直接编译失败——推导出了 `T = str`。如果 CI 只跑最新 stable，这个问题会在 Windows 侧（1.94.1）才炸出来。CI 因此固定安装 `rust-version` 下限那个版本。

## 6. 未完成的部分

- **arm64 真机全部未验证**：Android 侧的检索、插件、向量模型都只在 x86_64 模拟器上跑过。模拟器 CPU 与真实 arm64 设备完全不同——长文本推理在模拟器上是 114.4 ms、桌面 25.9 ms，差 4.4 倍，所以**耗时与内存数字不能外推到手机**；能成立的是「在这三个平台上行为一致」。
- **模型授权已定论**（见 3.4）：发布包用我们自己从上游 MIT 权重导出的 ONNX，
  第三方转换产物不带进发布包。
- **ORT 退出阶段崩溃已解决**（见 3.3）：Linux 用进程级单例（139 → 0）、Android 用
  `libc::_exit` 跳过 C 运行时收尾（134 → 0）。**未验证**的是「同一进程内反复初始化/释放
  ORT」这类场景，真实集成不要走那条路。
- 检索质量集、查询指令前缀、批量推理与线程配置都没有验证。
- 录音片段封闭间隔与最低系统版本仍缺真机条件。
