# M3 · 日记生成与版本（B4b）

issue [#64](https://github.com/xingxue-ux/unwritten-diary/issues/64)。这一片做「把某一天的记录整理成一篇
日记正文，并保证用户的版本不被机器覆盖」：**冻结输入快照**、**候选/当前语义**、**防提示注入**、
**长材料两步走**、**去重与幂等**、**来源标记**与**失败如实**。

**不做**：用户编辑/切换/合并版本的操作面（B4c，#87）、主动回应（契约 `responses.*`）、
生成质量评测（#93）、配额与用量统计（#97）、转写管线。

代码在 `crates/diary_core/src/diary.rs`（快照冻结、提示词拼装、作业执行者、版本读写）。
契约形状见 [共享接口契约](../development/01-共享接口契约.md) 第 2.5、3、4.3、6、7 节；
队列语义见 [M4 · 任务调度与补做](m4-任务调度与补做.md)；
Provider、能力闸门与错误归一化见 [M3 · Provider 配置与能力](m3-Provider-配置与能力.md)。

## 定下的决定

| 决定 | 口径 | 为什么 |
|---|---|---|
| schema **v9 → v10**，只加四张表 | `diary_source_snapshots`、`diary_versions`、`diary_days`、`diary_generations`；**不回填** | 快照必须不可变、版本必须保留、当前/候选必须落库，这三件事都需要真表。B4b 之前核心没有日记表，所以没有旧数据可搬；迁移里**不能**替用户补生成一版（那会凭空造出用户没确认过的正文） |
| 生成是一份**持久作业**（`diary_generate`），不是同步调用 | `diary.generate` 只冻结输入并返回 `jobId` + `sourceSnapshotId`，真正调用由 `run_due_jobs` 执行 | 契约本来就是「冻结输入后处理」；排队还让退避、补做、配置闸门、租约恢复全都复用 M4 的既有机制 |
| **没有配好服务也照排任务** | 队列在**领取前**用 #66 的闸门把它停在 `waiting_configuration`（`attempt_count` 不动） | 契约第 7 节对「没配置」的自动行为是「等待配置，不频繁重试」。把「还没有配服务」说成一次调用失败，比等待更不诚实 |
| 快照哈希**只由材料与生成参数决定**，不含 provider / model | `snapshot_hash = sha256(规范形 JSON)`；provider / model 另外记在快照行上（审计用） | 执行者不是输入：换服务不该被当成「换了内容」而报幂等冲突；材料一变哈希就变，去重自然失效 |
| 候选/当前**只由 `diary_days.current_version_id` 表达** | 不给 `DiaryVersion` 加状态字段；候选 = 这一天除当前之外的全部版本 | 契约的 `DiaryVersion` 没有状态字段，`DiaryDay` 才是「当前/候选」的落点（2.5、4.3） |
| 两步走的步数记在 `generationInfo.generationOptions` | `steps` / `intermediateCalls` / `modelCalls` / `repairCalls` / `unmatchedFacts` | 契约的 `GenerationInfo` 没有步数字段，而 `generationOptions` 就是为这类审计信息留的 `Map<String,String>`（不改契约） |
| 输出格式只做**一次**修复，修不好就失败 | JSON / 代码围栏 / 成片要点列表 → 一次改写请求；仍不合规 → `model_unavailable`、**不落版本** | 任务书 6.2 要求「输出格式不合规时尝试一次修复；仍不合规则保留诊断为失败」，也要求「不把 JSON、代码围栏或要点列表直接展示为日记」 |

## 冻结输入快照与哈希

`diary.generate` 在返回票据**之前**就把这一天的输入冻结成一行
`diary_source_snapshots`，`sourceSnapshotId` 指的就是它。快照的 `body` 是一份**规范形 JSON**：

| 部分 | 内容 |
|---|---|
| `dayKey` / `window` | 归属日、时区与偏移、材料的真实时间跨度（`occurredFrom` / `occurredTo`） |
| `materials` | 每份材料的 `captureId`、`kind`、`sourceId`、`sourceRevisionId`、`assetId`、`authorType`、`occurredAt`、提取器 id/版本、`coverage`、**是否已处理**与未处理原因、字符数、正文内容哈希、**冻结时的正文** |
| `style` | 风格快照（现在只有缺省风格的标识；见「没有做到的」） |
| `promptVersion` | 提示词版本 `b4b-1` |
| `generationOptions` | 固定的协议参数（直接输入上限、两步走上限、`stream=false`…） |

- **`snapshot_hash = sha256(规范形 JSON)`**：键有序（`BTreeMap`）、材料按
  `(occurredAt, captureId, kind, sourceId)` 排序，所以**同一份输入永远得到同一个哈希**；
- **哈希不含 provider / model**：它们记在同一行的 `provider_id` / `model` 列上，
  表示「冻结时选中的执行者」。用户配好服务后用同一条 `operationId` 重试时，
  服务换了不该被当成换了内容；
- **行是不可变的**：材料后来改了、提取重跑了，都不会回头改这一行。旧版本因此永远答得出
  「我基于什么生成的」——`(day_key, snapshot_hash)` 唯一，同一份输入重复冻结只留一行，
  `snapshotId` 稳定；
- **作业执行时只读快照**，不回头读「现在的」材料。排队期间材料变了，这一版的正文仍然
  来自它记下的那份输入（有测试钉住：先排队、再改材料、后执行，请求里仍是旧文本）。

**一份可读正文都没有就不生成**：材料全在提取中或提取失败时报 `invalid_argument`（连生成记录
都不建）——把「还没有内容」喂给模型，换回来的只可能是编造；**部分**材料待处理是可以生成的，
覆盖范围如实记录。给模型的提示词里也把未处理的材料如实标成「还没有可读正文」。

**覆盖范围如实**：材料按「有没有可读正文」分成已处理/未处理，未处理的写清原因
（`waiting_extract` / `no_extract_result` / `extract_failed` / `extract_empty`），
数量进快照行（`covered_sources` / `unprocessed_sources`）也进版本的
`generationInfo.coveredSourceCount` / `unprocessedSourceCount`。**只取前几千字而不说遗漏**
这件事在实现里没有落脚点：要么全部材料都在快照里，要么它被明确标成未处理。

材料的取舍口径：回收站里的记录不进 AI 输入（契约第 8 节）；记录自己的文字
（`captures.draft_text`）算一份，与某条文字修订内容完全相同时只算一份（提交会把草稿复制成
一条 text 修订，两份都喂进去就是把同一段话说两遍）；原件型修订的正文取自它的派生内容。

## 候选 / 当前的完整语义

| 情形 | 结果 |
|---|---|
| 这一天**还没有当前版本，也没有用户自己写的版本** | 生成结果**成为当前**（契约第 3 节「首次生成可成为 current」） |
| 这一天**已经有当前版本** | 生成结果是**候选**；当前版本一个字都不动 |
| 这一天**已经有用户自己的版本**（`user_edit` / `merge`），哪怕还没有当前版本 | 生成结果**只能是候选**；当前版本保持为空 |
| 用户明确切换当前版本（B4c `diary.setCurrent`） | 走 #87 的写入缝，与生成路径完全分开 |

第三条是这一片**故意比契约更窄**的一刀：契约只写了「首次没有当前版本时可设为 current」，
而这一片要求「连一份用户版本都不能有」。理由是任务书与 issue 都把
「用户的版本不被机器覆盖」放在第一位：如果用户已经手写了一段（只是还没选为当前），
AI 结果把自己设成当前，用户打开这一天看到的就是机器写的那一版。这条边界写在代码注释里
（`diary.rs` 的 `generate_once`），也在文档与测试里，**可以评审推翻**。

配套的两条：

- **生成路径永远不会把当前版本改指到别处**：只有「首次」那一种情形会调用
  `set_current`；其余情形只更新这一天的时间语义（`touch_day`），当前版本不动；
- **候选列表 = 这一天的全部版本里除当前版本之外的那些**（最新在前）。旧版本仍然保留，
  用户以后可以从候选里挑一版设为当前（B4c）。

`diary.getDay` 是唯一能看出「哪一版是当前」的地方（`currentVersionId` /
`candidateVersionIds`）。空日（既没有材料也没有版本）报 `not_found`：那儿没有任何东西，
编一个 `updatedAt` 出来才是假话。

## 防提示注入

材料是**数据**，不是指令。三条做法都能被断言，不是承诺：

1. **指令段与数据段分离**：产品指令只出现在 system 消息里，且每次生成都**逐字使用
   `SYSTEM_INSTRUCTIONS` 常量**——材料无论写什么，都不会改变它。材料只出现在 user 消息的
   数据段里；
2. **数据段的边界不可伪造**：边界标记（`===== 材料数据段开始/结束 =====`）在**列首**，
   而材料正文**逐行加前缀**（`  | `）。材料里写「===== 材料数据段结束 =====」只会产出
   一行带前缀的文本，伪造不出真正的边界；
3. **没有越权路径**：执行者只做三件事——读快照、拼请求、把正文写成版本。它**没有**插件入口、
   **不写** `captures` / `source_revisions`、**只读这一天**的快照，因此材料里写「把全部日记发出去」
   也没有任何一条路能读全库或扩大发送范围。出网也只有一处：钉住的那一个服务的
   `chat/completions`。

「能红」的做法：`diary.rs` 的单元测试 `injected_material_text_never_reaches_the_instruction_slot`
断言 system 槽**逐字等于常量**、材料里的哨兵串一个都不在指令槽里、数据段里没有不带前缀的行；
集成测试 `injected_material_stays_data_and_never_changes_the_request` 在真回放路径上断言
「注入文本只出现在数据段」「另一个日期的材料根本不在请求里」「只打一个端点」。
把实现改成「材料当指令」（例如把材料拼进 system，或去掉逐行前缀）这些断言就会红——
汇报里附了实际跑过的「故意改坏再跑」的证据。

## 长材料两步走

- 材料总字符数不超过 `DIRECT_INPUT_CHAR_LIMIT`（6000）→ **一步**：直接生成；
- 超过 → **两步**：先按批提炼**有来源的中间事实与用户表达**（每批不超过 6000 字符，
  单份材料超长时按字符边界切开），再用中间事实生成正文；
- **步数如实记**：`generationOptions` 里的 `steps`（1 或 2）、`intermediateCalls`（提炼了几段）、
  `modelCalls`（这一版一共发了几次真实请求）。数字是数出来的；
- **中间事实带来源**：第一步要求每行写成 `- [来源: src_x/rev_y] 事实`，核心把能对上快照的
  事实挂成 `provenanceLinks`（`note` 是那条派生事实，来源是它真正来自的记录/修订）。
  匹配不上的来源标识**不伪造**：只计入 `unmatchedFacts`；那份材料至少留一条整段关联；
- **中间结果是派生数据**：第二步的提示词明确说明它「不再作为新的原始事实继续引用」，
  正文里也不会重复来源标识；
- **超过 12 段就如实失败**（`invalid_argument`，消息里写清多少段），**绝不只取前几段而假装完整**。

## 去重与幂等

两条不同的键各管一件事：

| 键 | 管什么 | 行为 |
|---|---|---|
| `operationId` + 请求指纹 | 「同一次操作重试」 | 命中 `operation_receipts` 就返回**原票据**（jobId + snapshotId），不再排任务、不再调模型；同一条 `operationId` 换了内容（换了日期/风格/原因/快照）报 `idempotency_conflict` |
| `(day_key, snapshot_hash)` | 「同一份输入不重复产版本」 | 已经有版本、或者还有活着的任务 → 复用那条任务的 jobId，**不新建生成、不产第二个版本** |

- 失败重试沿用同一次操作：同一条 `operationId` 重试返回原票据，用户也可以用
  `jobs.retry` 重排那条任务；
- 一条生成**终态失败**之后（既没有版本、也没有活着的任务），换一条**新的** `operationId`
  再调会新排一次尝试——它仍然不会为同一份快照产出第二个版本（要么这份输入已经有一版、
  要么这次才是第一版）；
- **`reason = regenerate` 是唯一例外**：用户明确说「再生成一版」时才允许同一份输入产新候选
  （仍然按 `operationId` 幂等，仍然不覆盖当前版本）；
- 已经在跑的生成重入（租约恢复）直接返回：正文已在就不重复计费、不产第二个版本。

## 来源标记：AI 正文不冒充用户手写

- 生成的正文只落 `diary_versions`，`origin = generated`，并带上
  `sourceSnapshotId`、`styleSnapshotId`、`generationInfo`（`promptVersion`、`providerId`、
  `model`、生成选项、覆盖范围）与 `provenanceLinks`；**什么时间**由版本的 `createdAt`
  （写入时刻，毫秒精度）表达，冻结时刻另有快照行的 `created_at`；
- **不写** `captures.draft_text`、**不建** `source_revisions`：那两处的作者只有
  user / import（契约 2.2），AI 文本永远不会以 `author_type = user` 出现；
- 用户自己的版本（B4c 的 `user_edit` / `merge`）与生成版本在同一个 `origin` 字段上**一眼可分**；
- **检索**：AI 正文没有进用户材料的索引，关键词检索不会把它当成用户写下的话返回；
  带 `includeOldDiaryVersions` 查询时，核心如实给出「日记历史版本还没有进索引」的警告，
  **不返回假命中**（这是 #64 之前就有的诚实退化，B4b 沿用）；
- **导出/备份**：日记版本行带着 `origin` 与生成信息，导出日记版本时跟着走；用户材料的
  三处存储（`captures.draft_text` / `source_revisions.text` / `extracted_contents.text`）
  里没有 AI 正文。

## 失败如实

| 情形 | 错误码 | 作业状态 | 版本 |
|---|---|---|---|
| 没配置/没启用/没声明/没验过 `generate_text` | `provider_not_configured` | `waiting_configuration`（`attempt_count` 不动、`requires_user_action`） | 没有 |
| 执行期 401/403 | `authentication_failed` | `waiting_configuration`，并把服务结论改成失败 | 没有 |
| 超时 / 断网 / 5xx / 429 | `provider_timeout` / `network_unavailable` / `rate_limited` | `retry_wait`（有限退避，429 尊重 `Retry-After`） | 没有 |
| 端点/模型不对、响应解析不了 | `model_unavailable` | `failed` + `requires_user_action` | 没有 |
| 远端返回空正文 | `model_unavailable`（消息写明「不当成一次成功的生成」） | `failed` | **没有空版本** |
| 两次都是 JSON / 代码围栏 / 要点列表 | `model_unavailable` | `failed` | 没有 |
| 两步走中途失败 | 按上表 | 按上表 | **没有半截版本**（不拿中间结果凑一篇） |
| 材料长到超过 12 段 | `invalid_argument` | `failed`（说清多少段） | 没有 |
| 这一天一份可读正文都没有（全在提取中/失败） | `invalid_argument` | **不排任务**（拒绝在受理时，连生成记录都不建） | 没有 |

没配服务时 `diary.generate` **照样返回票据**（冻结已经发生），由 `jobs.get` 看状态；
「关键词检索与既有版本完全不受影响」（E23）有断言钉住：生成失败前后，用户自己写的文字
照样搜得到，既有版本一行未动。

## schema v9 → v10

`SCHEMA_VERSION` 9 → 10，迁移只做一件事：建四张新表（外加索引）。**没有回填、没有猜**：
B4b 之前核心没有日记表，老库里没有日记版本可搬；迁移里更不能替用户「补生成」一版。

| 表 | 作用 |
|---|---|
| `diary_source_snapshots` | 冻结的输入清单（`body` 规范 JSON + `snapshot_hash`）；`(day_key, snapshot_hash)` 唯一 |
| `diary_versions` | 版本正文与来源关联（`origin`、`source_snapshot_id`、`style_snapshot_id`、`generation_info`、`provenance_links`、`operation_id`） |
| `diary_days` | 一天的当前版本与时间语义（候选/当前的唯一落点） |
| `diary_generations` | 一次生成请求：快照、钉住的服务、原因、`operationId`、任务、最终版本、步数、最近错误 |

**没有改任何既有表**（`captures` / `source_revisions` / `jobs` / `providers` 的列一列未动），
所以 B4a 刚建的 `providers` / `ai_responses` 与它不打架。旧库升级后日记表是空的，
「升级不会凭空多出一篇日记」有回归测试钉住（`v9_library_migrates_to_v10_and_keeps_old_data_intact`）。

## 验证到了什么

`crates/diary_core/tests/diary_generation_test.rs`（14 条）与 `diary.rs` 的单元测试（6 条）：

- **候选/当前**：首次生成成为当前；材料变了再生成只进候选、当前版本的正文与快照一个字节都不变；
  用户手写版本被设为当前后，自动整理只产候选；有用户版本但还没有当前版本时，生成也只能进候选；
- **快照冻结**：排队后改材料再执行，请求里仍是冻结的旧文本；事后改材料，旧快照的哈希与
  清单一行不变，仍答得出「基于什么生成」；
- **防注入**：指令槽逐字等于常量；注入文本只在数据段里且逐行带前缀；另一个日期的材料不在
  请求里；只打一个端点；
- **去重/幂等**：同 `operationId` 重复调用只调一次模型、只有一条任务；同快照换 `operationId`
  复用同一条任务、不产第二个版本；同 `operationId` 换内容报 `idempotency_conflict`；
  `regenerate` 才产新候选；
- **两步走**：超长材料分两批提炼 + 一次正文生成（3 次调用），`steps=2`、`intermediateCalls=2`、
  中间事实带来源且能回溯到具体修订；第一批里看不到第二批的材料；
- **入参边界**：没有材料的一天 / 一份可读正文都没有的一天 / 未知风格 / 形状不对的 dayKey，
  都在受理时按契约错误码拒绝，不排空任务；
- **失败如实**：没配服务 → `waiting_configuration` + `provider_not_configured` + 0 次调用 +
  检索照常；401 → `waiting_configuration` + `authentication_failed` 且服务结论变失败；
  超时 → `retry_wait` + `provider_timeout`；空正文 / 结构化输出 → `failed` + `model_unavailable`；
  两步走中途失败 → 没有任何版本；
- **来源标记**：`origin=generated` + 生成信息 + 快照；AI 正文不在用户材料的三处存储里、
  不在关键词检索里；要求「包含旧日记版本」时如实给警告而不是假命中；用户版本 `user_edit` 可区分；
- **迁移**：v9 → v10 建表、不回填、旧数据一行未动，迁移后的库照样能生成。

Dart 侧：`packages/diary_bridge/test/bridge_diary_generation_test.dart` 走契约接口验证
「生成票据 → 没有服务时停在 `waiting_configuration` → 没有版本 → 关键词检索照常 →
同 `operationId` 返回原票据 → 空日/未知版本/未知风格的错误码」。

## 没有做到的

- **用户编辑/切换/合并的操作面（B4c / #87）没有实现**：`diary.saveEdit` / `diary.setCurrent` /
  `diary.merge` 不在能力清单里。核心留了写入缝（`diary::insert_user_version` /
  `diary::set_current`，只暴露给测试），B4c 接上时把契约方法补上即可；
- **没有与用户版本的合并策略**：B4c 的 `diary.merge` 要处理「AI 候选 + 用户手写 → 用户确认的
  新版本」。这一片只保证「AI 不等于用户」与「当前不被覆盖」，合并语义留给 #87；
- **风格只有缺省**：`styles.*` 没有实现，所以 `styleSnapshot` 现在恒为缺省标识
  `sty_default`；点名任何具体风格报 `not_found`。风格偏好、示例与禁用表达要等 styles 那一片；
- **质量评测见 #93**：这一片只做**格式闸门**（JSON / 代码围栏 / 要点列表），不做质量判断；
  任务书也写明「事实质量不能仅靠字符串校验保证」；
- **配额与用量统计见 #97**：`generationOptions` 只记调用次数，不记 token、不算钱；
- **日记版本没有进检索索引**：`includeOldDiaryVersions` 仍是诚实退化（给出警告、不返回命中）。
  让日记版本可检索要新增文档表与切片，属于检索那一片；
- **`provenanceLinks` 没有正文区间**：模型没有给出逐句引用，所以 `bodyRange` 一律为空
  （契约允许「整段关联时为空」），来源粒度到「材料/中间事实」而不是「正文第几段」；
- **未提交草稿没有来源关联**：草稿还没有 `source_revisions` 行，所以它的材料在
  `provenanceLinks` 里没有对应链接（快照里仍然记着它）；
- **导出入口本身还没实现**（`exports.*` 属后续切片）：这一片能证明的是「用户材料的存储里
  没有 AI 正文」与「版本行带着来源标记」，还没有跑过一个真实的导出包；
- **中间提炼只有一轮**：第二步用的是第一步的全部中间事实；没有做「事实太多再分层」的第三层；
- **没有真机/真实服务验证**：所有测试都用回放传输层（CI 不联网），真实服务商的输出形状、
  限流与计费都没在 CI 里跑过。

## 需要拍板

1. **「首次可成 current」要不要保持现在这条更窄的边界**（有用户版本、但还没有当前版本时
   生成也只能进候选）。契约字面上允许更宽的读法；这一片选了更保护用户的一侧，
   代价是「用户写了但没选当前」的日子不会自动显示 AI 版本。要不要放宽？
2. **`regenerate` 的语义**：现在它是「同一份输入再产一版新候选」的唯一入口。要不要让它也能
   指定另一个已配置的服务/模型（契约的 `diary.generate` 没有 `providerId` 参数，加了就是契约变更）？
3. **超时的落点**：这一片按契约第 7 节把 `provider_timeout` 放在 `retry_wait`（有限重试），
   而不是 `waiting_configuration`。如果产品希望超时也停下来等用户，需要改契约第 7 节的自动行为。
4. **风格快照的归宿**：`styles.*` 落地时要决定 styleSnapshot 是「一行不可变记录」还是
   「按 revision 引用」。现在只是一个常量标识，改起来没有包袱，但早点定更好。
5. **中间事实要不要落库**：现在只在版本的 `provenanceLinks.note` 里，够追溯但不便检索。
   要不要单独一张派生事实表（带来源、可重建、可清理）？
6. **`AiResponse` 的状态**（B4a 留下的问题）：这一片没有动 `ai_responses`；如果要做，
   建议与 #97 一起（生成状态 + 用量）。
