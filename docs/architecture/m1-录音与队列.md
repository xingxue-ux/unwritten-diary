# M1 · 录音会话与任务队列（B1c）

对应 issue [#22](https://github.com/xingxue-ux/unwritten-diary/issues/22) · 日期 2026-09-27 · 执行人 xingxue-ux

代码在 `crates/diary_core/`（`src/recordings.rs`、`src/jobs.rs`、schema v3）。记录这一片的决定与没做到的部分。

## 定下的决定

| 决定 | 理由 |
|---|---|
| 片段登记用 `(recording_id, segment_index)` 做主键 | 幂等由结构保证，不靠调用方自觉。同序号重复登记内容一致就返回原回执，内容不一致报 `idempotency_conflict` |
| 片段登记与最终化都**自己重算哈希** | 和导入一样，平台层声明的哈希只能当线索。对不上报 `integrity_failed` |
| 最终化把片段**流式拼成一份逻辑音频** | 契约要求「可按需连续播放和导出」，同时「不要求结束时一次性重编码全部音频」。拼接按 64 KiB 缓冲，内存与录音长度无关 |
| 有缺口时最终状态是 `recoverable` 而不是 `saved` | 少了一段还报 saved 就是撒谎。缺口序号与估算时长由 `recover_recording` 如实给出 |
| 最后一段之后的尾巴算「未知」 | 进程被杀时无法知道最后一段录到哪；notes 明确写「尾巴时长无法确定」，不用平均值冒充 |
| 重开资料库：有片段的是 `recoverable`，没有的是 `interrupted` | 两者含义不同，界面处理也不同 |
| `interrupted ≠ paused` | 来电中断后界面不能再显示「正在收音」。这是契约第 3 节的原话，用测试钉住 |
| **提交与入队同一个事务** | 任务书 3.2 节要求。`commit_with_jobs` 就是为了不让「音频建好了、转写任务永远丢了」发生 |
| 最终化自动排一个转写任务 | 「转写不阻塞完成」不等于「不排任务」。任务与最终化同事务 |
| 队列只做队列，不做事 | 领到任务之后做什么属于后面的切片。这里保证的是重启后队列还在、失败不影响原件 |
| 重试退避 30 秒起每次翻倍、上限 1 小时 | 不用无限重试；额度用完进 `failed`，由用户决定是否手动重试 |
| 手动重试会多给一次机会 | 用户明确要求重试时不该因为「次数用完了」被拒。多给的那次如实记在 `max_attempts` 上 |
| 通知去重用 `attention_acks` 表 | 契约第 2.7 节的 `attentionKey` 语义：同一个问题只提醒一次 |

## 验证到了什么

`cargo test -p diary_core` 共 **45 项**（15 录音与任务 + 12 文件库 + 16 记录 + 2 单测）。值得点名的：

- **录音进程被杀后重开**（E14 的后端部分）：写了两段、状态是 recording 就关库；重开后 `recover_recording(None)` 返回 `recoverable` 且列出已封闭序号，还能直接救回来拼成完整音频。
- **缺口如实报告**：只有第 0、2 段时最终化，状态是 `recoverable`，notes 写明「缺 1 个片段（序号 [1]）」并给出按时长估算的缺口。
- **提交与入队同事务**：`commit_with_jobs` 之后任务一定在；换一组任务复用同一个 operationId 会被判为幂等冲突。
- **队列按优先级领取**：保存类任务先跑，维护类最后；领取后状态是 running、attempt 记 1。
- **失败退避后放弃**：第一次失败进 `retry_wait` 且下次尝试时间在将来；没到点领不到；额度用完后进 `failed`。
- **取消不碰原件**：取消任务后记录仍是 draft、资产照旧。
- **队列重启后还在**：入队、关库、重开，任务仍是 queued。

## 过程中发现并修掉的一个真 bug

**写进去的值和读出来的值不相等。** 片段回执第一次返回用的是内存里纳秒精度的时间，库里存的是毫秒精度 ISO 字符串，于是「同序号重复登记返回原回执」这条测试直接失败。根因不是那一处，而是**所有返回给调用方的时间都可能带纳秒、而存储只到毫秒**。

修法：加了 `support::now()`（截断到毫秒），核心内所有生成时间的地方统一用它。这条如果留着，会让「重复调用结果一致」在别处也悄悄不成立。

## 没有做到的

- **任务只是排队，没有执行**：`run_due` / 真正的 worker 属于 B5。现在能领到任务、能标记成败，但没有任何代码会去转写或整理。
- **进度没有来源**：`progress` 恒为 None。契约说「没有可靠进度时必须为空」，这一点是遵守的，但也意味着任务中心现在只能显示状态、不能显示百分比。
- **等待类状态没有入口**：`waiting_configuration` / `waiting_dependency` / `waiting_network` 三种状态在枚举里，但还没有代码会切过去——那要等 provider 与依赖管理接上。
- **`input_device_changed` 只是记录**：状态里带了这个字段，核心如实存下来，但没有据此做任何处理。
- **不是真实录音**：所有测试都是自己写假的片段文件。真实收音、锁屏、来电中断这些必须真机验证，一条都没做。
- **桥接没接线**：`crates/diary_bridge` 还没暴露核心方法，前端仍然调不到。

# 平台层：Flutter（Windows / Android）

上面是核心这一侧。真正收音的是平台层，代码在 `apps/diary_app/lib/src/recording/`。
这一节记的是**平台层怎么接的、验证到哪一步、还有什么没做到**。

## 用了什么

| 环节 | 选择 | 理由 |
|---|---|---|
| 采集 | `record` 7.x（Windows 走 Media Foundation，Android 走 AudioRecord） | 能直接写 PCM WAV。转写链只解码 PCM WAV，用 aac/m4a 等于让录下来的音永远转不出文字 |
| 参数 | 16 kHz / 单声道 / 16 bit | 与 `wav.rs` 的解码口径、与鸿蒙侧采集参数一致；语音日记不需要立体声 |
| 播放 | `audioplayers` 6.x | Windows/Android 都支持；播放走 `assets.open` 给的只读租约路径，不自己拼 blob 路径 |
| 波形 | 自己扫 PCM（`waveform.dart`） | 按块流式扫，只留 160 个峰值；一小时录音 115 MiB 也不会整段进内存 |

## 片段边界为什么在「暂停」上

用户按暂停时，平台层**停掉当前片段、算哈希、登记，再释放麦克风**；按继续时开一个新片段。
不用插件的原生 `pause`/`resume`，理由：

- 原生暂停只把音频留在内存缓冲里，进程被杀就一起没了；停一段并登记之后，已经录好的部分在库里；
- 暂停期间本来就是静音，切段丢掉的那几十毫秒听不出来；
- 反过来「定时切段」（每 N 秒轮转）会在每次切换时丢掉几十到几百毫秒的**真实语音**，
  对转写质量是净损失。

## 丢弃：契约补了一条出口

`prepare → finalize` 原本是唯一出路。用户按了录音又立刻放弃时，会话会永远停在
`preparing`/`recording`，下次启动被 `count_open_recordings` 数成「上次没来得及收尾的录音」——
一句假警报。所以补了 `recordings.discard`：

- 幂等：会话不存在返回成功；
- 已经最终化的拒绝（`invalid_state`）：音频已经挂到记录上，删会话会留下指向空资产的来源；
- 删会话 + 删暂存目录，`blobs` 里没有它的东西（最终化才建）。

## 最终化现在会写一个合法的 WAV

以前是按字节直接拼，每段各带 44 字节头时拼出来是「头 + 数据 + 头 + 数据」，
第二个头会被当成采样读（爆音、转写里多出一两个字）。现在 `finalize` 先探测每段容器：
全是同一格式的 PCM WAV 时只取数据区、最后写一个头；有任何一个不是 WAV 时退回按字节拼
（兼容鸿蒙侧「只有第 0 段带头」的约定）。采样格式不一致（中途换设备）**不拼**，报
`integrity_failed`。

## 验证到了什么

- **单元/组件测试**：`apps/diary_app/test/recording_controller_test.dart` 11 项
  （申请票据 → 登记片段 → 最终化 → 跑转写、暂停切段、无权限不建会话、空片段不登记、
  丢弃、最终化失败、恢复、转写三种终态、电平归一化）；`recording_panel_test.dart` 5 项
  （按钮真的接到控制器上、保存后如实显示转写状态、播放器打不开时不假装能播）。
  这些用的是**假麦克风 + 假核心**，会真的写文件、真的算哈希。
- **核心这一侧**：`cargo test -p diary_core --test recording_job_test` 22 项，其中 4 项是
  这次补的（单头 WAV、格式不一致拒绝、丢弃幂等、最终化后不能丢弃）。
- **Windows 真机**：见下面的「没做到」。

## 没有做到的

- **没有真麦克风验证**（写这段时）：Windows 上跑过安装包，但录音按钮的真实收音、
  权限弹窗、设备切换这些**没有逐项手测**；Android 连设备都没有（没有 `/dev/kvm`，
  APK 构建过但从未安装运行）。所以「能录出声音」这件事目前只有代码与假麦克风测试支撑，
  不能算验证过。
- **崩溃只保到上一个片段**：正在录的那一段没有封闭，进程被杀就丢了。`recover` 会如实
  报「缺多少段、缺口估多少毫秒」，但救不回来。
- **`input_device_changed` 没有处理**：核心如实存下来，平台层没有据此提示用户。
- **没有降噪/自动增益**：`RecordConfig` 里的 `autoGain`/`noiseSuppress`/`echoCancel`
  没开，用的是设备默认。
