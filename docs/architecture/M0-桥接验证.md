# M0 桥接验证

对应 issue [#13](https://github.com/xingxue-ux/unwritten-diary/issues/13) · 日期 2026-09-27 · 执行人 xingxue-ux

契约第 5 节要求 M0 固定桥接路径、生成文件归属与后台运行入口。本文记录已经测到的事实、没测到的部分，以及由此产生的约定。

## 1. 结论

| 项目 | 结论 |
|---|---|
| 调用桥 | 采用 `flutter_rust_bridge` 2.13.0 |
| 生成文件归属 | Rust 侧 `crates/diary_bridge/src/frb_generated.rs`，Dart 侧 `packages/diary_bridge/lib/src/rust/`，两者都入库 |
| 同步调用 | 可用 |
| 异步调用 | 可用，Dart 侧返回 `Future` |
| 事件流（`StreamSink`） | **可用**：Linux 宿主、Windows x64、Android 模拟器都实测收到有序事件并正常关闭 |
| 调用取消 | **frb 2.13.0 没有内建取消通道**：源码里没有取消回调或 token。契约的取消语义只能靠应用层实现（显式 cancel 方法 + Rust 内部协作式取消），未实现也未验证 |
| Android 后台运行入口 | **部分验证**：后台 isolate（无 Widget、无页面对象）能加载并调用核心，Android 模拟器实测 5/5；**系统级唤醒（WorkManager / 前台服务）未验证**，那属于平台层实现，还没有做 |
| Windows x64 产物 | 已构建（PE32+ DLL，374 KB） |
| Android arm64 产物 | 已构建（aarch64 ELF，617 KB，只依赖 `libc` / `libm` / `libdl`） |
| 运行时加载 | **Linux 宿主、Windows x64、Android（x86_64 模拟器）都已实测**；arm64 真机未验证 |

```

$ cargo clippy --workspace --all-targets
（无警告，退出码 0）
```

Dart 真正调用到 Rust（Linux 宿主 cdylib，`packages/diary_bridge`）：

```

覆盖：同步计算 add(2,3)=5、open() 返回的 CoreInfo 字段映射、
传入库句柄原样返回、open 与 openAsync 结果一致、中文与 emoji 往返。

Windows x64 上的同一次调用（用 Windows 侧的 Dart 与 Rust 产物，`DIARY_BRIDGE_LIB` 指向 DLL）：

```

00:00 +5: All tests passed!
```

事件流（契约第 6 节）在三个平台上都验过：Rust 侧用 `StreamSink<ProbeEvent>` 依次发 5 条事件，Dart 侧 `watchProbeEvents(count: 5).toList()` 拿到 `[0,1,2,3,4]` 且流正常关闭；`count: 0` 时流为空。Linux 与 Windows 各 6/6 通过，Android 模拟器 4/4 通过。

Android（x86_64 模拟器，API 36）：把 `.so` 打进 `jniLibs/x86_64` 后，在一个**仓库外**的一次性探针 App（不是 `apps/diary_app`）里跑同一个调用：

```
$ flutter test integration_test/bridge_test.dart -d emulator-5554
Running Gradle task 'assembleDebug'...   175.3s
✓ Built build/app/outputs/flutter-apk/app-debug.apk
Installing build/app/outputs/flutter-apk/app-debug.apk...   1,955ms
00:01 +5: All tests passed!
```

其中一项专门验证契约第 5 节「不能依赖某个页面对象存在」：在一个**后台 isolate**（无 Widget 树）里加载 `.so`、调用 `open` 与 `echo`，再把结果通过 `SendPort` 传回主 isolate，断言通过。这证明**核心调用不需要界面对象**。

它**不**证明系统级唤醒：Android 用 WorkManager 或前台服务在应用完全不在前台时唤起进程、再由被唤起进程进入核心，这条路径还没有做（属于平台层实现）。

两端产物：

```

## 3. 过程中发现的三件事

1. **`u64` 映射成 Dart 的 `BigInt`。** 契约里的 `sequence`、`lastEventSequence` 用了 `u64` 语义，生成的 Dart 类型是 `BigInt` 而不是 `int`。`diary_api` 里的 `DomainEvent.sequence` 目前是 `int`，两者在适配层需要一次显式转换。属于已发现的类型接缝，B1 处理事件游标时必须先定死。
2. **两个 cargo 不能同时用同一个 `target/`。** 仓库在 `/mnt/e` 上，WSL 与 Windows 共用构建目录。并行构建时 `tokio` 编译失败，串行重跑即恢复。约定：Windows 侧一律带 `--target x86_64-pc-windows-msvc`，且两边不要同时构建。
3. **默认没有同步函数。** `flutter_rust_bridge` 把普通 `pub fn` 也生成成异步 Dart 方法；需要同步版本要显式标注。目前接口全部是异步的，对记录路径更安全（不阻塞界面线程），但启动时的轻量读取如果需要同步语义，要单独评估。

## 4. 由此固定的约定

- codegen 版本与依赖版本必须一致，且都以 `Cargo.toml` 里的精确版本为准（`=2.13.0`）。不一致时 Rust 侧启动直接拒绝加载。
- 生成文件入库，改 Rust 公开 API 必须重新生成并在同一个 PR 提交。
- 生成脚本由后端层代码维护；不手改生成代码。
- `crates/diary_bridge` 目前只有探针 API（`open` / `openAsync` / `snapshot` / `add` / `echo` / `watchProbeEvents`），**不是**真实实现；B1 起替换。

## 5. 仍未验证的部分

- **调用取消**：`flutter_rust_bridge` 2.13.0 的源码里没有取消回调、取消 token 或 `on_cancel`，所以桥接层不会替我们取消。契约第 1.2 节要求「取消停止后续处理，不删除已经保存的原件」，这只能靠应用层：每个可取消的长任务（搜索、整理、索引重建）都要有显式的 `cancel` 方法，并在 Rust 内部用协作式取消检查点实现。方案还没定，也没有验证。
- Android 后台运行入口：契约第 5 节明确要求 M0 验证 Android 如何进入核心、不能依赖页面对象。已证明「加载与调用不需要页面对象」（后台 isolate 实测通过），**没有**验证系统级唤醒（WorkManager / 前台服务）。
- **arm64 真机**上的加载与调用（x86_64 模拟器已补测，不能代表 arm64）。
- 打包集成只做了一半：Android 用 `jniLibs/x86_64` 打进 APK 已验证；Windows 侧目前靠显式路径加载 DLL，**Flutter Windows 工程的标准打包方式（CMake 集成）没做**；Linux 同理。
- 这条链路已在 Linux 宿主、Windows x64、Android x86_64 模拟器上端到端跑通；**arm64 真机与系统级唤醒仍未覆盖**，不能据此认为手机上的完整链路已经打通。
