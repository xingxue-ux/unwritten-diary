# M0 桥接验证

对应 issue [#13](https://github.com/xingxue-ux/unwritten-diary/issues/13) · 日期 2026-09-27 · 执行人 xingxue-ux

契约第 5 节要求 M0 固定桥接路径、生成文件归属与后台运行入口。本文记录已经测到的事实、没测到的部分，以及由此产生的约定。

## 1. 结论

| 项目 | 结论 |
|---|---|
| 调用桥 | 采用 `flutter_rust_bridge` 2.13.0 |
| 生成文件归属 | Rust 侧 `crates/diary_bridge/src/frb_generated.rs`，Dart 侧 `packages/diary_bridge/lib/src/rust/`，两者都入库 |
| 同步调用 | 可用 |
| 异步调用 | 可用，Dart 侧返回 `Future` |
| 事件流（`StreamSink`） | **未验证** |
| 调用取消 | **未验证** |
| Android 后台运行入口 | **未验证**（契约第 5 节的硬要求，仍是 M0 未完成项） |
| Windows x64 产物 | 已构建（PE32+ DLL，374 KB） |
| Android arm64 产物 | 已构建（aarch64 ELF，617 KB，只依赖 `libc` / `libm` / `libdl`） |
| 运行时加载 | **Linux 宿主、Windows x64、Android（x86_64 模拟器）都已实测**；arm64 真机未验证 |

## 3. 过程中发现的三件事

1. **`u64` 映射成 Dart 的 `BigInt`。** 契约里的 `sequence`、`lastEventSequence` 用了 `u64` 语义，生成的 Dart 类型是 `BigInt` 而不是 `int`。`diary_api` 里的 `DomainEvent.sequence` 目前是 `int`，两者在适配层需要一次显式转换。属于已发现的类型接缝，B1 处理事件游标时必须先定死。
2. **两个 cargo 不能同时用同一个 `target/`。** 仓库在 `/mnt/e` 上，WSL 与 Windows 共用构建目录。并行构建时 `tokio` 编译失败，串行重跑即恢复。约定：Windows 侧一律带 `--target x86_64-pc-windows-msvc`，且两边不要同时构建。
3. **默认没有同步函数。** `flutter_rust_bridge` 把普通 `pub fn` 也生成成异步 Dart 方法；需要同步版本要显式标注。目前接口全部是异步的，对记录路径更安全（不阻塞界面线程），但启动时的轻量读取如果需要同步语义，要单独评估。

## 4. 由此固定的约定

- codegen 版本与依赖版本必须一致，且都以 `Cargo.toml` 里的精确版本为准（`=2.13.0`）。不一致时 Rust 侧启动直接拒绝加载。
- 生成文件入库，改 Rust 公开 API 必须重新生成并在同一个 PR 提交。
- 生成脚本由后端层代码维护；不手改生成代码。
- `crates/diary_bridge` 目前只有探针 API（`open` / `openAsync` / `snapshot` / `add` / `echo`），**不是**真实实现；B1 起替换。

## 5. 仍未验证的部分

- 事件流、取消、后台运行入口（契约第 5 节明确要求 M0 验证 Android 如何进入核心，不能依赖页面对象）。
- **arm64 真机**上的加载与调用（x86_64 模拟器已补测，不能代表 arm64）。
- 打包集成：Flutter 工程如何把 `.so` / `.dll` 放进产物、加载路径如何确定。
- 这条链路目前只在 Linux 宿主上端到端跑通，**不能据此认为两端已经打通**。
