## 定下的决定

| 决定 | 理由 |
|---|---|
| 驱动放在核心：`run_due_jobs(now, budget_ms, trigger, max_jobs) -> JobRunSummary` | 「取到期任务 → 执行 → 记录结果/重试」是核心自己的事；**什么时候允许跑**由平台决定（#19 的系统级唤醒），核心只报「跑完什么、还剩多少、还在等什么」 |
| 平台给的是**毫秒预算**，不是条数 | 契约 `jobs.runDue` 的输入一直是 `budgetMs` + `trigger`（`packages/diary_api` 早就这么声明了），核心这边原来只有 `limit`，属于「契约先行、实现落后」。预算按真实流逝时间（`Instant`）算，与业务时钟 `now` 分开——测试会把 `now` 推到过去/未来排期，用它算预算会随调用方的时钟走 |
| **预算只在任务之间判断**，不打断正在跑的任务 | 核心不做抢占：`rebuild_keyword_index`、提取这些同步重活没有安全的取消点。所以「一条任务本身比预算还长」是**允许发生**的，预算是「这一轮还能不能再开一条」。不假装能中途抢占 |
| 另加一个**条数上限**（核心参数 `max_jobs`，桥接常量 64） | 预算挡长尾，它挡「队列很长 + 多条短任务」把一轮拖成没完没了。被两种上限截住的到期任务都留在队列里、如实进 `due_backlog` |
| `trigger` 只如实记进摘要 | 唤醒来源是排查用的：`startup` / `foreground` / `wake` / `manual` …。核心不认识这些值的语义，也不因为它改变行为——「什么时候调用」是 #19 的事 |
| 只实现**真有执行者**的 `kind`：`extract`、`index` | `transcribe` 要等 B4a 的 Provider。假装能跑比不跑更糟 |
| 没有执行者的 `kind` → `failed` + `error_code = no_handler` + `requires_user_action = 1` | 必须出现在状态里、能人工重试；**绝不静默 complete**。没有处理器不会因为多试几次就出现，所以不退避、不浪费额度 |
| `extract` 的成败 = **提取路径是否跑完** | 提取器自己裁决的 `status=failed` / `metadata_only` 已经如实落在 `extracted_contents`（带 coverage 与错误码），那才是「这个文件能不能搜」的答案。在这里再失败一次只会让确定性的格式问题白白退避重试五分钟。**结构性失败**（修订不存在、原件不在文件库、没有目标）才让任务失败 |
| `index` 的前置用**派生内容在不在**判断，而不是「提取任务成功过」 | 改过正文、重跑过提取的来源会换修订，队列里那条 `extract` 的成功与否已经不是当下的真相；`extracted_contents` 里有没有当前修订的行才是「现在能不能索引」的答案 |
| 前置未满足 → `waiting_dependency`，**不领取、不消耗重试额度、不退避** | 在等前置不是一次失败。领取会递增 `attempt_count` 并写 `job_attempts`，所以闸门在**领取之前**就把等待态维持住 |
| 闸门在**每次领取前**重评估，并在**轮末**再评估一次（不是「每轮只评估一次」） | 「每轮只评估一次」会让链停住：前置跑完时后继仍留在等待态，而 `next_wakeup` 不把等待态算成待办，队列空时摘要给出 `null`，按摘要安排唤醒的平台层不会再叫驱动（#74 评审指出）。每次领取前评估让链在**一次**驱动调用里走完；轮末评估是「有等待态就必须有可用唤醒」这条不变式的兜底。**不采用**「把 `nextWakeup` 设成立即唤醒」的补丁：那等于把链的完成寄托在平台层肯不肯再叫一次上，而 #19 可能因省电/退出不叫 |
| 等待 / 晋升期间**保留原 `next_attempt_at`**；只有「依赖满足」**且**「到期」同时成立才领取 | #67 二轮复审：`defer_for_dependency` / `promote_dependency` 清空排期会让「一小时后」的索引任务在前置提前完成时被**立刻领走**，原到期时刻还同时从 `next_wakeup` 与补做统计里消失。保留排期后它落在 `queued` + 未来排期，既有的领取判据（`next_attempt_at IS NULL OR <= now`）自然拦住，**不需要另加状态**；作为 `queued` 任务它照常进 `next_wakeup`，「何时该跑」不丢。等待态本身仍不算待办（由它的前置负责唤醒） |
| 前置不可能再满足 → 终态 `failed` + `dependency_extract_unmet` + `requires_user_action` | 挂死不如如实失败：提取被取消/放弃而派生内容永远不会出现时，留一条「永远没有下次唤醒」的任务对谁都没好处。错误码里点明等的是哪一环 |
| `index` 的空 `target_ids` = **整库**（`indexes.rebuild(scope=all)`） | 执行者走 `rebuild_keyword_index(None)`，与 `indexes.status` 不传范围、与同步入口的 `None` 同义；`sources:` 范围表达不了「没有来源的记录文字」，整库必须走 `None`。非空的 `target_ids` 只重建这些来源，行为不变。整库任务的前置是「队列里没有活着的 `extract`」：等提取收尾再按现状重刷，且**不判 `Broken`**——某条提取被取消只是少一份内容，不该把整库重建连坐成失败 |
| `indexes.rebuild(scope, reason, operationId)` **只排一条 `index` 任务**，返回 `jobId` | 契约 4.4 的返回本来就是 `jobId`（异步），这一片把它接上。不做同步重建：同步重建会阻塞界面，而队列的退避、补做与依赖闸门已经就绪。入口在 `index_rebuild.rs`，桥接是 `BridgeSession::rebuildIndexes` |
| `scope` 只有 `all` 与 `sources:<id>[,<id>]*` 两种写法 | id 只允许 `[A-Za-z0-9_]`，`,` 固定成分隔符、**不定义转义**；顺序无语义（解析时排序成规范形）；空列表、空记号、重复 id、越界字符报 `invalid_argument`，不存在的来源报 `not_found`。规范写在契约 4.4 节（共享场景文件里早就在写 `indexes.rebuild(scope=all)`） |
| 入口的幂等走**通用 operationId 回执**（`operation_receipts`），不只靠业务键 | 契约 1.2 要求「同一 id 换了内容报冲突」。回执只存任务 id，重放时按 id 读**当前**任务，所以返回的永远是这条任务此刻的真实状态，而不是入队那一刻的旧快照。任务自身的业务键 `(kind, target_ids, input_snapshot_hash)` 照 #67 口径一并生效 |
| `succeeded` 只发给真的跑完的任务 | `JobRunSummary.succeeded` 是「执行成功的任务数」，不是「有内容的来源数」 |
| 运行开始先回收上次没跑完的 `running` 任务 | 进程在任务进行中被杀（退出/断电）时任务会停在 `running`，而驱动只领取 `queued`/`retry_wait`——不回收就是**永久丢掉**。单写者 + 单驱动下，运行开始时还停在 `running` 的一定是上一次没走完的 |
| 业务键 `(kind, target_ids, input_snapshot_hash)`，同一个事务里先查后插 | 这一片不改 schema，所以键只能从现有列算；单写者 SQLite 下事务内检查足够。DB 级 UNIQUE 索引留给下一次 schema 变更 |
| 人工重试把 `attempt_count` **清零** | 用户在任务面板点一次重试，就再给一整份额度；`max_attempts` 不动。历史尝试记录（`job_attempts`）不删，编号跨人工重试累计 |
| `job.changed` 由**队列自己**发 | 入队（`enqueue_in_tx`）、开始（`claim_next_due`）、成功、失败、重试、取消、依赖状态变化各发一次。调用方不用记得发，也就不会漏；同一个事务里发，状态与通知不会一个成一个败 |
| 最近错误只带 `kind` + `error_code` + 时间（+不透明的 `job_id`） | `job_attempts.message` 里可能有文件路径或原始报错，那是排查信息，不该跟着状态摘要流出 |

## 状态机（含 `failed` 与「已放弃」的对应）

执行生命周期（#67 定下的，没有改）：

```
                  claim_next_due
   queued ──────────────────────────► running
     ▲                                  │
     │ 回收 interrupted（还有额度）      ├── complete ──────► succeeded
     │                                  ├── fail（还有额度）─► retry_wait ──┐
     │                                  └── fail（额度用完）─► failed       │
     │                                                                      │
     │                                           到点后 claim_next_due ◄────┘
     │
     └──────────── retry_job（人工，清零）◄──── failed（「已放弃」）

   queued / retry_wait / running ── cancel ──► cancelled
```

依赖闸门（#70 前半加的，只作用于有前置的 `kind`，现在只有 `index`）：

```
   入队（前置已知未满足）
        │
        ▼
   waiting_dependency ──每次领取前 / 轮末重新评估──┬─ 前置已满足 ──► queued（保留原排期；到期才领取）
   （attempt_count 不动、               ├─ 仍未满足 ──► waiting_dependency（原因码不变）
     不退避、不算失败、保留原排期）        └─ 不可能满足 ──► failed + requires_user_action
                                                        （dependency_extract_unmet）
```

issue #65 里的四个用户可见说法与内部状态名是一一对应的：

| 任务面板说法 | 状态名 | 说明 |
|---|---|---|
| 排队中 | `queued` | 已入队，等被领取；`next_attempt_at` 为空或已过。（被闸门从等待态晋升、但排期仍在未来的任务也在这里：它**过了排期**才会被领取） |
| 进行中 | `running` | 已经被驱动领取，正在执行 |
| 失败可重试 | `retry_wait` | 失败过、还有额度，`next_attempt_at` 是下次尝试时刻 |
| 已放弃 | `failed` | 额度用完、没有处理器（`no_handler`）、或前置不可能满足（`dependency_extract_unmet`）。`requires_user_action = 1`，等用户决定要不要重试 |
| 等待前置 | `waiting_dependency` | 前置（`extract`）还没跑完。**不是失败**：`attempt_count` 不动、没有退避、没有 `requires_user_action`；`error_code = waiting_extract` 说明在等哪一环 |

`waiting_configuration` / `waiting_network` 两个状态**现在还没有写入者**
（B4a 缺 Provider、网络等待时会有用武之地），计数照旧如实报 0，不假装用过它们。
`waiting_dependency` 从 #70 前半开始有真实写入者：**导入完成排下的 `index` 任务**
（`assets.rs::finish_import`，与 `extract` 入队同一个事务）。

## 依赖链与 `waiting_dependency`

这一片把「重活」串成链：**导入 → 提取（`extract`）→ 关键词索引（`index`）**。
链条的每一环都是一条持久任务，不靠调用方手工排队，也不靠「睡一会儿再试」。

**什么时候进等待态。** `finish_import` 在同一个事务里排两条任务：`extract`（对修订）
与 `index`（对来源）。后者的初始状态就是 `waiting_dependency` + `error_code = waiting_extract`
——这一刻提取一定还没跑。用户不用等一轮驱动就能在 `job_status()` / `list_jobs()` 里
看到它在等哪一环。

**在等什么（「闸门」`index_dependency` 的口径）。** 对 `target_ids` 里的每个**来源**：

- `target_ids` 为空 = **整库重建**（`indexes.rebuild(scope=all)`）：前置是「队列里没有
  活着的 `extract`」——等提取收尾再按现状重刷（见下「整库重建」）；
- 来源不存在 / 没有当前修订 / 当前修订读不到 → 前置**不成立**（终态 `not_found`）；
- 当前修订是**文字修订**（`source_revisions.asset_id` 为空）：提交时正文就落库并同步
  进了关键词索引，关键词这一路**没有「提取」这一环** → 视为可索引；
- 当前修订有资产：要有 `extracted_contents` 行（派生内容）才算提取完；还没有的话，
  看队列里还有没有**活着的** `extract` 任务瞄着这个修订（`state NOT IN
  ('succeeded','failed','cancelled')` 且 `target_ids` 精确含这个修订 id）：
  - 有 → 继续等（`waiting_extract`）；
  - 没有 → 前置**不可能再满足**（`dependency_extract_unmet`）。

**什么时候被拉起。** 驱动**每次领取前**先跑一次闸门（`resolve_dependencies`），
**一轮收尾时**再跑一次：

- 前置已满足的在等任务 → 状态回到 `queued`、清掉原因码，**保留它原本的
  `next_attempt_at`**；排期为空的，同一轮的下一次领取就能跑；排期在未来的，等到
  「依赖满足」**且**「到期」两个条件同时成立才被领走；
- 前置仍未满足的 → 留在 `waiting_dependency`（原因码只写一次，不每轮刷 `updated_at`），
  同样**保留原排期**；
- 前置不可能满足的 → 终态 `failed`，`requires_user_action = 1`。

**排期为什么不能在等待 / 晋升时清掉（#67 二轮复审）。** 一条任务可能本来就排在未来
（例如「一小时后执行」的索引任务）。等待前置期间把 `next_attempt_at` 清空、晋升时又
清空并放进 `queued`，它就变成「入队即到期」：前置若提前完成，这条任务会在**同一轮**
被立刻领走，而不是等一小时。保留排期之后，领取判据
（`next_attempt_at IS NULL OR next_attempt_at <= now`）自然把未到期的任务挡住——不必
另加「依赖已满足但未到期」的状态；同时它已经是 `queued`，`next_wakeup` 会如实地把
那个未来时刻报出来，补做统计也才拿得到真实的应跑时刻。**口径不变**：`waiting_dependency`
本身仍不算待办，等待态由它的前置任务负责唤醒。

**链在「一次」驱动调用里走完。** 提取跑完的那一刻，下一次领取前的闸门就会给 `index`
认账、把它拉起，于是同一次 `run_due_jobs` 里 `extract` → `index` 一路推进（受预算与
条数上限约束，见下）。前提是 `index` 自己**已经到期**：排期在未来的任务只是被拉到
`queued`，要等时间到才跑，不会被这一次驱动提前执行（见上）。这是 #74 评审要求的修法：**不能**把「链能不能走完」寄托在平台层
（#19）肯不肯再叫一次上——#19 本来就可能因省电/退出而不叫，那正是 E29 要诚实处理的
场景。旧行为是「一轮只推进一层依赖」，一轮结束后 `index` 仍是等待态、而 `next_wakeup`
不把等待态算成待办，队列里没有别的任务时摘要就会给出 `next_wakeup = null`：按摘要安排
唤醒的平台层不会再叫驱动，索引任务只有碰巧再次进前台才可能运行。

**一轮结束后不允许「有等待态却 `next_wakeup = null`」。** 收尾的那次闸门就是这条
不变式的兜底（循环可能因预算/条数上限在最后一条任务之后直接退出，没来得及在「领取前」
认账）。收尾之后还留下的等待态只可能是在等队列里 `queued` / `retry_wait` 的前置任务
（其 `next_attempt_at` / 「入队即到期」就是下一次唤醒时刻），或者前置已判 `Broken`——
而 `Broken` 在本轮已被终态失败，不会留下等待态。所以「有等待态」必然伴随「有可用的
下一次唤醒」；`run_due` 里的 `debug_assert` 与测试各钉住这条一遍。

**等前置不消耗重试额度。** 闸门只改 `state` / `error_code` / `updated_at`，**不碰**
`attempt_count`、**不改 `next_attempt_at`**（等待期保留原排期，见上）、不写
`job_attempts`。领取（`claim_next_due`）才是消耗额度的地方，而等待态的任务、以及
「依赖已满足但排期未到」的 `queued` 任务都不会被领取。测试钉住了这条（预算 0 的一轮后
`attempt_count` 仍是 0）。闸门本身是**纯查询**，不消耗预算；预算与条数上限照旧
**只在任务之间判断**，链式推进不会打断正在跑的任务。

**`next_wakeup` 的口径不变**：只由 `queued` / `retry_wait` 决定。在等前置的任务
要等的是「别人跑完」，不是时间到；前置那一环自己就在 `queued`/`retry_wait` 里，
下次唤醒时刻由它给。前置压根没有执行者时，闸门会把它终态失败，不会留下
「永远没有下一次唤醒」的挂死任务。

**为什么不用新状态、不改 schema。** `JobState::WaitingDependency` 本来就在契约里
（第 3 节任务状态机），只是此前没有写入者；「在等什么」写进现成的 `jobs.error_code`
列。新增状态或新列都要迁移与旧库兼容测试，这一片的约束明确要求不改 schema。

## 关键词索引任务化（`index`）

`kind = "index"` 的执行者：对任务 `target_ids` 里的**来源**跑
`Core::rebuild_keyword_index(Some(&target_ids))`；`target_ids` **为空表示整库**，
走 `Core::rebuild_keyword_index(None)`（关键词这一路；语义索引见下「没有做到的」）。

**为什么连索引也要排任务**，而不是只靠提取时的增量索引：增量索引写的是「那一刻」的
派生片段；重建任务是对现有材料的校准入口，也是 `indexes.rebuild`（契约 4.4）与后面
语义索引任务化要挂上去的位置。导入排的那条范围只限这条材料的来源，代价是这条来源的
片段数，不是整库；`indexes.rebuild(scope=all)` 排的才是整库那条。

**「运行期间关键词可用」怎么保证**（有测试钉住）：

- 重建按片段**先删后写、在事务里提交**，并且每次写入都 `bump_index_epoch`；
- 检索会话的快照按索引代次认账：索引一变，旧快照在下次读/翻页时如实报
  `search_expired`，前端重新发起查询，而不是拿半截/过期索引假装还准；
- 所以「索引任务在跑/没跑完」不等于「搜不到」：提取与增量索引在同一事务里就落库了，
  索引任务只是校准；跑完前后 `search.start` 都能查到同一段正文。

**失败口径**（照 #67 的 `HandlerFailure`）：

- **结构性**（目标来源不存在 `not_found`）→ 终态 `failed` + 明确错误码。
  正常路径上闸门在领取前就已经把它们终态失败了，执行者里再挡一次是
  防御：绕过闸门也不能悄悄成功；
- **可恢复**（IO / 数据库暂时不可用）→ 退避重试，消耗额度。

`no_target` 只有 `extract` 会用：提取没有「整库」这种语义，空目标是实打实的错误。

## `indexes.rebuild` 入口与 `scope` 编码

入口是 `Core::schedule_index_rebuild(scope, reason, operation_id)`（`index_rebuild.rs`），
桥接是 `BridgeSession::rebuildIndexes`，契约 4.4 节的 `indexes.rebuild`。它**只排一条
`index` 任务**并返回它，不做同步重建——同步重建会阻塞界面，而队列的退避、补做与依赖
闸门已经就绪。

`scope` 是一个字符串，只有两种合法写法（规范写在契约 4.4 节；共享场景文件里早就在写
`indexes.rebuild(scope=all)`）：

| 写法 | 排出的任务 |
|---|---|
| `all` | `target_ids` 为空 → 执行者走 `rebuild_keyword_index(None)`，重建整库（含没有来源的记录文字） |
| `sources:<id>[,<id>]*` | `target_ids` 是这些来源（已排序、无重复）→ 只重建它们，闸门按来源逐个评估前置 |

- id 只允许 `[A-Za-z0-9_]`：`,` 被固定成分隔符，**不定义转义**；
- **顺序没有语义**：解析时按字典序排成规范形，`sources:b,a` 与 `sources:a,b` 命中
  同一条任务；
- 空列表、空记号、重复 id、越界字符 → `invalid_argument`（契约第 7 节新增的码；
  「要整库」必须写 `all`，不能靠空列表）；不存在的来源 → `not_found`，**不排一条
  注定失败的任务**；
- **幂等**：同一个 `(scope, 原因, operationId)` 重复调用返回同一条任务，走通用
  `operation_receipts` 回执（契约 1.2）。回执只存任务 id，重放时按 id 读**当前**任务，
  所以重放返回的是这条任务此刻的真实状态；同一个 operationId 换了 scope 或原因报
  `idempotency_conflict`。任务自身的业务键
  `(kind, target_ids, input_snapshot_hash)` 照 #67 口径一并生效。

**整库任务等提取收尾。** `all` 没有 `target_ids`，闸门给它的前置是「队列里没有活着的
`extract`」：提取还在跑（`queued` / `retry_wait` / `running`）就落
`waiting_dependency` + `waiting_extract`，收尾后再按现状整库重刷。它**不判 `Broken`**：
某条提取被取消或放弃只是少一份内容，整库校准照样该跑，不该被连坐成终态失败。之所以
要等，是因为整库重建只重建「这一刻能索引的东西」——不等就会在提取落库前重建一次、
落库后又得靠那条 per-source 任务补，白跑一趟。代价是持续导入时它会一直等到队列里
没有提取为止：它是**最低优先级**的维护任务，宁可等，也不要在提取落库前重建到一半。
`sources:` 范围的任务在提取未完成时
照旧落 `waiting_dependency` + `waiting_extract`，提取一完成就被拉起（闸门在每次领取前
重评估，同一次驱动调用里走完；被条数上限截住时也会被推进到 `queued` 并给出可用的
`nextWakeup`，有测试钉住）。

## 退避规则

- `next_attempt_at = now + 30 秒 × 2^已用的尝试次数`，封顶 **1 小时**。
  也就是说第一次失败（`attempt_count = 1`）是 60 秒，之后 2 分钟、4 分钟……
  与 B1c 的 `backoff()` 完全一致，这一片没有改它。
- `attempt_count >= max_attempts` 时不再排期，直接进 `failed` 并把
  `requires_user_action` 置 1——「自动重试到头了」是需要用户看见的事实。
- **主动放弃（`no_handler` / 没有目标）不退避**：立刻进 `failed`，`job_attempts`
  里那次尝试仍然如实留着。
- 人工重试：`failed` → `queued`，`attempt_count = 0`、`next_attempt_at = NULL`、
  `error_code` 清空，并发出 `job.changed`。`job_attempts.attempt` 是**跨人工重试
  累计**的第几次（领取时取历史最大值 +1），所以清零不会撞上历史记录，也不会把
  「试过几次」抹掉。

## 业务键与幂等（以及为什么这一片不建 DB 约束）

`NewJob` 没有 `business_key` 字段，`jobs` 表也没有这一列。业务键在**同一个事务里**
现算现查：

```
业务键 = (kind, target_ids, input_snapshot_hash)
命中条件 = 同键 且 state NOT IN ('succeeded', 'failed', 'cancelled')
```

命中就返回已有任务（不新建、不发事件）；没有命中才插入。要点：

- `target_ids` 用它存库时的 JSON 文本，**数组顺序是语义的一部分**（多来源提取的
  顺序会影响结果），所以不做排序归一化。
- `input_snapshot_hash` 允许为空，比较用 SQLite 的 `IS`（空对空算相同）。
- **只有非终态才参与去重**：一条任务「已放弃」之后，同一个业务键可以重新入队——
  否则用户永远没法把它重新排上。
- 为什么不建 DB 级 UNIQUE 索引：目标索引得建立在
  `(kind, target_ids, input_snapshot_hash)` **且仅非终态**上，而 SQLite 的部分唯一
  索引（`WHERE state NOT IN (...)`）是 schema 变更，需要迁移、回填与旧库兼容测试。
  这一片的约束明确要求不改 schema，所以先用事务内检查——在**单写者**（`BridgeSession`
  用互斥锁串行化同一个 `Core`，见 `m1-桥接接线.md`）下它是充分的。多进程写入的保证
  留给下一次 schema 变更一起做，现在**不假装**已经有这个保证。

## E29：补做口径与「不谎报准时」

省电延迟、系统退出会让「到点了但没人跑」的任务留在队列里。核心必须能回答
「这次跑的有多少是补上的」，而且**不能把补上的说成准时完成的**。

**补做判定（写在 `jobs.rs::run_due` 里，也由测试钉住）：**

> 领取一条任务时，如果它的 `next_attempt_at` **存在且早于本次运行的开始时刻
> `started_at`**，这次执行就算「补做」。

**「按时」不算补做。** 在排期那一刻（`next_attempt_at == started_at`）或更早被领走
都不算；只有排在**过去**、这次才跑上的才算。等待依赖期间排期被保留（见上「依赖链」），
所以「排在未来、前置提前完成」的任务不会被提前跑，也就不会被误记成补做；反过来，
「排期已过、驱动当时没跑、后来才跑」的仍如实计入补做——两条方向都有测试钉住
（`index_job_test.rs` 的 #67 二轮复审回归）。

- 为什么用 `next_attempt_at`：它是队列里唯一记载「这条任务本该什么时候跑」的字段，
  也是退避唯一写入的字段。它已经过去了说明那一刻确实没人跑。
- 为什么**不**把 `next_attempt_at` 为空的任务算补做：空表示「入队即到期」，
  队列里根本没有它「本该何时跑」的信息。把 `created_at` 当应跑时刻会把
  「刚入队、紧接着就被跑」也算成补做，反而误导。这类**从未试过、排期为空**的积压
  由 `JobStatus.due_backlog` 和 `queued` 计数如实呈现。
- 这个边界是**已知的欠缺**：要如实区分「刚入队」与「重启后才补上的排队任务」，
  需要 schema 记录入队时的应跑时刻，或者记录「上次允许运行的时刻」。
  下一次 schema 变更一并做。现在宁可**少报**补做，也不虚构一个应跑时刻。

`JobRunSummary` 的字段就是「不谎报」的清单：

| 字段 | 含义 |
|---|---|
| `started_at` | 本次运行的开始时刻（调用方给的 `now`），补做判定的分界 |
| `trigger` | 唤醒来源，调用方给什么就记什么（`startup` / `foreground` / `wake` / `manual` …） |
| `processed` | 本次领取并执行的任务数，不超过条数上限 `max_jobs` |
| `succeeded` | 其中执行成功、进入 `succeeded` 的 |
| `failed` | 其中进入「已放弃」（`failed`）的（额度用完或没有处理器） |
| `retrying` | 其中失败但还有额度、已排退避重试（`retry_wait`）的 |
| `backfilled` | 其中属于补做的（口径如上） |
| `recovered` | 运行开始时回收的上次没跑完的 `running` 任务数 |
| `due_backlog` | 本次运行结束后**仍然到期**但没跑上的数量（被预算或条数截住） |
| `waiting_dependency` | 本次运行结束时还在等前置的任务数（现在只有 `index` 等 `extract`）；它们没被领取、没消耗额度，所以不在 `processed` 里 |
| `dependency_failed` | 本次运行里被闸门判定「前置不可能再满足」而终态失败的任务数；同样没被执行过，所以也不在 `processed` 里，但也不能让摘要把「什么都没跑」说成「一切正常」 |
| `next_wakeup` | 下一个到期时刻；没有待办时为 None（等前置的不算待办，见上） |

没有「准时完成」这样的字段，`backfilled` 也不会被折进 `succeeded` 之外的任何结论里：
界面可以同时说「补做了 N 个」，而不必（也不能）说「它们在计划时刻完成了」。
也没有单独的 `budget_exhausted`：`due_backlog > 0` 就说明这一轮**提前收手**了，
留两个字段只会互相矛盾。

**预算是时间（毫秒），条数是防御性上限。** `budget_ms` 是「这一轮还能不能再开一条」
的判据，按 `Instant` 的真实流逝时间算，**只在任务之间判断**：已经领取、正在跑的任务
不打断、也不能打断（核心不做抢占）。所以一条任务本身可以比预算还长——这是**已知且
有意**的行为，不假装能中途抢占。`max_jobs` 再夹一道条数上限，挡的是「队列很长 +
多条短任务」。`budget_ms = 0` 或 `max_jobs = 0` 都表示一条都不跑；被截住的到期任务
留在队列里、数量进 `due_backlog`，下次唤醒时刻照常给出。

## `no_handler` 的处理与将来的归宿

现在核心真实使用的 `kind` 有三个（`assets.rs` 的 `extract` 与 `index`、
`recordings.rs` 的 `transcribe`），其中 `extract` 与 `index` 有执行者。
`transcribe` 要等 B4a 的 Provider。驱动对没有执行者的 `kind` 一律：

1. 记一次尝试（`attempt_count` 递增，`job_attempts` 留下这次尝试）；
2. 立刻进 `failed`：`error_code = no_handler`、`requires_user_action = 1`、
   `attention_key = job-terminal:transcribe:no_handler`（同类同码的问题只提示一次）；
3. 发 `job.changed`。

它**不会**退避重试（没有处理器不会自己出现），也**绝不会**被算成 `succeeded`。
用户可以在任务面板看到它、点人工重试；在 B4a 接上 Provider 之后，重试就会真的
走转写执行者。`JobStatus.recent_errors` 会带着 `no_handler` 出现，界面据此提示
「转写能力还没配置」。

## 状态摘要字段（`Core::job_status()`）

- 各状态计数：`queued` / `running` / `retry_wait` / `waiting_*` / `failed` /
  `cancelled` / `succeeded`；
- `due_backlog`：**现在就该跑**的数量（`next_attempt_at` 为空或已过）；与
  `queued + retry_wait` 的区别是后者包含排在未来、还没到点的；
- `next_wakeup`：建议的下次唤醒时刻（`jobs::next_wakeup` 的口径）；
- `recent_errors`：最近 5 条，最新在前，每条只有 `job_id`（不透明 ID，供人工重试
  定位）、`kind`、`error_code`、`occurred_at`、`requires_user_action`。
  **没有 message、没有文件名、没有正文**。

桥接侧有 `BridgeSession::jobStatus()`（`jobs.status`）与
`BridgeSession::runDueJobs(budget_ms, trigger)`（`jobs.runDue`），都进了
`wired_capabilities()` 白名单。Dart 适配层（`packages/diary_bridge/lib/src/bridge_diary_api.dart`）
的 `_wiredMethods` 是更窄的一层，这两片都没有改它，所以适配层报的能力清单里仍然
看不到 `jobs.*`——这是它诚实的地方，不是遗漏。`packages/diary_api` 的
`DueRunSummary` 已经与核心摘要字段一一对齐，只等适配层接线。

## 与 #19、B4a 的边界

- **#19（系统级唤醒）**：负责「到点把进程叫起来」。这一片负责「叫起来之后，
  哪些任务该跑、跑完什么、还剩多少、还在等什么、哪些是补上的」。核心不自己定时、
  不起线程、不碰 WorkManager/AlarmManager。平台给多少毫秒预算、用什么 `trigger`
  调进来，是 #19 的事。
- **B4a（Provider）**：提供转写等真实能力。Provider 到位后，只要在 `jobs.rs::execute`
  的 `match` 里加一个分支（并让 `assets.rs`/`recordings.rs` 排的任务带够目标），
  `no_handler` 就会自然消失；那时「转写 → 索引」的前置要把 `transcribe` 也算进
  `index_dependency`（现在只看 `extract`）。用量与计费口径属于 B4a。

## 没有做到的

- **真机排期没有做**：没有 WorkManager / AlarmManager / 后台任务注册。平台给的毫秒
  预算现在**接了**（`runDueJobs(budgetMs, trigger)`），但「到点把进程叫起来」还是 #19
  的事；`trigger` 只是如实记录，核心不据此改变行为。
- **不抢占正在跑的任务**：预算只在任务之间判断，一条长任务可以把预算撑穿。要真正
  限时就得给提取/重建加可取消点，那是后续片的事。
- **语义索引任务化没做**：`build_semantic_index` 的任务化依赖
  [#58](https://github.com/xingxue-ux/unwritten-diary/issues/58)（本地向量接入）合入；
  这一片只把 `index` 执行者接到**关键词**重建上，`semantic_index_ready` 照旧为 false。
  `indexes.rebuild(scope=all)` 也只重建关键词这一路。
- **`indexes.rebuild` 的适配层（`BridgeDiaryApi`）还没接**：核心入口与桥接
  `BridgeSession::rebuildIndexes` 都通了（能力项 `indexes.rebuild` 进了
  `wired_capabilities()`），但 Dart 适配层的 `_wiredMethods` 这一片照旧没动——和
  `jobStatus` / `runDueJobs` 一样，适配层报的能力清单里看不到它们。这是它诚实的地方，
  等界面真正要用时再接。
- **`scope` 里没有「日期范围」「材料类型」这些范围**：契约只给了 `scope` 一个字符串，
  这一片只定义了整库与来源列表两种写法。要按时间或类型重建，先改契约。
- **插件任务没做**：插件的任务权限与限额属于 M4 插件片，这一片没有任何插件入口。
- **DB 级唯一约束没做**：见上「业务键与幂等」。跨进程写入的幂等保证还没有。
- **排期为空的任务不计入补做**：见上 E29 的边界，要等 schema 变更。
- **转写与「转写 → 索引」没接**：`transcribe` 仍走 `no_handler`（等 B4a），
  `index` 的前置只认 `extract`。B4a 到位后要把 `transcribe` 算进前置判断。
- **`waiting_configuration` / `waiting_network` 仍无写入者**：Provider 缺失、网络等待
  时该不该进这两个状态而不是 `failed`，等 B4a 定。
- **旧快照失效是「重取」不是「不中断」**：索引重建期间进行的检索会话会报
  `search_expired`，前端要重发查询；真正「边重建稳定翻页」的语义没有做（单连接
  串行下也不可能有并发重建）。
