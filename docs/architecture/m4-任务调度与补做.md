# M4 · 任务调度与后台补做（B5）

对应 issue [#65](https://github.com/xingxue-ux/unwritten-diary/issues/65) · 日期 2026-10-11 · 执行人 xingxue-ux

代码位置：`crates/diary_core/src/jobs.rs`（驱动、幂等、状态）、`crates/diary_core/src/model.rs`
（`JobRunSummary` / `JobStatus` / `NewJob.scheduledAt`）、`crates/diary_bridge/src/api.rs`
（桥接 `jobStatus` 与能力清单 `jobs.status`）。

**队列本身是 B1c 落的**（`docs/architecture/m1-录音与队列.md`）：入队、领取、成功/失败、
退避、取消、下次唤醒、`job.changed`。这一片加的是**按 `kind` 派活执行的驱动**、
**业务键幂等**、**补做口径**与**状态摘要**。不改 schema、不加依赖。

## 定下的决定

| 决定 | 理由 |
|---|---|
| 驱动放在核心：`run_due_jobs(now, limit) -> JobRunSummary` | 「取到期任务 → 执行 → 记录结果/重试」是核心自己的事；**什么时候允许跑**由平台决定（#19 的系统级唤醒），核心只报「跑完什么、还剩多少」 |
| 只实现**真有执行者**的 `kind`：`extract` | `transcribe` 要等 B4a 的 Provider。假装能跑比不跑更糟 |
| 没有执行者的 `kind` → `failed` + `error_code = no_handler` + `requires_user_action = 1` | 必须出现在状态里、能人工重试；**绝不静默 complete**。没有处理器不会因为多试几次就出现，所以不退避、不浪费额度 |
| `extract` 的成败 = **提取路径是否跑完** | 提取器自己裁决的 `status=failed` / `metadata_only` 已经如实落在 `extracted_contents`（带 coverage 与错误码），那才是「这个文件能不能搜」的答案。在这里再失败一次只会让确定性的格式问题白白退避重试五分钟。**结构性失败**（修订不存在、原件不在文件库、没有目标）才让任务失败 |
| `succeeded` 只发给真的跑完的任务 | `JobRunSummary.succeeded` 是「执行成功的任务数」，不是「有内容的来源数」 |
| 运行开始先回收上次没跑完的 `running` 任务 | 进程在任务进行中被杀（退出/断电）时任务会停在 `running`，而驱动只领取 `queued`/`retry_wait`——不回收就是**永久丢掉**。单写者 + 单驱动下，运行开始时还停在 `running` 的一定是上一次没走完的 |
| 业务键 `(kind, target_ids, input_snapshot_hash)`，同一个事务里先查后插 | 这一片不改 schema，所以键只能从现有列算；单写者 SQLite 下事务内检查足够。DB 级 UNIQUE 索引留给下一次 schema 变更 |
| 人工重试把 `attempt_count` **清零** | 用户在任务面板点一次重试，就再给一整份额度；`max_attempts` 不动。历史尝试记录（`job_attempts`）不删，编号跨人工重试累计 |
| `job.changed` 由**队列自己**发 | 入队（`enqueue_in_tx`）、开始（`claim_next_due`）、成功、失败、重试、取消各发一次。调用方不用记得发，也就不会漏；同一个事务里发，状态与通知不会一个成一个败 |
| 最近错误只带 `kind` + `error_code` + 时间（+不透明的 `job_id`） | `job_attempts.message` 里可能有文件路径或原始报错，那是排查信息，不该跟着状态摘要流出 |

## 状态机（含 `failed` 与「已放弃」的对应）

```
                  claim_next_due
   queued ──────────────────────────► running
     ▲                                  │
     │ 回收 interrupted（还有额度）      ├── complete ──────► succeeded
     │                                  ├── fail（还有额度）─► retry_wait ──┐
     │                                  └── fail（额度用完）─► failed       │
     │                                                                      │
     │                                           到点后 claim_next_due ◄────┘
     │
     └──────────── retry_job（人工，清零）◄──── failed（「已放弃」）

   queued / retry_wait / running ── cancel ──► cancelled
```

issue #65 里的四个用户可见说法与内部状态名是一一对应的：

| 任务面板说法 | 状态名 | 说明 |
|---|---|---|
| 排队中 | `queued` | 已入队，等被领取；`next_attempt_at` 为空或已过 |
| 进行中 | `running` | 已经被驱动领取，正在执行 |
| 失败可重试 | `retry_wait` | 失败过、还有额度，`next_attempt_at` 是下次尝试时刻 |
| 已放弃 | `failed` | 额度用完、或没有处理器（`no_handler`）。`requires_user_action = 1`，等用户决定要不要重试 |

`waiting_configuration` / `waiting_dependency` / `waiting_network` 三个状态**现在还
没有写入者**（B4a 缺 Provider 时会有用武之地），计数照旧如实报 0，不假装用过它们。

## 退避规则

- `next_attempt_at = now + 30 秒 × 2^已用的尝试次数`，封顶 **1 小时**。
  也就是说第一次失败（`attempt_count = 1`）是 60 秒，之后 2 分钟、4 分钟……
  与 B1c 的 `backoff()` 完全一致，这一片没有改它。
- `attempt_count >= max_attempts` 时不再排期，直接进 `failed` 并把
  `requires_user_action` 置 1——「自动重试到头了」是需要用户看见的事实。
- **主动放弃（`no_handler` / 没有目标）不退避**：立刻进 `failed`，`job_attempts`
  里那次尝试仍然如实留着。
- 人工重试：`failed` → `queued`，`attempt_count = 0`、`next_attempt_at = NULL`、
  `error_code` 清空，并发出 `job.changed`。`job_attempts.attempt` 是**跨人工重试
  累计**的第几次（领取时取历史最大值 +1），所以清零不会撞上历史记录，也不会把
  「试过几次」抹掉。

## 业务键与幂等（以及为什么这一片不建 DB 约束）

`NewJob` 没有 `business_key` 字段，`jobs` 表也没有这一列。业务键在**同一个事务里**
现算现查：

```
业务键 = (kind, target_ids, input_snapshot_hash)
命中条件 = 同键 且 state NOT IN ('succeeded', 'failed', 'cancelled')
```

命中就返回已有任务（不新建、不发事件）；没有命中才插入。要点：

- `target_ids` 用它存库时的 JSON 文本，**数组顺序是语义的一部分**（多来源提取的
  顺序会影响结果），所以不做排序归一化。
- `input_snapshot_hash` 允许为空，比较用 SQLite 的 `IS`（空对空算相同）。
- **只有非终态才参与去重**：一条任务「已放弃」之后，同一个业务键可以重新入队——
  否则用户永远没法把它重新排上。
- 为什么不建 DB 级 UNIQUE 索引：目标索引得建立在
  `(kind, target_ids, input_snapshot_hash)` **且仅非终态**上，而 SQLite 的部分唯一
  索引（`WHERE state NOT IN (...)`）是 schema 变更，需要迁移、回填与旧库兼容测试。
  这一片的约束明确要求不改 schema，所以先用事务内检查——在**单写者**（`BridgeSession`
  用互斥锁串行化同一个 `Core`，见 `m1-桥接接线.md`）下它是充分的。多进程写入的保证
  留给下一次 schema 变更一起做，现在**不假装**已经有这个保证。

## E29：补做口径与「不谎报准时」

省电延迟、系统退出会让「到点了但没人跑」的任务留在队列里。核心必须能回答
「这次跑的有多少是补上的」，而且**不能把补上的说成准时完成的**。

**补做判定（写在 `jobs.rs::run_due` 里，也由测试钉住）：**

> 领取一条任务时，如果它的 `next_attempt_at` **存在且早于本次运行的开始时刻
> `started_at`**，这次执行就算「补做」。

- 为什么用 `next_attempt_at`：它是队列里唯一记载「这条任务本该什么时候跑」的字段，
  也是退避唯一写入的字段。它已经过去了说明那一刻确实没人跑。
- 为什么**不**把 `next_attempt_at` 为空的任务算补做：空表示「入队即到期」，
  队列里根本没有它「本该何时跑」的信息。把 `created_at` 当应跑时刻会把
  「刚入队、紧接着就被跑」也算成补做，反而误导。这类**从未试过、排期为空**的积压
  由 `JobStatus.due_backlog` 和 `queued` 计数如实呈现。
- 这个边界是**已知的欠缺**：要如实区分「刚入队」与「重启后才补上的排队任务」，
  需要 schema 记录入队时的应跑时刻，或者记录「上次允许运行的时刻」。
  下一次 schema 变更一并做。现在宁可**少报**补做，也不虚构一个应跑时刻。

`JobRunSummary` 的字段就是「不谎报」的清单：

| 字段 | 含义 |
|---|---|
| `started_at` | 本次运行的开始时刻（调用方给的 `now`），补做判定的分界 |
| `processed` | 本次领取并执行的任务数，不超过 `limit` |
| `succeeded` | 其中执行成功、进入 `succeeded` 的 |
| `failed` | 其中进入「已放弃」（`failed`）的（额度用完或没有处理器） |
| `retrying` | 其中失败但还有额度、已排退避重试（`retry_wait`）的 |
| `backfilled` | 其中属于补做的（口径如上） |
| `recovered` | 运行开始时回收的上次没跑完的 `running` 任务数 |
| `due_backlog` | 本次运行结束后**仍然到期**但没跑上的数量（被 `limit` 截住） |
| `next_wakeup` | 下一个到期时刻；没有待办时为 None |

没有「准时完成」这样的字段，`backfilled` 也不会被折进 `succeeded` 之外的任何结论里：
界面可以同时说「补做了 N 个」，而不必（也不能）说「它们在计划时刻完成了」。

`limit` 是**预算**不是建议：`limit = 0` 一个都不跑，被截住的到期任务留在队列里、
数量进 `due_backlog`，下次唤醒时刻照常给出。

## `no_handler` 的处理与将来的归宿

现在核心真实使用的 `kind` 有两个（`assets.rs` 的 `extract`、`recordings.rs` 的
`transcribe`），但**只有 `extract` 有执行者**。`transcribe` 要等 B4a 的 Provider。
驱动对没有执行者的 `kind` 一律：

1. 记一次尝试（`attempt_count` 递增，`job_attempts` 留下这次尝试）；
2. 立刻进 `failed`：`error_code = no_handler`、`requires_user_action = 1`、
   `attention_key = job-terminal:transcribe:no_handler`（同类同码的问题只提示一次）；
3. 发 `job.changed`。

它**不会**退避重试（没有处理器不会自己出现），也**绝不会**被算成 `succeeded`。
用户可以在任务面板看到它、点人工重试；在 B4a 接上 Provider 之后，重试就会真的
走转写执行者。`JobStatus.recent_errors` 会带着 `no_handler` 出现，界面据此提示
「转写能力还没配置」。

## 状态摘要字段（`Core::job_status()`）

- 各状态计数：`queued` / `running` / `retry_wait` / `waiting_*` / `failed` /
  `cancelled` / `succeeded`；
- `due_backlog`：**现在就该跑**的数量（`next_attempt_at` 为空或已过）；与
  `queued + retry_wait` 的区别是后者包含排在未来、还没到点的；
- `next_wakeup`：建议的下次唤醒时刻（`jobs::next_wakeup` 的口径）；
- `recent_errors`：最近 5 条，最新在前，每条只有 `job_id`（不透明 ID，供人工重试
  定位）、`kind`、`error_code`、`occurred_at`、`requires_user_action`。
  **没有 message、没有文件名、没有正文**。

桥接侧加了 `BridgeSession::jobStatus()`（`jobs.status`）并把它加进
`wired_capabilities()` 白名单。Dart 适配层（`packages/diary_bridge/lib/src/bridge_diary_api.dart`）
的 `_wiredMethods` 是更窄的一层，这一片没有改它，所以适配层报的能力清单里仍然
看不到 `jobs.status`——这是它诚实的地方，不是遗漏。

## 与 #19、B4a 的边界

- **#19（系统级唤醒）**：负责「到点把进程叫起来」。这一片负责「叫起来之后，
  哪些任务该跑、跑完什么、还剩多少、哪些是补上的」。核心不自己定时、不起线程、
  不碰 WorkManager/AlarmManager。
- **B4a（Provider）**：提供转写等真实能力。Provider 到位后，只要在 `jobs.rs::execute`
  的 `match` 里加一个分支（并让 `assets.rs`/`recordings.rs` 排的任务带够目标），
  `no_handler` 就会自然消失。用量与计费口径属于 B4a。

## 验证到了什么

`cargo test -p diary_core` 全绿（新增 `tests/job_runner_test.rs` 10 项）：

- 驱动把导入排下的 `extract` 跑完：来源真的提取、关键词立刻能搜到、任务进
  `succeeded`；入队即到期的任务**不**算补做；
- 结构性失败：`attempt_count` 递增、`error_code = not_found`、退避落在将来、
  没到点领不到；到 `max_attempts` 后进 `failed` 且 `requires_user_action`；
  过了退避点才跑上的那一次**算补做**；
- 人工重试：`retry_job` 把 `attempt_count` 清零、清错误码、可再次被驱动执行；
  没到 `failed` 的任务拒绝重试；
- **E29**：排期在两小时前的一条 `extract` → **关库重开** → 驱动跑到它、
  真的提取完，`summary.backfilled == 1`，状态摘要报 `succeeded = 1`、
  零积压；
- `no_handler`：`transcribe` 进 `failed` + `no_handler` + `requires_user_action`，
  **不静默成功**，人工重试后仍然如实失败；状态摘要的最近错误里能看到它；
- 幂等：同业务键重复入队只有一条任务、驱动只执行一次（`processed == 1`、
  只尝试过一次）；换快照是另一条；到终态后可以重新入队；
- `limit` 语义：5 条到期任务 `limit = 2` → 只跑 2 条、3 条留在 `queued`、
  `due_backlog == 3`；`limit = 0` 一条都不跑；
- `job.changed` 在入队/开始/成功/失败/人工重试/取消时各发一次（用事件计数钉住）；
- 上次没跑完的 `running` 任务被回收并跑完，不会被永久跳过；
- 任务失败不影响本地优先：关键词检索（走 `search.start`，含记录正文）、
  查看、保存新记录全部照常。

另外：`cargo clippy --workspace --all-targets -- -D warnings` 零问题；
`cargo build --release` 通过；`packages/diary_bridge` 的 `dart analyze --fatal-infos`
与 `dart test` 全过（新增 `jobStatus()` 与能力清单断言）。

## 没有做到的

- **真机排期没有做**：没有 WorkManager / AlarmManager / 后台任务注册，也没有
  「运行预算（毫秒）」的强制中断。`limit` 现在按**任务条数**计，平台给的毫秒预算
  还没有接（`packages/diary_api` 的 `runDueJobs(budgetMs, trigger)` 只定了形状）。
- **插件任务没做**：插件的任务权限与限额属于 M4 插件片，这一片没有任何插件入口。
- **DB 级唯一约束没做**：见上「业务键与幂等」。跨进程写入的幂等保证还没有。
- **排期为空的任务不计入补做**：见上 E29 的边界，要等 schema 变更。
- **索引任务化没做**：`rebuild_keyword_index` 还是同步入口，语义索引
  （约 280 秒 / 10 万块）也还没任务化；这一片只提供了驱动与 `extract` 执行者，
  把「分块 / 关键词重建 / 向量索引」排成任务的活留给后续片。
- **`waiting_*` 三个状态仍无写入者**：Provider 缺失时该不该进
  `waiting_configuration` 而不是 `failed`，等 B4a 定。
- **运行预算按毫秒计、取消正在跑的任务**没有做：现在一次 `run_due_jobs` 会跑到
  `limit` 或没有到期任务为止，中途不能被取消。
