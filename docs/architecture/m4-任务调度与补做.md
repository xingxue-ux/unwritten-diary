## 定下的决定

| 决定 | 理由 |
|---|---|
| 驱动放在核心：`run_due_jobs(now, budget_ms, trigger, max_jobs) -> JobRunSummary` | 「取到期任务 → 执行 → 记录结果/重试」是核心自己的事；**什么时候允许跑**由平台决定（#19 的系统级唤醒），核心只报「跑完什么、还剩多少、还在等什么」 |
| 平台给的是**毫秒预算**，不是条数 | 契约 `jobs.runDue` 的输入一直是 `budgetMs` + `trigger`（`packages/diary_api` 早就这么声明了），核心这边原来只有 `limit`，属于「契约先行、实现落后」。预算按真实流逝时间（`Instant`）算，与业务时钟 `now` 分开——测试会把 `now` 推到过去/未来排期，用它算预算会随调用方的时钟走 |
| **预算只在任务之间判断**，不打断正在跑的任务 | 核心不做抢占：`rebuild_keyword_index`、提取这些同步重活没有安全的取消点。所以「一条任务本身比预算还长」是**允许发生**的，预算是「这一轮还能不能再开一条」。不假装能中途抢占。**例外是执行者自己会安全停下的任务**：语义重建在块与块之间看预算截止点，到点**主动让出**（不是被抢占），见「语义索引任务化」 |
| 另加一个**条数上限**（核心参数 `max_jobs`，桥接常量 64） | 预算挡长尾，它挡「队列很长 + 多条短任务」把一轮拖成没完没了。被两种上限截住的到期任务都留在队列里、如实进 `due_backlog` |
| `trigger` 只如实记进摘要 | 唤醒来源是排查用的：`startup` / `foreground` / `wake` / `manual` …。核心不认识这些值的语义，也不因为它改变行为——「什么时候调用」是 #19 的事 |
| 只实现**真有执行者**的 `kind`：`extract`、`index`、`semantic_index`、`respond`（B4a）、`transcribe`（#91，本机引擎） | 执行者的清单只有一处（`jobs::HANDLED_KINDS`）；假装能跑比不跑更糟 |
| 没有执行者的 `kind` → `failed` + `error_code = no_handler` + `requires_user_action = 1` | 必须出现在状态里、能人工重试；**绝不静默 complete**。没有处理器不会因为多试几次就出现，所以不退避、不浪费额度 |
| `extract` 的成败 = **提取路径是否跑完** | 提取器自己裁决的 `status=failed` / `metadata_only` 已经如实落在 `extracted_contents`（带 coverage 与错误码），那才是「这个文件能不能搜」的答案。在这里再失败一次只会让确定性的格式问题白白退避重试五分钟。**结构性失败**（修订不存在、原件不在文件库、没有目标）才让任务失败 |
| `index` 的前置用**派生内容在不在**判断，而不是「提取任务成功过」 | 改过正文、重跑过提取的来源会换修订，队列里那条 `extract` 的成功与否已经不是当下的真相；`extracted_contents` 里有没有当前修订的行才是「现在能不能索引」的答案 |
| 前置未满足 → `waiting_dependency`，**不领取、不消耗重试额度、不退避** | 在等前置不是一次失败。领取会递增 `attempt_count` 并写 `job_attempts`，所以闸门在**领取之前**就把等待态维持住 |
| 闸门在**每次领取前**重评估，并在**轮末**再评估一次（不是「每轮只评估一次」） | 「每轮只评估一次」会让链停住：前置跑完时后继仍留在等待态，而 `next_wakeup` 不把等待态算成待办，队列空时摘要给出 `null`，按摘要安排唤醒的平台层不会再叫驱动（#74 评审指出）。每次领取前评估让链在**一次**驱动调用里走完；轮末评估是「有等待态就必须有可用唤醒」这条不变式的兜底。**不采用**「把 `nextWakeup` 设成立即唤醒」的补丁：那等于把链的完成寄托在平台层肯不肯再叫一次上，而 #19 可能因省电/退出不叫 |
| 等待 / 晋升期间**保留原 `next_attempt_at`**；只有「依赖满足」**且**「到期」同时成立才领取 | #67 二轮复审：`defer_for_dependency` / `promote_dependency` 清空排期会让「一小时后」的索引任务在前置提前完成时被**立刻领走**，原到期时刻还同时从 `next_wakeup` 与补做统计里消失。保留排期后它落在 `queued` + 未来排期，既有的领取判据（`next_attempt_at IS NULL OR <= now`）自然拦住，**不需要另加状态**；作为 `queued` 任务它照常进 `next_wakeup`，「何时该跑」不丢。等待态本身仍不算待办（由它的前置负责唤醒） |
| 前置不可能再满足 → 终态 `failed` + `dependency_extract_unmet` + `requires_user_action` | 挂死不如如实失败：提取被取消/放弃而派生内容永远不会出现时，留一条「永远没有下次唤醒」的任务对谁都没好处。错误码里点明等的是哪一环 |
| `index` 的空 `target_ids` = **整库**（`indexes.rebuild(scope=all)`） | 执行者走 `rebuild_keyword_index(None)`，与 `indexes.status` 不传范围、与同步入口的 `None` 同义；`sources:` 范围表达不了「没有来源的记录文字」，整库必须走 `None`。非空的 `target_ids` 只重建这些来源，行为不变。整库任务的前置是「队列里没有活着的 `extract`」：等提取收尾再按现状重刷，且**不判 `Broken`**——某条提取被取消只是少一份内容，不该把整库重建连坐成失败 |
| `indexes.rebuild(scope, reason, operationId)` **只排一条 `index` 任务**，返回 `jobId` | 契约 4.4 的返回本来就是 `jobId`（异步），这一片把它接上。不做同步重建：同步重建会阻塞界面，而队列的退避、补做与依赖闸门已经就绪。入口在 `index_rebuild.rs`，桥接是 `BridgeSession::rebuildIndexes` |
| `scope` 只有 `all` 与 `sources:<id>[,<id>]*` 两种写法 | id 只允许 `[A-Za-z0-9_]`，`,` 固定成分隔符、**不定义转义**；顺序无语义（解析时排序成规范形）；空列表、空记号、重复 id、越界字符报 `invalid_argument`，不存在的来源报 `not_found`。规范写在契约 4.4 节（共享场景文件里早就在写 `indexes.rebuild(scope=all)`） |
| 入口的幂等走**通用 operationId 回执**（`operation_receipts`），不只靠业务键 | 契约 1.2 要求「同一 id 换了内容报冲突」。回执只存任务 id，重放时按 id 读**当前**任务，所以返回的永远是这条任务此刻的真实状态，而不是入队那一刻的旧快照。任务自身的业务键 `(kind, target_ids, input_snapshot_hash)` 照 #67 口径一并生效 |
| `succeeded` 只发给真的跑完的任务 | `JobRunSummary.succeeded` 是「执行成功的任务数」，不是「有内容的来源数」 |
| 运行开始先回收上次没跑完的 `running` 任务 | 进程在任务进行中被杀（退出/断电）时任务会停在 `running`，而驱动只领取 `queued`/`retry_wait`——不回收就是**永久丢掉**。单写者 + 单驱动下，运行开始时还停在 `running` 的一定是上一次没走完的 |
| 业务键 `(kind, target_ids, input_snapshot_hash)`，同一个事务里先查后插 | 这一片不改 schema，所以键只能从现有列算；单写者 SQLite 下事务内检查足够。DB 级 UNIQUE 索引留给下一次 schema 变更 |
| 人工重试把 `attempt_count` **清零** | 用户在任务面板点一次重试，就再给一整份额度；`max_attempts` 不动。历史尝试记录（`job_attempts`）不删，编号跨人工重试累计 |
| `job.changed` 由**队列自己**发 | 入队（`enqueue_in_tx`）、开始（`claim_next_due`）、成功、失败、重试、取消、依赖状态变化各发一次。调用方不用记得发，也就不会漏；同一个事务里发，状态与通知不会一个成一个败 |
| 最近错误只带 `kind` + `error_code` + 时间（+不透明的 `job_id`） | `job_attempts.message` 里可能有文件路径或原始报错，那是排查信息，不该跟着状态摘要流出 |
| 语义重建是**另一个 kind**（`semantic_index`），不是 `index` 的一个「种类」 | 两条路的前置（等模型配置 vs 等提取）、成败口径、能不能分段都不一样，而 `indexes.rebuild` 的契约语义是「只排一条 `index` 任务」、必须原样不动。理由详见「语义索引任务化」一节 |
| 语义重建的常规入口是**显式请求**（核心入口 `Core::schedule_semantic_index`）；**自动触发**只在模型 `Configured`/`Ready`、生效代次口径不一致（`storage`/`dims`/已加载时的 `model_version`）、队列里没有活着的 `semantic_index`、且同一口径（按**不一致的种类**计）自动尝试不到两次时排一条（#128 复审拍板） | 「什么时候值得花一次模型调用」仍是产品决定；自动触发只覆盖**已确定需要重建**的窄条件。没配模型**不排**（否则长期挂 `waiting_configuration` 噪声）；「正在建」看的是**活任务**而不是 `building_generation`（失败/取消留下的代次不能挡住重排）；持久标记让失败行不随每次 `open` 增长。判据都在既有信号里（`indexes.status` 的 `semantic_index_ready` / `reasons` / 覆盖数字、语义检索的口径警告），不另造「该不该排」的查询 API；去重靠业务键，重复 `open` 仍只有一条 |
| 语义任务**总是整库**（空 `target_ids`）、**不给快照** | 代次与向量是全局的（范围只决定重算哪些块），按来源排既不省模型调用、又会把去重键碎成好几条。业务键 `(semantic_index, [], NULL)` 于是成为「队列里至多一条活着的语义重建」——重复排队不产生第二份工作 |
| 长任务**在安全点让出**，而不是被抢占 | 语义重建每算一块就是一个提交点（向量一块一个事务写进 `building_generation`），所以它能安全停在块与块之间：回 `queued`、进度写 `progress_completed/total`、下一轮续跑。提取与关键词重建**没有**这样的点（一条批量 SQL / 一次同步重建），照旧一跑到底——它们的「不可中断」如实写在「没有做到的」里 |
| 让出**不算一次尝试**（`attempt_count` 减回去，`job_attempts` 记 `outcome = yielded`） | 一条整库重建可能要让出几十轮；按失败计会白白耗尽 `max_attempts`，把本来能跑完的任务变成「已放弃」。它确实开始过、也写过向量，所以历史记录留着，只是 outcome 说明它是让出结束的 |
| 摘要**不为让出加字段**：让出的任务计 `processed`，不计 `succeeded`/`failed`/`retrying` | 契约 `DueRunSummary` 的字段一个没多（不能改契约）。「还活着、还没跑完」由 `due_backlog > 0` + `next_wakeup` 指向「现在」+ 每条任务的 `progress` 说清楚 |
| 模型没就绪时落 `waiting_configuration`（`error_code = waiting_model`），**不进 `next_wakeup`** | 它等的不是「别人跑完」，是**配置**（模型目录 / ORT 动态库）。配置变化不是时间问题：下一次驱动（前台/唤醒/配置变化后）的闸门就会把它拉起。#74 的不变式只约束 `waiting_dependency`，这里不冲突也不破坏它 |
| 进度写入**不发** `job.changed` | 一次整库重建每算一块就写一次进度，几万条事件是噪声。状态变化（让出、完成、失败…）照旧发事件；纯进度用 `listJobs` / `jobStatus` 轮询看 |

## 状态机（含 `failed` 与「已放弃」的对应）

执行生命周期（#67 定下的，没有改）：

```
                  claim_next_due
   queued ──────────────────────────► running
     ▲                                  │
     │ 回收 interrupted（还有额度）      ├── complete ──────► succeeded
     │                                  ├── fail（还有额度）─► retry_wait ──┐
     │                                  └── fail（额度用完）─► failed       │
     │                                                                      │
     │                                           到点后 claim_next_due ◄────┘
     │
     └──────────── retry_job（人工，清零）◄──── failed（「已放弃」）

   queued / retry_wait / running ── cancel ──► cancelled
```

依赖闸门（#70 前半加的，作用于有前置的 `kind`：`index` 与 `semantic_index`）：

```
   入队（前置已知未满足）
        │
        ▼
   waiting_dependency ──每次领取前 / 轮末重新评估──┬─ 前置已满足 ──► queued（保留原排期；到期才领取）
   （attempt_count 不动、               ├─ 仍未满足 ──► waiting_dependency（原因码不变）
     不退避、不算失败、保留原排期）        ├─ 不可能满足 ──► failed + requires_user_action
                                        │                 （dependency_extract_unmet）
                                        └─ 前置是配置 ──► waiting_configuration + waiting_model
                                                           （模型没配/不可用；配置好了由下一次驱动拉起）

   分段让出（只有 semantic_index）：
   running ──预算到点、在块与块之间主动停下──► queued（清空排期 = 立刻接着跑；
                                              进度写进 progress_completed/total；
                                              attempt_count 减回去，job_attempts 记 yielded）
```

issue #65 里的四个用户可见说法与内部状态名是一一对应的：

| 任务面板说法 | 状态名 | 说明 |
|---|---|---|
| 排队中 | `queued` | 已入队，等被领取；`next_attempt_at` 为空或已过。（被闸门从等待态晋升、但排期仍在未来的任务也在这里：它**过了排期**才会被领取。语义索引**让出**之后也在这里：它已经算了一段、下一轮接着算） |
| 进行中 | `running` | 已经被驱动领取，正在执行。语义索引在跑的时候可以在 `Job.progress` 上看到「已完成 / 总数」 |
| 失败可重试 | `retry_wait` | 失败过、还有额度，`next_attempt_at` 是下次尝试时刻 |
| 已放弃 | `failed` | 额度用完、没有处理器（`no_handler`）、或前置不可能满足（`dependency_extract_unmet`）。`requires_user_action = 1`，等用户决定要不要重试 |
| 等待前置 | `waiting_dependency` | 前置（`extract`）还没跑完。**不是失败**：`attempt_count` 不动、没有退避、没有 `requires_user_action`；`error_code = waiting_extract` 说明在等哪一环 |
| 等待配置 | `waiting_configuration` | 在等**配置**：语义索引等本地模型配好（`error_code = waiting_model`）、Provider 作业等服务配好/修好（`provider_not_configured`、`authentication_failed`…）。**不是失败**：不退避、不消耗重试额度。但它**不是无需理会的状态**：`requires_user_action = 1` + `attention_key = job-config:<kind>:<error_code>`（界面靠它深链到「配哪一个」）。`attempt_count` 是唯一按「有没有真的跑过」区分的字段：闸门在领取前挡下 → 0；执行期才发现 → 如实记账。**不进 `next_wakeup`**——配置变化不是时间问题，下一次驱动的闸门会重新评估并拉起它 |

`waiting_network` **现在还没有写入者**（网络等待时会有用武之地），计数照旧如实报 0，
不假装用过它。`waiting_dependency` 从 #70 前半开始有真实写入者：**导入完成排下的
`index` 任务**（`assets.rs::finish_import`，与 `extract` 入队同一个事务）；
`waiting_configuration` 从**语义索引任务化**开始有真实写入者：**模型没配好时的
`semantic_index` 任务**（闸门 `semantic_index_dependency`，或执行者真正加载模型失败时）；
B4a 之后 Provider 作业（`respond`）也是它的写入者（能力闸门 `job_capability` /
`promote_configuration_waits`，或执行期撞上 401/额度用尽）；#91 之后 `transcribe` 同样
走这条闸门（本机 ASR 引擎/模型没就绪 → `provider_not_configured`，见
[M3 · 转写链](m3-转写链.md)）。

**等配置的语义（跨 kind 一把尺，#96 合 main 后统一）。** `waiting_configuration`
的含义**不因 kind 而异**，三件事分开说：

| 字段 | 两条路共同的答案 | 为什么 |
|---|---|---|
| `requires_user_action` | **恒为 1** | 等配置不是失败，但**不是一个用户无需理会的状态**：用户得去把服务配上 / 模型配好。旧口径（「等配置不置 `requiresUserAction`」）已经作废 |
| `attention_key` | **恒为 `job-config:<kind>:<error_code>`** | 界面要能深链到「去配哪一个服务 / 哪台机器的模型」；形状只有一处（`jobs::configuration_attention_key`），同一类问题也只提示一次 |
| `attempt_count` | **闸门路 = 0；执行期路 = 如实记账（不回退）** | 「没跑过就不计尝试，真跑了一次就如实记账」——差别只是**有没有真的跑过一次**，不是两套语义。`job_attempts` 里那次尝试以 `outcome = 'waiting_configuration'` 收尾 |

两条路：**闸门**（`defer_for_configuration`：语义闸门；`promote_configuration_waits`：
Provider 闸门）在**领取前**挡下，连一次尝试都没发生；**执行期**
（`defer_for_configuration_after_attempt`：Provider 真的发了请求撞 401、语义索引真的去
加载模型才发现失败）在领取之后才发现，于是那一次尝试照实记。两条都不排退避、不消耗
重试额度。回归测试 `waiting_configuration_means_the_same_thing_across_job_kinds`
钉住「同一个状态、不同 kind 的 `requiresUserAction` 必须相同」——把任一侧改回旧口径它就红。

## 依赖链与 `waiting_dependency`

这一片把「重活」串成链：**导入 → 提取（`extract`）→ 关键词索引（`index`）**；
语义那一路（`semantic_index`）**排在同一个依赖之后**，但要由调用方显式请求才会进队列
（见「语义索引任务化」的排队口径）。链条的每一环都是一条持久任务，不靠调用方手工排队，
也不靠「睡一会儿再试」。

**什么时候进等待态。** `finish_import` 在同一个事务里排两条任务：`extract`（对修订）
与 `index`（对来源）。后者的初始状态就是 `waiting_dependency` + `error_code = waiting_extract`
——这一刻提取一定还没跑。用户不用等一轮驱动就能在 `job_status()` / `list_jobs()` 里
看到它在等哪一环。显式请求来的 `semantic_index` 任务入队时是 `queued`（这一刻不知道
提取跑到哪了），**领取前的第一次闸门**就会按真相把它推到 `waiting_dependency` /
`waiting_configuration`——用户在一轮驱动之内就能看到它在等哪一环。

**在等什么（「闸门」`index_dependency` 的口径）。** 对 `target_ids` 里的每个**来源**：

- `target_ids` 为空 = **整库重建**（`indexes.rebuild(scope=all)`）：前置是「队列里没有
  活着的 `extract`」——等提取收尾再按现状重刷（见下「整库重建」）；
- 来源不存在 / 没有当前修订 / 当前修订读不到 → 前置**不成立**（终态 `not_found`）；
- 当前修订是**文字修订**（`source_revisions.asset_id` 为空）：提交时正文就落库并同步
  进了关键词索引，关键词这一路**没有「提取」这一环** → 视为可索引；
- 当前修订有资产：要有 `extracted_contents` 行（派生内容）才算提取完；还没有的话，
  看队列里还有没有**活着的** `extract` 任务瞄着这个修订（`state NOT IN
  ('succeeded','failed','cancelled')` 且 `target_ids` 精确含这个修订 id）：
  - 有 → 继续等（`waiting_extract`）；
  - 没有 → 前置**不可能再满足**（`dependency_extract_unmet`）。

**什么时候被拉起。** 驱动**每次领取前**先跑一次闸门（`resolve_dependencies`），
**一轮收尾时**再跑一次：

- 前置已满足的在等任务 → 状态回到 `queued`、清掉原因码，**保留它原本的
  `next_attempt_at`**；排期为空的，同一轮的下一次领取就能跑；排期在未来的，等到
  「依赖满足」**且**「到期」两个条件同时成立才被领走；
- 前置仍未满足的 → 留在 `waiting_dependency`（原因码只写一次，不每轮刷 `updated_at`），
  同样**保留原排期**；
- 前置不可能满足的 → 终态 `failed`，`requires_user_action = 1`。

**排期为什么不能在等待 / 晋升时清掉（#67 二轮复审）。** 一条任务可能本来就排在未来
（例如「一小时后执行」的索引任务）。等待前置期间把 `next_attempt_at` 清空、晋升时又
清空并放进 `queued`，它就变成「入队即到期」：前置若提前完成，这条任务会在**同一轮**
被立刻领走，而不是等一小时。保留排期之后，领取判据
（`next_attempt_at IS NULL OR next_attempt_at <= now`）自然把未到期的任务挡住——不必
另加「依赖已满足但未到期」的状态；同时它已经是 `queued`，`next_wakeup` 会如实地把
那个未来时刻报出来，补做统计也才拿得到真实的应跑时刻。**口径不变**：`waiting_dependency`
本身仍不算待办，等待态由它的前置任务负责唤醒。

**链在「一次」驱动调用里走完。** 提取跑完的那一刻，下一次领取前的闸门就会给 `index`
认账、把它拉起，于是同一次 `run_due_jobs` 里 `extract` → `index` 一路推进（受预算与
条数上限约束，见下）。前提是 `index` 自己**已经到期**：排期在未来的任务只是被拉到
`queued`，要等时间到才跑，不会被这一次驱动提前执行（见上）。这是 #74 评审要求的修法：**不能**把「链能不能走完」寄托在平台层
（#19）肯不肯再叫一次上——#19 本来就可能因省电/退出而不叫，那正是 E29 要诚实处理的
场景。旧行为是「一轮只推进一层依赖」，一轮结束后 `index` 仍是等待态、而 `next_wakeup`
不把等待态算成待办，队列里没有别的任务时摘要就会给出 `next_wakeup = null`：按摘要安排
唤醒的平台层不会再叫驱动，索引任务只有碰巧再次进前台才可能运行。

**一轮结束后不允许「有等待态却 `next_wakeup = null`」。** 收尾的那次闸门就是这条
不变式的兜底（循环可能因预算/条数上限在最后一条任务之后直接退出，没来得及在「领取前」
认账）。收尾之后还留下的等待态只可能是在等队列里 `queued` / `retry_wait` 的前置任务
（其 `next_attempt_at` / 「入队即到期」就是下一次唤醒时刻），或者前置已判 `Broken`——
而 `Broken` 在本轮已被终态失败，不会留下等待态。所以「有等待态」必然伴随「有可用的
下一次唤醒」；`run_due` 里的 `debug_assert` 与测试各钉住这条一遍。

**等前置不消耗重试额度。** 闸门只改 `state` / `error_code` / `updated_at`，**不碰**
`attempt_count`、**不改 `next_attempt_at`**（等待期保留原排期，见上）、不写
`job_attempts`。领取（`claim_next_due`）才是消耗额度的地方，而等待态的任务、以及
「依赖已满足但排期未到」的 `queued` 任务都不会被领取。测试钉住了这条（预算 0 的一轮后
`attempt_count` 仍是 0）。闸门本身是**纯查询**，不消耗预算；预算与条数上限照旧
**只在任务之间判断**，链式推进不会打断正在跑的任务。

**`next_wakeup` 的口径不变**：只由 `queued` / `retry_wait` 决定。在等前置的任务
要等的是「别人跑完」，不是时间到；前置那一环自己就在 `queued`/`retry_wait` 里，
下次唤醒时刻由它给。前置压根没有执行者时，闸门会把它终态失败，不会留下
「永远没有下一次唤醒」的挂死任务。

**为什么不用新状态、不改 schema。** `JobState::WaitingDependency` 本来就在契约里
（第 3 节任务状态机），只是此前没有写入者；「在等什么」写进现成的 `jobs.error_code`
列。新增状态或新列都要迁移与旧库兼容测试，这一片的约束明确要求不改 schema。

## 关键词索引任务化（`index`）

`kind = "index"` 的执行者：对任务 `target_ids` 里的**来源**跑
`Core::rebuild_keyword_index(Some(&target_ids))`；`target_ids` **为空表示整库**，
走 `Core::rebuild_keyword_index(None)`。**这条路只管关键词**，行为与 #70 前半一字未改：
`indexes.rebuild` 的范围口径（`all` / `sources:`）不变，语义索引是另一个 kind
（见下「语义索引任务化」）。

**为什么连索引也要排任务**，而不是只靠提取时的增量索引：增量索引写的是「那一刻」的
派生片段；重建任务是对现有材料的校准入口，也是 `indexes.rebuild`（契约 4.4）与
语义索引任务化挂上去的位置（语义那条是**另一个** kind，不是这条的一个分支）。
导入排的那条范围只限这条材料的来源，代价是这条来源的片段数，不是整库；
`indexes.rebuild(scope=all)` 排的才是整库那条。

**「运行期间关键词可用」怎么保证**（有测试钉住）：

- 重建按片段**先删后写、在事务里提交**，并且每次写入都 `bump_index_epoch`；
- 检索会话的快照按索引代次认账：索引一变，旧快照在下次读/翻页时如实报
  `search_expired`，前端重新发起查询，而不是拿半截/过期索引假装还准；
- 所以「索引任务在跑/没跑完」不等于「搜不到」：提取与增量索引在同一事务里就落库了，
  索引任务只是校准；跑完前后 `search.start` 都能查到同一段正文。

**失败口径**（照 #67 的 `HandlerFailure`）：

- **结构性**（目标来源不存在 `not_found`）→ 终态 `failed` + 明确错误码。
  正常路径上闸门在领取前就已经把它们终态失败了，执行者里再挡一次是
  防御：绕过闸门也不能悄悄成功；
- **可恢复**（IO / 数据库暂时不可用）→ 退避重试，消耗额度。

`no_target` 只有 `extract` 会用：提取没有「整库」这种语义，空目标是实打实的错误。

## 语义索引任务化（`semantic_index`）

`kind = "semantic_index"` 的执行者：对**整库**跑一遍语义重建（`semantic.rs`）——
重建块 → 开新代次 → 复用/补算向量 → **原子切换**。它与同步入口
`Core::build_semantic_index` 走的是**同一段实现**：`build_with_deadline` 多一个预算
截止点，`deadline = None` 就是原来的同步语义（跑完才返回）。换代规则、口径核对、
原子切换都没有第二套。

### 为什么是**两个 kind**，不是一个 kind 的两个「种类」

| | `index`（关键词） | `semantic_index`（语义） |
|---|---|---|
| 入口 | `indexes.rebuild(scope, reason, operationId)`（契约 4.4；核心 → 桥接 `BridgeSession::rebuildIndexes` 已接，Dart 适配层**没接**） | `indexes.rebuildSemantic(reason, operationId)`（契约 4.4；核心 `Core::schedule_semantic_index` → 桥接 `BridgeSession::rebuildSemanticIndex` → 能力项 `indexes.rebuildSemantic` → Dart 适配层 `BridgeDiaryApi.rebuildSemanticIndex` **全接**） |
| 目标 | `all` / `sources:` 两种范围，各有语义 | **总是整库**：代次与向量是全局的，范围只决定重算哪些块 |
| 前置 | 提取收尾（按来源逐个判） | **模型就绪**（等配置）+ 提取收尾 |
| 失败口径 | 目标来源不存在 = 结构性问题 | 模型拿不到 = **等配置**（不是失败） |
| 能不能分段 | 不能：`rebuild_keyword_index` 是同步批量写 | 能：每算一块就是一个提交点，可以在块与块之间让出 |
| 跑起来影响什么 | 关键词表 + `search_index_epoch`（旧检索快照 `search_expired`） | 块与向量表（关键词一路一根手指都不碰） |

把语义塞进 `index` 会同时改坏两件事：`indexes.rebuild` 的既有语义（契约明文「只排一条
`index` 任务」、必须原样不动），以及前置/失败/分段这三处只能靠分支猜的口径。
所以切法是**两个 kind、两个入口，共用队列与闸门**。

### 排队口径（「什么条件该排」）

常规入口是**显式请求**：契约 `indexes.rebuildSemantic(reason, operationId)`（Dart `DiaryApi.rebuildSemanticIndex`），核心入口是 `Core::schedule_semantic_index`。

**自动触发**（#128 复审拍板）在**两个发现点**用同一套判据（`semantic_index_job`）：

1. `Core::open`：不加载模型，只读库里的列；
2. 检索**加载模型之后**发现跨空间的那一刻：`open` 时模型通常只 `Configured`（没加载、也不许为 discovery 去读文件），只有这里才拿得到 `model_version`。

五个条件同时成立才排一条：模型 `Configured`/`Ready`；有生效代次且有向量；整代口径与当前不一致（`storage`/`dims`，或**内存里已有**的 `model_version`）；队列里**没有活着的** `semantic_index`；同一口径自动尝试次数 < 2（持久标记 `index_meta.auto_rebuild_marker`，v15）。`reasons` 说「需要重建」时不能没有执行入口，所以这一条窄路径由核心自己排。

指纹只由「生效代次 + 不一致的**种类**」（`storage` / `dims` / `model_version` 各一个布尔）构成，**不编当前版本字符串**：`open` 时版本必然未知、检索加载后必然已知，按值算会让两个发现点各得一个指纹，自动尝试上限在两者之间来回归零（#128 第五轮的真 bug）。

「没配模型不排」是硬要求：那会长期挂着 `waiting_configuration` + `requires_user_action` 的噪声任务，取消后下次 `open` 还会复活。「正在建」的判据是**没有活着的任务**，不是 `building_generation`——失败/取消不会清 `building_generation`（进度要留着续跑），拿它当判据会让自动重建永远早退，形成新的「需重建但无入口」死角。

其它情况仍不自动排队，理由与 `search.upgrade` 同源：什么时候值得花一次模型调用是产品决定；「刚导入完」不会替用户决定，也不会让导入链上多一条争预算的重活。口径本身有没有变，按**不一致的种类**判断：`open` 时模型版本未知只是「不比」，不会产生第二个指纹；同一类不一致里换具体值（例如存储从 f32→int8 改成 f32→f16）也不会重新从 0 算。重建成功换了生效代次、某一项从不一致变成一致、或种类换了，才算一次新的口径。

「该不该请求」的判据都在**既有信号**里（不另造一份查询 API，第二份口径最容易漂）：

| 情况 | 在哪看得见 | 建议 |
|---|---|---|
| 还没有生效代次 | `indexes.status`：`semantic_index_ready = false`、`model_version = null`、`reasons` 说「还没有生效的向量代次」 | 模型就绪时排一条 |
| 生效代次覆盖不全 | `embedded_chunks < total_chunks`，`reasons` 说「生效代次只覆盖了 X 块里的 Y 块」 | 排一条（增量：口径一致的向量整批复用） |
| 换过模型 / 历史混合代次 | 语义检索的警告「当前生效的向量代次是用另一个模型（或另一套口径）建的」（#80）；或 `reasons` 说「有 N 种模型口径」 | 排一条（整代按当前模型重算） |
| 上一次中断/让出 | `indexes.status` 的 `reasons` 说「有一代在建（第 N 代）」（这一片加的） | 排一条（**续跑**，不重头） |
| 刚写进新内容（导入完成、改过正文） | 调用方自己知道；块表要等重建才有新块 | 要语义检索前先排一条 |

**幂等**（重复排队不产生重复工作）走与 `indexes.rebuild` 同一套两层机制：

- **operationId 回执**：同一个 `operationId` + 同一个原因重复调用返回**同一条任务**
  （按 id 读此刻的真实状态）；同一个 `operationId` 换了原因报 `idempotency_conflict`；
- **任务业务键** `(semantic_index, [], NULL)`：任务总是整库、**不给快照**，于是
  「队列里至多一条活着的语义重建」——界面连点几次、几处代码同时请求，都只有一条。
  跑完之后再请求会建新的一条（用户要的是「按现状再来一遍」），这是对的。

### 依赖：等配置、等提取

闸门（每次领取前 + 轮末评估）按**由外到内**两段判：

1. **模型就绪**：`EmbedderReadiness` 是 `NotConfigured` / `Failed` → `waiting_configuration`
   + `waiting_model`，并置 `requires_user_action = 1` + `attention_key =
   job-config:semantic_index:waiting_model`（等配置要用户动手，见「等配置的语义」）。
   判据**不是**「已经加载好」：`Configured`（配了、文件在、还没建会话）
   是正常的生产路径（启动不做重活、第一次要算向量时才懒加载），闸门放行；真正加载失败
   由执行者按「等配置」处理（`HandlerOutcome::WaitingConfiguration`：状态与
   `requires_user_action` / `attention_key` 一字不差，**只有 `attempt_count` 如实记账**
   ——那一次确实跑过）；
2. **提取收尾**：队列里还有活着的 `extract` 就落 `waiting_dependency` + `waiting_extract`
   ——与关键词整库重建同一条规则。它**不判 `Broken`**：某条提取被取消只是少一份内容，
   语义重建照样该把块表里现有的块建完，不该被连坐成终态失败。

**不变式照旧成立**：留下 `waiting_dependency` 时，等的一定是队列里 `queued`/`retry_wait`
的提取（`next_wakeup` 由它给）。`waiting_configuration` **不进 `next_wakeup`**，因为它等
的是配置而不是时间——`run_due` 里的 `debug_assert` 只约束 `waiting_dependency`，
这一条不冲突也不破坏它。配置好了之后（下一次驱动，前台/唤醒/改配置之后都会调），
闸门在**同一次调用**里就会把它拉起、领取、跑完（有测试钉住）。

### 分段与预算：预算耗尽时是什么状态

整库重建会远超一次唤醒的预算（10 万块外推桌面约 280 秒），所以它必须在**安全点**让出：

- **安全点 = 块与块之间**：每算完一块，向量已经作为一个独立事务写进
  `building_generation`；让出不动 `active_generation`（半成品绝不激活）、不丢已算的块；
- **每算一块看一次钟**，到点就返回 `Yielded`；但**至少算完一块**才允许让出——一个极小
  预算的唤醒也必须前进，否则「算了 0 块就让出」会永远建不完；
- **预算耗尽时的取值**（这是这一片定死的口径）：
  | 位置 | 取值 |
  |---|---|
  | 任务状态 | `queued`（不是 `running`，也不是 `failed`/`retry_wait`） |
  | `next_attempt_at` | `NULL`——让出是「还想接着跑」，不是「等一等再试」，落到 `queued` 且入队即到期 |
  | `attempt_count` | **减回领取前的值**（让出不是一次失败）；`job_attempts` 留着那次记录，`outcome = 'yielded'` |
  | 进度 | `progress_completed / progress_total` = 「这一代已有口径一致向量的块数 / 块表块数」，每算一块更新一次 |
  | `error_code` | `NULL`（没有在等什么，也没有出错） |
  | 摘要 | 该任务计 `processed`（确实被领取执行过一段），**不计** `succeeded`/`failed`/`retrying`；`due_backlog ≥ 1`；`next_wakeup` = 「现在」（平台照摘要立刻再叫一次就接着跑） |
  | `index_status` | 生效代次照旧服务检索；`reasons` 多一句「语义索引有一代在建（第 N 代）：已经写了 X / Y 块的向量…」（#58 的「未就绪」文案不动，两者说的不是一件事）；新内容没成块/新代次没写满时 `semantic_index_ready` 本来就是 `false` |
- **用户看到什么**：任务面板里那条 `semantic_index` 停在「排队中」、进度条走 X/Y；`jobStatus.queued` 与 `dueBacklog` 把它算进去、`nextWakeup` 指向现在（要继续跑）；`indexStatus` 说明「有一代在建」。**不会**看到「已完成」——`succeeded` 只在整代切换之后才发；
- **不可中断的部分（如实说明）**：`chunks::rebuild` 的整日重打包与「从旧代次整批复用」的
  那条 `INSERT ... SELECT` 各自是一段批量 SQL，没有取消点；分段只覆盖**向量计算**这一环
  （真实代价的大头，也是唯一跑模型的环）。单块的模型推理本身也不能中断（一块通常几十毫秒），
  **懒加载模型**（第一次要算向量时建 ORT 会话）也在执行者里、同样不可分段——它是「这一轮
  开始算第一块之前」的一段，让出只发生在它之后。

### 可恢复与口径核对：绝不混两个模型

- **被杀/退出**：任务停在 `running`，下一轮驱动开头 `recover_interrupted_runs` 回收它
  （还有额度就回 `queued`），`building_generation` 与已写的向量留着 → **续跑**；
- **让出**：如上，任务自己回 `queued`，下一轮接着算；
- **续跑前核对口径**（#58 的规则，一次都没绕过）：每一次续跑（含让出后的下一轮）都先看
  `building_generation` 里已有的向量有没有与**当前嵌入器**的
  `model_version` / `dims` / `storage` 不一致的；有就**整代废弃**（`DELETE` 那一代，
  含口径一致的行）按当前模型从零重算。`missing_chunks` 也只把「存在**且**口径一致」的行
  算已完成。**回归测试 `a_foreign_caliber_left_by_an_interrupted_build_is_discarded_before_resuming`
  验证过：把这段核对去掉会红**（两条断言各自都会红：重算块数从 3 掉到 2、另一个模型的
  向量会留在生效代次里）；
- **整代永远只有一个口径**：切换是一个事务，切换前清掉更早的代次；生效代次的
  `model_version` / `dims` / `storage` 任一混了别的口径，`index_status` 就报
  `Mixed`（`model_version = None`、不就绪），检索路径（#80）整路不作数——所以混代次
  不是「悄悄降级」，是「明确地不能用」。

### 失败口径

- **模型拿不到**（没配 / 配了但加载失败）→ 等配置（见上），**不是失败**；
- **可恢复**（IO / 数据库暂时不可用）→ `HandlerFailure::retryable`：退避重试、消耗额度。
  `building_generation` 与向量留着，额度内重试就是续跑；
- **结构性**（算出来的向量维度与模型声明不符）→ 终态 `failed`，不假装成功。

### 与关键词 `index` 的关系（一句话）

**两个 kind、两个入口、两条独立的索引路**：关键词那条照旧（范围口径 `all` / `sources:`
不变、执行者不变、`indexes.rebuild` 不变）；语义这条新增，共用同一套队列、闸门、
退避、补做与摘要。`indexes.rebuild(scope=all)` **不会**顺手建语义索引——那会改掉既有
入口的行为（也有测试钉住关键词那一路的行为不变）。

## `indexes.rebuild` 入口与 `scope` 编码

入口是 `Core::schedule_index_rebuild(scope, reason, operation_id)`（`index_rebuild.rs`），
桥接是 `BridgeSession::rebuildIndexes`，契约 4.4 节的 `indexes.rebuild`。它**只排一条
`index` 任务**并返回它，不做同步重建——同步重建会阻塞界面，而队列的退避、补做与依赖
闸门已经就绪。

`scope` 是一个字符串，只有两种合法写法（规范写在契约 4.4 节；共享场景文件里早就在写
`indexes.rebuild(scope=all)`）：

| 写法 | 排出的任务 |
|---|---|
| `all` | `target_ids` 为空 → 执行者走 `rebuild_keyword_index(None)`，重建整库（含没有来源的记录文字） |
| `sources:<id>[,<id>]*` | `target_ids` 是这些来源（已排序、无重复）→ 只重建它们，闸门按来源逐个评估前置 |

- id 只允许 `[A-Za-z0-9_]`：`,` 被固定成分隔符，**不定义转义**；
- **顺序没有语义**：解析时按字典序排成规范形，`sources:b,a` 与 `sources:a,b` 命中
  同一条任务；
- 空列表、空记号、重复 id、越界字符 → `invalid_argument`（契约第 7 节新增的码；
  「要整库」必须写 `all`，不能靠空列表）；不存在的来源 → `not_found`，**不排一条
  注定失败的任务**；
- **幂等**：同一个 `(scope, 原因, operationId)` 重复调用返回同一条任务，走通用
  `operation_receipts` 回执（契约 1.2）。回执只存任务 id，重放时按 id 读**当前**任务，
  所以重放返回的是这条任务此刻的真实状态；同一个 operationId 换了 scope 或原因报
  `idempotency_conflict`。任务自身的业务键
  `(kind, target_ids, input_snapshot_hash)` 照 #67 口径一并生效。

**整库任务等提取收尾。** `all` 没有 `target_ids`，闸门给它的前置是「队列里没有活着的
`extract`」：提取还在跑（`queued` / `retry_wait` / `running`）就落
`waiting_dependency` + `waiting_extract`，收尾后再按现状整库重刷。它**不判 `Broken`**：
某条提取被取消或放弃只是少一份内容，整库校准照样该跑，不该被连坐成终态失败。之所以
要等，是因为整库重建只重建「这一刻能索引的东西」——不等就会在提取落库前重建一次、
落库后又得靠那条 per-source 任务补，白跑一趟。代价是持续导入时它会一直等到队列里
没有提取为止：它是**最低优先级**的维护任务，宁可等，也不要在提取落库前重建到一半。
`sources:` 范围的任务在提取未完成时
照旧落 `waiting_dependency` + `waiting_extract`，提取一完成就被拉起（闸门在每次领取前
重评估，同一次驱动调用里走完；被条数上限截住时也会被推进到 `queued` 并给出可用的
`nextWakeup`，有测试钉住）。

## 退避规则

- `next_attempt_at = now + 30 秒 × 2^已用的尝试次数`，封顶 **1 小时**。
  也就是说第一次失败（`attempt_count = 1`）是 60 秒，之后 2 分钟、4 分钟……
  与 B1c 的 `backoff()` 完全一致，这一片没有改它。
- `attempt_count >= max_attempts` 时不再排期，直接进 `failed` 并把
  `requires_user_action` 置 1——「自动重试到头了」是需要用户看见的事实。
- **主动放弃（`no_handler` / 没有目标）不退避**：立刻进 `failed`，`job_attempts`
  里那次尝试仍然如实留着。
- 人工重试：`failed` → `queued`，`attempt_count = 0`、`next_attempt_at = NULL`、
  `error_code` 清空，并发出 `job.changed`。`job_attempts.attempt` 是**跨人工重试
  累计**的第几次（领取时取历史最大值 +1），所以清零不会撞上历史记录，也不会把
  「试过几次」抹掉。

## 业务键与幂等（以及为什么这一片不建 DB 约束）

`NewJob` 没有 `business_key` 字段，`jobs` 表也没有这一列。业务键在**同一个事务里**
现算现查：

```
业务键 = (kind, target_ids, input_snapshot_hash)
命中条件 = 同键 且 state NOT IN ('succeeded', 'failed', 'cancelled')
```

命中就返回已有任务（不新建、不发事件）；没有命中才插入。要点：

- `target_ids` 用它存库时的 JSON 文本，**数组顺序是语义的一部分**（多来源提取的
  顺序会影响结果），所以不做排序归一化。
- `input_snapshot_hash` 允许为空，比较用 SQLite 的 `IS`（空对空算相同）。
- **只有非终态才参与去重**：一条任务「已放弃」之后，同一个业务键可以重新入队——
  否则用户永远没法把它重新排上。
- 为什么不建 DB 级 UNIQUE 索引：目标索引得建立在
  `(kind, target_ids, input_snapshot_hash)` **且仅非终态**上，而 SQLite 的部分唯一
  索引（`WHERE state NOT IN (...)`）是 schema 变更，需要迁移、回填与旧库兼容测试。
  这一片的约束明确要求不改 schema，所以先用事务内检查——在**单写者**（`BridgeSession`
  用互斥锁串行化同一个 `Core`，见 `m1-桥接接线.md`）下它是充分的。多进程写入的保证
  留给下一次 schema 变更一起做，现在**不假装**已经有这个保证。

## E29：补做口径与「不谎报准时」

省电延迟、系统退出会让「到点了但没人跑」的任务留在队列里。核心必须能回答
「这次跑的有多少是补上的」，而且**不能把补上的说成准时完成的**。

**补做判定（写在 `jobs.rs::run_due` 里，也由测试钉住）：**

> 领取一条任务时，如果它的 `next_attempt_at` **存在且早于本次运行的开始时刻
> `started_at`**，这次执行就算「补做」。

**「按时」不算补做。** 在排期那一刻（`next_attempt_at == started_at`）或更早被领走
都不算；只有排在**过去**、这次才跑上的才算。等待依赖期间排期被保留（见上「依赖链」），
所以「排在未来、前置提前完成」的任务不会被提前跑，也就不会被误记成补做；反过来，
「排期已过、驱动当时没跑、后来才跑」的仍如实计入补做——两条方向都有测试钉住
（`index_job_test.rs` 的 #67 二轮复审回归）。

- 为什么用 `next_attempt_at`：它是队列里唯一记载「这条任务本该什么时候跑」的字段，
  也是退避唯一写入的字段。它已经过去了说明那一刻确实没人跑。
- 为什么**不**把 `next_attempt_at` 为空的任务算补做：空表示「入队即到期」，
  队列里根本没有它「本该何时跑」的信息。把 `created_at` 当应跑时刻会把
  「刚入队、紧接着就被跑」也算成补做，反而误导。这类**从未试过、排期为空**的积压
  由 `JobStatus.due_backlog` 和 `queued` 计数如实呈现。
- 这个边界是**已知的欠缺**：要如实区分「刚入队」与「重启后才补上的排队任务」，
  需要 schema 记录入队时的应跑时刻，或者记录「上次允许运行的时刻」。
  下一次 schema 变更一并做。现在宁可**少报**补做，也不虚构一个应跑时刻。

`JobRunSummary` 的字段就是「不谎报」的清单：

| 字段 | 含义 |
|---|---|
| `started_at` | 本次运行的开始时刻（调用方给的 `now`），补做判定的分界 |
| `trigger` | 唤醒来源，调用方给什么就记什么（`startup` / `foreground` / `wake` / `manual` …） |
| `processed` | 本次领取并执行的任务数，不超过条数上限 `max_jobs`。**分段让出的语义任务算在内**（它确实被领取并执行了一段） |
| `succeeded` | 其中执行成功、进入 `succeeded` 的。**让出的任务不算**（整代还没切换） |
| `failed` | 其中进入「已放弃」（`failed`）的（额度用完或没有处理器） |
| `retrying` | 其中失败但还有额度、已排退避重试（`retry_wait`）的 |
| `backfilled` | 其中属于补做的（口径如上） |
| `recovered` | 运行开始时回收的上次没跑完的 `running` 任务数 |
| `due_backlog` | 本次运行结束后**仍然到期**但没跑上的数量（被预算或条数截住）。让出的语义任务回到 `queued` 且排期清空，所以它是**接着要跑**的那一类，算在这里 |
| `waiting_dependency` | 本次运行结束时还在等前置的任务数（`index` / `semantic_index` 等 `extract`）；它们没被领取、没消耗额度，所以不在 `processed` 里。**等配置**（`waiting_configuration`）不算在这里，状态摘要另有计数 |
| `dependency_failed` | 本次运行里被闸门判定「前置不可能再满足」而终态失败的任务数；同样没被执行过，所以也不在 `processed` 里，但也不能让摘要把「什么都没跑」说成「一切正常」 |
| `next_wakeup` | 下一个到期时刻；没有待办时为 None（等前置与等配置的都不算待办，见上） |

没有「准时完成」这样的字段，`backfilled` 也不会被折进 `succeeded` 之外的任何结论里：
界面可以同时说「补做了 N 个」，而不必（也不能）说「它们在计划时刻完成了」。
也没有单独的 `budget_exhausted`：`due_backlog > 0` 就说明这一轮**提前收手**了，
留两个字段只会互相矛盾。**也没有单独的 `yielded`**：让出的任务在 `processed` 里、
不在 `succeeded`/`failed`/`retrying` 里，差额正是它；它「还没跑完」由
`due_backlog ≥ 1` + `next_wakeup` 指向「现在」+ 那条任务的 `progress` 一起说清楚
（契约 `DueRunSummary` 的字段一个没多）。

**预算是时间（毫秒），条数是防御性上限。** `budget_ms` 是「这一轮还能不能再开一条」
的判据，按 `Instant` 的真实流逝时间算，**只在任务之间判断**：没有取消点的任务
（提取、关键词重建）一旦领取就一跑到底。所以「一条任务本身比预算还长」对它们仍然是
**已知且有意**的行为，不假装能中途抢占。**可分段的任务（语义索引）多一层**：执行者
拿到 `started + budget_ms` 这个截止点，在安全点（块与块之间）主动让出——它**自己**
停，不是被抢占（见「语义索引任务化」）。`max_jobs` 再夹一道条数上限，挡的是「队列很长 +
多条短任务」。`budget_ms = 0` 或 `max_jobs = 0` 都表示一条都不跑（让出发生在领取**之后**，
所以预算 0 连让出都不会发生）；被截住的到期任务留在队列里、数量进 `due_backlog`，
下次唤醒时刻照常给出。

## `no_handler` 的处理与历史包袱

核心真实使用的 `kind` 有五个：`extract`、`index`（`assets.rs`）、`semantic_index`
（`semantic_index_job.rs`）、`transcribe`（`recordings.rs`）、`respond`（`provider`），
**五个都有执行者**（`jobs::HANDLED_KINDS` 是唯一的事实来源）。驱动对没有执行者的 `kind` 一律：

1. 记一次尝试（`attempt_count` 递增，`job_attempts` 留下这次尝试）；
2. 立刻进 `failed`：`error_code = no_handler`、`requires_user_action = 1`、
   `attention_key = job-terminal:transcribe:no_handler`（同类同码的问题只提示一次）；
3. 发 `job.changed`。

它**不会**退避重试（没有处理器不会自己出现），也**绝不会**被算成 `succeeded`。
用户可以在任务面板看到它、点人工重试。`JobStatus.recent_errors` 会带着 `no_handler`
出现，界面据此提示「这个任务还没有执行者」。

### 历史包袱：`transcribe` 的旧账怎么清（#91）

`transcribe` 在 #91 之前没有执行者，那些任务按上面的规则进了「已放弃」+ `no_handler`。
执行者接上之后，`jobs::requeue_legacy_no_handler` 在**开库时**把它们一次性放回队列：

- 只放回**现在真有执行者**的 kind（`has_handler`）。没有执行者的 kind 仍然留着
  `no_handler`——那个理由是**真的**，改掉它才是撒谎；
- **判据自带幂等，不需要额外标记**：放回队列会把 `error_code` 清空，下一次开库
  `state='failed' AND error_code='no_handler'` 就再也查不到它。所以不需要「迁移过没有」
  的账面，也就**不需要改 schema**；
- 清零语义与人工重试完全一致（`attempt_count` 清零、发 `job.changed`，旧尝试留在
  `job_attempts` 里，编号跨人工重试累计）；
- 目标已经不在的任务也照样放回：它会以 `not_found` 终态失败——那是当下的真相（音频没了），
  比留着一句「核心还没有执行者」诚实。

测试：`crates/diary_core/tests/transcription_test.rs::legacy_no_handler_jobs_are_requeued_once_then_run`
（放回 → 真的跑完 → 再开库不重复动作）。

## 状态摘要字段（`Core::job_status()`）

- 各状态计数：`queued` / `running` / `retry_wait` / `waiting_*` / `failed` /
  `cancelled` / `succeeded`。从语义索引任务化起 `waiting_configuration` 也有真实写入者
  （等模型配置的 `semantic_index` 任务），B4a 之后 Provider 作业（等服务配好/修好）也是；
- `due_backlog`：**现在就该跑**的数量（`next_attempt_at` 为空或已过）；与
  `queued + retry_wait` 的区别是后者包含排在未来、还没到点的。**让出的语义任务**
  （回 `queued`、排期清空）算在这里——它就是「这一轮提前收手、还有活」的证据；
- `next_wakeup`：建议的下次唤醒时刻（`jobs::next_wakeup` 的口径）。等待
  `waiting_dependency` / `waiting_configuration` 的任务都**不算待办**：前者由它的前置
  任务给唤醒时刻，后者等的是配置（不是时间）；
- `recent_errors`：最近 5 条，最新在前，每条只有 `job_id`（不透明 ID，供人工重试
  定位）、`kind`、`error_code`、`occurred_at`、`requires_user_action`。
  **没有 message、没有文件名、没有正文**。

**每条任务的细粒度进度**在 `Job.progress`（`completed / total`）上：只有真有可靠进度的
任务才有值（现在只有 `semantic_index`：块数是真的分母、算完一块才算一个分子）；没有可靠
进度时是 `None`，**不虚构百分比**。语义任务的进度每算一块更新一次，但**不发
`job.changed`**（几万条事件是噪声）：轮询 `jobs.list` / `jobs.get` 能看到它，
状态变化（让出、完成、失败…）照旧发事件。

桥接侧有 `BridgeSession::jobStatus()`（`jobs.status`）与
`BridgeSession::runDueJobs(budget_ms, trigger)`（`jobs.runDue`），都进了
`wired_capabilities()` 白名单。Dart 适配层（`packages/diary_bridge/lib/src/bridge_diary_api.dart`）
的 `_wiredMethods` 是更窄的一层：上面这些 `jobs.*` 都没有加进去，所以适配层报的能力清单里
仍然看不到 `jobs.*`——这是它诚实的地方，不是遗漏（这一轮只为语义重建开了
`indexes.rebuildSemantic` 一项，见下）。`packages/diary_api` 的
`DueRunSummary` 已经与核心摘要字段一一对齐，只等适配层接线。
**语义重建的入口全接了**（#70 后半的第二轮）：契约 4.4 的
`indexes.rebuildSemantic(reason, operationId)` → 核心 `Core::schedule_semantic_index`
→ 桥接 `BridgeSession::rebuildSemanticIndex` → 能力项 `indexes.rebuildSemantic`（进了
`wired_capabilities()`）→ Dart 适配层 `BridgeDiaryApi.rebuildSemanticIndex`
（`_wiredMethods` 也加了这一项，调用拿到契约的 `JobTicket`）。**关键词那条
`indexes.rebuild` 在适配层仍然没接**：两条索引路的能力项各自独立，适配层报的能力清单里
有 `indexes.rebuildSemantic`、没有 `indexes.rebuild`——这是如实的窄化，不是遗漏。

## 与 #19、B4a 的边界

- **#19（系统级唤醒）**：负责「到点把进程叫起来」。这一片负责「叫起来之后，
  哪些任务该跑、跑完什么、还剩多少、还在等什么、哪些是补上的」。核心不自己定时、
  不起线程、不碰 WorkManager/AlarmManager。平台给多少毫秒预算、用什么 `trigger`
  调进来，是 #19 的事。
- **B4a（Provider）**：提供远端能力。**#91 已经接上转写执行者**（本机 ONNX 引擎，
  见 [M3 · 转写链](m3-转写链.md)）：`jobs::execute` 里有了 `transcribe` 分支，
  `provider::job_capability` 也把 `transcribe` 映射到 `transcribe_audio`（只认本机引擎），
  且 `index_dependency` 现在把**活着的转写任务**也算进前置（`waiting_transcribe`）。
  远端转写进产品链、用量与计费口径仍属于后续。

## 没有做到的

- **真机排期没有做**：没有 WorkManager / AlarmManager / 后台任务注册。平台给的毫秒
  预算现在**接了**（`runDueJobs(budgetMs, trigger)`），但「到点把进程叫起来」还是 #19
  的事；`trigger` 只是如实记录，核心不据此改变行为。
- **不抢占正在跑的任务**：预算只在任务之间判断。语义重建**自己知道怎么安全停下**
  （块与块之间让出，见「语义索引任务化」），但提取与关键词重建**没有**可取消点——
  它们照旧一跑到底、可以把预算撑穿。要真正给它们限时，得先给这两条路径加安全点。
- **语义重建的段落粒度只到「向量计算」这一环**：`chunks::rebuild` 的整日重打包与
  「从旧代次整批复用」的那条 `INSERT ... SELECT` 仍是一段不可中断的批量 SQL；单块的
  模型推理也不能中断（一块通常几十毫秒）。10 万块那一档的块重建与复用复制耗时没有实测。
- **语义重建的自动排队覆盖整代口径不一致，但有明确边界**：入口全接了（契约
  `indexes.rebuildSemantic` → 核心 → 桥接 → 能力项 → Dart 适配层）；`Core::open` 与
  「检索加载模型之后」在 `storage`/`dims`/已加载时的 `model_version` 不一致时会自动排
  一条去重任务（#128 复审），同一口径最多自动尝试两次，没配模型不排。除此之外仍
  **只有显式请求**会排队：「导入完成就自动建语义索引」这一片**没有做**；`apps/` 设置页
  也还没有显式 `rebuildSemanticIndex` 按钮（后续项）。
  冷启动时模型还没加载，`open` **不会**为了比 `model_version` 去读模型文件；换了一份
  同维度、同存储的模型文件时，自动排队只在**本次进程里模型加载过之后**（通常是第一次
  语义/混合检索）才发生——在那之前 `reasons` 会如实说「需要重建」，显式入口仍然可用。
  **残留**：只换模型文件、**从不做语义/混合检索、也不点按钮**的用户，会一直停在
  「需要重建」——没有进程内的加载时刻，就没有自动发现的那一下。
- **适配层没接关键词 `indexes.rebuild`**：核心与桥接都通了、能力项也在核心白名单里，
  但适配层的 `_wiredMethods` 只加了 `indexes.rebuildSemantic`（设置页需要它），
  `indexes.rebuild` 照旧没接——现有记录入口走导入链，界面要用时再接。
- **`Job.errorCode` 在 Dart 侧还表示不了 `waiting_model` / `waiting_extract`**：
  `packages/diary_api` 的 `Job.errorCode` 是 `DiaryErrorCode` 枚举，里面没有这两个
  「在等什么」的码（核心写的是字符串）。适配层现在还没接 `jobs.*`，所以这条路上没有
  实际映射；将来接 `jobs.get` / `listJobs` 时要么扩枚举（先改契约第 7 节），要么如实落
  `unknown` 并把原因说清，不能把「在等配置」翻成别的错误。
- **执行者真正加载模型失败那条路在 CI 里测不到**：闸门只看到「配了」（`Configured`）就
  放行，加载失败由执行者落回 `waiting_configuration`。CI 上没有模型、也不能在测试进程里
  改环境变量（会串到别的用例），所以这条只有代码与文档，没有测试。
- **换模型的自动发现只在「模型加载之后」**：`model_version` 要加载模型才知道，所以
  两个发现点的可见性不同——`storage`/`dims` 在 `open` 就能发现；`model_version` 只在
  本次进程里模型加载过之后（通常是第一次语义/混合检索）才发现。**残留**（与上面
  「自动排队边界」同源）：只换模型文件、从不做语义/混合检索、也不点按钮的用户，会
  一直停在「需要重建」；这一片不为了 discovery 去读模型文件（那是启动重活），显式入口
  `indexes.rebuildSemantic` 仍然可用。
- **语义任务的范围口径没有产品语义**：`semantic_index` 任务的 `target_ids` 为空 = 整库，
  非空 = 只重算这些来源的块（代次与向量仍是全局的），这一片只有整库那条有入口；
  「按来源重建语义索引」既不省模型调用、也没有契约表达，现在没有调用方。
- **`indexes.rebuild` 的适配层（`BridgeDiaryApi`）还没接**：核心入口与桥接
  `BridgeSession::rebuildIndexes` 都通了（能力项 `indexes.rebuild` 进了
  `wired_capabilities()`），但 Dart 适配层的 `_wiredMethods` 里仍然没有它——适配层这一轮
  只加了 `indexes.rebuildSemantic`（设置页需要的那一条）。和 `jobStatus` / `runDueJobs`
  一样，适配层报的能力清单里看不到它们，这是它诚实的地方，等界面真正要用时再接。
- **`scope` 里没有「日期范围」「材料类型」这些范围**：契约只给了 `scope` 一个字符串，
  这一片只定义了整库与来源列表两种写法。要按时间或类型重建，先改契约。
- **插件任务没做**：插件的任务权限与限额属于 M4 插件片，这一片没有任何插件入口。
- **DB 级唯一约束没做**：见上「业务键与幂等」。跨进程写入的幂等保证还没有。
- **排期为空的任务不计入补做**：见上 E29 的边界，要等 schema 变更。
- **转写与「转写 → 索引」已接（#91）**：`transcribe` 有执行者（本机引擎），`index`
  的前置同时认 `extract` 与 `transcribe`（后者按资产 id join 回修订）。细节与取舍见
  [M3 · 转写链](m3-转写链.md)；远端转写与用量口径仍未接。
- **`waiting_network` 仍无写入者**：`waiting_configuration` 从 B4a 起有写入者
  （Provider 缺失 / 鉴权失败 / 额度用尽 / 引擎或模型没就绪，见
  `docs/architecture/m3-Provider-配置与能力.md`），`waiting_network` 还没有——断网该不该
  单独一个状态而不是走退避重试，等一个真的会区分它的产品口径（本机引擎不出网，转写链
  用不到）。
- **旧快照失效是「重取」不是「不中断」**：索引重建期间进行的检索会话会报
  `search_expired`，前端要重发查询；真正「边重建稳定翻页」的语义没有做（单连接
  串行下也不可能有并发重建）。
