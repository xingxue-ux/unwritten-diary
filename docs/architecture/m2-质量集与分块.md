# M2 · 质量集与分块

对应 issue [#50](https://github.com/xingxue-ux/unwritten-diary/issues/50)（B3c-1）· 日期 2026-10-10 · 执行人 xingxue-ux

B3c 是把关键词检索扩成「关键词 + 语义 + 混合」。但在接模型之前得先回答两个问题：**怎么量**（质量集）与**切多大**（分块）。这一片只做这两件事，不接模型——所以可以在 B3c-2 之前做完。

## 为什么先建质量集，而不是先接模型

issue #32（现在收窄为 B3c-2）自己的验收标准第一条就是「质量集先建起来，再谈排序好坏」。理由很实在：

- 混合检索的卖点是「语义能召回关键词召不回的东西」。没有标注好的语料，这个说法只能靠举几个例子——**举例子不是数字**；
- 关键词这一路现在是唯一能跑的，它的数字是后面语义与 RRF 的**基线**。基线不在同一份语料、同一套口径上量出来，后面的「提升」就没有意义；
- 质量集里**必须**包含「关键词命中而语义不命中」与「语义命中而无相同词」两类，否则 RRF 是加分还是掺水根本看不出来。

## 分块规则（冻结）

`crates/diary_core/src/chunker.rs`，`CHUNKER_VERSION = "chunker-1-packday-line400-overlap48"`：

**三条断点原则**（别处不要另立规则）：

1. **篇内断**：一篇（一个来源的正文）太长时，在**篇内**按段尾切开；
2. **跨篇不断**：合块的单位是**整篇**——短篇可以拼在一起，但**绝不为了填满一块把一篇切开去凑**；放不下就让这一篇另起一块；
3. **段尾断，句尾不断**：断点候选只认**段尾（换行）**，句末标点（`。！？；`）**不是**断点：一段话说到底就让它说完。

| 项 | 取值 |
|---|---|
| 每块上限 | **400 字符**（保守上界，见下），篇与篇之间的分隔也计入 |
| 相邻段重叠 | **48 字符**，只用于「一篇自己超限被切开」的地方（篇与篇之间是整篇拼接，不需要重叠） |
| 合块条件 | **同一天（`day_key` 相同）**的短篇可以进同一块；跨天不合并 |
| 段没有换行时 | 只能按上限硬切（没有别的断点可选）——这是唯一会切进句子中间的情况 |
| 块的 `text` | 每篇两端去掉空白后拼接；`spans` 记下每篇在**篇内**的字符区间（`start`/`end`），便于回溯原文 |
| 空/全空白的一篇 | 跳过，不产生 `span` |

**合块的代价要说清**：一块里有多篇时，向量是对**整块**算的——这一块的相似度属于「这几篇合起来」，不是某一篇。命中回溯要按 `spans` 走；`SearchHit` 的 `sourceId`/`locator` 怎么映射到多篇的块，是 B3c-2 要定的事（现在只有关键词那一路，还没接块）。

**为什么按字符而不是按 token**：核心不该为了切块把分词器拉进来（体积与构建代价），而且切块规则一旦依赖具体词表，模型一换块边界就变、索引整库失效。字符数是**保守上界**：BERT WordPiece 对中文大致 1 字 ≈ 1 token，所以 400 字 ≤ 约 400 token；拉丁文本约 4 字/token，远低于上限。

**这个假设不能只写在注释里**：`tools/model-export/verify_chunk_tokens.py` 用**真实分词器**（上游固定 revision）核对质量集里所有块的 token 数，超出 400 就非零退出。核对方式：

```bash
DIARY_DUMP_CHUNKS=/tmp/chunks.json cargo run --release -p diary_probe -- quality-set
python3 tools/model-export/verify_chunk_tokens.py /tmp/chunks.json
```

**「短时间跨度」在数据里就是用 `day_key` 相同表达的**（与 `captures.day_key` 一致）：同一天的短篇可以打包，跨天不合并。这条口径换了（比如改成「同一天内相隔几小时」或「同一周」），要同时改 `CHUNKER_VERSION`。

`CHUNKER_VERSION` 是**冻结**的：改切块逻辑或那两个常量必须同时改版本号，索引状态里的 `chunkerVersion` 才能识别出「库里的是旧块」。有一条测试专门写死这个字符串，防止无意改动。

**这一片不把分块接进索引**：谁消费这些块（embedding、向量表、`indexGeneration`）是 B3c-2。现在 `IndexStatus.chunkerVersion` 仍是 `None`，接进去之后才该有值——提前填一个「这次分块用的版本」是假话，因为还没有任何块进索引。

## 质量集

`tests/quality/search_quality_set.json`（数据文件，入仓库）。每条 case 自带它的语料：

```json
{
  "id": "kw-01",
  "category": "keyword_only",
  "query": "妈妈",
  "expectedSourceIndex": 0,
  "expectedContains": "妈妈打电话来说她体检结果不太好",
  "sources": [{ "name": "日记A.txt", "dayKey": "2026-09-20", "text": "……" }],
  "filters": { "fromDayKey": null, "toDayKey": null }
}
```

| 类别 | 作用 |
|---|---|
| `keyword_only` | 关键词应当命中、语义未必——基线的主力 |
| `semantic_only` | 查询与来源**没有共同词**但语义相关：关键词这一路**应当miss**，这是后面语义/混合要补上的缺口 |
| `time_filter` | 同一个词在两个日期的来源里都出现，用日期范围限定到期望的那一个 |
| `long_transcript` | 一份长转写（≥1200 字）里相关句在中段：看长材料的相邻块会不会占满结果 |
| `contradiction` | 两个来源说法矛盾，**期望命中日期更晚的那一份**（排序规则是日期从近到远） |
| `no_answer` | 没有任何相关来源：量「不误报」 |

两条**标注约定**（写在这里，免得以后各自解释）：

- `expectedContains` 是**逐字子串**（标点算在内），不是「按字去标点」的匹配。所以跨标点的片段要连标点一起写；
- `contradiction` 的「期望命中日期更晚的那一份」**绑定当前的排序规则**（日期从近到远，见 [M2 · 检索会话](m2-检索会话.md)）。B3c-3 如果把混合排序改成分数优先，这条期望值要跟着重新定义，否则它会变成一条「测排序实现」而不是「测检索质量」的用例。

## 量测入口

探针子命令 `quality-set`（`tools/probe/src/quality.rs`）：

```bash
cargo run --release -p diary_probe -- quality-set
# 换一份质量集：DIARY_QUALITY_SET=/path/to/set.json
```

口径（写在代码注释里，避免以后各自解释）：

- **一条 case 一个独立内存库**：不同 case 的语料不能互相污染，否则某个查询可能命中另一个 case 的来源；
- 走**真实核心**（建库 → 导入 → 提取 → `start_search`），不是自己拼 SQL——这样量到的就是产品路径；
- `recall@k` 按**来源**算（同一来源的多个块只算一次），`MRR` 用名次倒数；`no_answer` 不算召回，单独报不误报率；
- 延迟是每 case 查询耗时的中位数，**不含建库与提取**；
- 分块统计（块数、最长、p99、平均）在同一趟里顺带报出来；
- **数据自检**：`keyword_only` 却有多于一个来源命中、`semantic_only` 却被关键词命中、`no_answer` 却返回结果——都打警告（那是**标注要修**，不是程序错误）。结构性错误（`expectedContains` 不在期望来源里、下标越界）直接失败。

## 验证

质量集：**36 条**（`keyword_only` 11 · `semantic_only` 6 · `time_filter` 5 · `long_transcript` 5 · `contradiction` 5 · `no_answer` 4）。其中 `kw-11` 是**故意同一天三篇短来源**的用例，用来覆盖「短时间跨度内多个短篇合进一块」的打包规则——其余 case 的来源都跨天，所以那条规则在块统计里本来根本看不见。

**关键词这一路的基线**（`cargo run --release -p diary_probe -- quality-set`，本机 WSL2 x86_64）：

| 类别 | 条数 | R@1 | R@5 | R@10 | MRR | 中位延迟 |
|---|---|---|---|---|---|---|
| keyword_only | 11 | 100% | 100% | 100% | 1.000 | 0.5 ms |
| long_transcript | 5 | 100% | 100% | 100% | 1.000 | 0.9 ms |
| time_filter | 5 | 100% | 100% | 100% | 1.000 | 0.6 ms |
| contradiction | 5 | 100% | 100% | 100% | 1.000 | 0.4 ms |
| **semantic_only** | 6 | **0%** | **0%** | **0%** | — | 0.5 ms |
| no_answer | 4 | — | — | — | — | 0.4 ms |

- **合计：R@1 81% · R@10 81% · MRR 0.812**（32 条可回答 case）；
- **不误报：4/4 条 `no_answer` 返回空结果**；
- **命中广度：平均每条 case 命中 0.9 个来源、最多 2 个**（`long_transcript` 也没出现「相邻块占满结果」）；
- **`semantic_only` 6 条全部 miss**——这不是缺陷，是这一片要**量出来**的缺口：后面语义与 RRF 的价值就应该是把这 6 条补上，同时不回退上面四类的数字；
- **数据自检：没有发现问题**（没有「keyword_only 多来源命中」「semantic_only 被关键词命中」「no_answer 却返回结果」）。

**分块**（同一趟顺带报出来，`chunkerVersion = chunker-1-packday-line400-overlap48`）：

| 指标 | 字符 | token（真实分词器核对） |
|---|---|---|
| 块数 | 107 | 107 |
| 最长 | 398 | **394** |
| p99 | 397 | 393 |
| 平均 | 97 | 96.0 |
| 超过 400 的块 | 0 | **0** |

token 数用上游固定 revision 的分词器核对（`tools/model-export/verify_chunk_tokens.py`）：**最长 394 token，全部在 400 以内**，所以「400 字符 ≤ 约 400 token」这个保守上界在本语料上成立。

**打包规则在量测里看得见**：107 块中 **1 块含多篇、最多 3 篇**（就是 `kw-11` 那条同一天三篇），其余是单篇。

**CI**：`probe` job 增加了 `quality-set` 一步。它只用仓库内的语料，不需要模型，所以能在 CI 跑；**不设阈值**——它报基线数字，并在语料被改坏（`expectedContains` 对不上、标注被污染）时失败。等 B3c-3 做出混合结果之后再谈「提升多少算达标」。

**打包的实测样子**（`kw-11`，同一天三篇）：三篇短正文合成一块，`spans` 三个，块正文是「薄荷…\n\n快递…\n\n晚饭…」这样的拼接；跨天的来源不会被合到一起。

## 没有做到的

- **只有关键词那一路的数字**：`semantic_only` 的 0% 是**基线**，不是混合检索的效果。语义与 RRF 的数字属于 B3c-2/B3c-3；
- **没有查询指令前缀的实验**：那需要跑 embedding，放到 B3c-2（那里才有模型）；
- **分块还没接进索引**：`IndexStatus.chunkerVersion` 仍是 `None`——现在没有任何块进索引，提前填一个「本次分块用的版本」是假话。接进去是 B3c-2；
- **合块后的命中映射还没定**：一块含多篇时，`SearchHit` 的 `sourceId`/`locator` 该指向哪一篇、还是按 `spans` 给多处，属于 B3c-2 的设计（这一片只把块切出来）；
- **「短时间跨度」目前就是「同一天」**：更细（同一天内相隔几小时）或更粗（同一周）的窗口都需要改常量与 `CHUNKER_VERSION`，没有做成可配置——在只有一个调用方之前，配置项只会让口径分裂；
- **打包只在小语料上验过**：`kw-11` 是三篇短文的构造用例，真实数据里「一天几十条短记录」会怎样（块里篇数上限、回溯到具体一条的体验）没有量过；
- **语料是合成的、规模小**（35 条、106 块）：它的作用是**口径**与**回归**，不是质量评估的终局。规模与真实分布要等真实库里的数据；
- **1-gram 回避这条标注约束很严**：`keyword_only` 要求查询的字不在其他来源里，中文里常用字（我/的/今天）几乎无法满足，所以这批查询刻意选了低频字（妈/邮/蛋/牙/橘/钥…）。以后的语料建议按「实际分词 + 2-gram 索引」来定义这条约束，而不是按单字——否则扩语料的人会被这条规则挡住；
- **语料的编写自查脚本没有进仓库**（只在本地跑过：schema、gram 纯度、日期范围、`expectedContains` 逐字命中、`long_transcript` 长度与位置共 9 组）。仓库里的门禁是探针的 `quality-set`：它做结构性检查（不通过就失败）与三条数据质量警告。如果以后要更严的标注门禁，再把那份自查脚本收进仓库；
- **延迟数字不能外推**：语料只有 106 块，0.4–0.9 ms 说明不了规模问题（规模数字看 B3a 的 10 万片段实测）；
- **`no_answer` 的「不误报」只对关键词那一路成立**：语义检索天生会返回「相似但无关」的结果，混合之后要重新量；
- **只在 Linux（WSL2 x86_64）宿主验过**，Android/Windows 未验（这一片不涉及模型，风险主要在检索排序，与平台无关）。
