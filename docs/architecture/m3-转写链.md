# M3 · 转写链：录音 → 转写 → 可检索可整理的正文（B4d / #91）

issue [#91](https://github.com/xingxue-ux/unwritten-diary/issues/91)。前置是
[B4a Provider 配置与能力](m3-Provider-配置与能力.md)（#66）：它把「能力协商、连接测试、
错误归一化、`waiting_configuration` 闸门」修好了，但**转写管线没接**——`transcribe`

（sherpa-onnx），**不联网**。

`crates/diary_core/src/transcription/`（`mod.rs` 执行者与分段、`sherpa.rs` 引擎 FFI、

**C API 形态**（`sherpa-onnx/c-api/c-api.h`，v1.13.8）与我们用到的部分：

```c
SherpaOnnxOfflineRecognizer *SherpaOnnxCreateOfflineRecognizer(
    const SherpaOnnxOfflineRecognizerConfig *config);
void SherpaOnnxDestroyOfflineRecognizer(const SherpaOnnxOfflineRecognizer *r);
const SherpaOnnxOfflineStream *SherpaOnnxCreateOfflineStream(const SherpaOnnxOfflineRecognizer *r);
void SherpaOnnxAcceptWaveformOffline(const SherpaOnnxOfflineStream *s, int32_t sample_rate,
                                     const float *samples, int32_t n);   /* 单声道 f32，引擎内部重采样 */
void SherpaOnnxDecodeOfflineStream(const SherpaOnnxOfflineRecognizer *r, const SherpaOnnxOfflineStream *s);
const char *SherpaOnnxGetOfflineStreamResultAsJson(const SherpaOnnxOfflineStream *s);
```

`AcceptWaveformOffline` 收的是 **PCM 采样而不是文件路径**，这与我们的分段转写正好合上：
自己按窗口读 PCM 喂进去，不需要引擎去解析容器。识别器配置是一整个**按值传入的结构体**
（`SherpaOnnxOfflineRecognizerConfig` 608 字节），字段布局写错了不会编译报错、只会静默错位
——所以这一片的 FFI **逐字段钉死并自检**，见下面「ABI 钉死」。

### 3. 与我们已有的 ONNX Runtime 是什么关系

- sherpa-onnx **自带/随包一份 ONNX Runtime**：`shared` 分发形态是**独立的
  `onnxruntime.dll` / `libonnxruntime.so`**（上面列了字节数），静态形态则把它链进
  `sherpa-onnx-c-api`。它不是「复用系统上已有的 ORT」，而是**它自己那一份**。
- **版本（分平台，不能互相套用）**：Windows/Android 的预编译产物里读到 **ORT 1.28.2**
  （`strings onnxruntime.dll | grep -E '1\.[0-9]+\.[0-9]+'` → `1.28.2`；CUDA 资产名里也
  写着 `onnxruntime1.28.2`）。**OHOS 的预编译产物是 ORT 1.16.3**——`strings` 是
  `1.16.3`，`llvm-readelf --dyn-syms` 是 `OrtGetApiBase@@VERS_1.16.3`。
- 我们自己的向量那一路用 `ort 2.0.0-rc.13` + `load-dynamic`，**要求 ORT ≥ API 17**
  （`ort-sys` 的 `ORT_API_VERSION = 17`，`GetApi(17)` 在更新的 ORT 上仍然有效），
  M0 实测用的是 ORT 1.22.0。
- **结论（分平台）**：
  - Windows/Android：**两者可以共用同一份 ORT 1.28.2**——`ort` 兼容更新的 ORT
    （向后兼容），sherpa-onnx 需要 1.28.2 这一代。但方向不能反：把我们的 1.22 给
    sherpa-onnx 是不行的。所以随包时放一份 1.28.2，两条路都指向它
    （`DIARY_ORT_DYLIB` / `ORT_DYLIB_PATH` 指同一个文件）；这一条**没有在本机跑过双路
    联调**（见「没有做到的」），它是由两边各自的版本要求推出来的结论。
  - OHOS：预编译 sherpa 要 **1.16.3**，而 `ort` 要 **≥ 1.17**，**同一份文件不满足两边**。
    PR #130 实测：把自编 1.29.1 改名成 `libonnxruntime.so` 直接替换，会因 musl-ldso 的
    符号版本哈希报 `symbol not found: OrtGetApiBase`（见 m6 探针 §23.3）。但**这不等于
    「只有重编 sherpa 一条路」**：`ort::init_from` 接受任意路径，1.29.1 的 SONAME 是
    `libonnxruntime.so.1`，与 sherpa `NEEDED` 的 `libonnxruntime.so` 不同名；让 sherpa
    继续用 1.16.3、语义索引显式加载另一个文件名的 1.29.1，两者可以并存。**#134
    （`feat/ohos-hap-config-20261018`，commit `6c45491`）已经按这条思路在产品身份真机
    验通**（`libonnxruntime-diary-1.29.1.so`，语义查询 `hits=26`、`matchedBy=["semantic"]`）。
    本 PR 不包含这条改动，也不再排除它。

### 4. 有没有哪个平台拿不到

Windows x64、Android arm64-v8a、Linux x64 都拿得到（上面已核实到字节数）。**没有因此
需要走 whisper.cpp 或云端替代**。鸿蒙（OHOS arm64-v8a）在 PR #130 里补做了真机验证：
HAD-W32 / API 23 / arm64-v8a 上加载 sherpa 1.13.8 + ORT 1.16.3，5 秒中文录音转写与
**关键词**检索跑通。**范围要说清**：默认 HAP 只到关键词检索（`matched_by=["keyword"]`）；

## 引擎形态：本地引擎适配器（不是 HTTP）

`ProtocolAdapter` 的每个方法都在拼 HTTP 请求，它的形状假设了「有 URL、有密钥、有一次出站
调用」。本地引擎三样都没有，所以这一片加了**并列的第二种形态**（
`provider/local_engine.rs`）：

| 共享的语义 | 谁提供 |
|---|---|
| 「这个适配器实现了哪些能力」 | `LocalEngine::capabilities()`（与 HTTP 同一张 `ProviderCapability` 表） |
| 能力闸门（声明 + 实现 + 测试结论） | `provider::evaluate`，两条路共用同一段判据 |
| 错误归一化与作业时间语义 | `CoreError` → `ErrorCode` → `jobs::FailureDisposition` |
| 连接测试 | 本机探针**真的加载模型并转写 0.05 秒静音**，一个字节都不出网 |

`adapter_for()` 返回的是枚举 `Adapter::Http | Adapter::Local`，所以「本地这条路没有
`Transport`」是类型上的事实，而不是一句注释：**它不可能出网**，`PanicTransport` 也拦不住
一条不存在的调用。测试 `transcription_never_touches_the_network` 把这一点钉住——内存库的
默认传输层就是「一调用就 panic」，转写全链跑通即为证明。

引擎实现（`transcription/sherpa.rs`）用 `libloading` **运行时**加载
`sherpa-onnx-c-api`，与 `ort` 的 `load-dynamic` 同一个理由：构建期不链接、不下载任何原生
二进制，**没有引擎库、没有模型的 CI 机器照样编得过、测得过**。许可证：libloading 是 ISC。

### ABI 钉死并自检

C API 的配置结构体是按值传进去的，布局错了只会在运行时静默错位。做法：

1. `#[repr(C)]` 逐字段对齐 **v1.13.8** 的 `c-api.h`；我们用不到的子结构体用不透明填充
   占位（注释里写明它对应 C 里的谁），需要的是**它们占的位置**对；
2. 测试 `abi_layout_matches_the_pinned_header` 断言**每一个我们会写的字段的偏移量**与
   结构体总大小（`OfflineModelConfig` 504、`OfflineRecognizerConfig` 608、…）。这些数字
   是用真实头文件跑 `offsetof` / `sizeof` 得到的（`gcc -o abi abi.c && ./abi`）；
3. 运行时再取一次 `SherpaOnnxGetVersionStr()`，版本写进连接测试报告。

**换引擎版本时这些断言会红**，逼人重新核对，而不是靠记忆。

## 模型目录：可配置，默认指向随包位置

解析顺序（`EngineConfig::resolve`，测试钉住）：

1. **配置行里显式给的目录**（`providers.model`，对本地引擎它是一个**目录**而不是模型名）；
2. 环境变量 `DIARY_ASR_MODEL_DIR`（开发、探针、CI）；
3. **随包默认位置**：可执行文件旁边的 `models/asr/sense-voice-int8`（退一步 `models/asr`）。

「随包」是产品决定（模型随安装包分发，**不要求联网、不依赖首次下载**），但核心这边
**只认「一个目录路径」**，不把分发策略写死：放资源目录、放 AAB 的 asset pack、还是让用户
导入，都是打包层的事。引擎库同理：`DIARY_ASR_ENGINE_LIB` 优先，其次可执行文件旁边的
`sherpa-onnx-c-api.*`；Android 上没给路径时**按库名加载**（由系统在应用的 native 库目录里
解析，这是那里的正常路径）。另有 `DIARY_ASR_MODEL_FILE`（同目录放多份模型时指定文件）、
`DIARY_ASR_MODEL_TYPE`（`sense_voice` / `paraformer`，不设时按目录里的文件推断）、
`DIARY_ASR_LANGUAGE`（语言提示，不设就让模型自己判）。

### 降级口径：缺什么、怎么办、绝不产出空文本

引擎库不在 / 模型目录不在 / 模型文件不齐 → 能力闸门给出 `provider_not_configured`
（作业侧落成 **`waiting_configuration`**：**没跑过就不计尝试**——`attempt_count` 不动、不排
退避；同时按统一口径置 `requires_user_action` + `attention_key =
job-config:transcribe:provider_not_configured`，等配置不是失败但**要用户动手**，见
[M4 · 等配置的语义](m4-任务调度与补做.md)），理由里写清：

- **缺什么**：路径一律带出来（`/…/models/asr/sense-voice-int8 里找不到模型文件（找过
  model.int8.onnx / model.onnx）`、`引擎的动态库不在：/…`），以及「同目录没看到
  onnxruntime.dll/.so」这种随包容易漏的一条；
- **怎么办**：把模型目录放到 `<exe_dir>/models/asr/sense-voice-int8`、或用
  `DIARY_ASR_MODEL_DIR` / `DIARY_ASR_ENGINE_LIB`、或在设置里保存一条 `adapter=sherpa_onnx`
  的服务配置把 `model` 填成自己的目录。

闸门在**领取前**就挡住，所以**一个派生内容行都不会写**——「引擎不可用」与「转写成功但
文本为空」在库里分得开（测试 `a_missing_engine_waits_for_configuration_without_writing_anything`）。

**内建引擎不是 `providers` 表里的一行**：它是核心自带能力，随包模型就绪时直接可用。
为什么不自动插一行——用户删掉那一行之后，下次开库又会原样长回来；没有墓碑就无法区分
「用户不要」与「还没配」，那是对用户的欺骗。要改模型目录/停用它，就**显式保存一条同
adapter 的配置**（`providers.save`），它的 `model` / `enabled` 覆盖内建默认；删掉覆盖行
就回到默认。`providers.list` 只返回配置行（与 B4a 的口径一致）；「转写到底能不能用」的
真相在 `Core::provider_capability_gate(TranscribeAudio)` 与 `providers.test` 里——
后者对**本机引擎的 id** 也能测（`builtin_local_asr`），报告里写明「本次测试完成了 N 次
本机推理，没有发起任何网络请求」。

## 分段、恢复、幂等（不改 schema）

- **分段**：按窗口 30 秒切（`WINDOW_MS`），每个窗口一次引擎调用。**不做重叠**：重叠会让
  同一段语音出现在两个片段里，而幂等要求「同片段重放只有一份文本」。代价写在
  「没有做到的」里。
- **片段行 id 是确定的**：`{content_id}:{ordinal}`，重放走 `ON CONFLICT(id) DO UPDATE`
  ——**幂等由主键保证**，不靠调用方自觉；同一份音频再排一条任务时，已完成的窗口直接跳过
  （不重复调用引擎、不重复插入）。
- **可恢复**：跑之前先读出这一份内容已有的窗口序号，已完成的跳过；进程被杀之后下一次领取
  从第一个缺的窗口继续，**不重头**。窗口永远是 `0..k` 的连续前缀（循环遇到错误就停），
  所以聚合正文可以在末尾追加，字符区间不会错位。
- **半截结果不当完整文本**：中途失败时已完成的片段留在库里，内容行 `status = partial`、
  `coverage = partial`、`coverage_reason` 写明「已完成 k/N 段 + 停下原因（错误码 + 消息）」；
  只有全部窗口跑完才变 `ready`。终态失败时那半截正文**仍然可搜**（如实标 partial），
  用户看得见「已经有多少、还缺多少」。
- **换模型就重来**：`extractor_version = <版本>:<模型身份>`，模型身份 = 类型 + 文件名 +
  字节数 + mtime + **sha256 前 12 位**（进程内缓存：228 MiB 的模型每次任务都哈希会拖慢
  半秒以上）。版本不一致 → 先删旧片段（索引行按 `segment_id` 级联）再从头跑，
  **两代文本不会混在一份内容里**。
- **进度**：窗口总数与已完成数都是真的，所以写进 `jobs.progress_completed/total`
  （契约说「没有可靠进度时必须为空」，现在有可靠来源了）。**进度不发 `job.changed`**：
  一个长录音一百多个窗口，每个窗口一条域事件会把事件表撑大，而进度是查询时读到的真值。

为什么**不改 schema**：`extracted_contents` 的 `(source_revision_id, extractor_id)` 唯一键、
`extracted_segments` 的 `id` 主键、`jobs.progress_*` 三样已经足够表达「一份内容的若干窗口、
跑到哪、属于哪个模型」。加表只会多一处不一致的机会。

## 结果怎么进材料：派生内容，不是用户原话

转写落成**派生内容**（`extracted_contents` + `extracted_segments`，`extractor_id =
local_transcription`），三条口径：

1. **不覆盖原始录音**：音频那条 `source_revisions` 行一个字节都不动（`author_type` 仍是
   `user`、仍带着 `asset_id`）。转写是可重建、可丢弃的派生正文；
2. **不冒充用户原话**：区分沿用 B4b 的口径（见 `model.rs` 里 `DiaryVersionOrigin` 的注释：
   `source_revisions.author_type` 只有 user/import，**AI 产物不写进用户原件**）——所以这里
   **不新造一个 `authorType`**，区分靠本来就有的 `extractor_id`（谁产的）、`coverage`
   （覆盖到什么程度）、`locator`（来自哪段时间）。`captures.draft_text`（用户自己写的）
   与它天然是两处，导出/搜索要区分时看这三个字段就够；
3. **就是这条材料的当前正文**：`search.rs`（关键词）与 `chunks.rs`（语义分块）都以「当前
   修订的派生内容」为正文来源，所以转写一落库，这张录音就同时进了关键词检索与分块——
   issue #91 的「与既有检索链一致」不需要另开一条通路。

与「提取」那条路的相互保护（都是音频来源会碰到的事）：

- `extractors::persist` 的重建删除**只删同一个 `extractor_id`** 的旧行——按修订整删会让
  一次重新提取顺手抹掉转写正文（唯一键本来就是 `(revision, extractor)`）；
- 音频的 `media_metadata_only` 提取器发现这条来源**已经有带正文的派生内容**时，原样返回
  它、不再落一条「没有转写能力」的空标记行；转写跑完时也会删掉这条空标记
  （`prune_superseded_markers`）。一步不做，消费者就会同时看到两条互相矛盾的派生内容。

### 时间戳对齐

| 列 | 值 | 含义 |
|---|---|---|
| `locator_type` | `audio` | 这一条定位的是音频 |
| `start_ms` / `end_ms` | 窗口在**逻辑音频**里的毫秒区间（帧区间由同一对毫秒换算，首尾相接） | 「这段文字来自哪段时间」 |
| `text_start` / `text_end` | 该段文字在**聚合正文**里的字符区间（Unicode 标量值，左闭右开；聚合 = 非空片段按 `ordinal` 用 `\n` 连接，与 `chunks.rs::segment_text` 同一口径） | 「哪段文字属于哪个片段」 |
| `asset_id` | 音频资产 id | 前端据此播放原件 |
| `source_revision_id` | 音频那条修订 | 与既有 locator 语义一致 |

检索命中时 `SearchHit.locator` 带的就是它，所以「这段文字来自这段录音」在结果里直接可读，
`sources.locate` 也能拿它去打开音频。转写期间每个窗口落库都会把**索引代次 +1**，
所以转写进行中打开的旧检索会话会如实报 `search_expired`（前端重取即可）——
这与 #70 的既有口径一致：检索始终可用，但不拿旧快照冒充新的。**不伪造精度**：窗口内不做词级时间戳——引擎其实给
token 级时间戳，但我们的落库单位是窗口，写一个更细的数字会让人以为它比实际更准。

## 作业执行者与旧账

- `provider::job_capability` 加了映射：`transcribe` → `ProviderCapability::TranscribeAudio`
  （B4a 特意留的钩子）。**只认本机引擎**（`capability_gate_for_with(local_only = true)`）：
  录音这条链跑的是本机引擎，让闸门把远端服务算成「可用」而执行者用另一个东西跑，是对用户的
  欺骗。远端转写在 #99 的评测路径里有（`OpenAiCompatibleTranscriptEngine`），产品化是后续事；
- 执行者是 `jobs::run_transcribe` → `transcription::run`，失败时间语义见
  `transcription::is_transient` 的表：文件暂时不在/IO/数据库 → 退避重试；引擎没就绪/能力
  不支持 → 等配置；模型坏了、容器不支持、目标不是当前修订 → 终态；
- **旧账一次性清账**：`transcribe` 在 #91 之前没有执行者，那些任务进了「已放弃」+
  `no_handler`。`jobs::requeue_legacy_no_handler` 在**开库时**把它们放回队列（与人工重试
  同一套清零语义：`attempt_count` 清零、发 `job.changed`、旧尝试留在 `job_attempts` 里）。
  三条口径：只放回**现在真有执行者**的 kind；判据自带幂等（放回后 `error_code` 就不是
  `no_handler` 了，不需要「迁移过没有」的账面，也就不需要改 schema）；目标没了的也照样放回，
  它会以 `not_found` 终态失败——那是当下的真相，比留着一句「核心还没有执行者」诚实。
- **`transcribe → index` 的前置**：m4 文档留的待办一并做了。`index_dependency` 现在也认
  **活着的转写任务**（转写任务的 `target_ids` 是资产 id，要 join 回修订再比），在等的理由
  写成 `waiting_transcribe`。不做这一条的话，「录音刚最终化、转写还没跑」时排的索引任务会被
  判成 `dependency_extract_unmet` 终态失败，而内容马上就有的。

## 接 #93 的质量集接缝

#93（PR #99）在 `crates/diary_core/src/quality/engine.rs` 留了 `TranscriptEngine` 接缝
（回放 / 真模型两种实现）。这一片补上**第三种：本机引擎**——
`transcription/seam.rs` 的 `LocalTranscriptEngine`，走 `LocalEngine`，**同样不联网**，
CER 因而第一次能量到「真引擎的输出」。

因为这一片的分支基于 B4a（#99 还没合进来），`seam.rs` 里的 `TranscriptRequest` /
`TranscriptOutcome` / `TranscriptEngine` 三个签名是**逐字对齐 #99** 的；#99 合入后要做的
只有一步：把 `use super::{...}` 换成 `use crate::quality::{...}` 并删掉本文件里那三个类型
定义，`LocalTranscriptEngine` 的方法体一行不动；探针 `tools/probe/src/ai_quality.rs` 的

**语料仍然是合成占位**：#99 喂进来的是全零静音的合法 WAV（`placeholder_audio`），所以这条
接缝今天证明的是「真引擎能加载、能吃 WAV、能返回文本、CER 管线能跑通」，**不是转写质量**。
真语音语料待补。

- Windows x64：228.4 + 23.1 + 17.0 + 4.4 + 核心 ≈ **273 MiB + 核心 `.dll`**。

**压缩后的实测**（安装包是压缩分发）：

| 项 | 原始 | `gzip -9`（实测） | `zstd -19`（实测） |
|---|---|---|---|
| SenseVoice int8 `model.int8.onnx` | 228.1 MiB | **152.7 MiB** | 149.1 MiB |
| sherpa-onnx C API + ORT（Android arm64 两个 `.so`，打包成 tar 再压） | 25.5 MiB | **11.2 MiB** | — |

## 没有做到的

- **没有真语音语料**：CI 里的音频是合成静音，真引擎那条用的是官方 `test_wavs/zh.wav`
  一句话。**转写质量（CER/WER）没有量过**，#93 的转写语料仍是合成占位——真语料要人工录/
  授权语料，那一步没做；
- **静音可能被转出一两个字**：实测 SenseVoice 在纯静音上会输出 `"그."` 这种无意义短串
  （模型行为，不是我们编的）。我们**如实落库**（coverage 仍是 complete），不替引擎做
  「这算不算有内容」的判断——过滤规则要有真语音语料才定得下来，随便加一条会误伤真人语音；
- **只解码 PCM WAV**：导入的 mp3/m4a/视频音轨不进转写链（走原有的 `metadata_only`）。
  要支持它们需要解码器或平台层「按需准备音轨」（任务书里是平台层的事），这一片没做；
  另外 `recordings::finalize` 是**把片段字节直接拼接**，如果平台层每个片段各带 44 字节头，
  拼出来的逻辑音频里第二个头会被当成 PCM 采样读——这一片不解、如实记在这里（修它属于
  F1 录音链的口径）；
- **Windows / Android 没有真机运行**：库的存在性与体积是核实过的（下载、解开、列内容、
  读版本字符串），但**没有在真机/模拟器上加载并转写**。Windows 与 Android 的 loader 语义
  差异（依赖搜索路径、Android 的 native 库目录）只在文档与错误消息里准备了兜底，真机
  验证待补。**鸿蒙已在 PR #130 补上真机验证**（见上）；
- **ORT 双路共用没有联调**：Windows/Android 的结论（可以共用 1.28.2）是从两边版本要求
  推出来的，没有把「同一进程里 `ort` 与 sherpa-onnx 同时用一份 `libonnxruntime.so`」
  跑通。OHOS 的两份版本不能共用，**双 ORT 并存（1.16.3 + 1.29.1，不同文件名）已由 #134
  在产品身份真机验通**，不在本 PR 的改动或验收范围；
- **OHOS 语义索引不在本 PR 闭环**：产品 `ort` crate 要求 ORT ≥ 1.17，而默认 HAP 随包的
  sherpa 要 1.16.3 ⇒ 默认 HAP 只到**关键词**检索（`matched_by=["keyword"]`）。语义检索
  要按 #134 的双 ORT 打包方式（多带 `libonnxruntime-diary-1.29.1.so`）；#134 已验通，
  但**不能按「默认 HAP 检索全通」验收**；
- **没有词级时间戳**：落库单位是窗口（30 秒），`start_ms/end_ms` 是窗口边界。引擎给的
  token 级时间戳没有消费（要用得先定「点到词」的交互与精度口径）；
- **窗口边界可能切断词**：不重叠是幂等的代价。要做得更好需要「重叠 + 去重口径」或
  VAD 切分（sherpa-onnx 有 VAD，这一片没用）；
- **没有取消/中断一次正在跑的窗口**：一次引擎调用不能被中途打断，时间预算只在任务之间
  判断（与 `run_due` 的既有口径一致）。一条长录音正在跑时，界面与检索照旧可用；
- **进度不发事件**：`jobs.progress_*` 只在 `jobs.get` / `jobs.list` 里读到，不会主动推送；
- **内建引擎不出现在 `providers.list` 里**：`providers.test("builtin_local_asr")` 能测它，
  但设置页要显示它、要提供「模型目录」输入框，需要前端加一个本机引擎卡片——
  这一片**不碰 `apps/**`**；
- **远端转写没有进产品链**：`OpenAiCompatibleTranscriptEngine` 是 #99 的评测路径；
  录音的转写链只跑本机引擎（闸门也是这么说的）。要让用户选远端转写，需要新的产品口径
  （计费、隐私、离线性），不在这一片；
- **许可核实有一处不确定**：Paraformer-zh 的上游 ModelScope 模型页许可没有逐字核到原文
  （只核到 HuggingFace 元数据的 `apache-2.0` 标签）。默认用的 SenseVoice 那条核到了 MIT
  全文与转换仓库的指向说明，但**转换产物仓库没有单独的许可全文**这一点也如实记着。

## 需要拍板

1. **模型分发策略**（本片只落地了「默认指向随包目录」这一条技术口径）：
   Google Play 的 AAB 基础包上限 150 MB，228 MiB 的 int8 模型放不进去。三条路：
   ①install-time asset pack（仍然「随包」但不进基础包）；②首次启动从安装包内解出（AAB 里
   仍要放，等价于 ①的限制）；③做成可选下载（与「不依赖首次下载」冲突）。**需要产品选一条**；
2. **要不要默认随包**，还是「随包引擎 + 用户可选下载模型」：后者能显著缩小基础包，代价是
   首次可用性；这一片按「随包」实现，但没有替产品决定下载策略；
3. **模型档位**：SenseVoice int8（228 MiB，5 语言 + 标点）对 Paraformer-zh int8（217 MiB，
   中文）差不多重；如果体积是硬约束，是否需要更小的模型（例如更小的 Zipformer-CTC）而
   牺牲一点效果？这需要真语料上的质量数字才好定，而那个数字这一片没有；
4. **静音/无语音的判定**：现在如实落库（可能是 `"그."` 这种串）。要不要引入 VAD 或
   「短于 N 字且无有效内容就标 metadata_only」的规则？规则要有真语料支撑，见上；
5. **鸿蒙路线**：PR #130 已在真机上跑通「录音 → 转写 → 关键词检索」，所以**转录支持
   矩阵可以列入 OHOS**。语义索引的**技术路已由 #134 验通**（双 ORT：sherpa 1.16.3 +
   自编 1.29.1，不同文件名，HAP 多 ~18.95 MiB）；**产品仍要拍板**是否接受这个体积与
   打包方式。默认 HAP 的验收口径仍只到关键词检索。
   本期验收口径只到关键词检索，不要把语义检索算进闭环。
