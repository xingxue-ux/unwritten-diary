# 共享接口契约 v1

本文件是两层共同依据，也是唯一的同步点。方法名是设计标识，不是已经存在的实现。

**状态：v1 已冻结（2026-09-27）**。冻结之后，新增字段、方法或改变语义都必须先更新本文件（或先提「契约变更请求」issue），再改实现；先改实现再补文档的 PR 不予合并。`packages/diary_api` 类型包与 Mock 实现都必须符合本文件，目录与流程见 [CONTRIBUTING.md](../../CONTRIBUTING.md)。

## 1. 调用与数据约定

### 1.1 两条独立接口

DiaryApi 是 Flutter 到本地业务核心的异步接口，涵盖资料、日记、搜索、任务与设置。PlatformHost 是系统能力接口，负责录音、播放、选文件、权限、系统凭据和后台唤醒。页面依赖抽象接口，不直接调用数据库、Rust 内部对象或某个模型服务的 HTTP API。

实际产品使用 RustBridgeDiaryApi；页面测试使用 MockDiaryApi。两者必须实现同一组方法、错误和事件语义。

### 1.2 基本规则

| 项目 | 契约 |
|---|---|
| 标识 | 不透明字符串 ID，不让前端解析或拼接；由核心生成 |
| 时间 | UTC 时间以带 Z 的 ISO 8601 表达；另存 IANA 时区和当时偏移 |
| 日归属 | dayKey 为 YYYY-MM-DD，按设置的 diaryTimeZone 计算；导入时间与事件时间分开 |
| 修改时区 | 只影响新材料的默认归属；不静默搬动历史日记；历史调整走明确操作 |
| 文本区间 | Unicode 标量值计数，左闭右开；前端在 Dart 中转换为实际字符串下标，不直接当 UTF-16 下标 |
| 音视频位置 | 从逻辑媒体开始的毫秒数，暂停间隔不计入播放时间；原始墙钟时间另存 |
| 页码 | 从 1 开始；无法可靠定位页码时返回空，不伪造 |
| 分页 | 不透明 cursor，默认 20 条，最大 100 条；确定性排序包含 ID 作为并列次序 |
| 大数据 | 音视频、原图、整库数据不通过一次桥接调用整体传输；使用分页、范围读取、受控文件句柄 |
| 修改并发 | 带 expectedRevision；不匹配返回 revision_conflict，不静默覆盖 |
| 幂等 | 可重试写入带 operationId；先查已完成操作再检查 revision；同一操作重试返回原结果；同一 ID 配不同内容报冲突 |
| 取消 | 长任务返回 jobId/searchSessionId；取消停止后续处理，不删除已经保存的原件 |
| 错误 | code、用户可读 message、retryable、可选 jobId/fieldErrors；堆栈只进入脱敏诊断 |
| 持久化确认 | 只有核心完成持久化后才返回 durable=true；UI 的“已保存”以此为准 |

建议初始默认：diaryTimeZone 为首次设置时的设备时区，可修改；自动整理 22:30；跨午夜长录音归入开始录音时的 dayKey。用户可以明确调整归属日期，调整不改录音时间戳。

### 1.3 协议版本

CoreInfo 返回 apiVersion、dataSchemaVersion、buildVersion、支持能力和当前库 ID。apiVersion 使用主次版本；新增可选字段为次版本，删除或改变语义为主版本。**新增必填的响应字段同样是次版本**：旧客户端忽略它是安全的，但新客户端在旧核心上读不到这个键——不升版本，客户端就没有任何依据判断「这个字段在不在」。1.0 → 1.1 就是 `SearchHit.captureId` 定的口径（见 2.6 节）。**新增方法**若为**加性且旧实现者仍可安全调用**（例如 `search.upgrade` 带诚实退化的默认实现，老实现者拿到的是关键词那一份、阶段如实保持 `keyword_ready`），**不改变 `apiVersion`**；删除方法或改变既有方法的语义才升主版本。本归类为 `search.upgrade` 落地时定的口径，欢迎评审推翻。UI 与核心主版本不兼容时进入恢复/更新页面，不继续写入。

**耦合警告（1.1 起要记住）**：`apiVersion` 现在**同时**承担两个职责——「API 表面的版本」与「备份格式的兼容边界」：备份清单的 `apiVersion` 与 `CoreInfo.apiVersion` 共用 `diary_core::API_VERSION`，而恢复只拒绝「高于本构建」的备份（见 [m5 §6](../architecture/m5-备份与恢复.md)）。后果是：**任何为响应字段抬次版本的改动，都会连带锁住备份降级**——1.1 上做的备份拿到 1.0 的安装包上会 `incompatible_backup`（用户可见的后果见 [`升级与迁移.md`](升级与迁移.md) §4.4）。所以**下次要为字段抬次版本之前，先考虑把备份格式版本拆成独立常量**（例如 `BACKUP_FORMAT_VERSION`，只在库内容真正不可读时才动），不要让一个搜索字段决定备份能不能恢复。

## 2. 主要数据对象

### 2.1 Capture：一次记录

Capture 表示用户的一次混合记录，可以同时包含文字、照片、录音和文件。

| 字段 | 含义 |
|---|---|
| id / revision | 标识及乐观锁版本。**新建记录的 `revision` 从 1 开始**，此后每次成功写入 +1（保存草稿、提交、改文字各算一次）；`expectedRevision` 必须等于当前值，否则 `revision_conflict` |
| state | draft、committed、trashed |
| occurredAt / createdAt / updatedAt | 事件时间、入库时间、最后修改时间 |
| timeZone / utcOffsetMinutes / dayKey | 时间语义与日记归属 |
| orderedSourceIds | 按展示顺序组织的文字或附件来源 |
| draftText | 草稿正文，仅 draft 阶段可直接变更 |
| processingSummary | 未处理、处理中、可检索、需关注的数量 |

草稿频繁保存只更新当前草稿与恢复日志，不为每个按键制造永久版本。提交时创建原始文字版本。提交后修改文字则创建新的 SourceRevision，旧版本保留。

### 2.2 SourceItem / SourceRevision：原始内容

| 字段 | 含义 |
|---|---|
| sourceId / captureId | 稳定来源标识及所属记录 |
| kind | text、image、audio、video、file、link |
| currentRevisionId | 当前原始文字或来源元数据版本 |
| revisionId / parentRevisionId | 本次原始内容修订及父版本 |
| text / assetId | 文字原件或文件库中的资产引用 |
| authorType | user、import；AI 生成正文不写成 user 来源 |
| occurredAt / provenance | 时间及来源信息，导入附带的元数据不得冒充已确认事实 |

已保存原件不能被模型或插件覆盖。用户明确删除是另一条操作，不与自动清理缓存混淆。链接本身先保存；网页抓取需要相应能力，抓取失败不丢失链接和备注。

### 2.3 Asset：文件库资产

| 字段 | 含义 |
|---|---|
| id / objectRef | 稳定 ID 和核心管理的内部文件引用 |
| originalName / detectedMime / byteSize / sha256 | 文件信息及完整性校验 |
| mediaDurationMs / width / height | 可选媒体属性 |
| storageState | importing、ready、recoverable、missing、trashed |
| importOrigin | picker、camera、paste、drop、share、recording、restore |
| createdAt | 本地入库时间 |

原始外部路径或 Android content URI 不作为长期资产地址。用户删掉下载目录中的原文件后，已成功导入的材料仍可打开。objectRef 不是供插件任意访问的系统路径。

### 2.4 ExtractedContent / SourceLocator

ExtractedContent 含 id、sourceId、sourceRevisionId、extractorId、extractorVersion、text、segments、status、coverage、errorCode。它是可重建的派生内容，与原件分开。

SourceLocator 含 type 与对应字段：text_range 使用 start/end；audio/video 使用 startMs/endMs；document 使用 pageNumber 和可选 blockId；image 使用可选归一化矩形；file 使用 assetId。每个 locator 必须携带 sourceRevisionId，保证定位到当时的原文版本。

coverage 要能表达 complete、partial、metadata_only、unavailable，以及用户可读原因。图片描述属于机器提取，不自动变成用户亲口表达的感受。

### 2.5 DiaryDay / DiaryVersion / StyleProfile

DiaryDay 含 dayKey、timeZone、currentVersionId、candidateVersionIds、revision、materialCounts、coverage、updatedAt。`revision` 是这一天的**持久、单调递增**的状态推进计数（新增一版 +1，换当前版本也 +1；没有推进过的天是 0），也是 `saveEdit` / `setCurrent` / `merge` 的 `expectedRevision` 的**唯一来源**（新增字段，2.5 的其余形状不变）。

DiaryVersion 含 id、dayKey、parentVersionId、origin（generated、user_edit、merge）、body、createdAt、sourceSnapshotId、styleSnapshotId、generationInfo、provenanceLinks。body 是自然段正文；来源关联放在独立字段，阅读页不把正文变成报告。

sourceSnapshotId 对应不可变的输入清单：来源 ID、修订 ID、已使用提取版本及未处理项。provenanceLinks 以段落或内容范围关联原件；不要求每一句抒情修辞都有机械式引用，但涉及事实的内容要能追溯。

StyleProfile 含长度偏好、叙述人称、语气、情绪温度、允许的修辞程度、可选示例和明确禁用表达。偏好变更不自动重写历史日记。风格默认只从用户明确设置和确认后的修改中调整；自动推断出的偏好应作为建议，不能悄悄固化。

### 2.6 SearchRequest / SearchHit / SearchSnapshot

SearchRequest：query、mode（keyword、semantic、hybrid）、filters、pageSize。filters 包括日期范围、材料类型、来源范围、是否包含旧日记版本；默认 hybrid、排除回收站、折叠历史版本。

SearchHit：hitId、groupId、captureId、sourceKind、sourceId、revisionId、dayKey、title、snippet、highlights、locator、matchedBy、coverage。matchedBy 为 keyword、semantic、metadata 中的一个或多个，不把向量相似度显示为事实置信度。

`groupId` 与 `captureId` **不是一回事**，不能混用：`groupId` 是「同一来源的命中折叠归组」用的键，片段命中时它就是 `sourceId`，记录文字命中时才是 `captureId`；`captureId` 是「这一条命中属于哪篇记录」，两种命中都一定有（语义那一路取 `chunk_spans` 里**该片段所属那段 span** 的 `capture_id`，不是块里第一段的）。界面要跳记录详情页时必须用 `captureId`（`groupId` 在片段命中上会让一半结果跳错）。

`captureId` 从 **apiVersion 1.1** 起是**必填**字段（Rust 上是 `String`：不是 `Option`，也没有 `#[serde(default)]`）。跨版本两个方向都要说清：

- **旧 JSON + 新 Rust（新核心读旧数据）**：缺这个键会直接 `missing field capture_id` 反序列化失败。仓内目前没有 `SearchHit` 的反序列化点（C ABI 只序列化、Dart 没有 `fromJson`），所以不是现有调用方的破坏；将来若加反序列化点，**不要**用 `#[serde(default)]` 兜成空串——空串会被当成一篇不存在的记录，问题只是从「读不进来」挪到「点进去 404」。
- **新 app + 旧 core（新客户端调旧核心，apiVersion 1.0）**：旧核心的 JSON 里**根本没有这个键**，ArkTS `JSON.parse` 得到的是 `undefined`（**不是 `null`**）；信封里的 `apiVersion` 会如实报 `1.0`。所以调用方必须按 `apiVersion >= 1.1` 判断字段在不在：1.0 时**不得**拿 `groupId` 顶替（片段命中上那是 `sourceId`，会跳到别人的日记），应当把「按记录跳转」降级为不可用并提示更新核心。
- **为什么不定成 `Option<String>`**：`Option` 只能让**本核心**在无值时序列化成 `null`；旧核心仍然缺键、ArkTS 仍然读到 `undefined`，那个方向一点没修。它还会把「两种命中都一定有」降级成「可能没有」，诱导调用方写 `captureId ?? groupId` 的静默错跳——正是这个字段要修的问题。字段在 1.1 核心上恒有值（两种命中都有测试钉住），所以用必填 `String` + 次版本表达，不用可空类型。

SearchSnapshot：sessionId、queryRevision、phase（initial、keyword_ready、hybrid_ready、done、cancelled）、results、cursor、indexCoverage、warnings。每次事件发送当前页的完整快照，前端按 hitId 更新；不得把两份完整快照当增量直接拼接。

旧查询的结果不能覆盖新查询。核心返回 queryRevision，前端同时校验当前 sessionId 与 queryRevision。翻页绑定原会话；索引变化造成快照失效时返回 search_expired，让前端重新开始。

`hybrid` 模式分两阶段交付：`search.start` 先只算关键词那一路，返回 keyword_ready 快照（首屏不等向量模型）；调用方**显式**调用 `search.upgrade` 才做 RRF 融合与重排，同一会话再返回一份 hybrid_ready 快照。升级是显式的、幂等的；语义拿不出可融合的证据时不融合，阶段如实停在 keyword_ready 并在 warnings 里说明，**绝不**假装 hybrid_ready。「有证据」不包括**口径不一致的向量**——生效代次的 `model_version` / `dims` / `storage` 与当前嵌入器不一致（换了模型/维度/存储格式但还没重建索引）时，语义这一路不作数，见 4.4。方法与错误细节见 4.4。

### 2.7 Job / Provider / Plugin

Job：id、kind、state、targetIds、inputSnapshotHash、progress（可空）、createdAt、updatedAt、attemptCount、nextAttemptAt、errorCode、requiresUserAction、attentionKey。attentionKey 表示同一个需处理问题，用于跨重启去重通知。没有可靠进度时 progress 为空，不能虚构百分比。

`errorCode` 对**在等前置**的 `waiting_dependency` 任务用来写明「在等什么」（例如 `waiting_extract`：等目标来源的提取完成）；这不是失败，`attemptCount`、`nextAttemptAt`、`requiresUserAction` 都不动，驱动每一轮开始时重新评估前置，满足了就回到 `queued`。前置不可能再满足时任务进 `failed` + 明确的 `errorCode`（例如 `dependency_extract_unmet`）并置 `requiresUserAction`。

**等配置**（`waiting_configuration`）用同一个字段写明等的是什么（例如 `waiting_model`：语义索引在等本地模型配置好）。它**不是失败**，但**不是一个用户无需理会的状态**：任务置 `requiresUserAction`，并给出 `attentionKey = job-config:<kind>:<errorCode>`（界面靠它深链到「去配哪个服务 / 哪台机器的模型」；同一个待处理问题只提示一次）。这一句**跨 kind 一把尺**——语义索引等模型、Provider 作业等服务，两条闸门与执行期那条路给出的 `requiresUserAction` 都是 `true`。它**不进 `nextWakeup`**：等的不是时间，而是配置变化——下一次 `jobs.runDue`（前台/唤醒/改配置之后都会调）的闸门会重新评估并把它拉回 `queued`（回 `queued` 时 `requiresUserAction` 与 `attentionKey` 一起清掉）。
`attemptCount` 是唯一按「有没有真的跑过」区分的地方：**闸门在领取前挡下**（没配模型、服务被移除）→ 一次都不记（0）；**执行期才发现配置坏了**（闸门放行后真的加载失败、真的发出请求撞上 401）→ 那次尝试**如实记账**（领取时已经 +1，不回退），并在 `job_attempts` 里以 `outcome = waiting_configuration` 收尾。不是失败，所以两种都不排退避、不消耗重试额度。

**分段让出**（长任务在安全点自己停下）用状态与 `progress` 表达，不新增错误码：任务回 `queued`（`nextAttemptAt` 为空 = 立刻可再跑）、`errorCode` 清空、`attemptCount` 不因让出而增加（让出不是一次失败），进度写在 `progress` 上。下一轮驱动接着跑，跑完才进 `succeeded`。

`jobs.runDue` 的返回值 `DueRunSummary`（Dart 类与核心 `JobRunSummary` 一一对应）：

| 字段 | 含义 |
|---|---|
| `startedAt` | 本轮开始时刻；「补做」以它为界 |
| `trigger` | 唤醒来源，调用方给什么就记什么（`startup` / `foreground` / `wake` / `manual` …）；只用于观察，不改变行为 |
| `processed` | 本轮领取并执行的任务数。分段让出、回到 `queued` 的长任务**算在内**（它确实被领取并执行了一段），但它不在 `succeeded`/`failed`/`retrying` 里——它还活着，进度在 `Job.progress` 上 |
| `succeeded` / `failed` / `retrying` | 其中成功 / 已放弃 / 排了退避重试的数量 |
| `backfilled` | 其中属于**补做**（领取时排期已过期）的数量；只报「补做」，不谎报「准时」 |
| `recovered` | 本轮开始时回收的上次没跑完（`running`）任务数 |
| `dueBacklog` | 本轮结束后仍到期但没跑上的数量（被预算/条数截住）；大于 0 就说明本轮提前收手。让出的长任务回到 `queued` 且排期清空，也算在这里（它是「接着要跑」的那一类） |
| `waitingDependency` | 本轮结束时还在等前置的任务数；没被领取、没消耗重试额度 |
| `dependencyFailed` | 本轮被判定「前置不可能再满足」而终态失败的任务数 |
| `nextWakeup` | 下一个到期时刻；没有待办时为空（等前置与等配置的都不算待办） |

Provider：id、label、endpoint、adapterId、model、capabilities、credentialRef、enabled、testStatus。capabilities 至少区分 generate_text、transcribe_audio、understand_image；本地 embedding 属于独立配置。API 返回凭据存在与否，不返回密钥明文。

Plugin：id、version、apiRange、supportedPlatforms、activationEvents、requestedPermissions、grantedPermissions、entryKind、state、lastError。模型提供者插件可请求核心代为调用已配置服务，普通处理插件不直接得到所有模型密钥。

## 3. 状态机

| 对象 | 状态流转与规则 |
|---|---|
| 草稿 | draft → committed；draft/committed → trashed；恢复回原状态 |
| 导入 | prepared → copying → verifying → ready；中断为 recoverable；失败明确 error，不提前宣称原件完整保存 |
| 录音 | idle → preparing → recording ↔ paused → stopping → saved；可进入 interrupted/recoverable/error |
| 任务 | queued → running → succeeded；可进入 retry_wait、waiting_configuration、waiting_dependency、waiting_network、failed、cancelled |
| 索引 | pending → processing → ready；可为 partial/failed/stale，按材料和模型版本维护 |
| 日记 | 首次生成可成为 current；后续生成默认 candidate；用户选择后成为 current；旧版本仍保留 |
| 插件 | installed → disabled/enabled；被触发才 running；出错回 enabled 或 quarantined，不影响原件存储 |

中断与失败不是同义词。来电中断显示“录音已暂停/中断”，不得继续显示正在收音。任务等待用户配置时不自动无限重试。

**`diary.*` 的落地口径（B4b 补充，2026-10-16；不改字段与方法签名，也不升 apiVersion）。** 完整解释见
[`docs/architecture/m3-日记生成与版本.md`](../architecture/m3-日记生成与版本.md)。B4b 已接上
`diary.generate` / `diary.getDay` / `diary.listVersions` / `diary.getVersion`；B4c（#87）已接上
`diary.saveEdit` / `diary.setCurrent` / `diary.merge`（能力清单里如实列出，口径见本节末的 B4c 补充）。

- **冻结输入的哈希覆盖什么**：`sourceSnapshotId` 指向一份不可变输入清单——相关日期与已授权上下文里的
  来源 ID、修订 ID、提取器版本、**已处理/未处理清单与原因**、时间范围、风格快照、`promptVersion` 与
  `generationOptions`，每份材料还带上冻结时的正文。`snapshot_hash` 是这份清单规范形（键有序、材料有序）
  的 sha256；**不含 provider/model**（执行者不是输入，换服务不该被当成换了内容）。材料一变哈希就变，
  去重自然失效，不会拿旧结果冒充新输入。「只取前几千字而隐藏遗漏」没有落脚点：材料要么在清单里，
  要么被明确标成未处理。
- **候选/当前**：契约第 3 节的「首次生成可成为 current」在这一片取**更窄**的边界——只有
  「这一天还没有当前版本、**而且一份用户自己写的版本都没有**」时，生成结果才成为当前；其余一律候选
  （`DiaryDay.currentVersionId` / `candidateVersionIds` 是唯一口径，不给 `DiaryVersion` 加状态字段）。
  生成路径**永远不会改写当前版本**；切换当前走 `diary.setCurrent`（B4c 已接，口径见本节末）。
- **去重与幂等**：同一条 `operationId` 重试返回原票据（`operation_receipts`），换了内容报
  `idempotency_conflict`；同一份 `(dayKey, snapshot_hash)` 在已有版本或还有活着的任务时**不重复产版本**，
  复用那条任务的 `jobId`。唯一例外是 `reason = regenerate`：用户明确要「再生成一版」时产新的候选版本
  （仍然按 `operationId` 幂等、仍然不覆盖当前）。
- **素材是数据，不是指令**：产品指令只出现在 system 消息里且每次逐字使用常量；材料只进 user 消息的
  **数据段**，边界标记在列首、材料正文逐行加前缀（材料里的同名标记伪造不出边界）。执行者只读这一天的
  快照、只调用一个服务，没有插件入口、不改资料、也不扩大发送范围。
- **长材料两步走**：材料超过直接输入上限（6000 字符）时先按批提炼**有来源的中间事实**再生成正文，
  步数如实记在 `generationInfo.generationOptions`（`steps` / `intermediateCalls` / `modelCalls`）；
  超过一次生成的分段上限时**如实失败**（`invalid_argument`），不截断冒充完整。
- **失败如实**：没配置/没验过 `generate_text` 时 `diary.generate` **照样返回票据**（输入已冻结），
  作业由 #66 的队列闸门停在 `waiting_configuration`（不消耗尝试次数、不发请求）；执行期 401/403 →
  `authentication_failed` + `waiting_configuration`；超时/断网/限流 → 按契约第 7 节有限重试
  （`retry_wait`）；端点/模型不符或响应解析不了、远端返回空正文、两次都是结构化输出 →
  `model_unavailable` + `failed`。**任何失败都不落版本**（不写空正文、不拿两步走的半截结果凑一篇）。
- **AI 正文不写成 user 来源**：生成正文只落 `diary_versions`（`origin = generated`，带
  `sourceSnapshotId` / `styleSnapshotId` / `generationInfo` / `provenanceLinks`），**不写**
  `captures.draft_text`、**不建** `source_revisions`（那两处的 `authorType` 只有 user/import）。

**`diary.*` 的编辑 / 指定当前 / 合并口径（B4c 补充，2026-10-16；不改字段与方法签名，也不升 apiVersion）。**
完整解释见 [`docs/architecture/m3-日记生成与版本.md`](../architecture/m3-日记生成与版本.md)。上面三行的
「输入」列是设计要点；按 1.2 节的修改并发与幂等规则，这三个写入都带 `expectedRevision`，
`diary.saveEdit` / `diary.merge` 另外带 `operationId`（`diary.setCurrent` 不产生任何东西，没有
`operationId`，见下）。

- **这一天的 `revision` 是持久、单调递增的状态推进计数**（#101 改准；B4c 原来按「版本数」实现，
  换当前版本不推进它，等于没有冲突保护）：落在 `diary_days.revision`（schema v10 → **v12**；
  与 B4e 的 v11 合并后本构建是 **v13**，回填成版本数），通过 `DiaryDay.revision`（2.5）读出来。新增一版（生成/编辑/合并）+1；`diary.setCurrent`
  **真的换了**当前版本也 +1（切到已经是当前的版本是无操作，不推进）；被拒绝的调用不推进。
  **调用方从 `diary.getDay.revision` 读、原样回传 `expectedRevision`**——不再从版本数推算
  （`candidateVersionIds.length + (currentVersionId == null ? 0 : 1)` 那个算法已经不对了）。
  `diary.currentChanged` 事件的 `revision` 带的是推进后的同一个值。
  **加性字段、方法签名不动，`apiVersion` 因此不升**（1.3 节：新增字段是次版本级变更）；但要把话说全：
  客户端不能再自己算 revision（老 UI 构建 + 新核心会算小、每次写都 `revision_conflict`——**失败是响亮的、
  不静默**，这是有意的取舍）。UI 与核心同版本发布，读 `getDay.revision`；要不要按「语义变更」升
  `apiVersion` 主版本，留给评审按 1.3 节的口径定。
- **`diary.saveEdit` 只新增、不原地改**：写一条 `origin = user_edit`、`parentVersionId = baseVersionId`
  的新版本，基版一个字节都不动；新版本**成为当前**（用户手写编辑就是「我要用这一版」），旧当前版退成
  候选、不删除、随时可取回原文。空正文是 `invalid_argument`；正文**不设长度上限**——契约没有给 `body`
  定上限，核心不截断用户的话。
- **`diary.setCurrent` 只认这一天自己的版本**：版本不存在 `not_found`，属于别的天 `invalid_argument`；
  旧当前版变候选、随时能切回来。它**没有 `operationId`**：不产生任何东西，重复调用收敛到同一个状态
  （切到已经是当前的版本是无操作，不重复发 `diary.currentChanged`）；换成另一个版本是**另一次合法操作**，
  不是幂等冲突。
- **`diary.merge` 的来源可追溯**：写一条 `origin = merge`、`parentVersionId = baseVersionId` 的新版本并
  成为当前；参与合并的全部版本 id 记在 `generationInfo.generationOptions.mergeSourceVersionIds`
  （另有 `mergeBaseVersionId` / `mergeCandidateVersionIds` / `mergedBy = user_confirmed` /
  `modelCalls = "0"`）——契约的 `DiaryVersion`（2.5）没有「由哪些版本合并而来」的字段，所以走这个
  已有的审计槽位。候选顺序没有语义（规范形按字典序）；候选为空 / 重复 / 含基版自己 / 跨天是
  `invalid_argument`，版本不存在是 `not_found`。核心不替用户合并、这一片也不调用模型：`body` 就是
  用户确认后的正文（「AI 辅助起草一份合并稿」是另一个入口，见 m3 文档的「需要拍板」）。
- **冲突与幂等**：`expectedRevision` 不符一律 `revision_conflict`，且**零改动**（校验在**写事务里**、
  与写同一个事务，事务回滚所以一个字节都不改，被拒的调用连回执都不留）。闸门放在事务里是必须的：
  在事务外先查再写会让两个窗口都通过检查、后一个静默覆盖前一个。`saveEdit` / `merge` 先查
  `operation_receipts` 再进事务校验 revision：同一条 `operationId` 重试返回**原版本**（哪怕 revision
  已经变了），换了正文 / 基版 / 候选 / `expectedRevision` 报 `idempotency_conflict`。
- **可见性**：默认视图是这一天的**当前版本**（`currentVersionId`）；旧版本只出现在 `candidateVersionIds`
  里，正文要按 id 取（`diary.getVersion` / `diary.listVersions`），任何时候都取得到原文。**检索**这一路
  沿用 B4b 的诚实退化：日记版本（含当前版）都没有进索引，所以默认看不见，带 `includeOldDiaryVersions`
  时核心给「日记历史版本还没有进索引（当前版本也没有）」的警告并指出按需读取的入口，且
  **不返回假命中**——「旧正文退出默认检索」在日记这一路是
  恒真的，不假装过滤器生效（日记正文要可检索是检索那一片的事）。

`search.upgrade` 的保证：

- **幂等**：重复调用（包括已经确认升不了级的情形）返回同一份快照，不重复计算；沿用 `search.start` 的 sessionId、queryRevision 与游标机制，不另造会话。
- **游标重置**：融合改变了顺序，升级后的 `cursor` 是融合结果第一页的游标，并递增**结果代次**；升级前发出的**所有**游标（含第一页那个与融合后第一页偏移相同的）再翻页都报 `cursor_expired`，而不是按新顺序返回一段对不上的结果。**幂等升级不递增代次**，所以升级后发出的游标继续可用。游标对外仍是不透明字符串，代次是核心的内部格式，不构成契约变更。
- **语义不可用时绝不假装**：没有可用模型、没有生效代次或没有可用块时不融合，阶段如实停在 keyword_ready，结果仍只有关键词那一路，并在 warnings 里说明「没有可融合的语义证据」；**不返回 hybrid_ready**。**生效代次与当前嵌入器口径不一致时同样不算有证据**：换了模型（`model_version`）或换过维度/存储格式（`dims` / `storage`）但还没重建索引时，语义这一路整路不作数——不融合、阶段停在 keyword_ready、warnings 说明原因与「重建索引即可恢复」；`mode = semantic` 时给空结果 + 同一条警告，不退化成关键词；关键词检索照常可用。
- **错误**：会话不存在或索引在会话期间变了报 `search_expired`；非 hybrid 会话要求升级报 `invalid_state`；已取消的会话返回 cancelled 快照、不融合（取消就是取消）。

**`indexes.rebuild` 的 `scope` 编码（v1）。** `scope` 是一个字符串，只有两种合法写法：

| 写法 | 含义 |
|---|---|
| `all` | 整库：重建全部派生内容片段与记录文字。与 `indexes.status` 不传来源范围同义 |
| `sources:<id>[,<id>]*` | 只重建这些来源：各自**当前修订**的派生片段，以及它们所属记录的记录文字 |

- 来源 id 是核心生成的**不透明字符串**（当前形如 `src_` + 32 位小写十六进制）。这个编码把 `,` 规定为分隔符，因此 id 记号只允许 `[A-Za-z0-9_]`；记号里出现其它字符（含空白）就是 `invalid_argument`。**不需要也不定义转义**——`all` 与来源列表是互斥的两种写法，来源列表内部只用这一个分隔符。
- **顺序没有语义**：重建是「按现状重刷」，与来源的处理顺序无关。解析时按 id 字典序排成规范形，所以 `sources:b,a` 与 `sources:a,b` 是同一次操作（同一个 `operationId` 命中同一条任务）。
- `sources:` 后面**至少要有一个 id**：空列表（`sources:`）与空记号（`sources:a,,b`）都是 `invalid_argument`。「要整库」必须写 `all`，不能靠空列表。这与 `indexes.status` 里「空数组是‘什么都不看’」刻意不同：重建一个空范围没有意义，明确报错好过静默排一条什么都不做的任务。
- **重复 id**（`sources:a,a`）也是 `invalid_argument`：scope 的规范形是集合，重复是调用方的错，静默去重会把它藏起来。
- 指定的来源必须**真实存在**，否则 `not_found`（不排一条注定失败的任务，与 `jobs.runDue` 的依赖闸门口径一致）。
- 任何不匹配上述写法的字符串（`ALL`、`all `、`sources`、`src_...`、空串……）都是 `invalid_argument`。

`indexes.rebuild` **只排一条 `index` 任务并返回它的 `jobId`**，不做同步重建：同步重建会阻塞界面，而队列的退避、补做与依赖闸门已经就绪（见 `docs/architecture/m4-任务调度与补做.md`）。同一个 `(scope, 原因, operationId)` 重复调用返回同一条任务（`operationId` 的通用幂等规则见 1.2 节；同一个 `operationId` 换了 scope 或原因报 `idempotency_conflict`）。整库任务（`all`）等队列里所有活着的提取收尾（`waiting_dependency` + `waiting_extract`）再按现状重刷，不会因为某条提取被取消而终态失败；指定来源的任务在其前置（提取）未满足时同样落在 `waiting_dependency`，原因写在 `errorCode` 上。**它只重建关键词这一路**（`index` 任务），不建语义索引。

**`indexes.rebuildSemantic`（语义索引重建，2026-10-12）。** 它排的是一条 `semantic_index` 任务，与 `indexes.rebuild` 是**两条独立的索引路**，区别在三处：

- **整库，没有 `scope`**：语义的代次与向量是全局的（一次重建总是把块表里所有块在新代次里补齐，范围只决定重算哪些块），所以任务总是整库。因此它的**幂等**不靠 scope 区分：任务业务键是 `(semantic_index, 空目标, 空快照)`，于是「队列里至多一条活着的语义重建」——界面连点几次、几处代码同时请求，队列里都只有一条；它跑完之后再请求才建新的一条（按现状增量重算：口径一致的向量整批复用）。同一个 `(原因, operationId)` 重复调用返回**同一条任务**（按 id 读它此刻的真实状态）；同一个 `operationId` 换了原因报 `idempotency_conflict`（契约 1.2 的通用规则）；
- **等模型配置**：前置是「模型就绪 + 提取收尾」。本地模型没配、或配了但不可用时，任务落在 `waiting_configuration` + `errorCode = waiting_model`，**不是失败**（不退避、不消耗 `attemptCount`——闸门在领取前挡下，没跑过就不计尝试），但**要用户动手**：`requiresUserAction = true`、`attentionKey = job-config:semantic_index:waiting_model`。它**不出现在 `nextWakeup` 里**：配置变化不是时间问题，下一次 `jobs.runDue`（前台/唤醒/改配置之后）的前置评估会把它拉起。提取还没收尾时它落 `waiting_dependency` + `waiting_extract`，与 `indexes.rebuild` 同一条规则；
- **可分段让出**：整库重建会远超一次唤醒的预算，所以它在**块与块之间**检查预算，到点就**回到 `queued`**（`nextAttemptAt` 清空＝立刻可再跑、进度写在 `Job.progress` 上、`attemptCount` **不因让出而增加**、`errorCode` 清空），下一轮接着算没算完的块。**让出不是失败、也不算「已完成」**：`jobs.runDue` 的 `succeeded` 只在整代切换之后才发；摘要里让出的任务计 `processed`、不计 `succeeded`/`failed`/`retrying`（见 2.7）。**代次切换仍然是原子的**（一个事务；半成品绝不被激活），让出也不会绕过「续跑前核对口径」——中途换过模型就整代废弃、按当前模型重算。

它是**加性方法**：不改变 `apiVersion`（契约 1.3）——调用方按能力清单里的 `indexes.rebuildSemantic` 判断能不能调，老实现者拿不到这一项、也不会走到它；不实现它的旧核心照样能被界面按能力清单安全地跳过。就绪与覆盖照旧由 `indexes.status` 报告（`semantic_index_ready` / `model_version` / `embedded_chunks` / `reasons`，包括「语义索引有一代在建」）。`indexes.rebuild(scope=all)` **不会**顺手建语义索引；反过来也一样。口径与理由见 `docs/architecture/m4-任务调度与补做.md` 的「语义索引任务化」。

Provider 凭据通过 PlatformHost 安全存储后得到 credentialRef，核心使用受控能力读取以发起请求。只有凭据输入页面短暂持有明文；核心与日志不长期保留明文。Mock 不应内置任何真实密钥。

**`providers.*` / `responses.*` 的落地口径（B4a 补充，2026-10-16；不改字段与方法签名，也不升 apiVersion）。** 完整解释见 `docs/architecture/m3-Provider-配置与能力.md`。

- **能力能不能用**由四件事共同决定，缺一不可：服务已启用、适配器实现了该能力、配置里声明了该能力、**没有测试结论或最近一次连接测试验过它**。「明确配置」（`declared`）与「通过验证」（`verified`）两条路都算数；一旦测过而没验过，就**不排任务**（与「不排注定终态失败的任务」同一口径）。连接测试的 `scope` 是用户授权的范围，只改这次真的探过的能力的结论。
- **`providers.test` 的失败分两种形态**：能力不成立（没实现 / 没声明）走**报告**（`results` 逐项 `failed`、`actualCallMade = false`、消息里写「未发起调用」）；可达性/认证/超时/响应解析这类走**错误码**（`authentication_failed` / `provider_timeout` / `model_unavailable` / `network_unavailable` / `rate_limited` / `quota_exceeded`），消息末尾写明「本次测试已发起 N 次真实请求（可能计费）」。报告里的 `actualCallMade` 只表示**是否真的发出了 HTTP 请求**。
- **`providers.save` 的密钥不进 DTO**：契约的 Provider 对象只有 `credentialRef`。桥接层的 `save_provider(config, secret)` 多一个明文参数（只在这一次调用里经过），核心写进密钥托管后只留引用。平台层凭据桥接到位后，这一路改成只传 `credentialRef`（过渡入口在 `packages/diary_bridge` 的 `BridgeDiaryApi.saveProviderCredential`，不是长期接口）。
- **`providerId` 点名却不存在**报 `not_found`；点名了但该服务承担不了所需能力报 `provider_not_configured`（消息里带可执行的下一步），**不创建任务**。
- **队列侧**：Provider 作业在**领取前**评估能力闸门，不满足时进 `waiting_configuration`（不是 `failed`、不排退避、不消耗 `attemptCount`——没跑过就不计尝试），并置 `requiresUserAction = true` + `attentionKey = job-config:<kind>:<errorCode>`（与「等模型配置」同一口径，见 2.7），配置改好后同一轮驱动即可继续。执行期才发现鉴权失败/模型不对时，同样落到 `waiting_configuration` + 同样的 `requiresUserAction` / `attentionKey`，**差别只是 `attemptCount` 如实记账**（真的跑过一次，领取时 +1 不回退），并把该服务的测试结论改成失败（避免每次唤醒都去撞）。
- **新增的错误码语义**（沿用第 7 节已有的码）：5xx 归 `network_unavailable`（材料还在、处理等远端恢复）；404、其它 4xx、3xx（不跟随重定向）与响应不可解析归 `model_unavailable`（检查端点/模型/适配器）。`provider_timeout` 是**有限**重试，且不承诺远端未计费。

**`settings.*` 的整理那一段 / 整理模板与自动整理（B4e 补充，2026-10-16；不改字段与方法签名，也不升 apiVersion）。**
完整解释见 [`docs/architecture/m4-整理与自动化.md`](../architecture/m4-整理与自动化.md)。
这一片把任务书 M4 的「自动整理」落到功能上：**整理模板**（三类核心内置规则）、
**开关与触发边界**、**「什么算待处理」的可判定判据**、**配额上限**与**候选产出**。

- **默认关是硬要求**：整理设置的 `enabled` 默认 `false`，迁移种下的那一行也是 0；没有用户显式
  开启，核心不会自动调用任何服务（测试用「一调用就 panic」的传输层钉住）。**开启与模板、
  上限都在「整理设置」这一份对象里**——它是契约 `settings.get / update` 里「整理」那一段的落地
  （桥接入口：`organizeSettings` / `updateOrganizeSettings`），但契约的完整设置对象还包含
  `diaryTimeZone` 等平台层字段，这一片**没有**实现完整对象，因此 `settings.get` 也**没有**进
  能力清单（能力清单只列真的接上的契约方法名，宁可少报）。将来完整设置对象落地时，整理这一段
  应当并进同一个 DTO——**在这里不新增契约字段**。
- **模板只进指令槽，参数只允许整数与布尔**：三类内置模板
  （`merge_by_theme` / `proofread` / `compress`）的规则是**产品常量**，拼进 system 消息；
  材料仍然只出现在数据段的逐行前缀里（#64 的口径）。参数（主题数、目标字数、几个开关）只有
  整数与布尔两种类型并带范围与默认值，**不接受自由文本**——参数没有地方可以承载
  「忽略上面的指令」。选中的模板、**生效参数**与**规则全文**冻结进输入快照
  （`promptVersion = b4e-1`），版本的 `generationInfo.generationOptions` 再记
  `organizeTemplateId` / `organizeTemplateParams` / `organizeRuleHash` / `organizeReason`，
  所以「这一版用了哪个模板、什么参数、哪一版规则」都答得出来。**规则全文进快照（#111）**：
  执行时用的是**冻结的那一份**，不按当前构建重新渲染——否则升级期间排队的任务会「用新规则、
  记旧哈希」，输出与审计对不上、重试也复现不了。快照里的 `rule_hash` 是这份文本的指纹，
  对不上（快照被改动）就按 `invalid_state` 明确失败；B4e 早期只有哈希的旧快照走
  「重渲染 + 必须与旧哈希一致」的兼容路径，不一致同样明确失败。
- **#88 的对接点**：模板对象的 `source` 是 `builtin` 或 `plugin`（插件模板另有 `pluginId`），
  解析只有一个入口。声明式插件模板已作为 `plugins.templates` 的独立列表落地；**还没有并进
  整理模板列表**（`organize.templates` 仍只有三个内置模板），未知模板 id 照旧报 `not_found`。
- **触发走作业系统，不新增调度**：驱动（`jobs.runDue`）每一轮开始时盘点「待处理」的日子，
  把它们冻结成快照并排成 `diary_generate`（`reason = scheduled`，优先级 `AutoOrganize`）；
  退避、补做、配置闸门、租约恢复、幂等全部复用既有机制。**「现在整理这一天」用设计好的
  `diary.generate(dayKey, reason = automatic)`**（共用场景 `edited-diary-then-new-material`
  写的就是这个），不新增方法。
- **「什么算待处理」是可判定的**（没有「AI 觉得该整理」）：①这一天有可读正文的材料；
  ②这一份输入（材料清单 + 模板 + 参数 + 提示词版本）**从来没有冻结过**
  （`diary_source_snapshots` 里没有 `(dayKey, snapshotHash)`——这一条同时覆盖「已产版本」
  「已排过任务」「还在队列里」）；③这一天还没有当前版本，或已经允许迟到材料补做；
  ④到了这一天的计划触发时刻（`autoOrganizeTime`，按当天材料的 UTC 偏移折算）。
  材料或模板一变哈希就变，待处理自然重新成立；材料没变，同一份输入永远不会被自动排第二次。
- **自动整理的结果一律候选**：`reason = scheduled / automatic` 时**不设当前版本**，
  连「这一天还是空的」也不例外（比契约第 3 节的「首次可成为 current」更窄一刀）；
  用户确认走 `diary.setCurrent` / `diary.merge`（#87）。生成路径永不改写当前版本。
- **配额上限有三层，超限如实停下**：单次材料条数/字数、单次与每日（滚动 24 小时）调用次数、
  失败率（样本 ≥3），另外还有核心既有的分段上限。**这些闸门只挡新请求**：按 1.2 节
  「先查已完成操作」的顺序，`diary.generate` 先查 `operation_receipts`，命中就返回原票据，
  配额预检在回执之后——配额用尽后重试一条已经受理过的请求，照样取回原 ticket（#111）。
  排期层超限 → 跳过或整轮停下，并在
  `organizeStatus` 里给出「哪一条上限 / 已经做了什么 / 下一步怎么办」；执行层超限 →
  `quota_exceeded`，任务进 `failed` + `requiresUserAction`（**不是** `waiting_configuration`：
  配置闸门会把在等配置的任务每一轮拉起来，对配额停下的任务等于每一轮偷偷再跑一次），
  **不落版本**。每次真的发出去的调用都记在调用账本里，配额与失败率只认这本账。
- **可恢复与幂等**：排期幂等靠「这份输入冻结过没有」；任务被杀后下次驱动回收补做
  （`recovered` 如实报），补做不重复产版本；计划的触发时刻写进 `job.nextAttemptAt`，
  驱动晚跑时如实计入 `backfilled`——**我们只说「补做」，不说「准时」**。
- **schema**：这一片的段号是 v11（`organize_settings`、`diary_model_calls`），**不回填**；
  从旧库升上来与新建库一样是**关的**。B4c（#101）的 `diary_days.revision` 是 v12，
  **合并后本构建是 v13**，迁移里 v11 → v12 两段都在。两段都带结构性守卫：
  v11 的表写成 `IF NOT EXISTS`、守卫是「版本号 < 11 **或**表不在」，所以只跑过 B4c 的库
  （`user_version` 已是 12、没有这两张表）也能在升级时被补上；v12 的列已经在就跳过、
  **不重复回填**。

**转写链的落地口径（#91 补充，2026-10-17；不改字段与方法签名，也不升 apiVersion）。** 完整解释见 `docs/architecture/m3-转写链.md`。

- **`transcribe` 作业**：`targetIds` 是**音频资产 id**（`recordings.finish` 最终化时在同一个事务里排出来）。执行者是本机 ONNX 引擎（`sherpa-onnx`），**不联网**；按 30 秒窗口分段转写，可恢复（重启从断点续跑）、幂等（同片段重放只有一份文本）。缺引擎/模型时任务停在 `waiting_configuration`（`errorCode = provider_not_configured`，不消耗 `attemptCount`），**不产出任何内容**。
- **结果落在哪里**：音频来源**当前修订**的**派生内容**（`sources.extractedContent` 返回的就是它）——`extractorId = local_transcription`、`segments[].locator.locatorType = audio` 且 `startMs` / `endMs` 是这段文字对应的音频区间。**原始录音那条修订一个字节都不动**（它仍然是 `authorType = user` 的原件），转写不是用户原话：要区分「谁产的/覆盖到什么程度」看 `extractorId` 与 `coverage`，不新增 `authorType` 取值。
- **检索**：转写文本在同一事务里进关键词索引，所以 `search.start(mode = keyword)` 立刻搜得到；命中的 `coverage` 如实反映覆盖程度（没跑完是 `partial`，整段没有识别出文字是 `metadata_only`），`locator` 带时间戳。语义分块也从这条派生内容取正文。
- **`jobs.get` / `jobs.list` 的 `progress`**：转写跑起来之后它是**真值**（已完成窗口 / 总窗口）；没有可靠进度时仍然为空（契约原话）。
- **`providers.save` 对本地引擎适配器**（`adapterId = sherpa_onnx`）：`model` 是**模型目录**（留空表示用随包/环境变量解析出的默认目录），`endpoint` 必须为空（配了会被拒绝，理由是「endpoint 是 HTTP 协议的事」），`credentialRef` 不适用。核心**自带**的本机引擎不是 `providers` 表里的一行，但 `providers.test` 可以用 id `builtin_local_asr` 测它；报告里写明「本次测试完成了 N 次本机推理，**没有发起任何网络请求**」。

## 5. PlatformHost 方法与所有权

| 系统能力 | 负责方 | 交接规则 |
|---|---|---|
| 权限查询/申请 | 前端平台层 | 返回 granted/denied/restricted；用户拒绝时其他记录方式继续可用 |
| start/pause/resume/stopRecording | 前端平台层 | 首个有效音频缓冲后发 recording；不能由按钮点击直接推定 |
| 录音状态订阅 | 前端平台层 | 含真实状态、已录时长、已持久化位置、输入设备变化 |
| 选择/拍摄/分享/粘贴/拖入 | 前端平台层 | 输出短期句柄，流式复制到 imports.prepare 提供的位置 |
| 播放及跳转 | 前端平台层 | 依据 core 提供的逻辑媒体与定位信息播放 |
| 视频音轨准备 | 前端平台层 | 按需将指定视频音轨导出到受控临时资产，保留时间映射；不支持的编码如实返回 |
| 凭据存储与读取 | 前端平台层，核心受控调用 | 使用系统能力；缺失或锁定时任务进入 waiting_configuration |
| 后台唤醒注册 | 前端平台层 | 向系统登记任务；唤醒后调用核心处理到期任务 |
| 平台生命周期 | 前端平台层 | 报告前后台、电源及内存压力，核心据此调整任务预算 |

M0 必须验证 Android 后台工作如何进入核心：可通过受控无界面运行入口，不能依赖某个页面对象存在。具体桥接路径在架构决定中固定。录音保存路径必须在无 Flutter UI 的情况下仍可工作。

初始化桥接时注册 PlatformHostBridge，暴露受控文件票据、凭据读取、媒体准备和系统状态等能力；测试以 FakePlatformHost 实现。调用不得经过 Widget，宿主不可用时返回明确错误或等待状态。录音状态与后台任务预算由宿主提供，核心不自行假定系统能力已获授权。

## 6. 事件与恢复

持久业务事件至少包含 eventId、sequence、type、entityId、revision、emittedAt。类型包括 capture.changed、asset.changed、diary.versionCreated、diary.currentChanged、job.changed、index.coverageChanged、plugin.changed。

前端从快照开始订阅，按 revision 去重。断线或进程恢复后先获取快照，再从可用游标补事件。事件游标过期返回 cursor_expired，前端重新读快照，不能无限等待遗漏事件。

事件表**有积压上限**：只保留最近 10000 条（清理在写入的同一个事务里做），因此游标不能无限期保留——早于保留窗口的游标就是 `cursor_expired`。游标**超前**（大于当前最大序号，例如库被恢复成更旧的备份）不报错、夹到当前最大序号：返回的 `next_sequence` 就是**真实最大序号**（`MAX(sequence)`），下一次调用从那里继续，不会把「未来序号」写回给调用方。**中间那段事件不会补发**——超前游标等价于「从当前末尾开始等」，要补状态就重读快照；调用方可以用「返回的 `next_sequence` 小于自己传的 `from_sequence`」识别这次被夹过。

搜索结果、音量波形和实时录音计时属于临时事件，不承诺历史回放。录音真实状态可由原生服务重新查询；搜索恢复时重新发起查询。高频波形不写数据库，不淹没业务事件队列。

## 7. 错误码与用户行为

| 错误码 | 用户界面行为 | 自动行为 |
|---|---|---|
| storage_full | 明确显示未保存/录音停止，提供空间信息 | 停止继续写入，保留已封闭片段 |
| permission_denied | 说明对应权限，保留文字等入口 | 不循环弹权限框 |
| revision_conflict | 展示当前版和用户待保存内容 | 不覆盖；用户内容保留在恢复草稿 |
| idempotency_conflict | 保留待保存输入，提示操作状态冲突 | 不复用旧结果覆盖不同输入 |
| not_found | 说明目标已不存在（例如已被清理），回到列表 | 不创建新记录，也不静默当作成功 |
| invalid_state | 说明当前状态不允许这个操作，显示真实状态 | 不改数据；提示刷新后重试 |
| invalid_argument | 说明哪一项输入不合法（例如 `indexes.rebuild` 的 `scope` 编码），保留用户输入 | 不改数据；原样报错，不自动重试 |
| asset_missing | 显示文件暂不可用与来源信息 | 不把无文件资产当作可播放 |
| integrity_failed | 说明这份材料没有完整保存，提供重试或取消入口 | 保留暂存文件；不创建资产，也不提前宣称已保存 |
| unsupported_format | 仍保留附件，注明仅文件信息可搜 | 不无限重试解析 |
| provider_not_configured / authentication_failed | 设置页和任务中心提示 | 等待配置，不频繁重试 |
| network_unavailable | 材料已保存，处理待联网 | 有退避地排队 |
| rate_limited / quota_exceeded | 提供简洁状态和手动处理入口 | 尊重 Retry-After；额度问题暂停 |
| provider_timeout | 显示本次整理未完成 | 有限重试；不承诺远端未计费 |
| model_unavailable | 关键词搜索仍可用，语义搜索状态可见 | 检查包及版本，恢复后补索引 |
| plugin_denied / plugin_budget_exceeded | 显示插件未完成，可停用 | 终止该调用，不连带中断记录 |
| incompatible_backup / corrupted_backup | 恢复失败原因清晰 | 不修改现有库 |
| search_expired / cursor_expired | 安静刷新当前范围 | 丢弃旧会话结果并重取 |

## 8. 删除、版本、备份与派生数据

回收站内容立即从默认搜索和后续 AI 输入中排除。恢复后重建必要索引。永久删除需要预览结果：原文件、提取内容、切片及向量一起清理；已存在的日记正文可能仍包含当时的信息，必须单独列出，让用户决定是否同时删除关联日记版本。

默认备份包含原件、原始文字版本、日记版本、风格、关系与必要元数据。索引和缓存可选，API 密钥、运行中会话、临时凭据不进入备份。首版基础备份是用户明确导出的普通归档包，界面明确标注含私人资料；不宣称已加密。加密备份可后续单独实现。

恢复先检验格式、版本、哈希、大小及安全路径，再导入新资料库；索引可后台重建。普通资料导出与可完整恢复的备份要有不同名称和入口。
