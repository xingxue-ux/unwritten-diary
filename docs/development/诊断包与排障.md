# M5 · 诊断包与排障

对应 issue **#89**。目标：排障时能拿到**版本、库统计、最近日志、索引状态**，
同时**可验证地不含用户正文与用户自定的名字**。

实现是一个工具脚本，不是 UI：

- [`tools/diagnostics/export_diagnostics.py`](../../tools/diagnostics/export_diagnostics.py)
- [`tools/diagnostics/test_no_user_content.py`](../../tools/diagnostics/test_no_user_content.py)（可执行的白名单/金丝雀断言）

> 为什么先做脚本：契约里还没有 `diagnostics.export` 方法；加桥接方法要改契约、codegen 与 Dart 适配层。
> 本文的脚本已经能覆盖发布/客服排障，接口化留给后续 issue。**本次没有新增桥接 API。**

## 1. 一条命令

```bash
python3 tools/diagnostics/export_diagnostics.py \
  --library "/path/to/unwritten_diary/library.sqlite" \
  --out diagnostics.zip
```

用 `--logs` 指定结构化日志（`wakeup-diagnostics.jsonl`）时取最后 **50** 条；不传则
`logs.entries` 为空。脚本不猜日志路径，避免把别的用户文件读进来。

```bash
# 指定日志与条数、输出 JSON（默认是 zip）
python3 tools/diagnostics/export_diagnostics.py \
  --library ... \
  --logs .../wakeup-diagnostics.jsonl \
  --limit 100 \
  --out diagnostics.json

# 覆盖已存在的输出（默认拒绝覆盖）
... --force

# 内置金丝雀自检（不读用户库）
python3 tools/diagnostics/export_diagnostics.py --self-test
```

退出码：`0` 成功；`2` 参数/库不存在/输出已存在；`1` 读取或导出失败。

| `diagnostics.json` | 全部元数据（见下） |

| `README.txt` | 固定说明：只含元数据 |

字段细节：

- **版本**：从 `apps/diary_app/pubspec.yaml` 读 `version: 0.1.0+1`；工具不依赖 Flutter 运行时。
- **库统计**：只做 `COUNT(*)`/`SUM(byte_size)`/`GROUP BY state`，不 `SELECT` 任何正文列。
- **索引状态**：关键词覆盖、语义代次/块数/向量数，以及 `modelVersionMatchesExpected` /
  `chunkerVersionMatchesExpected` 两个布尔（不导出模型/chunker 版本原文——见 3.2）。它是**聚合近似**，
  与 `core.index_status` 的口径差异写在 `index.notes` 里（例如已退役来源、非 ASCII 空白）。
- **日志**：只保留白名单键；`error` 只接受**精确白名单**里的机器码（不是“像机器码”的格式校验），
  时间戳必须像 ISO；`trigger` 只接受应用里固定的几个值；未知键、自由文本、非 JSON 行全部丢弃/计数。
  **不导出日志原文。**
- **文件名**：库文件名固定为 `<hidden>`，只保留**允许列表内的扩展名**；日志来源只保留
  `{present, extension}`。诊断包里不出现任何用户自定的名字（日记标题、文件名、目录名）。
- **不含数据库文件本身**，也不含 `blobs/` 字节；
- **zip 成员时间戳固定**为 `1980-01-01 00:00:00`（`ZIP_MEMBER_DATE_TIME`）。Python 的
  `zipfile` 默认写本地时间：成员时间减掉 `generatedAt` 就能反推用户时区，同数据两次导出
  哈希也不同。现在时间戳与 mode（`0600`）都是常量。

## 3. 怎么保证不含正文与隐私

四层，最后一层是可执行断言：

### 3.1 不查询正文列

导出器只用聚合 SQL。明确排除：

- `captures.draft_text`（草稿/记录正文）
- `source_revisions.text`（原件文字）
- `extracted_contents` / `extracted_segments` 的正文
- `diary_versions.body`（日记正文）
- `text_chunks.text`（检索块正文）
- `assets.original_name`（用户文件名）
- `blobs` 的字节与 `object_ref`
- 日志原文与未知字段

`privacy.excludedColumns` 会把这份清单写进包，方便复查。

### 3.2 错误码：精确白名单，不是格式校验

`error`（日志）与 `jobs.error_code`（库）只保留**精确匹配白名单**的值；其余一律写成
`<redacted>`。白名单从权威来源维护，不写“看起来像机器码”的正则：

| 来源 | 码 | 覆盖范围 |
|---|---|---|
| [`crates/diary_core/src/error.rs`](../../crates/diary_core/src/error.rs) 的 `ErrorCode::wire()` | 契约 §7 的错误码（21 个，如 `invalid_argument`、`storage_full`） | 用户可感知的错误、任务失败码 |
| [`crates/diary_core/src/jobs.rs`](../../crates/diary_core/src/jobs.rs) | `no_handler`、`interrupted`、`no_target`、`dependency_extract_unmet`、`waiting_extract`、`waiting_transcribe`、`waiting_model` | 任务队列专用码（含“在等哪一环”） |
| [`packages/diary_api/lib/src/values.dart`](../../packages/diary_api/lib/src/values.dart) 的 `DiaryErrorCode` | `plugin_denied`、`plugin_budget_exceeded`、`unknown` | 只在 Dart API 包里存在的码；`DiaryException.code.wire` 可能取到 |
| [`apps/diary_app/lib/src/core_wakeup.dart`](../../apps/diary_app/lib/src/core_wakeup.dart) | `installed_core_missing_job_capabilities`、`unclassified_error` | 日志专用码；前者是能力缺失，后者是「不是 DiaryException/PlatformException」的固定字面量。**Dart 运行时类型名不是机器码，仍会脱敏** |
| [`apps/ohos-diary-core/entry/src/main/cpp/napi_shim.cpp`](../../apps/ohos-diary-core/entry/src/main/cpp/napi_shim.cpp) | `ERR_DIARY_LIB/ARGS/HANDLE/OPEN/CLOSE/CALL` | NAPI 宿主码；`PlatformException.code` 就是它 |

**状态列也走同一套白名单。** `captures.state` / `jobs.state` 在 schema 里只是
`TEXT NOT NULL`（没有 `CHECK`），把任意字符串写进去，`GROUP BY state` 就会原样进包。
导出器只保留 `model.rs` 里 `CaptureState::wire()` / `JobState::wire()` 的值，其余合并成
`<redacted>`，并用漂移测试从 `model.rs` 反解这两个集合。

**版本列只导出布尔。** `chunk_vectors.model_version` 与 `text_chunks.chunker_version`
同样是可写的 TEXT 列；实测 canary 能原样进包。现在只导出
`modelVersionMatchesExpected` / `chunkerVersionMatchesExpected`，与脚本里的
`EXPECTED_MODEL_ID` / `EXPECTED_CHUNKER` 比较后给布尔；原文永不离开导出器。

为什么不用正则：`password123`、`secret42`、`mytoken1` 都满足“短小写字母数字”的形状。
**格式校验只能证明形状，不能证明内容是一个错误码**。诊断包是要发给别人排障的，
所以未知值必须无差别脱敏，而不是“看起来像就放行”。

防漂移：导出器里维护带来源注释的常量表（`ERROR_CODE_WHITELIST` /
`JOB_ONLY_ERROR_CODES` / `LOG_ONLY_ERROR_CODES`），测试再从源码反解：

- `test_error_code_whitelist_matches_error_rs`：解析 `error.rs` 的 `wire()` 分支，
  断言诊断白名单与 `ErrorCode` 集合**完全一致**；新增契约错误码而忘了更新白名单，测试就会红；
- `test_job_only_whitelist_is_sourced_from_jobs_rs`：断言每个任务专用码仍出现在 `jobs.rs`；
- `test_state_whitelists_match_model_rs`：从 `model.rs` 反解 `CaptureState` / `JobState`
  的 `wire()`，断言状态白名单与代码完全一致；
- `test_app_only_log_codes_match_dart_enum` / `test_napi_error_codes_are_sourced_from_shim`：
  断言 Dart-only 码仍在 `values.dart` 的 `DiaryErrorCode` 里、NAPI 码仍在 shim 里；
- `test_log_codes_and_triggers_are_sourced_from_the_app`：断言日志专用码与
  `trigger` 取值仍出现在 `core_wakeup.dart`。

`trigger` 同样是固定词表（`startup` / `foreground-schedule` / `wake`），不在词表里的值直接丢弃。
日志里未知的 `error` 保留 `<redacted>` 占位（让人看得出“这里原来有错误”，但不透露内容）。

> **如果将来要保留更多信息，必须走白名单，而不是放宽格式校验。** 先改权威来源
> （契约/枚举/任务码），再更新这里的白名单与漂移测试；不要临时加一条“允许更长的字符串”
> 之类的正则。

### 3.3 用户文件名一律不出现

目标：**诊断包里不出现任何用户自定的名字**（日记标题、文件名、目录名）。

- **库文件名**：`library.fileName` 固定为 `<hidden>`，另给 `library.extension`；
- **扩展名也要白名单**：只有 `SAFE_EXTENSIONS` 里的容器/格式后缀才会保留（如 `sqlite`、
  `diarybak`、`jsonl`、`pdf`）。没有后缀 → `<none>`；不在白名单 → `<unknown>`。
  这样 `report.password123` 不会把 `password123` 当扩展名带出去；
- **日志来源**：`logs.source` 改成 `{ "present": true/false, "extension": "jsonl" | null }`，
  原路径与文件名都不导出；
- `assets.original_name` 从不查询（见 3.1）；
- `quick_check` 失败时的错误文本经 `safe_error` 处理，库路径与文件名替换成 `<library>`。

### 3.4 日志白名单

只允许这些键：

```
observedAt, trigger, error,
processed, succeeded, failed, retrying, backfilled, recovered,
dueBacklog, waitingDependency, dependencyFailed, nextWakeup,
expectedAt, completedAt
```

- `error` 只保留**精确白名单**里的机器码（见 3.2），否则写成 `<redacted>`；
- `expectedAt` / `completedAt` 是 app 每次唤醒都会写的两个时间戳（以前被静默丢弃，
  导致「这次唤醒是不是按预期时间跑的」查不了）；和 `observedAt` 一样只接受 ISO 形状；
- `trigger` 只允许固定词表（见 3.2）；
- 其它字符串一律丢弃；
- 非 JSON 行计入 `malformedLines`，不进入 `entries`；
- 日志文件路径/文件名只以 `{present, extension}` 形式出现。

这能挡住“日志里顺手打了用户正文/路径/服务商响应”的常见事故；它不是对任意日志内容的
语义分类器，所以**不要在新日志里记录正文**，这条纪律仍然成立。

### 3.5 金丝雀测试

```bash
python3 tools/diagnostics/test_no_user_content.py
# 或
python3 tools/diagnostics/export_diagnostics.py --self-test
```

测试会：

1. 在 `build/` 下建一个临时库（不使用 `/tmp`）；
2. 往 `draft_text`、`source_revisions.text`、`diary_versions.body`、`text_chunks.text`、
   `assets.original_name`、blob 文件、日志未知字段/自由文本/非 JSON 行、`jobs.error_code`
   分别塞入不同的 `CANARY_*` 字符串；
3. **新增入口**：把 canary 塞进 `captures.state`、`jobs.state`、
   `chunk_vectors.model_version`、`text_chunks.chunker_version`，并断言状态归入
   `<redacted>`、版本只以 `matchesExpected=false` 出现；
4. **短单词敏感内容**：把 `password123`、`secret42`、`mytoken1` 塞进 `jobs.error_code`、
   日志 `error` 与日志 `trigger`——它们形状完全像机器码，必须全部变成 `<redacted>`/被丢弃；
5. **中文文件名**：临时库命名为 `体检报告-password123.sqlite`、日志命名为
   `体检报告-secret42.jsonl`，并在 `assets.original_name` 里放
   `体检报告-mytoken1-....pdf`；导出后这些名字与中文都不能出现；
6. 用真实 CLI 导出 zip 与 json；
7. **逐字节**搜索 zip 内所有条目名与内容、以及 json 文件，断言没有任一 canary、
   短敏感词、中文名或完整文件名；
8. **正向断言**：真错误码 `invalid_argument`（库与日志）与 `no_handler` 仍然正常出现，
   不能把有用的排障信息一起“红”掉；`<redacted>` 的计数也如实断言；
9. 断言 `containsUserContent=false`、manifest 哈希正确、`library.fileName="<hidden>"`、
   `logs.source={present,extension}`、日志只剩白名单键、漂移测试通过；
10. 另跑一条**未知后缀**端到端用例：库名 `体检报告-mytoken1.numbers`，断言只报
   `<unknown>`，后缀与名字都不出现（防止敏感串藏在扩展名里）。

11. **确定性**：同一份 payload 在 `TZ=Pacific/Kiritimati`（UTC+14）下再导一次，
    断言两次 zip 的 sha256 相同；并断言每个成员的 `date_time` 都是固定的
    `(1980,1,1,0,0,0)`、mode 是 `0600`——zip 时间戳不再带本地时区，
    同数据两次导出字节一致。

本次执行结果：**15/15 通过**（见第 6 节）。

## 4. 各平台怎么取库

| 平台 | 路径/方式 | 注意 |
|---|---|---|
| Windows | `%APPDATA%\Lingxing\不写日记\unwritten_diary\library.sqlite`（2026-10-19 起；旧构建是 `%APPDATA%\com.example\不写日记\`） | 先退出应用；用副本，不要对唯一库跑 |
| Android（debug） | `adb shell run-as <applicationId> cat files/unwritten_diary/library.sqlite > library.sqlite` | 仅 debuggable 包可用；不要在设备上直接改库 |
| Android（release） | 让用户做一次“完整备份”，把 `.diarybak` 取回，解压出 `db/library.sqlite`；或后续加应用内导出 | 诊断包不需要原件；备份里不要上传给第三方 |

**不要把用户的完整库/备份直接发到公开 issue**；诊断包才是可分享的最小集。
即使诊断包不含正文，计数、日志时间、错误码仍可能透露使用习惯，按隐私材料处理。

## 5. 与 `diagnostics.export` 的关系

issue 允许“实现 `diagnostics.export` 或在 `tools/` 加脚本”。本次选择脚本：

- 不改契约、不跑 codegen、不把排障代码塞进产品二进制；
- 发布/客服可以在拿到备份或开发机库后离线导出；
- 未来若要在应用内一键导出，应把同样的**白名单函数**抽到 Rust 核心，桥接只负责选路径与写 zip，
  并复用本测试的 canary 用例；不要另写一套“大概不含正文”的实现。

局限：

- 日志只解析 `wakeup-diagnostics.jsonl` 这一种结构化格式；其他自由文本日志不会进入包；
- 错误码白名单覆盖的是**当前** `ErrorCode` / 任务码 / 日志码。新增码必须同时更新常量表，
  漂移测试会提醒，但它不能自动生成代码——这是“显式白名单”的代价，也是它的保障；
- 扩展名白名单会丢掉未知后缀（报 `<unknown>`），这是有意的：宁可少一条信息，也不透传用户名字；
- 索引覆盖是聚合近似，不是 `core.index_status` 的逐字段镜像；
- `schema`/`tokenizer`/`chunker` 的期望常量在脚本里；升级 schema 时要同步改，否则会报
  `schemaMatches=false`（这是有意的提示，不是静默通过）。
