# M5 · 诊断包与排障

对应 issue **#89**。目标：排障时能拿到**版本、库统计、最近日志、索引状态**，
同时**可验证地不含用户正文**。

实现是一个工具脚本，不是 UI：

- [`tools/diagnostics/export_diagnostics.py`](../../tools/diagnostics/export_diagnostics.py)
- [`tools/diagnostics/test_no_user_content.py`](../../tools/diagnostics/test_no_user_content.py)（可执行的白名单/金丝雀断言）

> 为什么先做脚本：契约里还没有 `diagnostics.export` 方法；加桥接方法要改契约、codegen 与 Dart 适配层。
> 本文的脚本已经能覆盖发布/客服排障，接口化留给后续 issue。**本次没有新增桥接 API。**

## 1. 一条命令

```bash
python3 tools/diagnostics/export_diagnostics.py \
  --library "/path/to/unwritten_diary/library.sqlite" \
  --out diagnostics.zip
```

默认读取同目录的 `wakeup-diagnostics.jsonl`，取最后 **50** 条结构化日志。
没有日志文件也能导出，只是 `logs.entries` 为空。

```bash
# 指定日志与条数、输出 JSON（默认是 zip）
python3 tools/diagnostics/export_diagnostics.py \
  --library ... \
  --logs .../wakeup-diagnostics.jsonl \
  --limit 100 \
  --out diagnostics.json

# 覆盖已存在的输出（默认拒绝覆盖）
... --force

# 内置金丝雀自检（不读用户库）
python3 tools/diagnostics/export_diagnostics.py --self-test
```

退出码：`0` 成功；`2` 参数/库不存在/输出已存在；`1` 读取或导出失败。

## 2. 包里有什么

`diagnostics.zip` 固定三个条目：

| 条目 | 内容 |
|---|---|
| `diagnostics.json` | 全部元数据（见下） |
| `manifest.json` | 格式版本、`containsUserContent: false`、`diagnostics.json` 的 sha256 与字节数 |
| `README.txt` | 固定说明：只含元数据 |

`diagnostics.json` 顶层：

```json
{
  "format": "unwritten-diary-diagnostics",
  "formatVersion": 1,

```

字段细节：

- **版本**：从 `apps/diary_app/pubspec.yaml` 读 `version: 0.1.0+1`；工具不依赖 Flutter 运行时。
- **库统计**：只做 `COUNT(*)`/`SUM(byte_size)`/`GROUP BY state`，不 `SELECT` 任何正文列。
- **索引状态**：关键词覆盖、语义代次/块数/向量数/模型版本、chunker 版本。它是**聚合近似**，
  与 `core.index_status` 的口径差异写在 `index.notes` 里（例如已退役来源、非 ASCII 空白）。
- **日志**：只保留白名单键；只接受机器码形态的 `error`；时间戳必须像 ISO；未知键、
  自由文本、非 JSON 行全部丢弃/计数。**不导出日志原文。**
- **不含数据库文件本身**，也不含 `blobs/` 字节。

## 3. 怎么保证不含正文

三层，且第三层是可执行断言：

### 3.1 不查询正文列

导出器只用聚合 SQL。明确排除：

- `captures.draft_text`（草稿/记录正文）
- `source_revisions.text`（原件文字）
- `extracted_contents` / `extracted_segments` 的正文
- `diary_versions.body`（日记正文）
- `text_chunks.text`（检索块正文）
- `assets.original_name`（用户文件名）
- `blobs` 的字节与 `object_ref`
- 日志原文与未知字段

`privacy.excludedColumns` 会把这份清单写进包，方便复查。

### 3.2 日志白名单

只允许：

```
observedAt, trigger, error,
processed, succeeded, failed, retrying, backfilled, recovered,
dueBacklog, waitingDependency, dependencyFailed, nextWakeup
```

- `error` 只保留匹配 `^[a-z0-9_.:-]{1,120}$` 的机器码；否则写成 `<redacted>`；
- `trigger` 只允许小写蛇形 token；
- 其它字符串一律丢弃；
- 非 JSON 行计入 `malformedLines`，不进入 `entries`。

这能挡住“日志里顺手打了用户正文/路径/服务商响应”的常见事故；它不是对任意日志内容的
语义分类器，所以**不要在新日志里记录正文**，这条纪律仍然成立。

### 3.3 金丝雀测试

```bash
python3 tools/diagnostics/test_no_user_content.py
# 或
python3 tools/diagnostics/export_diagnostics.py --self-test
```

测试会：

1. 在 `build/` 下建一个临时库；
2. 往 `draft_text`、`source_revisions.text`、`diary_versions.body`、`text_chunks.text`、
   `assets.original_name`、blob 文件、日志未知字段/自由文本/非 JSON 行、`jobs.error_code`
   分别塞入不同的 `CANARY_*` 字符串；
3. 用真实 CLI 导出 zip 与 json；
4. **逐字节**搜索 zip 内所有条目与 json 文件，断言没有任一 canary；
5. 断言 `containsUserContent=false`、manifest 哈希正确、日志只剩白名单键、
   自由文本 `error` 变成 `<redacted>`、`jobs.error_code` 的任意文本被归入 `<redacted>`。

本次执行结果：**4/4 通过**（见第 6 节）。

## 4. 各平台怎么取库

| 平台 | 路径/方式 | 注意 |
|---|---|---|
| Windows | `%APPDATA%\<CompanyName>\<ProductName>\unwritten_diary\library.sqlite`；当前元数据预期是 `com.example\不写日记` | 先退出应用；用副本，不要对唯一库跑 |
| Android（debug） | `adb shell run-as <applicationId> cat files/unwritten_diary/library.sqlite > library.sqlite` | 仅 debuggable 包可用；不要在设备上直接改库 |
| Android（release） | 让用户做一次“完整备份”，把 `.diarybak` 取回，解压出 `db/library.sqlite`；或后续加应用内导出 | 诊断包不需要原件；备份里不要上传给第三方 |
| 鸿蒙 | 产品工程未落地；探针的 `filesDir` 路径见 m6 | 未验证 |
| 已拿到 `.diarybak` | 解压后把 `db/library.sqlite` 传给 `--library` | zip 里的快照是 `VACUUM INTO` 产物，不含 WAL，读取安全 |

**不要把用户的完整库/备份直接发到公开 issue**；诊断包才是可分享的最小集。
即使诊断包不含正文，计数、日志时间、错误码仍可能透露使用习惯，按隐私材料处理。

## 5. 与 `diagnostics.export` 的关系

issue 允许“实现 `diagnostics.export` 或在 `tools/` 加脚本”。本次选择脚本：

- 不改契约、不跑 codegen、不把排障代码塞进产品二进制；
- 发布/客服可以在拿到备份或开发机库后离线导出；
- 未来若要在应用内一键导出，应把同样的**白名单函数**抽到 Rust 核心，桥接只负责选路径与写 zip，
  并复用本测试的 canary 用例；不要另写一套“大概不含正文”的实现。

局限：

- 日志只解析 `wakeup-diagnostics.jsonl` 这一种结构化格式；其他自由文本日志不会进入包；
- 索引覆盖是聚合近似，不是 `core.index_status` 的逐字段镜像；
- `schema`/`tokenizer`/`chunker` 的期望常量在脚本里；升级 schema 时要同步改，否则会报
  `schemaMatches=false`（这是有意的提示，不是静默通过）。
