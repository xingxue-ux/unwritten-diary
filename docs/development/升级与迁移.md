# M5 · 升级、迁移与崩溃恢复

对应 issue **#89**。本文回答四件事：

1. 当前 schema 是 **18**，从 v1 到 v18 每一级改了什么；
2. 怎么用**真旧库回放**验证逐级迁移，而不是只跑手工改版本号的合成测试；
3. 数据目录位置变了怎么迁移（含 Windows 上最容易踩的“改公司名/产品名就换了目录”）；
4. 断电/崩溃/迁移失败时，WAL、备份与恢复各自负责什么。

配套脚本与测试：

- [`tools/migration/replay_old_library.sh`](../../tools/migration/replay_old_library.sh)
- [`crates/diary_core/tests/migration_replay_test.rs`](../../crates/diary_core/tests/migration_replay_test.rs)
- 备份实现见 [`m5-备份与恢复.md`](../architecture/m5-备份与恢复.md)

> 本文的“实测”指仓库已有证据或本次跑过的命令；“未验证”会明确写出来。
> **真旧库样本只有 v15 一份**（`crates/diary_core/tests/fixtures/v15-library/`，v15 构建真实写出、含未检查点 WAL）；它在每次 `cargo test` 里都会走一遍 v15 → 18。v8 / v10 / v12 等更早的真库仍需在发布前按第 3 节演练。

## 1. 当前状态

| 项 | 值 | 依据 |
|---|---|---|
| `SCHEMA_VERSION` | **18** | [`crates/diary_core/src/schema.rs`](../../crates/diary_core/src/schema.rs) |
| 记录方式 | `PRAGMA user_version` + `schema_migrations(version, applied_at)` | 同上 |
| 事务 | 所有 DDL/DML 在一个 `conn.transaction()` 里；失败整体回退 | `migrate()` |
| 高版本库 | `current > SCHEMA_VERSION` 直接拒绝打开，不写入 | `migrate()` |
| WAL / 同步 | `journal_mode=WAL`、`synchronous=FULL`、`foreign_keys=ON`、`busy_timeout=5s` | `Core::prepare` |
| 打开时恢复 | `assets::recover_on_open` / `recordings::recover_on_open` 把未完成操作如实标记，不假装成功 | `Core::prepare` |
| 备份格式 | 单文件 zip：`manifest.json` + `db/library.sqlite` + `blobs/...` | m5 文档 |

`schema_migrations` **只记录本次打开后落到的最终版本**，不是每一级一行；不要用它证明“逐级跑过”，
逐级证据要看迁移代码里的 `if current < N` 顺序与回放日志。

| 16 | `captures.trashed_from_state`（回收站，B7） | **不回填**：升级前没有回收站入口，老库里这一列只可能是 NULL | 恢复时 NULL 按 `committed` 兜底（无法得知原状态时的保守选择）；新列之后由 `trash` 写入 `draft` / `committed` |
| 17 | `styles` 表 + 默认风格行（风格线 #159） | 建表；种一行 `sty_default` 的空偏好版本 | 跳过 17 会让老库永远缺表；默认行让不点名风格的生成有真实快照可指 |
| 18 | `settings`（完整设置对象，#108） | 建表；把 v11 `organize_settings` 行**原值**搬进来（含 revision / updatedAt），**校验搬完行数**后删旧表；种默认行（`enabled = 0`） | 整理设置与完整设置从此是同一行；`diary_time_zone` 默认 `UTC`，平台层首次启动显式写设备时区 |

> **合入顺序是死的：16 → 17 → 18。** #166（v17）必须先合，本 PR（v18）后合。若顺序颠倒，
> 先合入库到 18、后合的构建只认 17，安装后 `current > SCHEMA_VERSION` 会直接拒绝打开用户
> 正常的库——那时 #166 必须重编号到 18 并改所有断言，不能只改常量。
>
> v14→v15 升级后的**首次启动**会为既有 `chunk_vectors` 建覆盖索引 `idx_chunk_vectors_caliber`，大库会有一次性开销（**未实测具体耗时**）。`user_version` 是最新版本（18）也不代表索引一定在：索引缺失（手工删过、补建失败）时每次 `open` 做一次 `sqlite_master` 轻量检查并补建。
> v17→v18 搬行**不回填** `diary_time_zone` / `default_style_id`：核心不知道设备时区，也不替用户猜风格。这两格在升级后分别是 `UTC` 与 NULL，平台层首次 `settings.update` 写入时区。
> v16 / v17 / v18 三段在本分支**同时存在**：版本号必须单调，跳过中间段等于那段迁移永远丢失。三段的守卫都是结构判定（`column_exists` / `table_exists` / `index_exists`），三条线谁先合入都不会重复执行；后合入的一方在合并时删掉重复段即可。
> `user_version` 是 18 不代表结构一定齐：`migrate` 在「版本已最新」分支与迁移末尾都会跑一次 `ensure_v16_v17_v18_structure`，缺列 / 缺表 / 缺 `idx_styles_current` 就补回来（与 v15 的覆盖索引补齐同一思路）。v18 删旧表前会数行数：`organize_settings` 有行而 `settings` 没搬到就报错回滚，**不静默 DROP**。

### 2.1 为什么 11/12 的守卫不只看版本号

两条分支可能写出四种库：

- `10`：两段都没有；
- `11`：有 v11 两张表、没有 `revision` 列；
- `12` 但没有 v11 表：只跑过 B4c 分支；
- `12` 且都有：合并后正常。

所以 `migrate()` 的守卫是：

```rust
if current < 11 || !table_exists(&tx, "organize_settings")? { ... }
if current < 12 || !column_exists(&tx, "diary_days", "revision")? { ... }
// v15：列与索引各自守卫。列看「版本号 + 结构」，索引每次 open 独立补（幂等）
if current < 15 && !column_exists(&tx, "index_meta", "auto_rebuild_marker")? { ... }
// 不论 current 是多少、列在不在：索引不在就建（见 ensure_v15_caliber_index）

// v16 / v17 / v18 三段一起带上：版本号单调，跳过中间段等于那段迁移永远丢失。
// 全部是**纯结构判定**（不看 current）：缺就补，已在就跳过，幂等、与起始版本无关。
if !column_exists(&tx, "captures", "trashed_from_state")? { ... }
if !table_exists(&tx, "styles")? { ... }
if !table_exists(&tx, "settings")? {
    // 建 settings → 搬 organize_settings 原值 → 数行数（不符就报错回滚）→ 删旧表 → 种默认行
}
// 版本号已是 18 但结构不全（中间构建 / 手工删表删索引）：ensure_v16_v17_v18_structure 补齐
// （含 idx_styles_current：表在不能证明索引在）
```

这些段都是幂等的：v11 的建表是 `IF NOT EXISTS`、种子是 `INSERT OR IGNORE`；v12 列已在就整段跳过，
**不重复回填**（否则会把已经推进过的 revision 改小，反而丢掉冲突保护）；v18 的新表已在就整段跳过
（否则重试会用旧行的值盖掉用户后来改过的设置）。

**v16 为什么不能写 `current < 16 && !column_exists(...)`**：一个 `user_version` 已经是 16、
却缺这一列的库（手工改过版本号，或旧构建在「版本号先写、DDL 没落」的窗口里崩过）会同时
满足 `current < 16 == false`，于是整段被跳过、版本停在 16、列**永远不补**。这与 #159 复审
指出的同一类守卫缺陷一致。所以：

- `migrate()` 的「版本已最新」早退分支也做一次结构检查，列在才真的返回；
- v16 段只问 `column_exists`，列不在就补；
- 修复路径最后写 `schema_migrations` 用 `INSERT OR IGNORE`，重复 open 不会因主键冲突回滚。

这样「自称 16 但缺列」的库下次 `open` 就修好，且版本号不会因为修复而改变；正常升级路径的
行为（只加列、不回填、不动旧数据）一个字都不变。

## 3. 真旧库回放：怎么做

### 3.1 准备

- 从**上一版真实安装**里取资料库目录，或从用户备份恢复出一份；
- **先关闭应用**（不要对着正在写的库跑）；
- 如果只有 `.diarybak`，先用上一版应用恢复到新目录，再拿恢复出来的 `library.sqlite`；
- 把样本放在只读/受控位置，记录来源版本、构建号、样本 sha256。

### 3.2 一条命令

```bash
tools/migration/replay_old_library.sh \
  --source /path/to/old-install/unwritten_diary \
  --with-blobs
```

脚本做的事：

1. 用 SQLite `.backup` 取**一致快照**（包含已提交的 WAL；普通 `cp library.sqlite` 会漏数据）；
2. 记录源库与 `-wal` 的 sha256、源 schema、`quick_check`；
3. 把快照放进 `build/migration-replay/<timestamp>/`（**不会写源库**）；
4. 跑 `migration_replay_test`，用当前 `Core::open` 走全部逐级迁移；
5. 断言最终 `schema=18`、`quick_check=ok`、`foreign_key_check` 为空；
6. 对比迁移前后的 `captures/source_items/assets/blobs/diary_versions/diary_days/...` 行数；
7. 再算源库与 `-wal` 的哈希，必须与步骤 2 完全一致。

只看拷贝与前置、不跑迁移：

```bash
tools/migration/replay_old_library.sh --source ... --dry-run
```

直接跑测试（脚本已经替你设置环境变量；不要手工指向唯一副本）：

```bash
DIARY_REPLAY_LIBRARY=/safe/copy/library.sqlite \
  cargo test -p diary_core --test migration_replay_test -- --ignored --nocapture
```

### 3.3 通过标准

- 源库 DB 与 `-wal` 哈希**逐位未变**；
- 迁移后 `user_version = 18`；
- `quick_check = ok`，`foreign_key_check` 为空；
- 业务行数逐表一致（旧库没有的表显示 `n/a`）；
- 记录文字仍能搜到（v7 回填路径）：抽 3 条旧记录的关键词做检索；
- 自动整理仍默认关（v11 种子）；
- 日记版本数、当前指针、`revision` 与升级前一致（v12 回填）；
- 索引覆盖状态可解释：关键词索引可以是 `partial`（派生索引可重建），但**不能把用户正文报丢**。

### 3.4 本次没验到的

- **真旧库样本只有 v15**：仓库里有 `v15-library` fixture（v15 构建写出、含未检查点 WAL，见 `crates/diary_core/tests/fixtures/v15-library/README.md`），v15 → 18 每次 CI 都跑；更早版本（v8 / v10 / v12）还没有真库样本；
- 没有在 Android/Windows 真机上用旧安装包升级（只有核心层回放）；
- 没有覆盖“旧库 + 未完成导入/录音”的真实组合（`recover_on_open` 的语义有测试，但没有真机样本）；
- v1–v5 的真库没有准备；合成测试覆盖更早的版本，真库演练按 v8/v10/v12 起步。

## 4. 数据目录位置

### 4.1 现在的路径

`apps/diary_app/lib/src/app_services.dart` 固定使用：

```text
getApplicationSupportDirectory()/unwritten_diary/library.sqlite
```

由 `path_provider` 解析到：

| 平台 | 实际路径（预期） | 依据 |
|---|---|---|
| Windows | `%APPDATA%\Lingxing\不写日记\unwritten_diary\library.sqlite`（`Runner.rc` 的 `CompanyName` = `Lingxing`、`ProductName` = `不写日记`，2026-10-19 定案冻结） | `Runner.rc` 的 `CompanyName`/`ProductName` + `path_provider_windows` 的约定 |
| Android | `/data/user/0/<applicationId>/files/unwritten_diary/library.sqlite` | `path_provider_android` 的 `getFilesDir()` |
| 鸿蒙（未来） | 应用 `filesDir` 下的 `unwritten_diary/`（产品工程尚未落地） | 与 Android 同一套“可写私有目录”原则 |

> **Windows 的坑**：`path_provider_windows` 用 exe 的版本信息（公司名 + 产品名）拼目录。
> 改 `Runner.rc` 里的 `CompanyName`/`ProductName`，或改 exe 文件名导致回退，都会**静默换目录**，
> 用户看起来就是“资料没了”。发布前把这两个值定死；发布后要改就必须走 §4.2 的迁移。
>
> **2026-10-19 已切一次（#137）**：`CompanyName` 从 `com.example` 改为 `Lingxing`，
> 目录因此从 `%APPDATA%\com.example\不写日记\` 变成 `%APPDATA%\Lingxing\不写日记\`。
> 这次切换在首发前完成，旧目录里的数据**不会被删，但新构建看不到**——升级机器上相当于全新安装。
> 之后就冻结，再改必须走迁移。
>
> **Android 的坑**：改 `applicationId` 等于换沙箱，旧数据在新包名下不可见。包名必须在首次发布前定案。

### 4.2 路径变更的迁移流程（推荐用备份，不手工搬 SQLite）

**不要**写“新路径不存在就建空库”的代码——那会把“路径变了”伪装成“用户是新人”。
推荐的一次性迁移：

```text
1. 应用启动，先探测旧路径；旧库存在且新路径不存在 ⇒ 进入迁移向导
2. 绝不删除旧目录；先在新位置建空目录
3. 用旧 Core 打开旧库 → create_backup(<新目录>/path-migration.diarybak)
   （备份内部用 VACUUM INTO，含已提交 WAL，不需要停写）
4. 用 restore_backup 恢复到新目录（只允许新空目录；失败不动旧库）
5. 用新 Core 打开新库，核对 counts（captures/assets/diary_versions/blob 哈希）
6. 写 path-migration.json：旧路径、新路径、备份 sha256、计数、时间
7. 旧目录保留至少一个发布周期；用户确认后再提供“删除旧数据”入口
8. 回滚：删新目录（刚恢复的副本），继续用旧路径；旧库从头到尾没被改
```

为什么不用 `cp`：

- WAL 下最近的提交可能只在 `-wal` 里，单拷 `.sqlite` 会得到旧状态；
- `-shm` 是临时索引，不能当数据；
- 备份包的 `manifest.json` 有哈希与计数，恢复时会逐条校验，手工 `cp` 没有这层保护。

如果路径变更发生在**首次发布前**（现在就是），直接改代码并清空开发库即可；
但必须在发布检查清单里确认“包名 / 公司名 / 产品名 / 数据目录”四项已经冻结。

### 4.3 备份里有什么、没有什么

`create_backup` 产出的是**一致性快照 + 内容寻址原件**：

- 有：`db/library.sqlite`（含 WAL 已提交内容）、`blobs/`、未收尾录音的已封闭片段；
- 没有：未完成导入的 `.part`、内存态租约/检索会话、日志；
- 索引与向量在快照里，但它们是派生数据，恢复后可以重建。

恢复只允许落到**新的空目录**，且不能是当前库目录；落地用一次 `rename`，失败不留半成品。
详见 [`m5-备份与恢复.md`](../architecture/m5-备份与恢复.md)。

### 4.4 1.1 的备份不能用 1.0 的安装包恢复（要看）

备份清单里的 `apiVersion` 与核心的 `API_VERSION` 是同一个常量，恢复时的规则是
**只拒绝「高于本构建」的备份**（[m5 §6](../architecture/m5-备份与恢复.md)）。当前核心是
**1.1**（为 `SearchHit.captureId` 这个必填响应字段从 1.0 抬上来的，见契约 1.3 / 2.6），
于是有一条**用户看得见**的后果：

- 用 **1.1** 的应用做的备份，拿到 **1.0** 的安装包上恢复，会失败并报
  `incompatible_backup`：「备份的 apiVersion 是 1.1，本核心支持到 1.0；请先升级应用再恢复」。
  这不是备份包坏了，是 `apiVersion` 的既定兼容规则；**升级应用到 1.1 或更高再恢复**即可。
- 反过来没有这个问题：1.0 的备份用 1.1 恢复，更老的备份由开库时的迁移接手。
- 支持口径：换机/重装时如果手里只有旧安装包，先升级应用再恢复，**不要**用「改清单里的
  `apiVersion`」绕过——那会让 1.0 核心读到一套它不认识的语义。
- 为什么值得单独写一段：这次抬版本的原因是「搜索结果多了一个字段」，与库内容能不能读
  毫无关系，却连带锁住了备份降级。耦合本身已记在契约 1.3 的「耦合警告」里；下次再为
  响应字段抬次版本之前，应先考虑把备份格式版本拆成独立常量。

## 5. 崩溃、断电与迁移失败

### 5.1 WAL + `synchronous=FULL` 保证什么

| 场景 | 结果 |
|---|---|
| 事务提交后立刻断电 | `synchronous=FULL` 保证提交记录已落盘；下次打开由 WAL 恢复 |
| 事务提交前进程被杀 | 该事务回滚；已提交的前一条不受影响 |
| 迁移中途崩溃 | 迁移在事务里；DDL/DML 与 `user_version` 一起回退，旧库仍是旧版本 |
| 迁移 SQL 报错 | `tx` 未 commit，`Core::open` 返回错误；**不要删除库文件**，先备份现场 |
| 迁移后打开失败 | 保留 `library.sqlite`、`-wal`、`-shm` 原样，复制整目录做证据；用最近备份恢复到新目录 |
| 磁盘满 | 迁移/写入失败；不要反复重试到把 WAL 撑大；先腾空间或恢复备份 |

关键实现：

```rust
conn.pragma_update(None, "journal_mode", "WAL")?;
conn.pragma_update(None, "synchronous", "FULL")?;
conn.pragma_update(None, "foreign_keys", "ON")?;
conn.busy_timeout(Duration::from_secs(5))?;
schema::migrate(&mut conn)?;
```

迁移事务里最后才 `PRAGMA user_version = 18` 并写 `schema_migrations`，然后 `commit`。
**不会出现“版本号已经 18、表却没建完”的中间态**。

### 5.2 断电后的现场处理

1. **不要**删 `-wal` / `-shm`；它们是恢复的一部分；
2. 把整个资料库目录复制一份（含 `blobs/`）作为现场；
3. 用当前构建打开副本：

   ```bash
   tools/migration/replay_old_library.sh --source /path/to/copy --dry-run
   ```

   这里只做一致快照与 `quick_check`；要跑完整迁移，去掉 `--dry-run`。
4. `quick_check` 不是 `ok` 或 `foreign_key_check` 非空 ⇒ 不要继续写；走备份恢复；
5. 用最近的 `.diarybak` 恢复到**新空目录**，核对 counts 与原件哈希；
6. 记录：崩溃时间、构建号、schema、日志、是否正在迁移/导入/录音。

### 5.3 迁移失败时用户看到什么

- 核心返回错误，应用不应显示“已保存/已升级”；
- 不应自动删除或重建资料库；
- 应提供“导出诊断包 / 从备份恢复”的入口；
- 诊断包只含统计与日志，不含正文（见 [`诊断包与排障.md`](诊断包与排障.md)）。
