### 2.3 为什么 `--split-per-abi` 只发一个 ABI

`build.gradle.kts` 的 `jniLibs.srcDirs` 指向 `target/android-jniLibs`，当前只产出
`arm64-v8a/libdiary_bridge.so`。`--split-per-abi` 会按 ABI 拆包；如果同时声明
`armeabi-v7a`/`x86_64`，那些 APK 里没有对应 `.so`，安装能成功、首启加载核心时失败。
所以脚本显式 `--target-platform android-arm64`，并把“单 ABI”写死为发布口径。

> 注意：`--split-per-abi` 会让 Flutter 在 `versionCode` 上加 ABI offset（默认
> `1000 * ABI_VERSION`）。如果必须使用 `pubspec.yaml` 的原值，加
> `-P force-version-code-ignoring-abi=true`；这会影响商店升级判定，发布前要定死一种。

### 2.4 SDK 现状与实际值

`android/app/build.gradle.kts` 用的是 Flutter 的默认值，不是硬编码数字：

```kotlin
compileSdk = flutter.compileSdkVersion   // 本机 Flutter 3.44.6 → 36
minSdk = flutter.minSdkVersion           // → 24
targetSdk = flutter.targetSdkVersion     // → 36
ndkVersion = flutter.ndkVersion          // → 28.2.13676358
```

- 这些是**本机 Flutter 版本**的值，换 Flutter 版本会变；`.metadata` 里的 revision 与
  本机 `flutter --version`（3.44.6）并不一致，发布机必须固定 Flutter 版本。
- `targetSdk 36` 是 2026 年的新目标；Android 15/16 的后台、通知、存储行为都要按 36 验。
  只验证旧 target 的结论不能直接搬过来。
- 最终 `AndroidManifest.xml` 的 `minSdkVersion/targetSdkVersion` 由插件 manifest 合并决定，
  用 `apkanalyzer manifest min-sdk` / `target-sdk` 复核。**本次没有产物，未复核**。
- `applicationId` 已定案为 `com.lingxing.unwrittendiary`（#102/#137，与鸿蒙 `bundleName` 一致）；
  发布后不可再改——签名、覆盖安装与商店记录都绑它。

### 2.5 R8 / ProGuard

Flutter 的 Gradle 插件在 release 构建里做三件事（本机 Flutter 源码实测）：

1. `releaseBuildType.isMinifyEnabled = true`；
2. 加 `proguard-android-optimize.txt`；
3. 加 `flutter_proguard_rules.pro`，如果 `android/app/proguard-rules.pro` 存在也一起加。

本仓库新增了 [`proguard-rules.pro`](../../apps/diary_app/android/app/proguard-rules.pro)，
当前只有注释、没有额外 keep 规则：`flutter_rust_bridge` 走 `dart:ffi`，不靠 JNI 反射。
如果以后加 Java/Kotlin 反射插件，应把规则加到这里，**不要**用
`minifyEnabled false` 换“打包能过”。

R8 的常见坑：

- 反射/序列化类被裁：表现为运行时 `ClassNotFoundException`/字段为空，不是编译错误；
- 只保留在 `AndroidManifest` 里注册的类不够，插件自己的 consumer rules 也要生效；
- `--release` 与 `--profile` 的 R8 行为不同，性能数字必须用 release 包量；
- 每次改规则都要跑“安装 → 首启 → 核心加载 → 搜索/录音”的真机冒烟，不能只看构建成功。

### 3.2 命令与产物

```powershell
# 仓库根目录，Windows PowerShell
powershell -ExecutionPolicy Bypass -File tools\release\build-windows.ps1

# 只打印命令
powershell -ExecutionPolicy Bypass -File tools\release\build-windows.ps1 -DryRun
```

两个都是可选的：不加也能出便携 zip，只是会在签名/SmartScreen 上留一条 warning。

脚本先构建：


```powershell
cd apps\diary_app
```

### 3.3 便携包

脚本把 `Release\` 复制到 `dist\windows\unwritten-diary-<version>-windows-x64\`，并打 zip。
便携包不写注册表、不建开始菜单；用户解压即用。适合内测，不适合正式分发（没有卸载/升级/文件关联）。

### 3.4 安装包方案对比（首版定案 Inno Setup）

| 方案 | 一句话取舍 | 签名/升级 | 适合 |
|---|---|---|---|
| **MSIX** | 系统原生打包，安装/卸载/自动更新最规范，但需要可信证书、打包清单与 MSIX 工具链，调试链路最重 | 必须签名；App Installer 可自动更新 | 长期正式分发、有证书与 CI |
| **Inno Setup** | 脚本简单、Windows 用户熟悉、能写开始菜单/卸载/按用户安装；升级逻辑要自己维护 | 安装包与 exe 都要 Authenticode 签名 | **首版采用**：工程量与可控性平衡 |
| **NSIS** | 体积小、可定制性最强，但脚本容易写错，安全审查与维护成本更高 | 同上 | 需要极细安装逻辑/极小安装器 |

**首版按 Inno Setup 落地**：脚本在 `tools/release/windows-installer.iss`，
由 `build-windows.ps1 -Installer` 调用 `ISCC`。已经处理的三件事：

- **AppId 固定**（`B73EFDA3-…`）：覆盖安装走「升级」而不是装出第二个应用。发布后不得更改。
- **默认按用户安装**（`PrivilegesRequired=lowest`，装到 `%LOCALAPPDATA%\Programs\`），
  需要装到 `Program Files` 时向导会自己请求提权。
- **卸载不删数据**：用户数据在 `%APPDATA%\Lingxing\不写日记\`，不在 `{app}` 下；
  卸载完成会弹窗明说「日记数据没有被删除」及它的路径。

无论选哪个：**未签名的 exe 或安装器都会触发 SmartScreen**。这不是“杀毒误报”，是
Windows 对“未知发布者 + 低下载信誉”的默认拦截。正确做法是购买代码签名证书
（OV 需要积累信誉，EV 通常更快），用 `signtool sign /fd SHA256 /tr <RFC3161 时间戳> /td SHA256`
签 **exe 和安装器**，并保留时间戳。签名不能保证 100% 不弹（信誉仍需积累），但未签名一定更容易弹。

脚本已经把这一步做成开关，不用手敲 `signtool`：

```powershell
# 证书在证书存储里（推荐）
powershell -ExecutionPolicy Bypass -File tools\release\build-windows.ps1 `
  -Installer -Sign -Thumbprint <证书指纹>

# CI 用 PFX
powershell -ExecutionPolicy Bypass -File tools\release\build-windows.ps1 `
  -Installer -Sign -PfxPath release.pfx -PfxPassword <口令>
```

`-Sign` 会签 `unwritten_diary.exe`、`diary_bridge.dll` 与安装包，**签完立即用
`Get-AuthenticodeSignature` 校验**，`Status != Valid` 就失败退出（不会产出半签名包）。
时间戳默认走 DigiCert，可用 `-TimestampUrl` 换。

## 4. 体积账

### 4.1 已知字节数（可核对）

| 项 | 字节 | 十进制 | MiB | 来源 |
|---|---:|---:|---:|---|
| 核心桥接 `.so`/`.dll`（量级） | 约 12,700,000 | 12.70 MB | 12.11 MiB | issue #89 给定“约 12.7 MB”；m3 文档记录 Linux x64 为 12,615,392 B，**不是 Android/Windows 实测** |
| ONNX Runtime（自编 1.29.1，strip） | 19,623,560 | 19.62 MB | 18.71 MiB | m6 文档实测 |
| bge-small-zh int8 `model_quantized.onnx` | 23,830,209 | 23.83 MB | 22.73 MiB | `models/manifest/bge-small-zh-v1.5.json` |
| bge `tokenizer.json` | 439,125 | 0.44 MB | 0.42 MiB | 同上 |
| SenseVoice int8 `model.int8.onnx` | 239,233,841 | 239.23 MB | 228.15 MiB | `models/manifest/sense-voice-small-int8-2024-07-17.json` |
| SenseVoice `tokens.txt` | 315,894 | 0.32 MB | 0.30 MiB | 同上 |
| sherpa-onnx C API（Android arm64） | 4,465,168 | 4.47 MB | 4.26 MiB | 同上，预编译产物 |
| sherpa-onnx 自带 ORT（Android arm64） | 22,249,560 | 22.25 MB | 21.22 MiB | 同上，**是否复用见下** |
| `libc++_shared.so`（Android） | 1,262,504 | 1.26 MB | 1.20 MiB | m6 文档实测 |

### 4.2 关键不确定性：只能带一份 `libonnxruntime.so`

bge 走 `ort` crate（要求 ORT ≥ 1.17，当前用自编 1.29.1）；sherpa-onnx 预编译包也带
`libonnxruntime.so`（1.28.2）。**两者同名，不能同时原样塞进 APK**。两条路：

| 路线 | 做法 | 体积 | 风险 |
|---|---|---:|---|
| **A（推荐先验）** | 用自编 ORT 1.29.1 同时服务 bge 与 sherpa C API，只带一份 | **19.62 MB** | sherpa 1.13.8 是否兼容 1.29.1 的 C API/算子，**未验证**；需要一次真机转写冒烟 |
| B | 用 sherpa 自带的 ORT 1.28.2，替换自编版本；`ort` crate 也加载它 | **22.25 MB** | bge 全链路要重验；版本从 1.29.1 降到 1.28.2 |
| C | 两份都带 | 41.87 MB | **不可行**：同名 `.so` 在安装时只会保留一份，加载哪份不可控 |

下面的账按 **A（一份 19.62 MB ORT）** 算；B 再加 2.63 MB。**这是估算，不是打包实测**。

### 4.3 Android 预估

已计入的“载荷”：

```
核心 12.70
+ ORT 19.62
+ bge 23.83 + tokenizer 0.44
+ SenseVoice 239.23 + tokens 0.32
+ sherpa C API 4.47
+ libc++_shared 1.26
= 301.87 MB（287.9 MiB）
```

**没有计入**：Flutter engine 的 `libflutter.so`、Dart AOT 的 `libapp.so`、dex、资源、
启动图、字体（0.21 MiB）等。这些在 release 下受 ABI 拆分、strip、R8 影响很大，**本次没有产物**，
按 **25–45 MB** 预留（估算）。

| 场景 | APK 预估（十进制） | AAB 预估（十进制） | 说明 |
|---|---:|---:|---|
| 带 bge + 带 SenseVoice | **327–347 MB** | **约 308–340 MB** | APK 里 `.so` 常不压缩，模型按接近原体积；AAB 会 deflate，模型压 3–8% 是估算 |
| 带 bge，SenseVoice 不随首包 | **87–107 MB** | **约 85–105 MB** | 不含 239.55 MB 转写模型；这是唯一可能接近 120 MB 预算的形态 |
| 带 bge，ASR 用 sherpa 自带 ORT（B 路线） | 约 330–350 MB | 约 303–333 MB | 比 A 多 2.63 MB |

**结论**：

- 只要 **SenseVoice 228.15 MiB 随包**，Android 首包就**不可能**落在验收计划的 120 MB 内；
  连“≤180 MB”也超。这不是打包技巧能解决的，必须做产品取舍（§6）。
- 不带 ASR 时，按本账仍在 120 MB 以内，但只剩十几 MB 余量；Flutter 外壳若超 45 MB 就会破线，
  所以**必须用真实 release 包复核**，不能拿这张表当验收。
- AAB 不是安装体积：Play 会按 ABI/语言/密度拆。上表只用于判断“上传包大不大”，
  不能直接对用户说“安装只要 300 MB”。

**APK/AAB 里哪些是估算**：

| 项 | 实测/来源 | 是否估算 |
|---|---|---|
| 核心、ORT、bge、ASR、sherpa、libc++ | 字节数有文件/manifest 依据 | 字节数不是估算；但“Android/Windows 上也正好这么大”是假设 |
| Flutter 外壳 25–45 MB | 无本次产物 | **是估算** |
| APK 压缩率 / AAB deflate 3–8% | 无本次产物 | **是估算** |
| ABI 拆分后的最终安装体积 | 无本次产物 | **是估算** |

### 5.2 命令

```bash
export OHOS_SIGN_STORE_FILE=/abs/path/product.p12
export OHOS_SIGN_CERT_FILE=/abs/path/product.cer

# 只看前置与命令

```

脚本会：

1. 固定导出 `OHOS_BUNDLE_NAME=com.lingxing.unwrittendiary`，拒绝覆盖；
2. 检查 hvigorw/ohpm/java/NDK/Rust target；
3. 用 `hap-sign-tool.jar verify-profile` 解出 `.p7b` 的 `bundle-info.bundle-name`，**不等于目标就报错退出**；
4. 调 `probes/ohos-bge-smoke/scripts/build-hap.sh`（内部：原生库 → 模型进 rawfile → ohpm install →
   注入 `signingConfigs` → `assembleHap`）；
5. 把签名 HAP 复制到 `dist/ohos/`，再解开 `module.json` 复核包内 bundleName。

### 5.4 体积

m6 的实测：**bge + ORT + 核心的 unsigned HAP = 48,865,723 B（46.60 MiB）**，
signed 49,120,600 B。这是**探针**（UI 极简），不是产品 HAP。若再加 SenseVoice
（239.55 MB）与 sherpa C API（4.47 MB），HAP 会到 **约 290 MB 以上**（估算），
且 HAP 内条目是 `Stored`，不会靠压缩变小。**本次没有跑 HAP 构建，未复核新 bundleName 下的体积。**
