# 任务交接提示词

我们**不预设分工**：下面几段提示词按**任务**复制，不按人复制。同一个人今天做前端层任务就用前端层那段，明天做后端层任务就用后端层那段，两个人都可以只用其中一段。

每次开新任务时：先在 issue 上看清楚要求和文件范围（认领规则见 `CONTRIBUTING.md` 第 1 节），再把「通用开场」+ 对应任务层那段一起发给模型。以下说明供后续开发使用，本次计划编写不启动开发。

## 通用开场（每次都要带上）

一次只做一个已认领的 issue，只开一个分支、只提一个 PR。

固定阅读顺序：`docs/development/00-开发总览.md`、`01-共享接口契约.md`、本任务所在层的任务书（前端层看 `02`，后端层看 `03`）、`04-验收与测试计划.md` 里与本任务相关的案例。**不要两份任务书一起喂**，那会让模型越界改另一层。

最低限度的禁令，每次都要重申，模型不重申就会"顺手帮你补上"：

- 不修改共享契约的语义；缺接口先提「契约变更请求」issue，先改文档和场景样例，再改实现。
- 不手改生成代码（`packages/diary_bridge/` 等生成输出）；需要重新生成时在同一个 PR 里跑生成脚本。
- 不为绕过缺口在页面或插件里直接访问数据库、Rust 内部对象或模型服务 HTTP API。
- 只改 issue 里列出的文件范围；要扩大范围，先在 issue 里写一句再动。
- 不自行升级或新增依赖，不自行更换整体技术栈，不降低产品范围。

交付时必须给出：改动文件清单、真实/Mock 接入状态、实际跑过的测试与输出、未验证的部分、需要对方接入的内容。没有实机、凭据或构建条件时如实标注，不把未验证功能报告为完成。

## 前端层任务提示词

本任务属于"不写日记"的前端层（Flutter 应用与 Windows/Android 平台适配）。产品要求已经在计划文档中确认，不要重新发散成社交平台、普通聊天机器人或云端网站。

首版目标为 Windows x64 和 Android arm64 上的单设备应用，建议栈为 Flutter/Dart；后端层的 Rust 本地核心由另一个人（可能是同一个人）另行实现，本任务不实现第二套数据库、模型服务或索引。前端层的范围是记录、日记阅读、搜索、来源查看、版本、设置、插件管理和备份恢复界面，以及原生录音、文件选择/分享/拖放、播放、系统凭据和后台唤醒。

本任务只应改动 `apps/diary_app`、`packages/platform_host`、`packages/diary_mock`、`tests/e2e` 这类前端层路径。不要自行改 `crates/`、共享 DTO 或桥接生成文件；接口缺口走契约变更流程，由认领契约改动的人更新 `01-共享接口契约.md` 和类型包。界面一律通过可注入的 DiaryApi 调用核心，切换 Mock/真实实现不修改页面逻辑。

用户最重视打开快、立即能记、可靠保存和舒服的长时间倾诉。默认安静记录，主动请求时才回应。AI 日记正文必须是简洁、有感染力、忠于事实的自然段，不能显示为要点总结。所有"已保存""正在录音""已完成整理"状态必须来自真实确认，没有依据时不要显示百分比。

先完成本任务书里 M0 的可行性验证及 Mock 页面，再按任务顺序推进。Mock 与真实实现共用 DiaryApi；尽早联调首个真实保存和录音闭环。录音不得依赖页面存活，Android 需验证锁屏和系统中断；大文件与长音频不能整体读进内存。

请先交付执行顺序、环境检查和 M0 验证结果，再完成实际开发。遇到未冻结选型，以目标设备测量和文档依据作决定并记录。每阶段提供已完成内容、真实/Mock 接入状态、测试结果和需要对方处理的问题。

## 后端层任务提示词

本任务属于"不写日记"的后端层（设备内本地核心）。后端在用户设备内运行，不建设必须部署的云业务服务器。产品要求已在计划文档中确认，不要自行扩大成云端同步、账号体系或微服务。

首版目标是 Windows x64 与 Android arm64。建议使用 Rust 本地核心、SQLite、独立原件文件库、内置小型向量模型及嵌入式检索，通过 flutter_rust_bridge 对接 Flutter。后端层的范围是存储、原件/录音片段接收、解析、关键词和向量混合检索、模型服务适配、自动整理、版本、持久队列、插件宿主、备份与恢复。

本任务涉及 `crates/diary_core`、`crates/diary_bridge`、`packages/diary_api`、`packages/diary_bridge`、`models/manifest`、`plugins/examples`、共享测试资料与架构决定这类后端层路径。不要编辑前端页面和平台工程；打包依赖通过清单交给认领前端层任务的人合入。共享 DTO 与 DiaryApi 必须与契约文档一致，先提供与 Rust 内部实现无关的 Dart 类型，页面才能独立开发 Mock。

最重要的规则：记录不等待模型/网络/索引；原件不被 AI 或插件覆盖；日记修改保留版本；自动生成不覆盖人工修改；默认不回应倾诉；搜索覆盖原文和日记且能定位来源；队列失败不影响原件。日记允许润色，但正文必须自然段、简洁、有感染力并忠于事实。

先完成任务书里 M0 的 B0，验证两个目标平台上的桥接、本地模型、中文短词搜索和插件运行候选，冻结契约和依赖。模型候选及性能数字尚未实测，不应当成已证明的事实。之后按 B1 至 B8 推进，每阶段给出一个可调用的真实闭环。M1 开始联调，不把接口对接拖到最后。

插件接口需要真实可安装的示例、权限与执行预算，不能只留空函数。搜索需要验证中文口语与短词，不能只拿几条英文样例演示。录音由前端平台层采集，后端层提供可恢复的交接协议；后台任务入口不能依赖页面对象。

请先报告环境检查、执行顺序及 M0 结果，再完成开发。每阶段附接口/数据版本、实际测试、构建产物、性能测量和已知限制。没有实际运行的部分明确标记，不能使用固定假输出代替 AI 或真实持久化。

## 跨层与契约变更任务提示词

如果同一个人同时改两层（或改动共享契约），额外强调：

- 先改 `01-共享接口契约.md` 和场景样例，再改实现，顺序不能反。
- 在同一个 PR 里说明：动机、字段/行为变化、是否兼容、需要对方调整什么。
- 会改变对方调用行为的改动，合并前必须请另一个人 review（见 `CONTRIBUTING.md` 第 4 节）。
- 生成代码、锁文件、`packages/diary_api` 的改动要放在一起提交，并说明重新生成用的命令。

## 两人协作约定

共享契约是两层唯一的同步点，由正在改它的人更新，另一人以调用方身份审核，不能在实现里绕过去。

每次交换的交付信息固定为：提交/构建版本、完成任务编号、接口版本、运行方式、测试结果、未解决问题、需要另一方接入的内容。缺陷定位优先用最小复现和真实输入状态，不凭猜测去改对方的文件；要改别人的文件，先在对应 issue 或 PR 下说清楚。

首个集成目标只有一条完整路径：输入一句话，核心持久化，关闭重开仍在，离线关键词搜索能找到。第二条路径是长录音保存与恢复。接着加入本地语义检索，最后接入远端整理和扩展能力。界面完整度不能替代这些真实闭环。

整体应用打包与应用工程配置属于前端层任务，后端层提供可复现核心与模型资源。双方按验收计划共同确认发布；遇到缺少凭据、实机或其他外部条件时，标出未验证范围并完成其余独立工作，不伪造通过结论。
