# 验收与测试计划

所有数值都是首轮设计目标，尚未在本项目中测量。M0 固定参考设备、构建方式和基线；修改目标需要记录原因，不能在失败后直接放宽数值并宣称通过。

## 1. 验收层级

| 层级 | 负责人 | 验证内容 |
|---|---|---|
| 核心正确性 | 后端 | 事务、恢复、版本、来源、索引、任务、插件边界 |
| 组件及状态 | 前端 | 保存反馈、冲突、录音中断、搜索取消、加载/空/错误状态 |
| 契约一致性 | 双方，后端维护契约 | Mock 和真实核心的类型、错误、状态、事件一致 |
| 平台集成 | 前端主导，后端协助 | 麦克风、锁屏、后台、URI、拖放、打包和凭据 |
| 真实 AI 能力 | 后端主导 | 实际服务配置、转写、生成、错误和来源关联 |
| 产品端到端 | 前端组织 | 从记录到回看、搜索、版本、备份恢复的完整流程 |
| 性能与规模 | 双方 | 冷启动、记录、搜索、长录音、内存、包体、耗电 |

不能只用 Mock 验收真实保存，不能只用单元测试替代真机长录音，不能只看“首页画出来”判定启动完成。

## 2. 测试资料与设备

全部样例使用虚构资料。两方共享一组固定 ID、时间和预期来源，测试中可以控制时钟。至少包含中文人名、昵称、一至二字词、英文缩写、emoji、错别字、模糊回忆、明确否定、相互矛盾的想法和跨午夜事件。

建议规模集：空库；1,000 条记录；10,000 条记录及约 100,000 个可搜索片段。媒体另准备一小时录音、短视频、数百页文本 PDF、扫描 PDF、包含表格的 DOCX、不支持的二进制文件，以及超出可用空间的大文件导入场景。

Windows 至少一台普通 x64 SSD/8 GB 内存设备；Android 至少一台 arm64/6–8 GB 的中档真机和一台较弱设备。M0 记录具体型号、系统、存储、电量和温度，冻结参考设备。模拟器用于日常开发，不能代替录音、耗电、系统调度和性能结论。

## 4. 性能目标与测量方法

### 4.1 首轮预算

以下按冻结参考设备、Release 构建、无首次权限弹窗测量。弱设备另列结果，不混入平均值掩盖参考设备问题。远端服务等待时间单列，不归为本地性能。

| 指标 | Windows 目标 | Android 目标 | 测量边界 |
|---|---|---|---|
| 冷启动到可记录 | P95 ≤ 1.5 s | P95 ≤ 1.8 s | 从启动到文字输入能被接收并可提交本地存储，不能只有空壳 |
| 热恢复到可记录 | P95 ≤ 400 ms | P95 ≤ 500 ms | 从恢复应用到输入可用 |
| 已授权录音开始 | P95 ≤ 350 ms | P95 ≤ 350 ms | 点击到真实首个有效音频缓冲，设备异常另计 |
| 草稿核心提交 | P95 ≤ 200 ms | P95 ≤ 250 ms | 防抖结束后，到 durable 确认；另报告总保存等待 |
| 录音停止并确认已保存 | P95 ≤ 700 ms | P95 ≤ 700 ms | 不含转写、向量和生成 |
| 关键词首屏结果 | P95 ≤ 150 ms | P95 ≤ 250 ms | 10 万片段；记录查询构成 |
| 模型已加载的混合搜索 | P95 ≤ 600 ms | P95 ≤ 900 ms | 查询向量、两路检索、合并到首屏结果 |
| 模型未加载的首次语义搜索 | P95 ≤ 2 s | P95 ≤ 2 s | 包括加载与推理；关键词先返回 |
| 常规交互掉帧 | 严重卡顿可定位并修复 | 参考设备卡顿帧比例目标 < 1% | 同时存在后台增量索引时测量 |
| 基础空闲内存 | 目标 ≤ 300 MiB | 目标 ≤ 200 MiB | 无模型、无媒体解码；Windows 私有工作集、Android PSS 分开报 |
| 搜索活跃内存 | 目标 ≤ 550 MiB | 目标 ≤ 400 MiB | 含模型与索引；峰值和稳定值均报告 |
| 单架构发布包 | 参考 ≤ 180 MB（**已偏离**，见 4.1 末尾） | 参考 ≤ 120 MB（**已偏离**，见 4.1 末尾） | Android **实际预算 ≤ 350 MB**（含转写模型）；Windows 当前构建**不含任何模型** |

这些预算用于约束设计，不是宣传承诺。M0 发现不可行时，需要呈现测量、瓶颈及两个可选择的改进方案；不得直接删掉内置模型或把搜索搬到云端来满足数字。

**已决的偏离（2026-10-18）**：转写模型（SenseVoice int8，228.15 MiB）**随首包分发**，因此 Android 单架构发布包**预计 327–347 MB**，**主动超出上面「≤120 MB / ≤180 MB」两档**。理由与边界：产品是**本地优先**（不依赖首次下载才能用语音日记），分发渠道是**官网/GitHub 直发与鸿蒙商店**（不上海外 Play），体积是**可接受的代价**；上表该两档自本日起改为**参考目标**，实际预算为「≤350 MB（含转写模型）」。若将来要上对包体有硬限制的商店，必须回到本节的「呈现测量 + 两个可选方案」流程，而不是悄悄删掉模型。

**Windows 侧与上面的账不同（2026-10-19 核对）**：Windows 便携包**不含任何模型**。
三条证据：`apps/diary_app/pubspec.yaml` 的 `flutter.assets` 只有 `app_icon.png`、`assets/legal/`、`assets/fonts/OFL.txt`；
`apps/diary_app/windows/CMakeLists.txt` 的 `install()` 只装 exe、`icudtl.dat`、`flutter_windows.dll`、
`diary_bridge.dll` 与插件库；`tools/release/build-windows.ps1` 的产物校验清单（`$required`）里没有模型文件。

因此「Windows ≤ 180 MB」是**纯程序体积**，此前写的「包括内置向量模型」与事实不符，已改。
⇒ 这也意味着 Windows 端要用语义搜索或转写，模型**只能由 `modelDir` 配置或环境变量指向外部目录**
（`crates/diary_core/src/config_file.rs:93`、`:246`），当前**没有任何自动获取路径**。
若将来把模型打进 Windows 包，本节预算必须重算，不能沿用 180 MB。

### 4.2 运行方式

至少测 20 次冷启动、50 次热恢复和 100 次不同查询，报告中位数、P95、最大值及异常样本。明确进程是否已结束、系统缓存是否保留、模型是否已加载；不要把全部预热后的结果称为冷启动。

分别测试空库与规模库；对比正在录音、后台索引、批量导入和普通空闲状态。检查模型未使用时没有常驻初始化、插件未触发时没有执行、重建索引没有占满界面线程。

一小时录音测试报告原文件大小、峰值内存、耗电、温度变化、片段完整率和异常。内存不能随音频长度线性增长；不以无限常驻内存保存整段录音。与相同设备基础录音方案比较额外开销，但不预先承诺固定电量百分比。

## 5. 检索质量评估

建立至少 100 条人工标注查询，每条给出相关来源及可接受定位。覆盖精确人名/短词、语义改写、情绪描述、否定、时间范围、多媒体提取内容、历史版本与同主题多事件。

建议初始目标：明确的原文精确查询相关项进入前 5 的比例 ≥ 95%；语义改写查询相关项进入前 5 的比例 ≥ 85%。这些是自建测试集目标，不能作为对所有用户查询的准确率承诺。单独列出最差类别及失败样例。

比较关键词、仅向量、混合检索三种结果。若 ANN、量化或低精度存储降低召回，需要与精确/未量化基线比较。不能只选择有利样例证明模型可用。

位置检查是硬门槛：每个结果必须打开其声明的来源和版本；语义相近但不支持问题事实的内容，不得作为确定性答案。新材料未被索引时 coverage 必须反映这一点。

## 6. 日记生成质量评估

至少准备 30 组一天材料：只有一句话、纯图片、长倾诉、情绪矛盾、事实冲突、讽刺表达、姓名歧义、没有明显主题、快乐事件、丧气但不希望被劝慰、材料部分缺失、用户修改后再生成等。

逐项人工评估事实忠实、细节保留、简洁程度、情绪合适、风格一致和自然段阅读体验。关键事实虚构、把 AI 建议当用户事实、覆盖人工修改、遗漏却声称完整，是发布阻断问题。

“没有编号或列表”可以自动检查格式，但事实与感染力不能靠格式检查代替。真实服务评估应记录模型、提示词版本、输入快照和费用范围，重复运行部分样例检查不稳定性。

## 7. 数据恢复与升级门槛

必须对保存、文件复制、片段封闭、任务输出提交、备份创建、索引切换和数据库迁移的关键边界做故障注入。每次恢复检查原件哈希、版本关系、任务是否重复、索引是否引用失效对象。

发布前至少完成一次从上一测试版本的数据升级，以及一次完整备份在全新资料库恢复。原件和日记版本数量、哈希、来源关系要一致；可重建索引不要求备份字节完全一致。

录音正常进程终止场景要求已确认封闭的片段全部可恢复。未封闭尾段的损失范围需实测并标注，初始目标控制在检查点间隔内。不能把未确认数据的恢复能力宣传成所有断电情况下零丢失。

## 8. 发布阻断与允许后续改进

发布阻断包括：丢失已确认保存的原件、版本被静默覆盖、伪录音状态、插件能越权写原件、密钥泄露、备份恢复破坏现库、搜索定位错源、明显卡死、核心流程在其中一个目标平台不可用。

允许留到后续但必须明示的限制包括：不支持的附件格式、未实现的视频视觉检索、精确夜间执行不保证、未实现的平台、某些模型服务缺少时间戳。限制不能隐藏成“没搜到”“今天没有发生什么”或“整理已全部完成”。

## 9. 最终验收报告格式

报告包括构建版本、接口/数据库/模型版本、设备和系统、测试通过/失败/未验证项、性能原始数据及统计、检索质量样例、真实 AI 评估、恢复证明、依赖许可证清单和剩余问题。

两方只报告实际执行的检查。未运行、仅 Mock、仅模拟器、仅桌面验证的项目要分别标明。达到门槛后不为堆数字重复执行无意义测试，把时间用于解决剩余风险和完成交付。
